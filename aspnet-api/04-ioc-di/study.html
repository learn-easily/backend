Inversion of Control და Dependency Injection

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

ლექცია 3 — DTO და Mapping. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

წინა ლექციის საშინაო: MembersController — პაროლი გარეთ არ გადის. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • Models/Member: Id (Guid), FullName, Email, PasswordHash, JoinedAt
  • Dtos/: CreateMemberRequest (FullName, Email, Password), UpdateMemberRequest (FullName, Email), MemberResponse (Id, FullName, Email, JoinedAt)

💡

Argon2.Hash აბრუნებს ერთ სტრიქონს, მაგალითად $argon2id$v=19$m=…,t=…,p=…$…. მასშივე წერია ალგორითმი, პარამეტრები და „მარილი“ (salt) — ამიტომ ერთი და იგივე პაროლი ორჯერ ერთნაირ hash-ს არ იძლევა, და ცალკე სვეტი salt-ისთვის არ გვჭირდება. პაროლის შემოწმებას (Argon2.Verify) ავტორიზაციის თემაში ვნახავთ.

დღის თემა: Inversion of Control და Dependency Injection

სლაიდი 4

ShopApi-ში პროდუქტები Controller-ის შიგნით, static სიაშია ჩაკეტილი. როგორც კი ისინი მეორე Controller-საც დასჭირდება, ეს გამოსავალი ინგრევა. დღეს ვპასუხობთ კითხვას: ვინ უნდა ქმნიდეს ობიექტებს? პასუხი ორი ტერმინია — Inversion of Control და Dependency Injection — რომლებსაც ყველა .NET გასაუბრებაზე გკითხავენ.

ლექციის ბოლოს შეძლებ:

  • მონაცემების Controller-იდან ცალკე კლასში (Store) გატანა
  • ახსნა, რატომ არ მუშაობს new Controller-ის შიგნით
  • IoC-ს და DI-ს განსხვავების ახსნა
  • dependency-ს constructor-ით მოთხოვნა და AddSingleton-ით რეგისტრაცია

ლექციის გეგმა

სლაიდი 5
  1. ახალი მოთხოვნა — სტატისტიკა, რომელსაც პროდუქტები სჭირდება, და ჩვენი კოდი მისთვის მზად არ არის.
  2. ProductStore — მონაცემებს Controller-იდან საკუთარ კლასში გავიტანთ და ახალ პრობლემას წავაწყდებით.
  3. Inversion of Control — ვინ მართავს ჩვენს პროგრამას.
  4. Dependency Injection — როგორ ხსნის ის პრობლემას ბოლომდე.
  5. პრაქტიკა — იგივე ცვლილება LibraryApi-ში.

დღის თემა

სადაც შევჩერდით

სლაიდი 6

ShopApi-ს ხუთი endpoint აქვს, სწორი სტატუს კოდებით და Swagger-ში გატესტილი. პროდუქტები ინახება static სიაში, Controller-ის შიგნით:

Controllers/ProductsController.cs
private static List<Product> _products = new List<Product> { ... };

სია static იმიტომ არის, რომ Controller ყოველ მოთხოვნაზე თავიდან იქმნება — static-ის გარეშე ყოველ მოთხოვნას საკუთარი, ახალი სია ექნებოდა. თვითონვე ვთქვით, რომ ეს დროებითი გამოსავალია. დღეს ვნახავთ, რატომ და რით შევცვალოთ.

💡

ამ ლექციის მაგალითებში Controller-ი Product-ს პირდაპირ იღებს და აბრუნებს — რომ ყურადღება მხოლოდ ProductStore-სა და DI-ზე იყოს. შენს პროექტში DTO-ები და Mapper წინა ლექციიდან ადგილზე რჩება: ProductStore Product-ებს ინახავს, Controller კი შემოსვლისას ToEntity()-ს და გასვლისას ToResponse()-ს იძახებს.

რეალურ პროექტში მოთხოვნები მუდმივად ემატება. ვნახოთ, როგორ უმკლავდება ჩვენი კოდი პირველივე ახალ მოთხოვნას.

GET /api/stats→ 200 OK  { "count": 3, "totalValue": 2565 }

REST-ის წესით stats ახალი რესურსია, ამიტომ ახალი Controller სჭირდება — StatsController. ამოცანა მარტივია: StatsController-მა პროდუქტები უნდა წაიკითხოს. მაგრამ… პროდუქტები სად არის? ProductsController-ის შიგნით.

პრობლემა: სია ProductsController-შია ჩაკეტილი

სლაიდი 9

როგორ წავიკითხოთ პროდუქტები StatsController-იდან? სამი „მარტივი“ იდეა — და სამივე ცუდია:

  1. სიას StatsController-შიც გადავაკოპირებთ. მაშინ ორი სხვადასხვა სია გვექნება: POST-ით დამატებულ მონიტორს სტატისტიკა ვერ დაინახავს.
  2. სიას public static-ად ვაქცევთ და ProductsController._products-ით მივწვდებით. იმუშავებს, მაგრამ ერთი Controller მეორის შიგნით იქექება, და სიას პროექტში ნებისმიერი კლასი შეცვლის — ვერასდროს გაიგებ, ვინ შეცვალა.
  3. სტატისტიკასაც ProductsController-ში ჩავწერთ. შემდეგ შეკვეთები, კალათა, ფასდაკლებები… და ერთი Controller ყველაფერს აკეთებს.

მიზეზი: ProductsController ორ საქმეს აკეთებს

სლაიდი 10

ProductsController-ის შიგნით ორი სრულიად სხვადასხვა საქმეა:

  • 🌐 HTTP — მოთხოვნის მიღება, პასუხი, სტატუს კოდი.
  • 🗃️ მონაცემები — სია, Id-ის დათვლა, ძებნა, დამატება.

Controller-ის ნამდვილი საქმე HTTP-ა: მიიღოს მოთხოვნა და დააბრუნოს სწორი პასუხი სწორი კოდით. მონაცემებს საკუთარი კლასი სჭირდება — და ყველა, ვისაც პროდუქტები სჭირდება, ერთსა და იმავე ობიექტს უნდა იყენებდეს.

💡

ამ იდეას — „ერთ კლასს ერთი საქმე“ — Single Responsibility ჰქვია. ის SOLID-ის ერთ-ერთი პრინციპია, რომელსაც არქიტექტურის თემაში ვნახავთ.

მონაცემებს Controller-იდან ახალ კლასში, ProductStore-ში გავიტანთ.

ProductStore — პროდუქტების საცავი

სლაიდი 12

ვქმნით ფოლდერს Services და მასში კლასს ProductStore:

Services/ProductStore.cs
public class ProductStore{    private List<Product> _products = new List<Product>    {        new Product { Id = Guid.NewGuid(), Name = "ლეპტოპი", Price = 2400 },        new Product { Id = Guid.NewGuid(), Name = "მაუსი", Price = 45 },        new Product { Id = Guid.NewGuid(), Name = "კლავიატურა", Price = 120 }    };     public List<Product> GetAll() => _products;     public Product? GetById(Guid id) => _products.FirstOrDefault(p => p.Id == id);     public Product Add(Product product)    {        product.Id = Guid.NewGuid();        _products.Add(product);        return product;    }     public bool Update(Guid id, Product updated)    {        var product = GetById(id);        if (product is null) return false;        product.Name = updated.Name;        product.Price = updated.Price;        return true;    }     public bool Delete(Guid id)    {        var product = GetById(id);        if (product is null) return false;        _products.Remove(product);        return true;    }}
  • სია Controller-იდან გადმოვიდა — და static აღარ წერია. რატომ — ცოტა ხანში გამოჩნდება.
  • მეთოდებში HTTP არ არის: არც Ok, არც NotFound. ProductStore მხოლოდ მონაცემებზე ზრუნავს.
  • Product? — კითხვის ნიშანი ნიშნავს, რომ შეიძლება null დაბრუნდეს (პროდუქტი ვერ მოიძებნა).
  • Add Id-ს თვითონ ანიჭებს და შექმნილ პროდუქტს აბრუნებს.
  • Update და Delete აბრუნებს bool-ს — „გამოვიდა თუ არა“. 404-ის დაბრუნებას Controller თვითონ გადაწყვეტს.

ვუშვებთ… და მონიტორი ისევ გაქრა

სლაიდი 14
  1. POST „დაამატე მონიტორი“ → ASP.NET Core ქმნის ProductsController #1-ს → ის new-ით ქმნის ProductStore #1-ს → მონიტორი მის სიაში ემატება. პასუხი წავიდა — Controller და მისი ProductStore ქრება.
  2. GET „მომეცი ყველა“ → ახალი ProductsController #2 → ახალი ProductStore #2 → ახალი სია, ისევ სამი პროდუქტით. 😱 მონიტორი სად არის?
  3. GET /api/stats → StatsController ქმნის ProductStore #3-ს — კიდევ ერთ, საკუთარ სიას.

ყოველი new = ახალი ProductStore = ახალი სია. თუნდაც მონაცემი არ ქრებოდეს, ორ Controller-ს მაინც სხვადასხვა სია ექნებოდა.

მთავარი კითხვა: ვინ უნდა შექმნას ProductStore?

სლაიდი 15
  • 🙅 თავად Controller-ი — ყველა თავის ასლს ქმნის, და ვერავინ აკონტროლებს, რამდენი ასლი არსებობს.
  • 🤝 ვიღაც გარედან — შექმნის ერთხელ და მიაწვდის ყველა Controller-ს, ვისაც სჭირდება. Controller-ი მხოლოდ იტყვის: „მე ProductStore მჭირდება“.

სლაიდი 23

ორივე Controller იყენებს ProductStore-ს. შეუძლია ProductsController-ს იმუშაოს ProductStore-ის გარეშე? არა — მონაცემები იქ არის. ესე იგი ის ProductStore-ზეა დამოკიდებული.

DI Container — ობიექტების ქარხანა

სლაიდი 27

ASP.NET Core-ს აქვს ჩაშენებული DI Container: ის ქმნის ობიექტებს და აწვდის მათ, ვისაც სჭირდება. Controller-ებსაც ის ქმნის.

ეს ხაზები Program.cs-ში პირველი ლექციიდან გვიწერია:

Program.cs
var builder = WebApplication.CreateBuilder(args); builder.Services.AddControllers();builder.Services.AddOpenApi();builder.Services.AddSwaggerGen();

builder.Services — სწორედ Container-ის სიაა. AddControllers, AddOpenApi, AddSwaggerGen — რეგისტრაციებია: Container-ს ვეუბნებით „ესენი იცოდე“. მასში ასობით სერვისია, მაგრამ ProductStore სიაში არ არის — ამიტომ Container ვერ ქმნის მას.

builder.Services

  • Add… — „Container, ProductStore იცოდე · ვინც მოითხოვს, მიაწოდე“.
  • Singleton — ერთი ობიექტი მთელი აპლიკაციისთვის. პირველად რომ დასჭირდება ვინმეს, შექმნის, მერე ყველას — ყველა Controller-ს, ყველა მოთხოვნაზე — იმავეს აწვდის.

სხვა ვარიანტებიც არსებობს — AddScoped, AddTransient. მათ ბაზასთან ერთად ვისწავლით: იქ ყველაზე კარგად ჩანს, რატომ გვჭირდება.

🤖 Singleton, Scoped, Transient
ASP.NET Core-ში ვსწავლობ Dependency Injection-ს. ვიცი AddSingleton. ამიხსენი მარტივად AddSingleton, AddScoped და AddTransient-ის განსხვავება: რამდენჯერ იქმნება ობიექტი თითოეულ შემთხვევაში და როდის რომელს იყენებენ? მაგალითისთვის გამოიყენე ProductStore და HTTP მოთხოვნები. ახსნა ქართულად, დამწყებისთვის.

რა ხდება ახლა: Controller ახალია, ProductStore — ერთი

  • GET მოდის → Container ქმნის ProductsController #1-ს → ხედავს constructor-ს: ProductStore სჭირდება → სიაში ეძებს, Singleton-ია → პირველად სჭირდებათ, ქმნის და constructor-ში აწვდის.
