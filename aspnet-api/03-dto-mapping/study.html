წინა ლექციის საშინაო: LibraryApi — BooksController სრულად. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • Book: Id, Title, Author, Year, Price
  • BooksController — static სია 3 წიგნით, 5 endpoint

[HttpGet("cheap")] მუშაობს [HttpGet("{id}")]-თან ერთად, რადგან cheap რიცხვი არ არის: ASP.NET Core ჯერ ზუსტ მისამართს ეძებს. GetCheap კლასში სადაც გინდა, იქ შეიძლება იდგეს.

string.IsNullOrWhiteSpace ცარიელ ტექსტსაც იჭერს და მხოლოდ სივრცეებისგან შედგენილსაც (" "). უბრალო book.Title == "" მეორე შემთხვევას გამოტოვებდა.

💡

თუ ცარიელი title გააგზავნეთ და პასუხად 400 მიიღეთ ტექსტით „The Title field is required“, ჯერ თქვენი if-მდეც არ მისულა. [ApiController] string Title-ს სავალდებულოდ თვლის და ცარიელ მნიშვნელობას თვითონ უარყოფს. ჩვენი if ამ წესს კოდში ცხადად აჩვენებს და იმუშავებს მაშინაც, თუ ეს ავტომატური შემოწმება გამორთულია.

სლაიდი 4

წინა ლექციაზე API მუშაობს, მაგრამ Product პირდაპირ შემოდის და პირდაპირ გადის. როგორც კი ცხრილს შიდა ველი დაემატება — შესყიდვის ფასი, პაროლის hash — ის ყველას დაენახება. დღეს ვნახავთ, როგორ წერენ API-ს რეალურ პროექტებში: რას ვიღებთ კლიენტისგან, რას ვაჩვენებთ მას და როგორ გადავიტანოთ მონაცემი ერთი ფორმიდან მეორეში.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რატომ არ უნდა გავიდეს Entity API-დან პირდაპირ
  • Request და Response DTO-ების დაწერა record-ით
  • mapping-ის ერთ ადგილას გატანა — ხელით დაწერილი Mapper
  • Mapperly-ის დაყენება და მისი გაფრთხილებების გაგება

საიდან ვიწყებთ

სლაიდი 5

წინა ლექციაზე ProductsController დავწერეთ და ხუთივე endpoint მუშაობს. სტატუს კოდებიც სწორია: Ok, NotFound, CreatedAtAction, NoContent.

მაგრამ ერთ რამეს დააკვირდი: ყველგან ერთი და იგივე კლასი, Product, გამოიყენება.

  • GetAll — Ok(_products): კლიენტს პირდაპირ Product-ების სია მიდის.
  • Create — კლიენტისგან პირდაპირ Product შემოდის და პასუხადაც Product გადის.
  • Update — განახლებაც Product-ით ხდება.

ანუ ერთი კლასი სამ საქმეს აკეთებს: მასში ვინახავთ მონაცემს, მას ვიღებთ კლიენტისგან და მას ვაგზავნით კლიენტთან. პატარა სასწავლო პროექტში ეს მუშაობს. რეალურ პროექტში კი ასე არ წერენ — ამ ლექციაში ვნახავთ, რატომ.

👉

წინა ლექციაზე Id-ს _nextId++-ით ვითვლიდით. აქედან Id-ის ტიპი Guid-ია — 128-ბიტიანი უნიკალური მნიშვნელობა, მაგალითად 7c9e6679-7425-40de-944b-e07fc1f90ae7:

  • მთვლელი არ გვჭირდება — Guid.NewGuid() ყოველ ჯერზე ახალ მნიშვნელობას იძლევა, ბაზის გარეშეც.
  • ვერ გამოიცნობ — /api/products/1-ის შემდეგ ყველამ იცის, რომ /2 და /3 არსებობს; Guid-ზე ასე ვერ იტყვი.
  • route-ში ვწერთ {id:guid} — თუ მისამართში Guid არ არის, endpoint უბრალოდ არ დაემთხვევა (404).

კლასს, რომელიც ბაზის ცხრილს აღწერს, Entity ჰქვია. Product ჩვენი Entity-ა.

ბაზა ჯერ არ გვაქვს — მის ადგილს static List<Product> იკავებს. მაგრამ კოდი ახლავე ისე უნდა დავწეროთ, თითქოს ბაზა უკვე გვაქვს. მაშინ, როცა ნამდვილი ბაზა შემოვა, Controller-ის თავიდან წერა არ მოგვიწევს.

💡

ამიტომ ჩნდება კითხვა, რომელზეც მთელი ლექცია დგას: ბაზის ცხრილი პირდაპირ უნდა ვაჩვენოთ კლიენტს? და კლიენტმა პირდაპირ უნდა ჩაწეროს მასში?

სლაიდი 7
  1. სამი პრობლემა — რა ხდება, როცა Entity API-დან პირდაპირ გადის.
  2. DTO — გამოსავალი: ცალკე კლასები შემოსავალი და გასავალი მონაცემისთვის.
  3. Mapper — DTO-ს ახალი სამუშაო მოაქვს: მონაცემის გადატანა ერთი კლასიდან მეორეში. ჯერ ხელით დავწერთ.
  4. Mapperly — package, რომელიც ამ გადატანის კოდს ჩვენს მაგივრად წერს.

სლაიდი 8

ვნახოთ, რა პრობლემებს იწვევს, როცა Product-ს პირდაპირ ვაბრუნებთ და პირდაპირ ვიღებთ. სამი პრობლემაა — და სამივე რეალურ პროექტებში ხშირად ხდება.

ცხრილს ახალი სვეტები სჭირდება

სლაიდი 9

რეალურ პროექტში ცხრილი იზრდება. ვთქვათ, მაღაზიამ მოითხოვა ორი ახალი ველი:

Models/Product.cs
public class Product{    public Guid Id { get; set; }    public string Name { get; set; } = "";    public decimal Price { get; set; }    public decimal CostPrice { get; set; }  // შესყიდვის ფასი    public DateTime CreatedAt { get; set; } // როდის დაემატა}
  • CostPrice — რამდენად იყიდა მაღაზიამ პროდუქტი. საჭიროა მოგების დასათვლელად.
  • CreatedAt — როდის დაემატა პროდუქტი. ამას კლიენტი კი არ წერს, სერვერი წერს.

ორივე შიდა ინფორმაციაა: ბაზას და ჩვენ გვჭირდება, მყიდველს — არა. ახლა ვნახოთ, რა მოხდება, თუ Controller-ს არ შევეხებით.

პრობლემა 1 · შიდა მონაცემი გაიპარა

სლაიდი 10

GET /api/products/7c9e…-ის პასუხი ახლა ასეთია:

json
{ "id": "7c9e6679-7425-40de-944b-e07fc1f90ae7", "name": "ლეპტოპი", "price": 2400, "costPrice": 1650, "createdAt": "2026-10-26T…" }

ჩვენ GET-ში არაფერი შეგვიცვლია — უბრალოდ ცხრილს სვეტი დავუმატეთ. მაგრამ რადგან GET Product-ს პირდაპირ აბრუნებს, ახალი სვეტი თვითონ გავიდა გარეთ. ახლა ყველა მყიდველი და კონკურენტიც ხედავს, რომ 1650-ად ვყიდულობთ და 2400-ად ვყიდით.

⚠️

წარმოიდგინე მომხმარებლების ცხრილი სვეტით PasswordHash და endpoint GET /api/users. ერთი მოთხოვნა — და ყველა პაროლის hash გარეთაა. ეს ნამდვილი და ძალიან გავრცელებული უსაფრთხოების შეცდომაა.

პრობლემა 2 · კლიენტი ავსებს იმას, რასაც არ უნდა ეხებოდეს

სლაიდი 11

Swagger-ში POST-ის მაგალითი ახლა ასეთია:

json
{ "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6", "name": "string", "price": 0, "costPrice": 0, "createdAt": "2026-10-26…" }

Swagger კლიენტს სთხოვს id-ს და createdAt-ს. მაგრამ:

  • Id-ს ჩვენ ვანიჭებთ (Guid.NewGuid()) — კლიენტს არაფერი უნდა ჰქონდეს სათქმელი.
  • CreatedAt-ს სერვერი წერს.

თუ რომელიმეს გადაწერა დაგვავიწყდა, კლიენტის გამოგზავნილი მნიშვნელობა პირდაპირ ცხრილში ჩაიწერება.

PUT-ში კიდევ უარესია: Id ორ ადგილას მოდის — მისამართში (/api/products/7c9e…) და body-ში ("id": "1f4b…"). რომელს დავუჯეროთ? სწორი პასუხი — მისამართს. body-ში Id საერთოდ ზედმეტია.

💡

Swagger აღწერს კონტრაქტს — რა უნდა გამოგზავნოს კლიენტმა და რას მიიღებს. ახლა ჩვენი კონტრაქტი იტყუება: „გამომიგზავნე Id“ — თუმცა ის არ გვჭირდება.

პრობლემა 3 · ცხრილის ცვლილება ამტვრევს კლიენტებს

სლაიდი 12

ბაზაში სვეტს გადავარქმევთ: Name → Title. კოდში ეს ერთი ცვლილებაა — Visual Studio ყველგან ჩაანაცვლებს.

მაგრამ JSON-შიც შეიცვალა ველის სახელი: "name" → "title".

  • საიტი ეძებს product.name-ს და იღებს undefined-ს.
  • მობილური აპლიკაცია, რომელიც უკვე ხალხის ტელეფონებზეა, ფუჭდება. მის განახლებას კვირები სჭირდება.

მიზეზი ის არის, რომ ერთი კლასი ორ სხვადასხვა როლს ასრულებს:

რა არის როდის იცვლება

DTO — Data Transfer Object

სლაიდი 14

DTO არის კლასი, რომელიც მხოლოდ მონაცემის გადასატანად არსებობს. მასში ლოგიკა არ არის — მხოლოდ ველები. წესი მარტივია: Entity შიგნით რჩება, გარეთ DTO გადის.

ბანკის მაგალითი:

  • 📝 Request DTO — ანგარიშის გასახსნელი განაცხადი. მხოლოდ ის ველები, რაც შენ უნდა შეავსო: სახელი, პირადი ნომერი, ტელეფონი. ანგარიშის ნომერს არ წერ — ბანკი გაძლევს.
  • 🗄️ Entity — ბანკის შიდა ბაზა: ყველაფერი, რაც ბანკმა იცის. რისკის შეფასება, ვინ გახსნა, როდის. გარედან ამას არავინ ხედავს.
  • 🧾 Response DTO — ამონაწერი, რომელსაც ბანკი გაძლევს: მხოლოდ ის, რაც შენ გჭირდება.

ერთი ანგარიში — სამი ფორმა. ზუსტად იგივეს ვაკეთებთ პროდუქტისთვის: CreateProductRequest → Product → ProductResponse.

📘 ტერმინები

🤖 DTO-ს სხვა მაგალითით ახსნა
მე ვსწავლობ ASP.NET Core Web API-ს. ვიცი Controller, IActionResult და CRUD, მაგრამ DTO ახალია ჩემთვის. ამიხსენი, რა არის DTO და რატომ არ უნდა დავაბრუნო Entity პირდაპირ. გამოიყენე ცხოვრებისეული მაგალითი (არა ბანკის) და მერე C#-ის პატარა მაგალითი Product-ზე: CreateProductRequest, Product, ProductResponse. ახსნა ქართულად, მარტივად.

მონაცემის გზა POST-ის დროს

სლაიდი 15

ასე გაივლის მონაცემი, როცა ახალ პროდუქტს ვამატებთ:

  1. JSON → CreateProductRequest — კლიენტის JSON ჯდება Request-ში. მასში მხოლოდ სამი ველია: Name, Price, CostPrice. Id და CreatedAt იქ საერთოდ არ არის.
  2. Request → Product — Request-იდან ვაწყობთ Entity-ს. სერვერი ამატებს Id-ს და CreatedAt-ს. Product ინახება.
  3. Product → ProductResponse — პასუხისთვის Entity-დან ვაწყობთ Response-ს. CostPrice და CreatedAt აქ აღარ არის.
  4. Response → JSON — კლიენტთან მიდის მხოლოდ id, name, price.

ველების გადატანას ერთი ობიექტიდან მეორეში mapping ჰქვია. ამ სქემაში ის ორჯერ ხდება: Request → Entity და Entity → Response.

შედეგად სამივე პრობლემა მოგვარდა:

  • CostPrice გარეთ აღარ გადის.
  • Id და CreatedAt კლიენტს აღარ ეთხოვება.
  • ცხრილის ცვლილება JSON-ს აღარ ცვლის.

Mapping

DTO-ები კოდში — record

სლაიდი 16

პროექტში ვქმნით ფოლდერს Dtos და მასში სამ DTO-ს (რეალურად — თითო ფაილი თითოზე):

Dtos/
public record CreateProductRequest(    string Name,    decimal Price,    decimal CostPrice); public record UpdateProductRequest(    string Name,    decimal Price,    decimal CostPrice); public record ProductResponse(    Guid Id,    string Name,    decimal Price);
  • CreateProductRequest — შექმნისას: Id-ს და CreatedAt-ის გარეშე.
  • UpdateProductRequest — განახლებისას: Id-ს გარეშე, რადგან Id მისამართიდან მოდის.
  • ProductResponse — პასუხში: CostPrice-ის და CreatedAt-ის გარეშე.

რატომ record? DTO-სთვის class-იც გამოდგება, მაგრამ record ერთ ხაზში აკეთებს ყველაფერს: ფრჩხილებში ჩამოწერილი პარამეტრები ავტომატურად ხდება property-ები და constructor. JSON-ში Name ისევ "name"-ად გადაიქცევა, როგორც ადრე.

სახელები: …Request — რაც შემოდის, …Response — რაც გადის. ასე ფაილის სახელიდანვე ჩანს, რისთვის არის კლასი.

💡

CreateProductRequest და UpdateProductRequest ახლა ერთნაირია — მაშ, რატომ ცალკე? იმიტომ, რომ ხვალ შეიძლება განსხვავდებოდეს: მაგალითად, განახლებისას შესყიდვის ფასის შეცვლა აიკრძალოს. ცალკე კლასით ერთის შეცვლა მეორეს არ დააზიანებს.

🤖 record vs class
ამიხსენი C#-ში record-ის და class-ის განსხვავება მარტივად. მაგალითად აიღე: public record ProductResponse(Guid Id, string Name, decimal Price); რა იქმნება ავტომატურად ამ ერთი ხაზით? რატომ ჯობია record DTO-სთვის? ახსნა ქართულად, დამწყებისთვის.

ProductMapper — mapping ერთ ადგილას

სლაიდი 23

ვქმნით ფოლდერს Mappers და მასში კლასს ProductMapper:

Mappers/ProductMapper.cs
public static class ProductMapper{    public static ProductResponse ToResponse(this Product product)    {        return new ProductResponse(product.Id, product.Name, product.Price);    }     public static Product ToEntity(this CreateProductRequest request)    {        return new Product        {            Name = request.Name,            Price = request.Price,            CostPrice = request.CostPrice        };    }     public static void UpdateFrom(this Product product, UpdateProductRequest request)    {        product.Name = request.Name;        product.Price = request.Price;        product.CostPrice = request.CostPrice;    }}
  • static class — მისი ობიექტის შექმნა არ გვჭირდება, მხოლოდ მეთოდები.
  • ToResponse — Product → ProductResponse. ზუსტად ის ხაზი, რომელიც სამ ადგილას გვქონდა.
  • ToEntity — Request → ახალი Product. Id-ს და CreatedAt-ს აქ არ ვავსებთ — ეს სერვერის გადაწყვეტილებაა და Controller-ში რჩება.
  • UpdateFrom — ახალს არ ქმნის, არსებულ Product-ს ცვლის. ამიტომ void-ია.

this პარამეტრის წინ — extension method

this საშუალებას გვაძლევს მეთოდი ისე გამოვიძახოთ, თითქოს ის Product-ს ეკუთვნის:

csharp
product.ToResponse();               // extension method — ასე ვწერთProductMapper.ToResponse(product);  // იგივეა, უბრალოდ ნაკლებად იკითხება

ორივე ხაზი ზუსტად ერთსა და იმავეს აკეთებს. extension method-ისთვის კლასიც და მეთოდიც static უნდა იყოს. LINQ-ის Select და Where ზუსტად ასეთი extension method-ებია.

📘 ტერმინები
Extension method
static მეთოდი, რომლის პირველ პარამეტრს this უწერია; იძახება ისე, თითქოს იმ ტიპს ეკუთვნის: product.ToResponse()
🤖 extension method-ის გაგება
ამიხსენი C#-ის extension method მარტივად. მაგალითი: public static ProductResponse ToResponse(this Product product) { ... } რატომ შეიძლება product.ToResponse() დავწერო, თუ ეს მეთოდი Product კლასში არ არის? რატომ უნდა იყოს კლასი static? მომიყევი, რომელი ცნობილი extension method-ები მაქვს უკვე გამოყენებული (LINQ). ახსნა ქართულად.

Mapperly გეკითხება: „განზრახ გამოტოვე?“

სლაიდი 30

Build-ის შემდეგ Error List-ში გაფრთხილება ჩნდება:

Warning RMG020
The member CostPrice on the mapping source type Product is not mappedto any member on the mapping target type ProductResponse

Mapperly ამბობს: Product-ს CostPrice აქვს, ProductResponse-ში კი ის არსად წავიდა. „შემთხვევით ხომ არ დაგავიწყდა?“ ვპასუხობთ ატრიბუტებით:

Mappers/ProductMapper.cs
[MapperIgnoreSource(nameof(Product.CostPrice))][MapperIgnoreSource(nameof(Product.CreatedAt))]public static partial ProductResponse ToResponse(this Product product); [MapperIgnoreTarget(nameof(Product.Id))][MapperIgnoreTarget(nameof(Product.CreatedAt))]public static partial Product ToEntity(this CreateProductRequest request);
  • MapperIgnoreSource — „წყაროს ეს ველი განზრახ არ გადავიტანე“.
  • MapperIgnoreTarget — „სამიზნის ეს ველი სხვა ავსებს“ (აქ — სერვერი). იგივე დაამატე UpdateFrom-ზეც.
  • nameof(...) — სახელს ტექსტად არ ვწერთ, რომ შეცდომა არ დავუშვათ. თუ ველს გადავარქმევთ, nameof კომპილაციისას შეგვახსენებს.

ხელით დაწერილ Mapper-ში ახალი ველის დამატება შეიძლებოდა დაგვვიწყებოდა. Mapperly-ში ახალ ველზე ის თვითონ გვეტყვის — ზუსტად ის პრობლემა მოგვარდა, რომლითაც ეს ნაწილი დავიწყეთ.

using Isopoh.Cryptography.Argon2; member.PasswordHash = Argon2.Hash(request.Password);   // Argon2id, salt-ითbool ok = Argon2.Verify(member.PasswordHash, password); // შემოწმება — შესვლისას
