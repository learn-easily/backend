Minimal API vs Controller, REST, CRUD და Swagger

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: კატეგორიები და REST ცხრილი. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • record Category(int Id, string Name) და სია 3-4 კატეგორიით
  • GET /api/categories — კატეგორიების სია
  • შეამოწმეთ .http ფაილით: 200 და JSON
  • ცხრილი (რვეულში ან ფაილში): Category-ს 5 REST endpoint — მეთოდი, მისამართი, წარმატების სტატუს კოდი

დღის თემა: Minimal API vs Controller, REST, CRUD და Swagger

სლაიდი 4

წინა ლექციაზე ერთი endpoint Program.cs-ში დავწერეთ. რეალურ API-ს ათეულობით endpoint აქვს — ერთ ფაილში ყველაფერი აირევა, და ბრაუზერით მხოლოდ GET-ის შემოწმება შეიძლება. დღეს ვნახავთ API-ის აწყობის ორ გზას, REST-ის წესებს, Swagger-ს — და ვწერთ პროდუქტების სრულ CRUD-ს.

ლექციის ბოლოს შეძლებ:

  • Minimal API-სა და Controller-ის განსხვავება, Controller-ის ანატომია
  • REST-ის 4 წესი და სწორი სტატუს კოდი ყოველ მეთოდზე
  • Swagger-ის დაყენება და endpoint-ების ტესტირება
  • სრული CRUD: GetAll, GetById, Create, Update, Delete

ლექციის გეგმა

სლაიდი 5
  1. ორი გზა — Minimal API და Controller: რით განსხვავდებიან და რატომ ვიწყებთ Controller-ით.
  2. REST — რატომ არსებობს და რა წესებს გვაძლევს.
  3. პირველი GET — ProductsController.
  4. Swagger — გარემო ტესტირებისთვის.
  5. 🛠️ სრული CRUD — ვწერთ → მაშინვე ვტესტავთ.
  6. პრაქტიკა — BooksController.

მიზანი ერთია — API, რომელიც მოთხოვნას იღებს და JSON-ს აბრუნებს. ASP.NET Core-ში მას ორი გზით ვაწყობთ.

წინა ლექციაზე: Minimal API

სლაიდი 7

წინა ლექციაზე endpoint პირდაპირ Program.cs-ში დავწერეთ:

Program.cs

ერთი ხაზი = ერთი endpoint: მისამართი + რა დავაბრუნოთ. (შენ შეიძლება სხვა მისამართი დაწერე, მაგ. /api/products — იდეა იგივეა.) ამ სტილს Minimal API ჰქვია: ყველაფერი Program.cs-ში, მინიმალური კოდით.

სხვა გზებიც არსებობს?

სლაიდი 9

ძირში დგას ASP.NET Core — იღებს HTTP მოთხოვნას, პოულობს, ვინ უნდა უპასუხოს, და JSON-ს აბრუნებს. მასზე ორი ჩაშენებული გზაა — Minimal API და Controllers; სწორედ ამ ორს გვთავაზობს შაბლონი და არაფრის დაყენება არ სჭირდება.

არსებობს სხვა გზებიც — მაგ. FastEndpoints, Carter. ეს საზოგადოების მიერ დაწერილი NuGet პაკეტებია, იგივე საძირკველზე. ჩვენ ჩაშენებულ ორს ვსწავლობთ.

ერთი და იგივე endpoint — ორი გზით

სლაიდი 10
Minimal API · Program.cs
app.MapGet("/api/products", () =>{    return new[] { "ლეპტოპი", "მაუსი" };});
Controller · Controllers/ProductsController.cs

Minimal API Controller
მისამართი + მეთოდი MapGet("/api/products") — ერთ ხაზში [Route] + [HttpGet]
რას ვაბრუნებთ ფუნქცია (lambda) კლასის მეთოდი + Ok(...)

Controller-ში მეტი კოდია — ვნახოთ, რატომ.

Controller — ნაწილ-ნაწილ

სლაიდი 11
Controllers/ProductsController.cs
[ApiController][Route("api/[controller]")]public class ProductsController : ControllerBase{    [HttpGet]    public IActionResult GetAll()    {        return Ok(new[] { "ლეპტოპი", "მაუსი" });    }}
  1. [ApiController] — ატრიბუტი: „ეს კლასი API-ს ემსახურება“. რთავს API-სთვის საჭირო ქცევას — მაგ. არასწორ მონაცემზე თვითონ აბრუნებს 400-ს.
  2. [Route("api/[controller]")] — მისამართი. [controller] = კლასის სახელი „Controller“-ის გარეშე: ProductsController → api/products.
  3. : ControllerBase — მზა მეთოდებს გვაძლევს: Ok(), NotFound(), NoContent()…
  4. [HttpGet] — HTTP მეთოდი.
  5. IActionResult — „HTTP პასუხი“: სტატუს კოდი + მონაცემი.

ატრიბუტი
[კვადრატულ ფრჩხილებში] დაწერილი „ნიშანი“ კლასზე ან მეთოდზე, რომელსაც framework კითხულობს
IActionResult
მეთოდის დასაბრუნებელი ტიპი: სტატუს კოდი + (არასავალდებულო) მონაცემი

Controller-ებს Program.cs-ში ორი ხაზი სჭირდება

სლაიდი 12
Program.cs

  1. AddControllers() — „ჩემს პროექტში Controller-ები იქნება“ (რეგისტრაცია).
  2. MapControllers() — „იპოვე ყველა Controller და მათი მისამართები მიაბი“: ProductsController → api/products, CategoriesController → api/categories…

  • 📁 Controllers — ყოველ თემას თავისი ფაილი აქვს: პროდუქტებზე სამუშაოდ ProductsController-ს ხსნი და მეტს არაფერს.

(Minimal API-საც შეიძლება ფაილებად დაყოფა — ოღონდ ეს სტრუქტურა შენ თვითონ უნდა მოიფიქრო.)

Minimal API vs Controller

სლაიდი 14
Minimal API Controller
სად წერია Program.cs-ში (ან ჩვენ მიერ შექმნილ ფაილებში) ცალკე კლასებში, Controllers/ ფოლდერში

რატომ ვიწყებთ Controller-ებით

სლაიდი 15

🏗️ ახლა: Controllers (CRUD, REST, მომდევნო ლექციები) → 📐 არქიტექტურა (როგორ დავალაგოთ პროექტი) → ⚡ Minimal API — უკვე სწორი სტრუქტურით.

  • 🧭 სტრუქტურა მზადაა — ვფიქრობთ API-ზე და არა იმაზე, რომელ ფაილში რა ჩავწეროთ.
  • 🏢 სამსახურში შეხვდები — არსებული პროექტების დიდი ნაწილი Controller-ებითაა დაწერილი.

2 · REST

ნაწილი 2 · REST — წესები ყველასთვის

სლაიდი 16

REST წინა ლექციაზე თეორიულად ვახსენეთ. დღეს ვნახავთ, რატომ არსებობს და რა მოხდებოდა მის გარეშე.

REST რომ არ არსებობდეს…

სლაიდი 17

სამ დეველოპერს ერთი დავალება აქვს — პროდუქტების API:

  • 👩‍💻 A ყველაფერს POST-ით აკეთებს, მოქმედებას მისამართში წერს: POST /getAllProducts, POST /addNewProduct, POST /removeProduct?id=5.
  • 🧑‍💻 B ყველაფერს GET-ით, წაშლასაც კი: GET /products_list, GET /product/create?name=…, GET /delete-product/5.
  • 👨‍💻 C-ს ერთი მისამართი აქვს, და რა ქნას — JSON-ში წერს.

სამივე მუშაობს — მაგრამ Frontend დეველოპერმა ყოველ API-ზე თავიდან უნდა ისწავლოს ყველაფერი.

REST-ით: ერთი მისამართი + HTTP მეთოდი = მოქმედება

სლაიდი 18
მოთხოვნა მოქმედება
GET /api/products ყველა პროდუქტი
GET /api/products/5 ერთი პროდუქტი (Id = 5)
POST /api/products ახალი პროდუქტის დამატება
PUT /api/products/5 პროდუქტი 5-ის განახლება
DELETE /api/products/5 პროდუქტი 5-ის წაშლა

მისამართი = რას, მეთოდი = რა ვუყოთ. შენიშნე: POST-ის მისამართი იგივეა, რაც ყველას წაკითხვისას — განსხვავება მხოლოდ მეთოდშია.

REST-ის 4 მთავარი წესი

სლაიდი 19
  1. რესურსი — მისამართი არსებითი სახელია, მრავლობითში: ✓ /api/products ✗ /getProducts.
  2. მოქმედება — ვირჩევთ HTTP მეთოდით: GET · POST · PUT · DELETE.
  3. შედეგი — ვაცნობებთ სტატუს კოდით: 200 · 201 · 204 · 404. აღარავითარი { "success": false } 200-იან პასუხში.
  4. ფორმატი — მონაცემი მიდის და მოდის JSON-ით: { "name": "მაუსი", "price": 45 }.

რომელ კოდს რომელი მეთოდი აბრუნებს

სლაიდი 20
  • 2xx — წარმატება ✓ · 4xx — კლიენტის შეცდომა (შენ გაგზავნე რაღაც არასწორად) · 5xx — სერვერის შეცდომა (ჩვენ დაგვიშავდა)
კოდი Controller-ში როდის
200 OK Ok(data) მონაცემს ვაბრუნებთ
201 Created CreatedAtAction(...) ახალი რამ შეიქმნა
204 No Content NoContent() შესრულდა, დასაბრუნებელი არაფერია
400 Bad Request BadRequest() არასწორი მოთხოვნა
