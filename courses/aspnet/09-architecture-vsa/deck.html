Controller-ი Service-ს, Service-ი DataContext-ს. ```csharp Services/CourseService.cs public class CourseService { private readonly DataContext _db; public CourseService(DataContext db) { _db = db; } public async Task> GetAllAsync() { ... } public async Task GetByIdAsync(Guid id) { ... } public async Task CreateAsync(CreateCourseRequest r) { ... } public async Task UpdateAsync(Guid id, UpdateCourseRequest r) { ... } public async Task DeleteAsync(Guid id) { ... } } ``` ```csharp Controllers/CoursesController.cs · GetById [HttpGet("{id:guid}")] public async Task GetById(Guid id) { var course = await _courseService.GetByIdAsync(id); if (course is null) return NotFound(); return Ok(course); } ``` ტკივილი №3 გამოსწორდა: Controller-ში მხოლოდ HTTP დარჩა, წესები Service-ში გადავიდა. ```note ხშირად მესამე ფენასაც ამატებენ: **Repository** (`CourseRepository`), რომელიც DataContext-ს „ფარავს“. EF Core-ის DbSet თვითონ არის repository-ის მსგავსი, ამიტომ ჩვენ მას არ ვამატებთ. ```

## ნაწილი 2 · SRP და DIP SOLID ხუთი პრინციპია, რომლებიც კოდის დიზაინის შეფასებაში გვეხმარება. დღეს ორი გვჭირდება: **S** (SRP) და **D** (DIP). ორივეს ჩვენს კოდზე ვნახავთ.
S · Single Responsibility Principle

კლასს — ერთი მიზეზი შესაცვლელად

CoursesController / CourseService იცვლება, როცა:
1კურსის შექმნას ახალი წესი დაემატა
2სიას დალაგება შეეცვალა
3ერთი კურსის პასუხს ველი დაემატა
4ცვლილებას ახალი შემოწმება დაემატა
5წაშლა აიკრძალა, თუ კურსს ჯგუფები აქვს
ხუთი მიზეზი = ხუთი პასუხისმგებლობა ერთ კლასში
ერთი კლასი — ერთი საქმე: CreateCourseHandler იცვლება მხოლოდ მაშინ, როცა კურსის შექმნა იცვლება
„ერთი საქმე“ ≠ „ერთი მეთოდი“. საზომი — ვინ და რატომ მოითხოვს ცვლილებას
### SRP: კლასს შეცვლის ერთი მიზეზი უნდა ჰქონდეს **SRP** (Single Responsibility Principle, ერთი პასუხისმგებლობის პრინციპი): **კლასს შეცვლის მხოლოდ ერთი მიზეზი უნდა ჰქონდეს.** ჩამოვწეროთ, როდის იცვლება `CoursesController` (ან Layers-ში `CourseService`): 1. კურსის შექმნას ახალი წესი დაემატა; 2. სიას დალაგება შეეცვალა; 3. ერთი კურსის პასუხს ველი დაემატა; 4. ცვლილებას ახალი შემოწმება დაემატა; 5. წაშლა აიკრძალა, თუ კურსს ჯგუფები აქვს. ხუთი მიზეზი ხუთი პასუხისმგებლობაა ერთ კლასში. როცა ერთს ცვლი, დანარჩენ ოთხსაც ეხები და შეიძლება გააფუჭო. SRP-ს მიხედვით: ერთი კლასი, ერთი საქმე. თუ გვექნება `CreateCourseHandler`, ის მხოლოდ მაშინ შეიცვლება, როცა **კურსის შექმნა** იცვლება. ```warn „ერთი საქმე“ „ერთ მეთოდს“ არ ნიშნავს. საზომი ისაა, **ვინ და რატომ** მოითხოვს ცვლილებას. თუ ორ სხვადასხვა მოთხოვნას ერთი კლასის შეცვლა სჭირდება, კლასს ორი პასუხისმგებლობა აქვს. ``` ```terms SRP (Single Responsibility Principle) — კლასს შეცვლის ერთი მიზეზი უნდა ჰქონდეს SOLID — კოდის დიზაინის ხუთი პრინციპი: S · O · L · I · D ```

### DIP: არ ქმნი, ითხოვ, და დეტალი არ გაინტერესებს **DIP** (Dependency Inversion Principle, დამოკიდებულების ინვერსიის პრინციპი) ორ რამეს ამბობს: 1. **კლასი თავის დამოკიდებულებებს თვითონ არ ქმნის, ითხოვს.** ეს 04 ლექციიდან ვიცით: DataContext-ს constructor-ით ვითხოვთ, Container კი ქმნის და გვაწვდის. 2. **კლასი აბსტრაქციაზე მუშაობს და არა დეტალზე.** ბიზნესის კოდს არ უნდა აინტერესებდეს, რომელი ბაზაა, როგორი connection string აქვს ან როგორ იგზავნება email. ```csharp ❌ თვითონ ქმნის public class CreateCourseHandler { private readonly DataContext _db = new DataContext( "Server=(localdb)\\MSSQLLocalDB;Database=LmsDb;…"); } ``` ```csharp ✅ ითხოვს public class CreateCourseHandler { private readonly DataContext _db; public CreateCourseHandler(DataContext db) { _db = db; } } ``` მეორე ვერსიაში handler-მა არ იცის, როგორ იქმნება DataContext. მან ისიც არ იცის, რომ ბაზა SQL Server-ია: `_db.Courses.AnyAsync(…)` ნებისმიერ ბაზაზე იმუშავებს, რომელსაც EF Core იცნობს. თუ აკადემია PostgreSQL-ზე გადავა, შეიცვლება **მხოლოდ Program.cs** (`UseSqlServer` → `UseNpgsql`). ერთი handler-იც არ შეიცვლება. DataContext აქ **აბსტრაქციაა**: ის SQL Server-ის დეტალებს მალავს. სხვა შემთხვევაში აბსტრაქციად `interface` გამოიყენება, მაგალითად email-ის გაგზავნისთვის, სადაც ნამდვილი სერვისი და სატესტო ვერსია უნდა შევცვალოთ. interface-ს მაშინ შემოვიტანთ, როცა ასეთი საჭიროება მართლა გაჩნდება. ```terms DIP (Dependency Inversion Principle) — კლასი დამოკიდებულებებს ითხოვს და აბსტრაქციაზე მუშაობს, არა კონკრეტულ დეტალზე აბსტრაქცია — რაც დეტალს მალავს: გვეუბნება, რა შეუძლია, და არა როგორ აკეთებს ```

### ერთი feature, ერთი საქაღალდე **Vertical Slice Architecture** (VSA) კოდს **feature-ის** მიხედვით ჭრის. თითო feature („slice“, ნაჭერი) ერთ backlog story-ს ან მის ერთ მოქმედებას შეესაბამება: `CreateCourse`, `GetCourses`, `EnrollStudent`. ყველაფერი, რაც ამ feature-ს სჭირდება, ერთ საქაღალდეში დევს: ```text Lms.Api Features/ Courses/ CreateCourse/ CreateCourseRequest.cs ← რა შემოდის CreateCourseHandler.cs ← საქმე: წესები, ბაზა, პასუხი CreateCourseEndpoint.cs ← მისამართი და მეთოდი GetCourses/ … GetCourseById/ … CourseResponse.cs ← საერთო Courses-ის slice-ებისთვის CourseMapper.cs ← საერთო (ToResponse) CourseEndpoints.cs ← Courses-ის რეგისტრაცია Students/ … Entities/ ← საერთო ყველასთვის Data/ ← საერთო ყველასთვის ``` ერთი მთავარი წესი: **რაც ერთად იცვლება, ერთად დევს.** - „კურსის შექმნას“ ახალი ველი დაემატა? → მხოლოდ `CreateCourse/` საქაღალდე (და, თუ ბაზაშიც უნდა შეინახო, `Course` entity). - ორი დეველოპერი ორ სხვადასხვა feature-ზე მუშაობს? → ორ სხვადასხვა საქაღალდეში. ერთ ფაილზე აღარ ეჯახებიან. **რა რჩება საერთო?** ის, რასაც ბევრი slice იყენებს: `Entities` (ბიზნესის ცნებები), `Data` (DataContext) და ერთი ჯგუფის საერთო პასუხი (`CourseResponse`). `ToEntity`-ს მხოლოდ CreateCourse იყენებს, ამიტომ ის handler-ში გადადის. Mapper-ში მხოლოდ `ToResponse` რჩება. ```terms Vertical Slice Architecture (VSA) — კოდის დალაგება feature-ის მიხედვით: ერთი feature, ერთი საქაღალდე Slice (ნაჭერი) — ერთი feature-ის ყველა ნაწილი: Request, Handler, Endpoint ```

## შეჯამება · რაც ერთად იცვლება, ერთად დევს **დაიმახსოვრე:** 1. **Layers** (Controller → Service → Data) კოდს **ტექნიკური როლით** ყოფს. ის მოწესრიგებულია, მაგრამ ერთი feature ყველა ფენაში ხვდება, Service-ები კი იზრდება. 2. **SRP:** კლასს შეცვლის ერთი მიზეზი უნდა ჰქონდეს. CoursesController-ს ხუთი ჰქონდა. 3. **DIP:** კლასი დამოკიდებულებებს ითხოვს და აბსტრაქციაზე მუშაობს. handler-მა არ იცის, რომ ბაზა SQL Server-ია. 4. **Vertical Slice Architecture** კოდს **feature-ით** ყოფს: რაც ერთად იცვლება, ერთად დევს. Entities და DataContext საერთოა. 5. **Slice = Request + Handler + Endpoint.** Handler ჩვეულებრივი class-ია, Scoped-ად რეგისტრირებული. Endpoint Minimal API-ა `MapGroup`-ის შიგნით. ყველაფერი ხელით ჩანს: MediatR არ არის. 6. Minimal API პარამეტრებს თვითონ ავსებს: body-დან (Request), DI-დან (Handler) და მისამართიდან (`Guid id`). 7. .NET 10 OpenAPI დოკუმენტს თვითონ ქმნის, **Scalar** კი მას `/scalar`-ზე ხატავს. ```prompt არქიტექტურა — გასაუბრებისთვის ვემზადები .NET Junior გასაუბრებისთვის. დამისვი კითხვები: Layered Architecture vs Vertical Slice Architecture (უპირატესობები და ნაკლი), SRP და DIP მაგალითებით, Minimal API-ში parameter binding (body, route, DI), handler-ის lifetime DbContext-თან ერთად, OpenAPI და Scalar .NET 10-ში. სათითაოდ დასვი, დაელოდე ჩემს პასუხს, შემიფასე და აუხსენი, რა გამომრჩა. 8 კითხვა. ქართულად. ```
