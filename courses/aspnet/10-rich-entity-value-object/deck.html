### Rich entity: ცვლილება მხოლოდ „კარიდან“ **Rich entity** (მდიდარი entity) თავის მონაცემებს თვითონ იცავს. ამისთვის ოთხი რამ ვცვალეთ: 1. **`private set`.** თვისებას გარედან წაიკითხავ (`course.Title`), მაგრამ ვერ შეცვლი. `course.DurationWeeks = -5;` აღარ კომპილირდება. 2. **`private` constructor.** `new Course { ... }` გარედან აღარ შეიძლება. EF Core-ს მაინც შეუძლია მისი გამოძახება, როცა ბაზიდან კითხულობს: მას private constructor-იც „ხედავს“. 3. **შექმნა მხოლოდ `Create`-ით.** ეს static მეთოდია, რომელიც ჯერ წესს ამოწმებს და მხოლოდ მერე ქმნის ობიექტს. ასეთ მეთოდს **factory method** ჰქვია. 4. **ცვლილება მხოლოდ მეთოდით.** `Update` ჯერ წესს ამოწმებს, მერე ცვლის. ასე წესი **ერთ ადგილას** იწერება და ყველა handler, ახალიც, ავტომატურად ემორჩილება მას. ერთი კითხვა დარჩა: თუ წესი დაირღვა, **რა დააბრუნოს `Create`-მა?** ამაზე შემდეგ ნაწილში. ```terms Rich entity — entity, რომელიც თავის წესებს თვითონ იცავს: private set, ცვლილება მხოლოდ მეთოდებით Factory method — static მეთოდი (Create), რომელიც ობიექტს ქმნის მხოლოდ მაშინ, თუ წესი დაცულია ```

### exception თუ Result? **exception-ით:** ```csharp if (durationWeeks is < 1 or > 52) throw new ArgumentException("ხანგრძლივობა 1-დან 52 კვირამდეა"); ``` სამი პრობლემა აქვს: - მეთოდის ხელმოწერა `Course Create(...)` **არ ამბობს**, რომ შეიძლება ჩავარდეს. ამას მხოლოდ კოდის წაკითხვით გაიგებ. - თუ handler-მა `try/catch` დაავიწყდა, კლიენტი **500**-ს მიიღებს („სერვერის შეცდომა“), თუმცა ბრალი მისია და სწორი პასუხი **400**-ია. - exception შეიქმნა **მოულოდნელი** სიტუაციებისთვის და შედარებით ძვირია. ცარიელი სახელი მოულოდნელი არ არის: მომხმარებლები ამას ყოველდღე აკეთებენ. **Result-ით:** ```csharp if (durationWeeks is < 1 or > 52) return Result.Failure(CourseErrors.InvalidDuration); ``` - ხელმოწერა `Result Create(...)` თვითონ ამბობს: „შეიძლება კურსი მოგცე, შეიძლება შეცდომა“. - handler-ი შედეგს ამოწმებს და **თვითონ წყვეტს**, რა უპასუხოს: 400, 404 თუ 409. - ჩვეულებრივი `return`-ია, არაფერი „ფრინავს“. **წესი:** მოსალოდნელი, ბიზნესის შეცდომა → **Result**. მოულოდნელი (ბაზა გაითიშა, კოდში ბაგი) → **exception**. ```terms Result pattern — მეთოდი აბრუნებს ან მნიშვნელობას (წარმატება), ან შეცდომას (Error), exception-ის სროლის ნაცვლად ```

## შეჯამება · წესი ცხოვრობს იქ, სადაც მონაცემი 1. **ანემიური entity** მხოლოდ მონაცემებია: ნებისმიერ კოდს შეუძლია მისი არასწორ მდგომარეობაში ჩაგდება. 2. **Rich entity** თავის წესებს თვითონ იცავს: `private set`, `private` constructor, შექმნა `Create`-ით, ცვლილება მეთოდებით (`Update`). 3. **Result pattern:** მოსალოდნელი ბიზნეს-შეცდომა ბრუნდება `Result`-ით (`Error`: Code + Message), exception-ის გარეშე. exception მოულოდნელისთვისაა. 4. **entity მხოლოდ საკუთარ მდგომარეობას იცავს.** წესები, რომლებსაც ბაზა სჭირდება (R1: სახელი უნიკალურია, R2: Email უნიკალურია, „კურსი არსებობს“), handler-ში რჩება. 5. **Value Object**-ს Id არ აქვს, მნიშვნელობით დარდება და არ იცვლება. C#-ში: `sealed record`. `Email` ერთხელ მოწმდება და ყველგან სანდოა. 6. EF Core Value Object-ს `HasConversion`-ით ინახავს ჩვეულებრივ სვეტად. 7. **Group** თავიდანვე rich entity-ა: ≤ 20 ადგილი, წარსულში ვერ დაიწყება. `today` handler-იდან მოდის. ```prompt DDD-ის საფუძვლები — გასაუბრებისთვის ვემზადები .NET Junior გასაუბრებისთვის. დამისვი კითხვები: anemic vs rich domain model, factory method, Result pattern vs exceptions (როდის რომელი), Entity vs Value Object (მაგალითებით), C# record და მნიშვნელობით შედარება, EF Core value conversion, რომელი წესი ეკუთვნის entity-ს და რომელი handler-ს. სათითაოდ დასვი, დაელოდე ჩემს პასუხს, შემიფასე და აუხსენი, რა გამომრჩა. 8 კითხვა. ქართულად. ```
