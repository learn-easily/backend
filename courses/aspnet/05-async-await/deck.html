### Thread და Thread Pool **Thread (ნაკადი)** — „მუშა“, რომელიც კოდს ხაზ-ხაზ ასრულებს. აქამდე ჩვენს კონსოლის პროგრამებს ერთი ნაკადი ასრულებდა: `Main`-იდან დაიწყებდა და ბოლომდე მივიდოდა. სერვერზე სხვა სურათია: ერთდროულად ბევრი მოთხოვნა მოდის. ASP.NET Core-ს აქვს **Thread Pool** — მზა ნაკადების „აუზი“. მოთხოვნა მოვიდა → აუზიდან თავისუფალი ნაკადი იღებს და ჩვენს Controller-ის მეთოდს ასრულებს → მოთხოვნა დასრულდა → ნაკადი აუზში ბრუნდება და შემდეგ მოთხოვნას ელოდება. თუ ყველა ნაკადი დაკავებულია, ახალი მოთხოვნა **რიგში დგება**. რატომ არ ვქმნით ათასობით ნაკადს? იმიტომ, რომ ნაკადი ძვირია: - თითოეულს საკუთარი მეხსიერება სჭირდება (სტეკისთვის — დაახლოებით 1 MB); - ოპერაციულ სისტემას მათ შორის გადართვა უწევს; - Thread Pool ახალ ნაკადებს **ნელ-ნელა** ამატებს — უეცარ დატვირთვაზე ვერ ასწრებს. ```terms Thread (ნაკადი) — „მუშა“, რომელიც კოდს ასრულებს Thread Pool — მზა ნაკადების აუზი; ASP.NET Core ყოველ მოთხოვნას იქიდან აძლევს ნაკადს ```

### სამი ცვლილება: async · Task<…> · await ```csharp ადრე — სინქრონული [HttpGet] public IActionResult GetAll() { var products = _db.Products.ToList(); return Ok(products); } ``` ```csharp ახლა — ასინქრონული [HttpGet] public async Task GetAll() { var products = await _db.Products.ToListAsync(); return Ok(products); } ``` 1. **`async`** — მეთოდის ნიშანი: „ამ მეთოდში `await` იქნება“. მის გარეშე `await`-ის დაწერა არ შეიძლება. 2. **`Task`** — async მეთოდი თვითონაც დაპირებას აბრუნებს. Controller-ის მეთოდიც ლოდინს შეიცავს, ესე იგი ისიც მაშინვე შედეგს ვერ აბრუნებს. ASP.NET Core ამ Task-ს თვითონ ელოდება და პასუხს მერე აგზავნის. 3. **`await _db.Products.ToListAsync()`** — `ToListAsync` მოთხოვნას ბაზაში აგზავნის და მაშინვე `Task>`-ს აბრუნებს. `await` ამბობს: „დაველოდოთ შედეგს“ — და ამ დროს ნაკადი თავისუფლდება. `await`-ის შემდეგ `products` უკვე **`List`**-ია, არა Task: `await` დაპირებას „ხსნის“ და შიგნით არსებულ შედეგს გვაძლევს. ამიტომ დანარჩენი კოდი (`Ok(products)`) არ იცვლება. ```tip async მეთოდი თავიდან ბოლომდე ჩვეულებრივ კოდს ჰგავს — ზემოდან ქვემოთ იკითხება. ეს არის async/await-ის მთავარი ღირსება: ასინქრონულ კოდს ვწერთ ისე, თითქოს სინქრონული იყოს. ```

### async ერთ მოთხოვნას არ აჩქარებს ეს ყველაზე ხშირი მცდარი წარმოდგენაა — და გასაუბრებაზეც ხშირად ამოწმებენ. **ერთ მომხმარებელზე** სინქრონულიც და ასინქრონულიც ერთნაირ დროს ხარჯავს: ბაზა ისევ 40 ms-ს ფიქრობს, ქსელიც იგივეა. async-ს ცოტა დამატებითი სამუშაოც აქვს (კომპილატორის მიერ აგებული „მდგომარეობის მანქანა“), მაგრამ ის მიკროწამებია — შეუმჩნეველი. **ბევრ მომხმარებელზე** კი სურათი იცვლება: - სინქრონულად ნაკადები ლოდინში დგანან → ახალი მოთხოვნები რიგში → **ყველასთვის ნელდება**, ზოგს timeout. - ასინქრონულად ნაკადები ლოდინის დროს თავისუფლდებიან → იგივე სერვერი **ბევრად მეტ** ერთდროულ მომხმარებელს ემსახურება, და თითოეული ისევ ~40 ms-ში იღებს პასუხს. async-ის მოგება **მასშტაბია** (scalability) — რამდენ მომხმარებელს გაუძლებს სერვერი, და არა ერთი მოთხოვნის სიჩქარე. ```terms Scalability (მასშტაბირება) — რამდენ დატვირთვას უძლებს სისტემა ისე, რომ არ ნელდება ```
