### პრობლემა: `git add .` — და ყველაფერი წავიდა `git add .` საქაღალდეში **ყველაფერს** იღებს. ორი რეალური ისტორია: **📦 node_modules.** Angular პროექტში შენი კოდი შეიძლება 200 KB იყოს, `node_modules` კი — 300+ MB და ათიათასობით ფაილი. push დიდხანს გრძელდება, რეპო მძიმდება. ამასთან, ეს საქაღალდე `npm install`-ით ნებისმიერ დროს თავიდან იქმნება — მისი შენახვა აზრს მოკლებულია. **🔑 .env.** ფაილი პაროლებით და API გასაღებებით public რეპოში მოხვდა. ბოტები GitHub-ს მუდმივად სკანავენ და ასეთ გასაღებებს **წუთებში** პოულობენ — შედეგი: მოპარული ბაზა ან უცნობი ხარჯები ღრუბლოვან ანგარიშზე. ```warn შემდეგ commit-ში ფაილის წაშლა **არ შველის** — ის ისტორიაში რჩება და ნებისმიერს შეუძლია ძველი commit-ის ნახვა. თუ საიდუმლო გაჟონა, **გასაღები უნდა შეიცვალოს** (ახალი პაროლი, ახალი API key). საიდუმლოების სწორად შენახვას — GitHub Secrets — კურსში მოგვიანებით ვისწავლით. ```

### `.gitignore` — „ამას ნუ ხედავ“ `.gitignore` — ტექსტური ფაილი რეპოს root-ში. მასში ჩამოწერილ ფაილებს Git **ვერ ხედავს**: `git status` არ აჩვენებს, `git add .` არ იღებს. **წესი:** ფაილი ავტომატურად **იქმნება** (npm install, build) ან **საიდუმლოა**? → `.gitignore`-ში. ```plain .gitignore # 📦 დამოკიდებულებები node_modules/ # 🏗️ ბილდის შედეგი dist/ bin/ obj/ # 🔑 საიდუმლოები .env *.pfx # 🖥️ IDE და OS .vscode/ .vs/ .idea/ .DS_Store ``` | ჩანაწერი | რას ნიშნავს | |---|---| | `dist/` | საქაღალდე `dist`, სადაც არ უნდა იყოს | | `*.log` | ყველა `.log` ფაილი | | `!keep.log` | გამონაკლისი — ეს ფაილი არ დაიმალოს | | `/config.json` | მხოლოდ root-ში მყოფი `config.json` | | `# …` | კომენტარი | `bin/` და `obj/` — .NET-ის ბილდის საქაღალდეებია, `dist/` — Angular-ის, `node_modules/` — npm-ის.

### მზა შაბლონები და „უკვე ავტვირთე“ **`.gitignore` ხელით იშვიათად იწერება:** - **Angular** — `ng new` მას თვითონ ქმნის. - **.NET** — `dotnet new gitignore`, ან Visual Studio-ში Git → Create Git Repository. - **სხვა ყველაფერი** — [github.com/github/gitignore](https://github.com/github/gitignore): მზა შაბლონები თითქმის ყველა ენისა და ფრეიმვორკისთვის. **ფაილი უკვე commit-ში მოხვდა?** `.gitignore`-ში ჩაწერა საკმარისი არ არის — Git უკვე „თვალს ადევნებს“ ამ ფაილს. ჯერ უნდა ამოიღო: ```console Git Bash $ echo ".env" >> .gitignore $ git rm --cached .env rm '.env' $ git commit -m "Stop tracking .env" ``` `--cached` — ფაილი Git-იდან ამოიღე, მაგრამ დისკზე **დატოვე**. მის გარეშე ფაილი კომპიუტერიდანაც წაიშლება. ```warn თუ ფაილი საიდუმლო იყო და უკვე GitHub-ზე ავიდა — ის ძველ commit-ში მაინც ჩანს. **გასაღები/პაროლი შეცვალე.** ```

### პრაქტიკა · საიდუმლო ფაილი და .gitignore ვქმნით „საიდუმლო“ ფაილს და ვნახოთ, რას ფიქრობს Git: ```console Git Bash $ echo "API_KEY=12345-secret" > .env $ git status Untracked files: .env ``` Git `.env`-ს ხედავს — `git add .` მას წაიღებდა. ვამატებთ `.gitignore`-ს: ```console Git Bash $ echo ".env" > .gitignore $ git status Untracked files: .gitignore $ git add . $ git commit -m "Add .gitignore" $ git push ``` `.env` სიიდან გაქრა. `.gitignore` კი **თვითონ commit-დება** — ის რეპოს ნაწილია, რომ ყველა, ვინც რეპოს ჩამოიტვირთავს, იმავე წესებს იყენებდეს. ```note `echo "…" > file` — ფაილში ტექსტის ჩაწერა (ფაილს თავიდან ქმნის). `>>` — ბოლოში მიწერა. Linux-ის ბრძანებებს მოგვიანებით დეტალურად ვნახავთ; ფაილი შეგიძლია VS Code-შიც შექმნა. ```

## ნაწილი 2 · branch · merge · conflict ახალ ფიჩაზე ვმუშაობთ ცალკე შტოზე, `main` კი ხელუხლებელი რჩება. მზად რომ იქნება — ვაბრუნებთ მთავარში. თუ ორმა ადამიანმა ერთი და იგივე ხაზი შეცვალა — Git გვკითხავს, რომელი დავტოვოთ.
ისტორია

commit-ები = ჯაჭვი

$ git log --oneline a3f9c21 (HEAD -> main) Add contact section c41a8e0 Add styles 7b2e0d4 Add home page
main — მთავარი branch, მიუთითებს ბოლო commit-ზე
HEAD — „სად ვარ ახლა“
### ისტორია = commit-ების ჯაჭვი ყოველი commit წინას „იცნობს“ (მშობლის hash-ით) — ასე იქმნება ჯაჭვი: ```console Git Bash $ git log --oneline a3f9c21 (HEAD -> main) Add contact section c41a8e0 Add styles 7b2e0d4 Add home page ``` ზემოდან ქვემოთ — ახლიდან ძველისკენ. - **`main`** — მთავარი branch (შტო). ის უბრალოდ **მიმთითებელია** ბოლო commit-ზე და ახალ commit-თან ერთად წინ მიიწევს. - **`HEAD`** — „სად ვარ ახლა“: რომელ branch-ზე ან commit-ზე ვდგავართ. ```note ძველ პროექტებში მთავარ branch-ს `master` ჰქვია. დღეს სტანდარტია `main` — GitHub-იც ასე ქმნის. ```

🌿 Branch

ისტორიის პარალელური ხაზი. main ხელუხლებელი რჩება

🧪 ექსპერიმენტი

არ გამოვიდა? branch-ს წაშლი — main-ს არაფერი მოსვლია

👥 გუნდი

ყველა თავის branch-ზე მუშაობს და ერთმანეთს არ უშლის

### ცნება 4 · Branch (შტო) **პრობლემა:** საიტი მუშაობს და სერვერზე დევს. გინდა ახალი სექცია დაამატო, მაგრამ ამას 2 დღე სჭირდება — ამ ხნის განმავლობაში `main` ნახევრად დაწერილი კოდით უნდა იყოს? და თუ ამასობაში `main`-ზე სასწრაფო შესწორება დაგჭირდა? **Branch** — ისტორიის პარალელური ხაზი. ის მიმდინარე commit-იდან იწყება და `main`-ს არ ეხება. - 🌿 **იზოლაცია** — `main` სტაბილური რჩება, ახალ ფიჩაზე branch-ში მუშაობ. - 🧪 **ექსპერიმენტი** — არ გამოვიდა? branch-ს წაშლი, `main`-ს არაფერი მოსვლია. - 👥 **გუნდი** — ყველა თავის branch-ზე მუშაობს და ერთმანეთს ხელს არ უშლის. ```bash git branch # რა branch-ები მაქვს git switch -c feature/contacts # ახალი branch + გადასვლა git switch main # main-ზე დაბრუნება ``` ```tip სახელი — `feature/...` ახალი ფუნქციონალისთვის, `fix/...` შესწორებისთვის. ასე ერთი შეხედვით ჩანს, რას ეხება branch-ი. ```

Merge — შტოს დაბრუნება მთავარში

$ git switch main $ git merge feature/contacts Merge made by the 'ort' strategy. index.html | 12 ++++++++++++ $ git branch -d feature/contacts
① გადადი იქ, სადაც უნდა შეერწყას (main)
② merge — branch-ის ცვლილებები main-ში გადმოდის
③ branch აღარ გვჭირდება — ვშლით
### ცნება 5 · Merge (შერწყმა) ფიჩა მზადაა — ახლა branch-ის ცვლილებები `main`-ში უნდა დაბრუნდეს: ```console Git Bash $ git switch main $ git merge feature/contacts Merge made by the 'ort' strategy. index.html | 12 ++++++++++++ $ git branch -d feature/contacts ``` 1. **გადადი იმ branch-ზე, რომელშიც უნდა შეერწყას** — ჩვეულებრივ `main`. 2. **`git merge `** — მითითებული branch-ის ცვლილებები მიმდინარეში გადმოდის. 3. branch აღარ გვჭირდება — **ვშლით** (`-d`). commit-ები არ იკარგება, ისინი უკვე `main`-შია. **ორი შემთხვევა:** - თუ `main` branch-ის შექმნის შემდეგ **არ შეცვლილა**, Git უბრალოდ `main`-ს წინ გადაწევს — **fast-forward**. ახალი commit არ იქმნება. - თუ `main`-ზეც იყო ცვლილებები (როგორც სურათზე), Git ქმნის **merge commit**-ს, რომელსაც ორი მშობელი ჰყავს. ორივე შემთხვევაში შედეგი ერთია: `main`-ში ორივე ხაზის ცვლილებებია.
როცა Git ვერ წყვეტს

ორივე შტოში ერთი და იგივე ხაზი შეიცვალა → Git გეკითხება: „რომელი დავტოვო?“

### Conflict — ეს შეცდომა არ არის როცა ორივე branch-ში **ერთი და იგივე ხაზი** სხვადასხვანაირად შეიცვალა, Git ვერ გამოიცნობს, რომელია სწორი, და გეკითხება: ```html index.html <<<<<<< HEAD

გიორგის პორტფოლიო

=======

გიორგი ბერიძე — დეველოპერი

>>>>>>> feature/title ``` - `<<<<<<< HEAD` … `=======` — რაც მიმდინარე branch-ზეა (`main`). - `=======` … `>>>>>>> feature/title` — რაც შემოსულ branch-ზეა. **როგორ ვაგვარებთ:** 1. ფაილში ვტოვებთ სწორ ვარიანტს (ან ორივეს ვაერთიანებთ). 2. ვშლით სამივე ნიშანს: `<<<<<<<`, `=======`, `>>>>>>>`. 3. `git add index.html` → `git commit`. ```tip VS Code კონფლიქტს ფერებით აჩვენებს და ღილაკებს გთავაზობს: **Accept Current**, **Accept Incoming**, **Accept Both**. ```
