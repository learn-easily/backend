## ნაწილი 1 · GitHub Actions და CI მე-4 ლექციაზე Actions ჩანართში პირველი workflow ვნახეთ — `pages build and deployment`, რომელიც GitHub-მა თვითონ შექმნა. დღეს საკუთარს ვწერთ.
პრობლემა

ყოველი განახლება — ხელით

$ git push # შენთან # Termius → lms-server $ cd ~/lms $ git pull $ docker compose up -d --build # build 1 GB RAM-ზე 😬 $ docker compose logs -f api # მუშაობს?
😴 დაგავიწყდა → სერვერზე ძველი ვერსიაა
💥 main-ში მოხვდა კოდი, რომელიც არ იკომპილირდება → deploy ჩავარდა
👥 გუნდში 5 ადამიანი — ყველას სერვერის SSH უნდა ჰქონდეს?
CI — ყოველი ცვლილების შემოწმება · CD — ყოველი ცვლილების deploy. ავტომატურად
### პრობლემა: ყოველი განახლება — ხელით მე-10 ლექციის შემდეგ LMS-ის განახლება ასე გამოიყურება: ```console ყოველ ჯერზე $ git push # Termius → lms-server $ cd ~/lms $ git pull $ docker compose up -d --build $ docker compose logs -f api ``` - 😴 დაგავიწყდა — სერვერზე ძველი ვერსიაა; - 💥 `main`-ში მოხვდა კოდი, რომელიც არც კი იკომპილირდება — deploy ჩავარდება; - 👥 გუნდში ხუთი ადამიანია — ყველას სერვერზე SSH წვდომა ჰქონდეს? - 🐢 build 1 GB RAM-იან სერვერზე — ნელი და სახიფათო. **CI (Continuous Integration)** — ყოველი ცვლილება **ავტომატურად მოწმდება** (build, ტესტები), სანამ `main`-ში მოხვდება. **CD (Continuous Deployment)** — `main`-ის ყოველი ცვლილება **ავტომატურად** გადის სერვერზე. ორივეს GitHub Actions აკეთებს — ზუსტად იმ ნაბიჯებით, რასაც აქამდე ხელით ვაკეთებდით.

### ცნებები: workflow · trigger · job · runner · step | ცნება | რა არის | |---|---| | **workflow** | YAML ფაილი რეპოს `.github/workflows/` საქაღალდეში | | **trigger** (`on:`) | **როდის** გაეშვას: `push`, `pull_request`, ხელით (`workflow_dispatch`), განრიგით | | **job** | ნაბიჯების ჯგუფი, რომელიც ერთ მანქანაზე სრულდება | | **runner** (`runs-on:`) | ეს მანქანა: GitHub-ის **ვირტუალური Ubuntu**, ყოველ გაშვებაზე ახალი და სუფთა | | **step** | ერთი ნაბიჯი: `uses:` — მზა action, `run:` — ბრძანება ტერმინალში | | **action** | მზა „ბლოკი“ (`actions/checkout@v4`) — `მფლობელი/სახელი@ვერსია`, როგორც NuGet პაკეტი | **runner = ცარიელი სერვერი.** მასზე შენი კოდი არ არის — ამიტომ პირველი ნაბიჯი ყოველთვის `actions/checkout` (რეპოს ჩამოტვირთვა). .NET SDK არ არის — `actions/setup-dotnet`. ეს ზუსტად ის, რასაც მე-8 ლექციაზე სერვერზე ხელით ვაკეთებდით, ოღონდ ყოველ ჯერზე ავტომატურად. ```note public რეპოებისთვის GitHub-ის runner-ები უფასოა; private-ისთვის — თვეში შეზღუდული წუთები. ```

### ნაბიჯი 1 · ci.yml — ყოველ Pull Request-ზე ```yaml .github/workflows/ci.yml name: CI on: pull_request: branches: [main] jobs: build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: actions/setup-dotnet@v4 with: dotnet-version: '10.0.x' - run: dotnet restore - run: dotnet build --no-restore -c Release ``` - `on: pull_request` → `branches: [main]` — ყოველ PR-ზე, რომელიც `main`-ში უნდა შეირწყას (და მის ყოველ ახალ push-ზე); - `jobs: build:` — ერთი job, სახელით `build` (ეს სახელი branch protection-ში დაგვჭირდება); - `with:` — action-ის პარამეტრები; `10.0.x` — .NET 10-ის უახლესი patch. push → Actions ჩანართში ჩანს გაშვება: ყოველი step-ის ლოგი, ხანგრძლივობა, შეცდომა. PR-ის გვერდზე კი — ❌ ან ✅. ```tip როცა API-ის კურსზე ტესტებს დაწერთ, ბოლოს ერთი ხაზი დაემატება: `- run: dotnet test --no-build -c Release`. ამიერიდან PR, რომელიც ტესტს ამტვრევს, ვერ შეირწყმება. ```

Target: main · ✓ Require a pull request before merging · ✓ Require status checks → build

🚫 შედეგი

$ git push origin main

### ნაბიჯი 2 · branch protection: main — მხოლოდ მწვანე PR-ით CI სასარგებლოა მხოლოდ მაშინ, თუ წითელ PR-ს **ვერ** შეურწყავ. ამას **branch protection** აკეთებს. რეპოს **Settings → Rules → Rulesets → New branch ruleset** (ძველ ინტერფეისში: Settings → Branches → Add branch protection rule): - **Target branches:** `main` (Include default branch); - ✓ **Require a pull request before merging** — პირდაპირ push `main`-ში აკრძალულია; - ✓ **Require status checks to pass** → დაამატე `build` (ჩვენი CI job-ის სახელი). ამიერიდან გზა ერთია — ის, რაც მე-3 ლექციაზე branch-ებით დავიწყეთ: 1. `feature/...` branch → `git push`; 2. **Pull Request** GitHub-ზე — ცვლილების აღწერა; 3. **CI** ავტომატურად აწყობს კოდს → ❌ ან ✅; 4. **review** — გუნდელი კითხულობს კოდს, წერს კომენტარებს; 5. **merge** `main`-ში → (მეორე ნაწილი) ავტომატური deploy. ```console WSL $ git push origin main ! [remote rejected] main -> main (push declined due to repository rule violations) ``` ```tip Pull Request-ში review გუნდურ მუშაობაში ერთ-ერთი ყველაზე მნიშვნელოვანი ჩვევაა — junior-ისთვის მის კოდზე დაწერილი კომენტარი ყველაზე სწრაფი სწავლაა. ```

## ნაწილი 2 · CD — merge → live
გეგმა

build — GitHub-ზე, სერვერი მხოლოდ იღებს

### გეგმა: build — GitHub-ზე, სერვერი მხოლოდ იღებს მე-10 ლექციაში image-ს **სერვერზე** ვაწყობდით (`up --build`) — 1 GB RAM-ზე ნელა და რისკით. ახლა: **GitHub Actions runner-ზე:** 1. `checkout` — კოდი; 2. `docker build` — **იგივე Dockerfile**, მე-9 ლექციიდან; 3. `push` → **GHCR** (GitHub Container Registry) — image-ს ორი tag-ით ვინახავთ: `latest` და commit-ის **sha** (rollback-ისთვის); 4. SSH-ით სერვერზე შესვლა. **სერვერზე** (SSH-ით, ავტომატურად): ```console Termius · lms-server $ cd ~/lms $ git pull # compose.yaml-ის ცვლილებებისთვის $ docker compose pull api # ახალი image GHCR-იდან $ docker compose up -d # კონტეინერის შეცვლა ``` სერვერი აღარაფერს აწყობს — მხოლოდ მზა image-ს იღებს. ეს უფრო სწრაფია, და რაც მთავარია: **ზუსტად ის image**, რომელიც აეწყო, მიდის სერვერზე. ```terms GHCR — ghcr.io, GitHub-ის image-ების საცავი (registry) — როგორც Docker Hub, ოღონდ GitHub-ში sha — commit-ის უნიკალური იდენტიფიკატორი (git log-ში ჩანს), image-ის tag-ად ვიყენებთ ```

### ნაბიჯი 3 · deploy გასაღები და GitHub Secrets GitHub Actions-ს სერვერზე შესასვლელად SSH გასაღები სჭირდება. **შენს** გასაღებს არ ვაძლევთ — ვქმნით **ცალკე**, მხოლოდ ამ საქმისთვის: ```console WSL $ ssh-keygen -t ed25519 -f ~/.ssh/github-deploy -N "" -C "github-actions-deploy" $ ssh-copy-id -i ~/.ssh/github-deploy.pub lms $ ssh -i ~/.ssh/github-deploy giorgi@164.90.12.34 "docker ps" # შემოწმება ``` - `-f` — ფაილის სახელი, `-N ""` — passphrase-ის გარეშე (robot-ს მის აკრეფა არ შეუძლია); - `ssh-copy-id` — `.pub`-ს სერვერის `~/.ssh/authorized_keys`-ში ამატებს. **რატომ ცალკე?** თუ GitHub-ის secret ოდესმე გაჟონავს, საკმარისია ამ **ერთი** ხაზის წაშლა `authorized_keys`-იდან. შენი პირადი გასაღები და სხვა სერვერები ხელშეუხებელია. **GitHub Secrets** — რეპოს **Settings → Secrets and variables → Actions → New repository secret**: | Secret | მნიშვნელობა | |---|---| | `SSH_HOST` | სერვერის IP | | `SSH_USER` | `giorgi` | | `SSH_KEY` | `cat ~/.ssh/github-deploy`-ის **მთელი** შიგთავსი, `-----BEGIN`-იდან `-----END`-ის ჩათვლით | workflow მათ `${{ secrets.SSH_KEY }}`-ით კითხულობს. ლოგებში ისინი `***`-ით იმალება, შენახვის შემდეგ კი GitHub მათ აღარავის აჩვენებს — მხოლოდ შეცვლა შეიძლება. **`GITHUB_TOKEN`** — დროებითი ტოკენი, რომელსაც GitHub ყოველ workflow-ს **თვითონ** აძლევს. GHCR-ში image-ის ატვირთვას ის ეყოფა (თუ workflow-ში `packages: write` უფლებაა).

🎫 PAT: GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → scope მხოლოდ read:packages

### ნაბიჯი 5 · სერვერზე — ორი პატარა ცვლილება **1. compose.yaml** — `api`-ს ვუმატებთ image-ის სახელს: ```yaml compose.yaml — api api: build: . image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest} ... ``` როცა `build` და `image` ერთადაა: `docker compose up --build` (შენთან) ააწყობს და ამ სახელს დაარქმევს; `docker compose pull` (სერვერზე) კი GHCR-იდან ჩამოტვირთავს. `${IMAGE_TAG:-latest}` — ნაგულისხმევად `latest`, rollback-ისთვის კი `.env`-იდან შეგვიძლია შევცვალოთ. ეს ცვლილება commit → PR → merge — და deploy-ის `git pull` მას სერვერზე თვითონ მიიტანს. **2. GHCR-ში შესვლა სერვერზე — ერთხელ.** GHCR-ის package ნაგულისხმევად private-ია, ამიტომ სერვერს წაკითხვის უფლება სჭირდება. GitHub → Settings → Developer settings → Personal access tokens → **Tokens (classic)** → Generate, scope **მხოლოდ** `read:packages`: ```console Termius · lms-server $ echo "ghp_xxxx" | docker login ghcr.io -u giorgi --password-stdin Login Succeeded ``` `--password-stdin` — ტოკენი ბრძანებების ისტორიაში არ ჩაიწერება ისე, როგორც `-p ghp_…` ჩაიწერებოდა. Docker მას სერვერზე იმახსოვრებს. ```note ტოკენი მინიმალური უფლებით (`read:packages`) — იგივე პრინციპი, რაც ცალკე deploy გასაღებისთვის და `User=www-data`-სთვის: ყველას — მხოლოდ ის, რაც სჭირდება. ```

ნაბიჯი 7 · rollback

ახალმა ვერსიამ გატეხა? — წამებში უკან

$ git log --oneline -3 a91c3f2 Add course capacity ← გატეხა 💥 7be04d1 Fix grades pagination ← მუშაობდა ✓ 3f2e9aa Add attendance export $ echo "IMAGE_TAG=7be04d1..." >> .env # სრული sha $ docker compose up -d ✔ Container lms-api-1 Recreated # გასწორდა main-ში → .env-იდან IMAGE_TAG-ის წაშლა $ docker compose up -d # ისევ latest

### ნაბიჯი 7 · rollback ყოველი image GHCR-ში commit-ის **sha**-ითაცაა მონიშნული. ამიტომ წინა ვერსიაზე დაბრუნება = სხვა tag-ის გაშვება: ```console Termius · lms-server · ~/lms $ git log --oneline -3 a91c3f2 Add course capacity ← გატეხა 7be04d1 Fix grades pagination ← მუშაობდა 3f2e9aa Add attendance export ``` GitHub-ზე commit-ის სრული sha (40 სიმბოლო) ჩანს commit-ის გვერდზე ან Actions-ის გაშვებაში: ```console Termius · lms-server · ~/lms $ echo "IMAGE_TAG=7be04d1e5c..." >> .env $ docker compose up -d ✔ Container lms-api-1 Recreated ``` `compose.yaml`-ში `image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest}` — ახლა ის ძველ ვერსიას იღებს. წამებში LMS ისევ მუშაობს, და მშვიდად ასწორებ შეცდომას — ჩვეულებრივ: branch → PR → CI → merge. მერე `.env`-იდან `IMAGE_TAG` შლი და `up -d` — ისევ `latest`. ```warn rollback კოდს აბრუნებს, **ბაზას — არა**. თუ ახალმა ვერსიამ მიგრაციით სქემა შეცვალა, ძველი კოდი შეიძლება ახალ სქემასთან ვერ იმუშაოს. ამიტომ რისკიანი მიგრაციების წინ — `pg_dump` backup (მე-10 ლექცია). ```
