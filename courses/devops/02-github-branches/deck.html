## ნაწილი 1 · GitHub — კოდის ჰოსტინგი ანგარიში, რეპოზიტორია, push და pull. Git ისტორიას შენს კომპიუტერზე ინახავს — ახლა ის ინტერნეტში გავიტანოთ.
Local ↔ Remote

ერთი რეპო — რამდენიმე ასლი

push — ჩემი commit-ები → GitHub
pull — GitHub-ის ახალი commit-ები → ჩემთან
clone — მთელი რეპოს პირველი ჩამოტვირთვა
### Local ↔ Remote: ერთი რეპო — რამდენიმე ასლი - **Local** — რეპოზიტორია შენს კომპიუტერზე. - **Remote** — იგივე რეპოზიტორია GitHub-ზე. ჩვეულებრივ მას **`origin`** ჰქვია. ყოველ ასლს **სრული ისტორია** აქვს. GitHub „მთავარ“ ასლად გამოიყენება, რომლითაც ყველა სინქრონიზდება: | ბრძანება | მიმართულება | როდის | |---|---|---| | `git push` | ჩემი commit-ები → GitHub | როცა რამე დავასრულე და გაზიარება მინდა | | `git pull` | GitHub-ის ახალი commit-ები → ჩემთან | მუშაობის დაწყებამდე | | `git clone ` | მთელი რეპო → ახალ კომპიუტერზე | ერთხელ, პირველად | ```note „ნიკას კომპიუტერი“ შეიძლება **სერვერიც** იყოს: კურსში სერვერი თვითონ ჩამოიტვირთავს კოდს GitHub-იდან. ასე მუშაობს დეპლოიმენტი. ```

$ git remote add origin https://github.com/giorgi-beridze/my-portfolio.git $ git branch -M main $ git push -u origin main Enumerating objects: 9, done. To https://github.com/giorgi-beridze/my-portfolio.git * [new branch] main -> main
remote add — „GitHub-ის ამ მისამართს origin დავარქვათ“
branch-ს main ერქმევა (თუ უკვე ასეა — არაფერს ცვლის)
push — commit-ები მიდის. -u — დაიმახსოვრე; შემდეგ უბრალოდ git push
🔐 პირველ push-ზე გაიხსნება ბრაუზერი → Sign in with your browser. GitHub-ის პაროლი ტერმინალში აღარ მუშაობს.
### ნაბიჯი 3 · ლოკალური რეპო → GitHub ```console Git Bash $ git remote add origin https://github.com/giorgi-beridze/my-portfolio.git $ git branch -M main $ git push -u origin main ``` - **`git remote add origin `** — ლოკალურ რეპოს ვეუბნებით: „GitHub-ზე შენი ასლი ამ მისამართზეა, და მას `origin` დავარქვათ“. ერთხელ კეთდება. - **`git branch -M main`** — მიმდინარე branch-ს `main` ერქმევა. თუ `init.defaultBranch main` დააყენე, უკვე ასეა და არაფერი იცვლება. - **`git push -u origin main`** — `main`-ის commit-ები GitHub-ზე მიდის. `-u` აკავშირებს ლოკალურ `main`-ს GitHub-ის `main`-თან, ამიტომ შემდეგ ჯერზე საკმარისია უბრალოდ `git push` და `git pull`. ```note **ავტორიზაცია:** პირველ push-ზე გაიხსნება ფანჯარა → **Sign in with your browser** → ბრაუზერში დაადასტურე. Windows-ზე ამას Git-თან ერთად დაყენებული Git Credential Manager აკეთებს და ავტორიზაციას იმახსოვრებს. GitHub-ის პაროლი ტერმინალში აღარ მუშაობს. სხვა გზაა SSH გასაღებები — მათ კურსში მოგვიანებით ვისწავლით. ``` push-ის შემდეგ GitHub-ის გვერდი განაახლე — ფაილები და commit-ები იქ არის.

### რა არის GitHub-ის რეპოს გვერდზე? - 📁 **Code** — ფაილები და branch-ები. თუ რეპოში `README.md` არის, GitHub მას ფაილების ქვემოთ ლამაზად აჩვენებს — ეს პროექტის „სავიზიტო ბარათია“. - 🕓 **Commits** — მთელი ისტორია. ყოველ commit-ზე დაჭერით ჩანს, რა შეიცვალა: წაშლილი ხაზები წითლად, დამატებული — მწვანედ. - ✏️ **რედაქტირება** — ფაილი შეგიძლია პირდაპირ ბრაუზერში შეცვალო (✏️ ხატულა). შენახვისას GitHub commit-ს ქმნის — ლოკალურად მის ჩამოსატანად `git pull` დაგჭირდება. - 🔀 **Pull requests** — „ჩემი branch გადახედეთ და `main`-ს შეურწყით“. ასე მუშაობს გუნდი: კოდს `main`-ში პირდაპირ არავინ წერს. - ⚙️ **Actions** — ავტომატიზაცია (build, ტესტი, დეპლოი). - 📄 **Settings → Pages** — რეპოს საიტად გადაქცევა.
ყოველდღიური ციკლი

pull → შეცვლა → add → commit → push 🔁

მუშაობის დაწყებამდე — pull. დასრულების შემდეგ — push. შუაში — ხშირი, პატარა commit-ები.
### ყოველდღიური ციკლი 1. **`git pull`** — მუშაობის დაწყებამდე ჩამოიტანე, რაც სხვებმა (ან შენ, სხვა კომპიუტერიდან) ატვირთეს. 2. **კოდის შეცვლა.** 3. **`git add .`** — ცვლილებები staging-ში. 4. **`git commit -m "…"`** — შენახვა ისტორიაში. 5. **`git push`** — GitHub-ზე გაგზავნა. 3–4 ნაბიჯი დღეში ბევრჯერ მეორდება: **ხშირი, პატარა commit-ები** სჯობს ერთ უზარმაზარს — ადვილია გადახედვა და, საჭიროებისას, დაბრუნება. ```tip ნებისმიერ მომენტში, როცა არ იცი, რა ხდება — `git status`. ის გეტყვის, რომელ branch-ზე ხარ, რა შეიცვალა და რა დევს staging-ში. ```

### ცნება 4 · Branch (შტო) **პრობლემა:** საიტი მუშაობს და სერვერზე დევს. გინდა ახალი სექცია დაამატო, მაგრამ ამას 2 დღე სჭირდება — ამ ხნის განმავლობაში `main` ნახევრად დაწერილი კოდით უნდა იყოს? და თუ ამასობაში `main`-ზე სასწრაფო შესწორება დაგჭირდა? **Branch** — ისტორიის პარალელური ხაზი. ის მიმდინარე commit-იდან იწყება და `main`-ს არ ეხება. - 🌿 **იზოლაცია** — `main` სტაბილური რჩება, ახალ ფიჩაზე branch-ში მუშაობ. - 🧪 **ექსპერიმენტი** — არ გამოვიდა? branch-ს წაშლი, `main`-ს არაფერი მოსვლია. - 👥 **გუნდი** — ყველა თავის branch-ზე მუშაობს და ერთმანეთს ხელს არ უშლის. ```bash git branch # რა branch-ები მაქვს git switch -c feature/contacts # ახალი branch + გადასვლა git switch main # main-ზე დაბრუნება ``` ```tip სახელი — `feature/...` ახალი ფუნქციონალისთვის, `fix/...` შესწორებისთვის. ასე ერთი შეხედვით ჩანს, რას ეხება branch-ი. ```

Git-მა საქაღალდე `main`-ის მდგომარეობაზე დააბრუნა — ცვლილება მხოლოდ branch-შია. ```console Git Bash $ git merge feature/contacts Fast-forward $ git branch -d feature/contacts $ git push $ git log --oneline a3f9c21 (HEAD -> main, origin/main) Add contact section e81b0f2 Create README.md c41a8e0 Add .gitignore ``` **Fast-forward** — branch-ის შექმნის შემდეგ `main`-ზე სხვა არაფერი შეცვლილა, ამიტომ Git-მა `main` უბრალოდ წინ გადაწია. merge commit არ შექმნილა და ისტორია სწორი ხაზია. ბოლოს `git push`-ით ახალი commit GitHub-ზეც ავიდა — `origin/main` ახლა იმავე commit-ზეა.

## შეჯამება · დღეს ვისწავლეთ - 🐙 **GitHub** — კოდის ჰოსტინგი: remote (`origin`), `push`, `pull`, `clone`. ერთი რეპო — რამდენიმე ასლი (ლეპტოპი, GitHub, გუნდელი, სერვერი). - 🙈 **.gitignore** — ავტომატურად შექმნილი (`node_modules/`, `bin/`, `obj/`) და საიდუმლო (`.env`) ფაილები რეპოში არ შედის. - 🌿 **branch** — ახალ ფიჩაზე ცალკე შტოზე ვმუშაობთ, `main` ხელუხლებელი რჩება. - 🔀 **merge / conflict** — მზა შტოს `main`-ში ვაბრუნებთ. თუ ორივე შტოში ერთი და იგივე ხაზი შეიცვალა — Git გეკითხება, და შენ წყვეტ. **შემდეგ ლექციაზე:** `my-portfolio` → ინტერნეტში GitHub Pages-ით. ```prompt გამოცდა მეორე ლექციაზე ვსწავლობ DevOps-ს. მეორე ლექციაზე გავიარეთ: GitHub (remote, push, pull, clone), .gitignore (რა იწერება და რატომ; რა ვქნა, თუ საიდუმლო უკვე ავტვირთე), branch, merge (fast-forward) და conflict. დამისვი 8 კითხვა სათითაოდ, მარტივიდან რთულისკენ — ნაწილი პრაქტიკული სიტუაციები იყოს („რა ბრძანებას გაუშვებ, როცა…“). ყოველ პასუხზე შემიფასე და ამიხსენი. ბოლოს მითხარი, რა გავიმეორო. ქართულად. ``` ```prompt Git-ის ბრძანება არ მესმის ვსწავლობ Git-ს. ამიხსენი ეს ბრძანება მარტივად, ქართულად: რას აკეთებს, როდის ვიყენებ, და ერთი პატარა მაგალითი ტერმინალის გამოსავლით. ბრძანება: [აქ ჩასვი ბრძანება] ```
