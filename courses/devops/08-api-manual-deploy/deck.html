### ნაბიჯი 2 · PostgreSQL ```console lms-server $ sudo apt install -y postgresql $ systemctl status postgresql ``` PostgreSQL-ის დაყენებისას იქმნება Linux-ის user `postgres` — ბაზის ადმინისტრატორი. მისი სახელით ვხსნით `psql`-ს (ბაზის კონსოლი) და ვქმნით user-ს და ბაზას LMS-სთვის: ```console lms-server $ sudo -u postgres psql postgres=# CREATE USER lms WITH PASSWORD 'Str0ng!Pass'; CREATE ROLE postgres=# CREATE DATABASE lms OWNER lms; CREATE DATABASE postgres=# \q ``` - `sudo -u postgres` — ბრძანება user `postgres`-ის სახელით; - API ბაზას **ცალკე** user-ით (`lms`) უკავშირდება და არა სუპერ-user-ით — თუ API-ს გატეხავენ, ზიანი მხოლოდ ამ ბაზით შემოიფარგლება; - `\q` — psql-იდან გამოსვლა. ```console lms-server $ sudo ss -tlnp | grep 5432 LISTEN 127.0.0.1:5432 postgres ``` PostgreSQL ნაგულისხმევად მხოლოდ `127.0.0.1`-ზე უსმენს — ინტერნეტიდან ბაზა არ ჩანს. ასეც უნდა დარჩეს: ufw-ში 5432-ს **არ** ვხსნით.

Release build + ყველა საჭირო ფაილი ერთ საქაღალდეში

📜 --idempotent

$ psql "host=localhost dbname=lms user=lms" -f ~/migrate.sql Password: ******** CREATE TABLE ...
### ნაბიჯი 4 · publish და მიგრაციები **შენს კომპიუტერზე** (სადაც SDK და `dotnet ef` გაქვს): ```console WSL · LMS-ის პროექტი $ dotnet publish -c Release -o ./publish $ ls publish Lms.Api.dll Lms.Api.deps.json appsettings.json Npgsql.dll ... $ dotnet ef migrations script --idempotent -o migrate.sql ``` - `dotnet publish -c Release` — ოპტიმიზებული build და ყველა საჭირო ფაილი (`.dll`-ები, `appsettings.json`) ერთ საქაღალდეში. ეს არის ის, რაც სერვერზე გაეშვება. - `migrations script --idempotent` — მიგრაციები ჩვეულებრივ SQL-ად. **idempotent** ნიშნავს: სკრიპტი თვითონ ამოწმებს, რომელი მიგრაცია უკვე გაეშვა, და მხოლოდ აკლებულს უშვებს — ორჯერ გაშვებაც უსაფრთხოა. სერვერზე `dotnet ef` არ გვაქვს (SDK არ არის) — `psql` კი გვაქვს. **ატვირთვა:** ```console WSL $ ssh lms "sudo mkdir -p /var/www/lms-api && sudo chown giorgi:giorgi /var/www/lms-api" $ rsync -avz --delete publish/ lms:/var/www/lms-api/ $ scp migrate.sql lms:~ ``` `ssh lms "<ბრძანება>"` — ერთი ბრძანება სერვერზე, შესვლის გარეშე. `scp` — ერთი ფაილის კოპირება SSH-ით. **ცხრილები ბაზაში:** ```console lms-server $ psql "host=localhost dbname=lms user=lms" -f ~/migrate.sql Password: ******** CREATE TABLE ... ```

ASP.NET Core მათ კითხულობს და ისინი `appsettings.json`-ის მნიშვნელობებს **ფარავს**: - `ASPNETCORE_URLS` — სად უსმინოს Kestrel-მა. `127.0.0.1` — მხოლოდ სერვერის შიგნიდან; - `ConnectionStrings__Default` — `__` (ორი ქვედა ტირე) ნიშნავს JSON-ის ჩადგმულ დონეს, ანუ `ConnectionStrings:Default`. მეორე SSH ფანჯრიდან: ```console lms-server · ფანჯარა 2 $ curl http://127.0.0.1:5000/api/courses [] ``` API მუშაობს და ბაზას უკავშირდება. მაგრამ ზუსტად იგივე პრობლემები, რაც მე-4 ლექციაზე `dotnet run`-ს ჰქონდა: - ფანჯარა დახურე → API **გაჩერდა**; - crash → **არავინ** ჩართავს თავიდან; - სერვერის reboot → API **აღარ** ირთვება. ```note Production-ში Swagger ჩვეულებრივ გამორთულია (`if (app.Environment.IsDevelopment())`), ამიტომ ვამოწმებთ `curl`-ით. `curl` — HTTP მოთხოვნა ტერმინალიდან. ```

### ნაბიჯი 7 · ჩართვა და ლოგები ```console lms-server $ sudo systemctl daemon-reload # systemd-მა ახალი unit ფაილი წაიკითხოს $ sudo systemctl enable --now lms-api # enable + start ერთად $ systemctl status lms-api ● lms-api.service - LMS API Active: active (running) Main PID: 4120 (dotnet) ``` **ლოგები.** ყველაფერი, რასაც API კონსოლში წერს (`ILogger`, შეცდომები), systemd **journal**-ში ინახება: ```console lms-server $ journalctl -u lms-api -f # ცოცხლად $ journalctl -u lms-api -n 50 # ბოლო 50 ხაზი $ journalctl -u lms-api --since "10 min ago" ``` **crash-ის ტესტი:** ```console lms-server $ sudo kill -9 4120 # ვკლავთ პროცესს $ systemctl status lms-api # 5 წამში — active (running), ახალი PID ``` `Restart=always` მუშაობს. `sudo reboot`-ის შემდეგაც API თავისით ჩაირთვება. ```tip unit ფაილის **ყოველი** ცვლილების შემდეგ: `daemon-reload` → `restart lms-api`. ახალი ვერსიის ატვირთვის შემდეგ კი საკმარისია `sudo systemctl restart lms-api`. ```

### ნაბიჯი 8 · Nginx — reverse proxy API `127.0.0.1:5000`-ზე უსმენს — ინტერნეტიდან არ ჩანს. Nginx-ს ვაყენებთ მის წინ, როგორც **reverse proxy**: ის იღებს მოთხოვნას და API-ს გადასცემს. ```nginx sites-available/lms-api server { listen 8081; server_name _; location / { proxy_pass http://127.0.0.1:5000; proxy_http_version 1.1; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; } } ``` - `proxy_pass` — სად გადასცეს მოთხოვნა; - `proxy_set_header` — API-ს გადაეცემა ორიგინალი დომენი (`Host`), მომხმარებლის ნამდვილი IP (`X-Forwarded-For`) და პროტოკოლი (`X-Forwarded-Proto`: http თუ https). მის გარეშე API-ს ეგონება, რომ ყველა მოთხოვნა Nginx-იდან (127.0.0.1) მოდის. ```console lms-server $ sudo ln -s /etc/nginx/sites-available/lms-api /etc/nginx/sites-enabled/ $ sudo nginx -t && sudo systemctl reload nginx $ sudo ufw allow 8081/tcp ``` ბრაუზერში `http://:8081/api/courses` → JSON. 🎉 **რატომ არ ვხსნით Kestrel-ს პირდაპირ?** Nginx — სასტუმროს მიმღებია: სტუმარს იღებს და სწორ ოთახში აგზავნის. - ერთ სერვერზე ბევრი აპი — portfolio, Angular, API — ყველა Nginx-ის უკან; - **HTTPS** ერთ ადგილას — Nginx-ში (მე-11 ლექცია), API-ს ამაზე ფიქრი არ სჭირდება; - ლოგები, შეზღუდვები, სტატიკური ფაილები — Nginx ამაში ძლიერია. ```note 8081 — დროებითია, სანამ დომენი არ გვაქვს. მე-11 ლექციაზე API იქნება `api.<შენი-დომენი>`-ზე, port 443-ზე. ```

### 502 Bad Gateway — ვინ არის დამნაშავე? **502** ნიშნავს: Nginx მუშაობს, მაგრამ მან, ვისაც მოთხოვნა გადასცა (upstream — ჩვენი API), **არ უპასუხა**. ძებნა ფენა-ფენა, ზემოდან ქვემოთ: ```console lms-server $ sudo tail -n 3 /var/log/nginx/error.log connect() failed (111: Connection refused) while connecting to upstream, upstream: "http://127.0.0.1:5000/api/courses" $ systemctl status lms-api Active: activating (auto-restart) (Result: exit-code) $ journalctl -u lms-api -n 20 Unhandled exception. Npgsql.PostgresException: 28P01: password authentication failed for user "lms" ``` 1. **Nginx** — 502 თვითონ ამბობს, რომ Nginx მუშაობს. `error.log`: API-სთან ვერ დაუკავშირდა. 2. **API** — `systemctl status`: `auto-restart` — ირთვება, ვარდება, ისევ ირთვება. 3. **რატომ** — `journalctl`: ბაზის პაროლი არასწორია. | რას ხედავ | ფენა | სად ეძებ | |---|---|---| | Can't be reached | ქსელი / Nginx | `ufw status`, `systemctl status nginx` | | 502 Bad Gateway | API არ პასუხობს | `systemctl status lms-api`, `journalctl -u lms-api` | | 500 Internal Server Error | API-ს კოდი | `journalctl -u lms-api` — exception | | password authentication failed | ბაზა / connection string | `Environment=` unit ფაილში |
