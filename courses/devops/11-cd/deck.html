## ნაწილი 1 · CD — გეგმა და გასაღებები CI ყოველ PR-ს ამოწმებს. დღეს ჯაჭვს ვაგრძელებთ: merge-ის შემდეგ GitHub Actions image-ს ააწყობს, შეინახავს და სერვერზე თვითონ გაუშვებს.
პრობლემა

CI მწვანეა — deploy კი ისევ ხელით

# GitHub: PR → CI ✅ → merge # Termius → lms-server $ cd ~/lms $ git pull $ docker compose up -d --build # build 1 GB RAM-ზე 😬 $ docker compose logs -f api # მუშაობს?
😴 merge გააკეთე, სერვერზე შესვლა დაგავიწყდა → ძველი ვერსია
🐢 build სერვერზე — ნელა, და RAM-ს საიტისგან „იპარავს“
👥 გუნდში 5 ადამიანი — ყველას სერვერის SSH უნდა ჰქონდეს?
CD — merge main-ში → სერვერზე ავტომატურად. ხელით — არაფერი
### პრობლემა: CI მწვანეა — deploy კი ისევ ხელით წინა ლექციის შემდეგ `main`-ში მხოლოდ შემოწმებული კოდი ხვდება. მაგრამ სერვერამდე ის ისევ ხელით მიდის: ```console merge-ის შემდეგ — ყოველ ჯერზე # Termius → lms-server $ cd ~/lms $ git pull $ docker compose up -d --build $ docker compose logs -f api ``` - 😴 merge გააკეთე და სერვერზე შესვლა დაგავიწყდა — მომხმარებელი ძველ ვერსიას ხედავს; - 🐢 image სერვერზე იწყობა — 1 GB RAM-ზე ნელა, და ამ დროს საიტი მეხსიერებისთვის „ეჯიბრება“ build-ს; - 👥 გუნდში ხუთი ადამიანია — ყველას სერვერზე SSH წვდომა ჰქონდეს? **CD (Continuous Deployment)** — `main`-ის ყოველი ცვლილება **ავტომატურად** გადის სერვერზე. დღეს ამას ვაკეთებთ: CI-ს შემდეგ ჯაჭვს ვაგრძელებთ სერვერამდე.
გეგმა

build — GitHub-ზე, სერვერი მხოლოდ იღებს

### გეგმა: build — GitHub-ზე, სერვერი მხოლოდ იღებს მე-8 ლექციაში image-ს **სერვერზე** ვაწყობდით (`up --build`) — 1 GB RAM-ზე ნელა და რისკით. ახლა: **GitHub Actions runner-ზე:** 1. `checkout` — კოდი; 2. `docker build` — **იგივე Dockerfile**, მე-7 ლექციიდან; 3. `push` → **GHCR** (GitHub Container Registry) — image-ს ორი tag-ით ვინახავთ: `latest` და commit-ის **sha** (rollback-ისთვის); 4. SSH-ით სერვერზე შესვლა. **სერვერზე** (SSH-ით, ავტომატურად): ```console Termius · lms-server $ cd ~/lms $ git pull # compose.yaml-ის ცვლილებებისთვის $ docker compose pull api # ახალი image GHCR-იდან $ docker compose up -d # კონტეინერის შეცვლა ``` სერვერი აღარაფერს აწყობს — მხოლოდ მზა image-ს იღებს. ეს უფრო სწრაფია, და რაც მთავარია: **ზუსტად ის image**, რომელიც აეწყო, მიდის სერვერზე. ```terms GHCR — ghcr.io, GitHub-ის image-ების საცავი (registry) — როგორც Docker Hub, ოღონდ GitHub-ში sha — commit-ის უნიკალური იდენტიფიკატორი (git log-ში ჩანს), image-ის tag-ად ვიყენებთ ```

### ნაბიჯი 1 · deploy გასაღები და GitHub Secrets GitHub Actions-ს სერვერზე შესასვლელად SSH გასაღები სჭირდება. **შენს** გასაღებს არ ვაძლევთ — ვქმნით **ცალკე**, მხოლოდ ამ საქმისთვის: ```console WSL $ ssh-keygen -t ed25519 -f ~/.ssh/github-deploy -N "" -C "github-actions-deploy" $ ssh-copy-id -i ~/.ssh/github-deploy.pub lms $ ssh -i ~/.ssh/github-deploy giorgi@164.90.12.34 "docker ps" # შემოწმება ``` - `-f` — ფაილის სახელი, `-N ""` — passphrase-ის გარეშე (robot-ს მის აკრეფა არ შეუძლია); - `ssh-copy-id` — `.pub`-ს სერვერის `~/.ssh/authorized_keys`-ში ამატებს. **რატომ ცალკე?** თუ GitHub-ის secret ოდესმე გაჟონავს, საკმარისია ამ **ერთი** ხაზის წაშლა `authorized_keys`-იდან. შენი პირადი გასაღები და სხვა სერვერები ხელშეუხებელია. **GitHub Secrets** — რეპოს **Settings → Secrets and variables → Actions → New repository secret**: | Secret | მნიშვნელობა | |---|---| | `SSH_HOST` | სერვერის IP | | `SSH_USER` | `giorgi` | | `SSH_KEY` | `cat ~/.ssh/github-deploy`-ის **მთელი** შიგთავსი, `-----BEGIN`-იდან `-----END`-ის ჩათვლით | workflow მათ `${{ secrets.SSH_KEY }}`-ით კითხულობს. ლოგებში ისინი `***`-ით იმალება, შენახვის შემდეგ კი GitHub მათ აღარავის აჩვენებს — მხოლოდ შეცვლა შეიძლება. **`GITHUB_TOKEN`** — დროებითი ტოკენი, რომელსაც GitHub ყოველ workflow-ს **თვითონ** აძლევს. GHCR-ში image-ის ატვირთვას ის ეყოფა (თუ workflow-ში `packages: write` უფლებაა).

ნაბიჯი 2 · deploy.yml

deploy.yml — push main-ში

name: Deploy on: push: branches: [main] permissions: contents: read packages: write jobs: deploy: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: docker/login-action@v3 with: registry: ghcr.io username: ${{ github.actor }} password: ${{ secrets.GITHUB_TOKEN }} - uses: docker/build-push-action@v6 with: push: true tags: | ghcr.io/${{ github.repository }}:latest ghcr.io/${{ github.repository }}:${{ github.sha }} - uses: appleboy/ssh-action@v1 with: host: ${{ secrets.SSH_HOST }} username: ${{ secrets.SSH_USER }} key: ${{ secrets.SSH_KEY }} script: | cd ~/lms git pull docker compose pull api docker compose up -d
ბოლო script — ზუსტად ის, რასაც ხელით ვკრეფდით
### ნაბიჯი 2 · deploy.yml ```yaml .github/workflows/deploy.yml name: Deploy on: push: branches: [main] permissions: contents: read packages: write jobs: deploy: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - uses: docker/login-action@v3 with: registry: ghcr.io username: ${{ github.actor }} password: ${{ secrets.GITHUB_TOKEN }} - uses: docker/build-push-action@v6 with: push: true tags: | ghcr.io/${{ github.repository }}:latest ghcr.io/${{ github.repository }}:${{ github.sha }} - uses: appleboy/ssh-action@v1 with: host: ${{ secrets.SSH_HOST }} username: ${{ secrets.SSH_USER }} key: ${{ secrets.SSH_KEY }} script: | cd ~/lms git pull docker compose pull api docker compose up -d ``` | ნაწილი | რას აკეთებს | |---|---| | `on: push: branches: [main]` | ყოველ push-ზე `main`-ში — branch protection-ით ეს მხოლოდ **merge**-ია | | `permissions: packages: write` | `GITHUB_TOKEN`-ს GHCR-ში ჩაწერის უფლება | | `docker/login-action` | `docker login ghcr.io` | | `docker/build-push-action` | `docker build` + `docker push` — ორი tag-ით | | `appleboy/ssh-action` | SSH სერვერზე და `script`-ის ბრძანებები | `${{ … }}` — workflow-ის ცვლადები: `github.repository` = `giorgi/lms`, `github.sha` = commit-ის id, `github.actor` = ვინც გაუშვა. ```warn GHCR-ში image-ის სახელი **მხოლოდ პატარა ასოებით** შეიძლება. თუ რეპოს ჰქვია `Giorgi/LMS`, build-push ჩავარდება — გადაარქვი რეპოს სახელი პატარა ასოებით. ```

api: build: . image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest} ...
build — შენთან (up --build) · image — სერვერზე (pull)

🎫 PAT: GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → scope მხოლოდ read:packages

### ნაბიჯი 3 · სერვერზე — ორი პატარა ცვლილება **1. compose.yaml** — `api`-ს ვუმატებთ image-ის სახელს: ```yaml compose.yaml — api api: build: . image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest} ... ``` როცა `build` და `image` ერთადაა: `docker compose up --build` (შენთან) ააწყობს და ამ სახელს დაარქმევს; `docker compose pull` (სერვერზე) კი GHCR-იდან ჩამოტვირთავს. `${IMAGE_TAG:-latest}` — ნაგულისხმევად `latest`, rollback-ისთვის კი `.env`-იდან შეგვიძლია შევცვალოთ. ეს ცვლილება commit → PR → merge — და deploy-ის `git pull` მას სერვერზე თვითონ მიიტანს. **2. GHCR-ში შესვლა სერვერზე — ერთხელ.** GHCR-ის package ნაგულისხმევად private-ია, ამიტომ სერვერს წაკითხვის უფლება სჭირდება. GitHub → Settings → Developer settings → Personal access tokens → **Tokens (classic)** → Generate, scope **მხოლოდ** `read:packages`: ```console Termius · lms-server $ echo "ghp_xxxx" | docker login ghcr.io -u giorgi --password-stdin Login Succeeded ``` `--password-stdin` — ტოკენი ბრძანებების ისტორიაში არ ჩაიწერება ისე, როგორც `-p ghp_…` ჩაიწერებოდა. Docker მას სერვერზე იმახსოვრებს. ```note ტოკენი მინიმალური უფლებით (`read:packages`) — იგივე პრინციპი, რაც ცალკე deploy გასაღებისთვის და `User=www-data`-სთვის: ყველას — მხოლოდ ის, რაც სჭირდება. ```

ნაბიჯი 5 · rollback

ახალმა ვერსიამ გატეხა? — წამებში უკან

$ git log --oneline -3 a91c3f2 Add course capacity ← გატეხა 💥 7be04d1 Fix grades pagination ← მუშაობდა ✓ 3f2e9aa Add attendance export $ echo "IMAGE_TAG=7be04d1..." >> .env # სრული sha $ docker compose up -d ✔ Container lms-api-1 Recreated # გასწორდა main-ში → .env-იდან IMAGE_TAG-ის წაშლა $ docker compose up -d # ისევ latest

🏷️ ყოველი image — sha-ით

GHCR-ში ინახება ყველა ვერსია. ძველზე დაბრუნება = სხვა tag

🗄️ ბაზა?

volume-ში რჩება. თუ ახალმა მიგრაციამ სქემა შეცვალა — ჯერ backup (მე-8 ლექცია)

### ნაბიჯი 5 · rollback ყოველი image GHCR-ში commit-ის **sha**-ითაცაა მონიშნული. ამიტომ წინა ვერსიაზე დაბრუნება = სხვა tag-ის გაშვება: ```console Termius · lms-server · ~/lms $ git log --oneline -3 a91c3f2 Add course capacity ← გატეხა 7be04d1 Fix grades pagination ← მუშაობდა 3f2e9aa Add attendance export ``` GitHub-ზე commit-ის სრული sha (40 სიმბოლო) ჩანს commit-ის გვერდზე ან Actions-ის გაშვებაში: ```console Termius · lms-server · ~/lms $ echo "IMAGE_TAG=7be04d1e5c..." >> .env $ docker compose up -d ✔ Container lms-api-1 Recreated ``` `compose.yaml`-ში `image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest}` — ახლა ის ძველ ვერსიას იღებს. წამებში LMS ისევ მუშაობს, და მშვიდად ასწორებ შეცდომას — ჩვეულებრივ: branch → PR → CI → merge. მერე `.env`-იდან `IMAGE_TAG` შლი და `up -d` — ისევ `latest`. ```warn rollback კოდს აბრუნებს, **ბაზას — არა**. თუ ახალმა ვერსიამ მიგრაციით სქემა შეცვალა, ძველი კოდი შეიძლება ახალ სქემასთან ვერ იმუშაოს. ამიტომ რისკიანი მიგრაციების წინ — `pg_dump` backup (მე-8 ლექცია). ```
