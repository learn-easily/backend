## რა არის DevOps? ### რატომ არსებობს DevOps წარმოიდგინე ორი გუნდი: - 👩‍💻 **Dev (Development)** — დეველოპერები. წერენ კოდს და მათ ლეპტოპზე ყველაფერი მუშაობს. - 🛠️ **Ops (Operations)** — ადმინისტრატორები. მართავენ სერვერებს, სადაც საიტი რეალურად ცხოვრობს. ძველად მათ შორის **კედელი** იდგა: დეველოპერი კოდს „კედელს იქით გადააგდებდა“, ადმინისტრატორი კი ცდილობდა, ის სერვერზე როგორმე გაეშვა. შედეგი: - 🐢 ახალი ვერსია თვეში ერთხელ გამოდიოდა — ხელით და შიშით. - 🔥 რამე თუ გაფუჭდა, იწყებოდა: „ჩემთან მუშაობს!“ — „სერვერზე არ მუშაობს!“ - 🌙 სერვერი ღამით ჩავარდებოდა და დილამდე ამას ვერავინ ამჩნევდა. **DevOps = Dev + Ops.** კედელი ქრება: კოდი დეველოპერის ლეპტოპიდან მომხმარებლამდე **ერთი, ავტომატური გზით** მიდის, და ამ გზას ერთი გუნდი აკონტროლებს.

DevOps კულტურა თითქმის ყველა სერიოზულ IT კომპანიაშია, ხოლო DevOps / Cloud ინჟინერი — მოთხოვნადი პროფესია.

DevOps ტექნოლოგია კი არა, შეთანხმებაა: ერთი გუნდი, ერთი მიზანი, ავტომატური გზა კოდიდან მომხმარებლამდე.
### როგორ გაჩნდა DevOps? - **2000-იანები — ორი ცალკე გუნდი.** დეველოპერები (Dev) კოდს წერდნენ, ადმინისტრატორები (Ops) კი მას სერვერზე უშვებდნენ. ახალი ვერსია თვეში ან კვარტალშიც კი ერთხელ გამოდიოდა, და ყოველი გაშვება დიდი, საშიში მოვლენა იყო. - **2009 · Flickr.** Velocity კონფერენციაზე Flickr-ის ორმა ხელმძღვანელმა — John Allspaw (Ops) და Paul Hammond (Dev) — აჩვენეს მოხსენება „10+ Deploys Per Day: Dev and Ops Cooperation at Flickr“: Dev და Ops ერთად მუშაობენ, ყველაფერი ავტომატიზებულია, და საიტი დღეში 10-ჯერ და მეტჯერ ახლდება. - **2009 · ბელგია.** Patrick Debois-მ ამ მოხსენებით შთაგონებულმა საკუთარი კონფერენცია მოაწყო — **DevOpsDays**. სიტყვა „DevOps“ აქედან გავრცელდა. - **დღეს.** DevOps კულტურა თითქმის ყველა სერიოზულ IT კომპანიაშია, ხოლო DevOps / Cloud ინჟინერი მოთხოვნადი პროფესიაა. **მთავარი:** DevOps ტექნოლოგია ან პროგრამა არ არის — ეს შეთანხმებაა: ერთი გუნდი, ერთი მიზანი და ავტომატური გზა კოდიდან მომხმარებლამდე.
DevOps ციკლი

DevOps = კოდის უწყვეტი გზა ♾️

DevOps — ერთი პროგრამა კი არა, მიდგომაა: ყველაფერი, რაც კოდს მომხმარებლამდე მიიყვანს, ავტომატური, სწრაფი და კონტროლირებადია. და ციკლი არ მთავრდება.
### DevOps ციკლი — კოდის უწყვეტი გზა ♾️ DevOps ხშირად უსასრულობის ნიშნით (♾️) იხატება: მარცხენა ნახევარი **Dev**-ია, მარჯვენა — **Ops**. ციკლი არასოდეს მთავრდება — მონიტორინგში დანახული პრობლემა შემდეგი გეგმის ნაწილი ხდება. | ეტაპი | რა ხდება | ამ კურსში | |---|---|---| | 📝 Plan | ვწყვეტთ, რას ვაკეთებთ | — | | 💻 Code | ვწერთ კოდს და ვინახავთ Git-ში | Git/GitHub — **დღეს** | | ⚙️ Build | კოდიდან გასაშვებ ვერსიას ვაწყობთ | GitHub Actions | | 🧪 Test | ავტომატურად ვამოწმებთ, ხომ არაფერი გატყდა | GitHub Actions | | 📦 Release | ვამზადებთ ვერსიას გასაშვებად | სრული CI/CD | | 🚀 Deploy | ვერსია სერვერზე მიდის | GitHub Pages, Droplet | | 🖥️ Operate | სერვერი მუშაობს და ვუვლით | Linux + SSH | | 📈 Monitor | ვაკვირდებით: სწრაფია? ჩავარდა? | მონიტორინგი | **DevOps ერთი პროგრამა არ არის** — ეს მიდგომაა: ყველაფერი, რაც კოდს მომხმარებლამდე მიიყვანს, ავტომატური, სწრაფი და კონტროლირებადი უნდა იყოს. Git, GitHub Actions, Linux, Nginx, Docker — ეს ის ინსტრუმენტებია, რომლითაც ამას ვაკეთებთ. ```terms DevOps — Development + Operations: მიდგომა, რომლითაც კოდი დეველოპერიდან მომხმარებლამდე სწრაფად, ავტომატურად და კონტროლირებადად მიდის Deploy (დეპლოი) — ახალი ვერსიის სერვერზე გაშვება, რომ მომხმარებელმა დაინახოს CI/CD — ავტომატური აწყობა, ტესტი და დეპლოი ყოველ ცვლილებაზე ```
ძველად vs დღეს

git push = deploy 🚀

ძველად: ფაილებს ხელით აგზავნიდი FTP-ით. რომელი ვერსია დევს სერვერზე? ვინ ატვირთა? 🤷
დღეს: ერთხელ ვაწყობთ ამ გზას — მერე ყოველი git push ავტომატურად ქვეყნდება
ამ გზის აწყობა და მოვლა — DevOps ინჟინრის საქმეა.
### თანამედროვე მიდგომა: `git push` = deploy დღეს კარგ გუნდში საიტს ხელით არავინ ტვირთავს. DevOps ინჟინერი **ერთხელ აწყობს გზას**, და მერე ის ასე მუშაობს: 1. 💻 დეველოპერი კოდს წერს და `git push`-ით GitHub-ზე აგზავნის. 2. 🐙 GitHub ამას ამჩნევს და ავტომატურად უშვებს **GitHub Actions**-ს. 3. ⚙️ Actions აწყობს (build) და ამოწმებს (ტესტები) პროექტს. 4. ☁️ წარმატების შემთხვევაში ახალი ვერსია სერვერზე ავტომატურად იდება. 5. 👥 მომხმარებელი ახალ ვერსიას ხედავს. **ძველად:** ფაილებს ხელით ტვირთავდი FTP-ით. რომელი ვერსია დევს სერვერზე? ვინ ატვირთა? რა შეიცვალა? — არავინ იცოდა. **დღეს:** კოდი Git-შია, გზა კი ერთხელ არის აწყობილი. ყოველი ცვლილება ჩანს, ავტომატურად ქვეყნდება და, თუ რამე გაფუჭდა, წინა ვერსიაზე დაბრუნება წამებია. `git push` თავისით არაფერს აქვეყნებს — ამას ჩვენ ვაწყობთ, და ამის აწყობას ვისწავლით. ამ პროცესს **CI/CD** ჰქვია. მის აწყობას და მოვლას DevOps ინჟინერი აკეთებს — და ის **Git-ით იწყება**, ამიტომ კურსს Git-ით დავიწყებთ.

ეს კურსი ≠ მთელი DevOps 🧊

ეს კურსი — საძირკველია: ერთი აპის სრული გზა ლეპტოპიდან ინტერნეტამდე. დანარჩენს ამ საძირკველზე ააშენებ.
### ეს კურსი ≠ მთელი DevOps გულწრფელად: DevOps ძალიან დიდი სფეროა, და ერთ კურსში მთლიანად არ ისწავლება. ჩვენ **საძირკველს** ვყრით — აისბერგის იმ ნაწილს, რომელიც წყლის ზემოთ ჩანს. **✓ ამ კურსში ვისწავლით (საფუძველი):** - Git, GitHub და GitHub Actions — კოდის ისტორია და ავტომატიზაცია; - Linux და SSH — საკუთარი სერვერის მართვა; - დომენი, HTTPS და ავტომატური deploy — ერთი აპის სრული გზა ლეპტოპიდან ინტერნეტამდე. **🌊 წყლის ქვეშ — შემდეგი ნაბიჯები, თუ DevOps-ში გააგრძელებ:** - 📦 **Docker** და ☸️ **Kubernetes** — კონტეინერები და მათი მართვა დიდი მასშტაბით; - 🏗️ **Terraform, Ansible** — ინფრასტრუქტურა კოდით; - ☁️ **AWS / Azure** — დიდი ღრუბლოვანი პლატფორმები (ხშირად სერტიფიკატებით); - 📈 **Prometheus, Grafana** — სერიოზული მონიტორინგი; - 🔐 **DevSecOps** — უსაფრთხოება მთელ გზაზე; - ⚖️ მასშტაბირება და 🧯 **SRE** (Site Reliability Engineering) — მილიონობით მომხმარებლის მომსახურება. **რატომ ღირს საძირკველი:** წყლის ქვეშ ყველაფერი სწორედ ამ ცოდნაზე დგას. ვინც Git-ს, Linux-ს, სერვერს და deploy-ს არ იცნობს, Kubernetes-ს ვერ გაიგებს.

### DNS — სახელების და მისამართების საცავი ინტერნეტში კომპიუტერები ერთმანეთს **IP მისამართით** პოულობენ — მაგალითად `164.90.12.34`. ადამიანისთვის ციფრების დამახსოვრება რთულია, ამიტომ გვაქვს **დომენის სახელები**: `google.com`, `myportfolio.ge`. **DNS (Domain Name System)** — ინტერნეტის „კონტაქტების წიგნი“: საცავი, სადაც ყოველ **სახელს** მისი სერვერის **მისამართი** (IP) უწერია. | სახელი (დომენი) | მისამართი (IP) | |---|---| | `google.com` | `142.250.185.78` | | `facebook.com` | `157.240.1.35` | | `myportfolio.ge` | `164.90.12.34` | **როგორ მუშაობს:** 1. ① ბრაუზერი DNS-ს ეკითხება: „`myportfolio.ge` სად არის?“ 2. ② DNS წიგნში პოულობს და პასუხობს: „`164.90.12.34`“. 3. ③ ბრაუზერი ამ მისამართზე მიდის — სერვერთან. 📱 **ანალოგია — ტელეფონის კონტაქტები:** შენ ეძებ „დედა“-ს, ტელეფონი კი ნომერზე რეკავს. სახელს იმახსოვრებ შენ, ნომერს — ტელეფონი. ```note ეს „წიგნი“ თვითონ არ ივსება: როცა დომენს იყიდი, DNS-ში შენ ჩაწერ, რომ `myportfolio.ge` → შენი სერვერის IP. ამას კურსში თვითონ გავაკეთებთ. ### რა ხდება, როცა აკრეფ `myportfolio.ge`? 1. **DNS** — ბრაუზერმა სახელი იცის, მაგრამ ინტერნეტში კომპიუტრები **IP მისამართით** პოულობენ ერთმანეთს. DNS „სატელეფონო წიგნია“: `myportfolio.ge` → `164.90.12.34`. 2. **მოთხოვნა** — ბრაუზერი ამ IP-ზე აგზავნის HTTP მოთხოვნას: `GET /`. 3. **სერვერი** — იღებს მოთხოვნას და პოულობს შესაბამის ფაილს. 4. **პასუხი** — `200 OK` და HTML-ის შიგთავსი. 5. **დამატებითი მოთხოვნები** — ბრაუზერი HTML-ში ხედავს `style.css`-ს, `app.js`-ს, სურათებს და თითოეულს ცალკე ითხოვს. ერთი გვერდი = ათობით მოთხოვნა. ```note DNS-ს და დომენებს კურსში დეტალურად გავივლით. დღეს მთავარია სურათი: **სახელი → IP → სერვერი → ფაილი → პასუხი**. ``` ```terms IP მისამართი — მოწყობილობის ნომერი ინტერნეტში, მაგ. 164.90.12.34 DNS — სისტემა, რომელიც დომენის სახელს IP მისამართად თარგმნის ```
