📀 image

აპი + runtime + ფაილები. მხოლოდ წასაკითხი შაბლონი

📦 container

image-იდან გაშვებული პროცესი — თავისი იზოლირებული ფაილებით და ქსელით

🏪 registry

image-ების „მაღაზია“: Docker Hub, mcr.microsoft.com, GHCR

### image = კლასი · container = ობიექტი C#-ში უკვე იცი ეს იდეა: ```csharp C# class Course { ... } // შაბლონი var c1 = new Course(); // ეგზემპლარი var c2 = new Course(); // კიდევ ერთი, დამოუკიდებელი ``` Docker-ში: | ტერმინი | რა არის | C# ანალოგია | |---|---|---| | **image** | აპი + runtime + საჭირო ფაილები, „გაყინული“ — მხოლოდ წასაკითხი შაბლონი | კლასი | | **container** | image-იდან **გაშვებული** ეგზემპლარი: საკუთარი იზოლირებული ფაილებით, ქსელით, პროცესებით | ობიექტი | | **registry** | image-ების საცავი, საიდანაც `docker` მათ ჩამოტვირთავს | NuGet | ცნობილი registry-ები: **Docker Hub** (`postgres`, `nginx`, `redis`...), **mcr.microsoft.com** (Microsoft-ის .NET image-ები), **GHCR** (GitHub-ის — მე-11 ლექციაზე გამოვიყენებთ). image-ის სახელი: `postgres:17` — `სახელი:tag`, სადაც tag ჩვეულებრივ ვერსიაა. `latest` — ნაგულისხმევი tag.

### კონტეინერი vs ვირტუალური მანქანა **ვირტუალური მანქანა** (VM — მაგ. ჩვენი Droplet) — მთელი კომპიუტერის იმიტაცია: თავისი სრული OS-ით. ყოველი VM რამდენიმე GB-ია და ჩართვას წუთები სჭირდება. **კონტეინერი** მთელ OS-ს არ შეიცავს: ყველა კონტეინერი ერთ საერთო Linux-ის **ბირთვს** იყენებს, თითოეულს კი მხოლოდ საკუთარი ფაილები, ბიბლიოთეკები და აპი აქვს. ამიტომ კონტეინერი MB-ებია და **წამებში** ირთვება. | | VM | კონტეინერი | |---|---|---| | შეიცავს | მთელ OS-ს | აპს და მის ფაილებს | | ზომა | GB-ები | MB-ები | | ჩართვა | წუთები | წამები | | იზოლაცია | ძალიან ძლიერი | ძლიერი, საკმარისი აპებისთვის | ისინი ერთმანეთს არ ცვლის: ჩვენ Droplet-ზე (VM) **კონტეინერებს** გავუშვებთ. ```note Windows-ზე Docker Desktop კონტეინერებს WSL 2-ის Linux-ში უშვებს — სწორედ ამიტომ გჭირდებოდათ virtualization BIOS-ში. ```

### ნაბიჯი 1 · PostgreSQL — ერთი ბრძანებით ჯერ შემოწმება — Docker Desktop ჩართულია და მუშაობს: ```console WSL $ docker run hello-world Hello from Docker! ``` ახლა — წინა ლექციის „PostgreSQL-ის დაყენება + user + ბაზა“, ერთი ბრძანებით: ```console WSL $ docker run -d --name lms-db \ -e POSTGRES_USER=lms \ -e POSTGRES_PASSWORD=dev \ -e POSTGRES_DB=lms \ -p 5432:5432 \ -v lms-data:/var/lib/postgresql/data \ postgres:17 ``` | ნაწილი | რას ნიშნავს | |---|---| | `-d` | detached — ფონზე, terminal-ი თავისუფალი რჩება | | `--name lms-db` | სახელი, რომლითაც კონტეინერს მივმართავთ | | `-e POSTGRES_USER=lms` … | გარემოს ცვლადები: image პირველ გაშვებაზე თვითონ ქმნის user-ს, პაროლს და ბაზას | | `-p 5432:5432` | `ჰოსტის-port:კონტეინერის-port` — შენი კომპიუტერის 5432 → კონტეინერის 5432 | | `-v lms-data:/var/lib/postgresql/data` | volume — სადაც PostgreSQL მონაცემებს ინახავს (იხ. შემდეგი სლაიდები) | | `postgres:17` | image Docker Hub-იდან, ვერსია 17 | პირველად Docker image-ს ჩამოტვირთავს (pull), შემდეგ ჯერზე — უკვე ლოკალურად აქვს. ```console WSL $ docker ps CONTAINER ID IMAGE STATUS PORTS NAMES a3f9c1e2b7d4 postgres:17 Up 5 seconds 0.0.0.0:5432->5432/tcp lms-db ``` LMS-ის connection string ლოკალურად: `Host=localhost;Database=lms;Username=lms;Password=dev` → `dotnet ef database update` → `dotnet run`. ბაზა მზადაა — ინსტალაციის გარეშე.

### ნაბიჯი 2 · კონტეინერების მართვა ```console WSL $ docker ps # მუშა კონტეინერები $ docker ps -a # ყველა, გაჩერებულებიც $ docker logs -f lms-db # ლოგი ცოცხლად (Ctrl+C — გამოსვლა) $ docker exec -it lms-db psql -U lms # ბრძანება კონტეინერის შიგნით $ docker stop lms-db # გაჩერება $ docker start lms-db # ჩართვა $ docker rm -f lms-db # წაშლა (-f: გაჩერებულიც და მუშაც) $ docker images # ლოკალური image-ები ``` | ბრძანება | ანალოგია უკვე ნასწავლიდან | |---|---| | `docker ps` | `ps aux` / `systemctl status` | | `docker logs -f` | `journalctl -u … -f` | | `docker exec -it bash` | `ssh` — „შესვლა“ კონტეინერში | | `docker stop` / `start` | `systemctl stop` / `start` | `exec -it`: `-i` — შეყვანა ღიაა, `-t` — ტერმინალი. `docker exec -it lms-db bash` — Linux-ის ტერმინალი კონტეინერის შიგნით (`exit` — გამოსვლა).
volume

კონტეინერი ქრება — მონაცემები რჩება

⚠ volume-ის გარეშე: docker rm = ბაზა წაიშალა. ბაზას ყოველთვის volume
### volume — კონტეინერი ქრება, მონაცემები რჩება კონტეინერის ფაილები **დროებითია**: `docker rm` — და ყველაფერი, რაც კონტეინერის შიგნით შეიქმნა, ქრება. აპისთვის ეს კარგია (ახალი ვერსია = ახალი კონტეინერი, სუფთა). **ბაზისთვის** — კატასტროფა. **volume** — Docker-ის მიერ მართული საცავი დისკზე, რომელიც კონტეინერის შიგნით საქაღალდედ ჩანს: ```plain -v lms-data:/var/lib/postgresql/data ↑ volume ↑ საქაღალდე კონტეინერში, სადაც PostgreSQL მონაცემებს წერს ``` ექსპერიმენტი: ```console WSL $ docker rm -f lms-db $ docker run -d --name lms-db ... -v lms-data:/var/lib/postgresql/data postgres:17 $ docker exec -it lms-db psql -U lms -c 'SELECT * FROM "Courses";' # ჩანაწერები ისევ იქაა ✅ ``` ```console WSL $ docker volume ls # ყველა volume $ docker volume rm lms-data # ⚠ ეს უკვე ნამდვილად შლის მონაცემებს ``` ```warn ბაზის კონტეინერს **ყოველთვის** volume სჭირდება. volume-ის გარეშე `docker rm` (ან სერვერზე კონტეინერის განახლება) = ბაზა წაიშალა. ```

RUN dotnet publish Lms.Api/Lms.Api.csproj \ -c Release -o /app/publish # ── ეტაპი 2: runtime (მხოლოდ გაშვება) ───── FROM mcr.microsoft.com/dotnet/aspnet:10.0 WORKDIR /app COPY --from=build /app/publish . ### ნაბიჯი 3 · Dockerfile: ორი ეტაპი LMS-ის რეპოს root-ში (იქ, სადაც `.sln`-ია) — ფაილი `Dockerfile` (გაფართოების გარეშე): ```dockerfile Dockerfile # ── ეტაპი 1: build (SDK) ── FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build WORKDIR /src COPY Lms.Api/Lms.Api.csproj Lms.Api/ RUN dotnet restore Lms.Api/Lms.Api.csproj COPY . . RUN dotnet publish Lms.Api/Lms.Api.csproj -c Release -o /app/publish # ── ეტაპი 2: runtime (მხოლოდ გაშვება) ── FROM mcr.microsoft.com/dotnet/aspnet:10.0 WORKDIR /app COPY --from=build /app/publish . USER $APP_UID EXPOSE 8080 ENTRYPOINT ["dotnet", "Lms.Api.dll"] ``` | ინსტრუქცია | რას აკეთებს | |---|---| | `FROM AS build` | საწყისი image; `AS` — ეტაპის სახელი | | `WORKDIR /src` | მიმდინარე საქაღალდე image-ის შიგნით (არ არსებობს — შეიქმნება) | | `COPY <შენთან> ` | ფაილების კოპირება | | `RUN <ბრძანება>` | ბრძანება **აწყობისას** (`restore`, `publish`) | | `COPY --from=build` | ფაილები **წინა ეტაპიდან** | | `USER $APP_UID` | .NET-ის image-ში მზა არა-root user `app` | | `EXPOSE 8080` | დოკუმენტაცია: აპი 8080-ს უსმენს (.NET image-ის ნაგულისხმევი port) | | `ENTRYPOINT` | ბრძანება, რომელიც **კონტეინერის ჩართვისას** სრულდება | **რატომ ორი ეტაპი (multi-stage)?** აწყობას **SDK** სჭირდება (დიდია), გაშვებას — მხოლოდ **runtime** (წინა ლექციის იგივე იდეა). საბოლოო image მხოლოდ მეორე ეტაპია: მასში არ არის SDK და შენი საწყისი კოდი — ის პატარაა და უსაფრთხო. ```note `Lms.Api` — პროექტის საქაღალდე და სახელი. შენი თუ სხვაა, შეცვალე. თუ რამდენიმე პროექტია (მაგ. ცალკე class library), `COPY` ყველა `.csproj`-ისთვის დაამატე, ან უბრალოდ `COPY . .` → `restore`. ```

② RUN restore      ✓ CACHED ← 40 წმ დაზოგილი
③ COPY . .         ↻ კოდი შეიცვალა
④ RUN publish      ↻

ყოველი ინსტრუქცია = ფენა (layer). შეუცვლელი ფენა ქეშიდან აიღება
**/bin/ **/obj/ .git/ .vs/ .vscode/ *.user
როგორც .gitignore — ოღონდ build-ისთვის: ნაკლები ფაილი → სწრაფი build, სუფთა image
### ნაბიჯი 4 · ფენები და .dockerignore **ფენები (layers).** Dockerfile-ის ყოველი ინსტრუქცია ქმნის **ფენას** და Docker მას ქეშავს. თუ ფენის შემავალი არ შეცვლილა, Docker მას ხელახლა აღარ ასრულებს: ```plain docker build — მეორედ, კოდის ცვლილების შემდეგ ① COPY Lms.Api/Lms.Api.csproj ✓ CACHED ② RUN dotnet restore ✓ CACHED ← NuGet პაკეტები აღარ იტვირთება ③ COPY . . ↻ კოდი შეიცვალა ④ RUN dotnet publish ↻ ``` ამიტომ ჯერ **მხოლოდ** `.csproj`-ს ვაკოპირებთ და `restore`-ს ვუშვებთ: პაკეტები იშვიათად იცვლება, კოდი — ხშირად. `COPY . .` რომ პირველი ყოფილიყო, კოდის ყოველი ცვლილება `restore`-ს თავიდან გაუშვებდა. **`.dockerignore`** — როგორც `.gitignore`, ოღონდ `docker build`-ისთვის: ეს ფაილები build-ში არ გადაიგზავნება. ```plain .dockerignore **/bin/ **/obj/ .git/ .vs/ .vscode/ *.user ``` ლოკალური `bin/` და `obj/` image-ში არ გვინდა — `publish` თავისას შექმნის. ნაკლები ფაილი = სწრაფი build და სუფთა image.
