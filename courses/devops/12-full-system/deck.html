### პრობლემა: API — ავტომატურად, ფრონტი — ხელით? API უკვე სრულ გზას გადის: merge → CI → GHCR → სერვერი. ფრონტი კი, თუ მე-5 ლექციის გზით წავიდოდით, ხელით გავიდოდა: `ng build` → `rsync` → `/var/www/app`. ორი პრობლემა: - **API-ს მისამართი.** თუ Angular-ის კოდში წერია `https://api.giorgi.ge`, ბრაუზერისთვის ეს **სხვა დომენია** (`app.` ≠ `api.`) — API-ს CORS სჭირდება, და ყოველ გარემოს (შენი ლეპტოპი, სერვერი) თავისი build. - **ორი სხვადასხვა გზა.** სერვერის გამოცვლისას ორივე ცალ-ცალკე უნდა გადავიტანოთ. **გამოსავალი:** ფრონტსაც ვაქცევთ **კონტეინერად**. მის შიგნით — Nginx, რომელიც Angular-ის ფაილებს აძლევს, ხოლო `/api/...` მოთხოვნებს API-ის კონტეინერს გადასცემს. ბრაუზერისთვის ყველაფერი **ერთ დომენზეა** — CORS აღარ სჭირდება, და Angular-ში API-ის მისამართი უბრალოდ `/api`-ა, ნებისმიერ გარემოში.
ვაკეთებთ ერთად · ნაბიჯი 1

web/Dockerfile — node აწყობს, nginx აძლევს

# 1 — აწყობა FROM node:24-alpine AS build WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build # 2 — გაშვება FROM nginx:alpine COPY nginx.conf /etc/nginx/conf.d/default.conf COPY --from=build /app/dist/lms-web/browser \ /usr/share/nginx/html server { listen 80; root /usr/share/nginx/html; index index.html; location /api/ { proxy_pass http://api:8080; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto; } location / { try_files $uri $uri/ /index.html; } }
ორივე ნაცნობია: multi-stage — მე-7 ლექციიდან, try_files და proxy_pass — მე-5 და მე-6-დან. api — სერვისის სახელი Compose-ში
### ნაბიჯი 1 · web/Dockerfile — node აწყობს, nginx აძლევს ფრონტი რეპოს `web/` საქაღალდეშია (API-ის გვერდით). მისი Dockerfile ორეტაპიანია — ზუსტად ისე, როგორც API-ის (მე-7 ლექცია): აწყობას ერთი გარემო სჭირდება, გაშვებას — სხვა, ბევრად პატარა. ```dockerfile web/Dockerfile # 1 — აწყობა: Node + npm FROM node:24-alpine AS build WORKDIR /app COPY package*.json ./ RUN npm ci COPY . . RUN npm run build # 2 — გაშვება: მხოლოდ Nginx და მზა ფაილები FROM nginx:alpine COPY nginx.conf /etc/nginx/conf.d/default.conf COPY --from=build /app/dist/lms-web/browser /usr/share/nginx/html ``` - `npm ci` — ზუსტად `package-lock.json`-ის ვერსიებს აყენებს (CI-სა და Docker-ისთვის ეს ჯობია `npm install`-ს); - `dist/lms-web/browser` — Angular-ის build-ის შედეგი; `lms-web` — პროექტის სახელი `angular.json`-დან; - საბოლოო image-ში **Node არ არის** — მხოლოდ Nginx და HTML/CSS/JS ფაილები. ```nginx web/nginx.conf server { listen 80; root /usr/share/nginx/html; index index.html; location /api/ { proxy_pass http://api:8080; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto; } location / { try_files $uri $uri/ /index.html; } } ``` - `location /api/` — `/api/...` მოთხოვნები API-ის კონტეინერს გადაეცემა. `api` — სერვისის სახელი Compose-ში (როგორც `Host=db` ბაზისთვის, მე-8 ლექცია), `8080` — port **კონტეინერის შიგნით**; - `X-Forwarded-Proto` — სერვერის Nginx-მა უკვე იცის, რომ მოთხოვნა HTTPS-ით მოვიდა; ამ ინფორმაციას API-მდე ვატარებთ (მე-9 ლექცია); - `try_files … /index.html` — SPA-ს refresh → 404 პრობლემა, მე-5 ლექციიდან. ```warn Angular-ში API-ის მისამართი ახლა **ფარდობითია**: `/api/courses`, არა `https://api.giorgi.ge/api/courses`. ასე ერთი და იგივე build ყველგან მუშაობს, და CORS არ გვჭირდება — ბრაუზერისთვის ფრონტიც და API-ც ერთ დომენზეა. ```

web — მესამე სერვისი

web: build: ./web image: ghcr.io/giorgi/lms-web:${IMAGE_TAG:-latest} ports: - "127.0.0.1:4000:80" depends_on: - api restart: unless-stopped

root /var/www/app → proxy_pass. ფაილებს აწი კონტეინერი აძლევს
### ნაბიჯი 2 · Compose + სერვერის Nginx `compose.yaml`-ში მესამე სერვისი ემატება: ```yaml compose.yaml — web web: build: ./web image: ghcr.io/giorgi/lms-web:${IMAGE_TAG:-latest} ports: - "127.0.0.1:4000:80" depends_on: - api restart: unless-stopped ``` - `build: ./web` — Dockerfile `web/` საქაღალდიდან (შენთან, `up --build`-ისთვის); - `image` — იგივე `IMAGE_TAG`, რაც API-ს: ორივე ერთი commit-იდან აეწყობა, და rollback-იც ორივეს ერთად აბრუნებს; - `127.0.0.1:4000` — როგორც API-ს `5000`: ინტერნეტიდან პირდაპირ არ ჩანს, მხოლოდ სერვერის Nginx-ისთვის. შენთან: `docker compose up -d --build` → `http://localhost:4000` — ფრონტი იხსნება და `/api/courses`-ს API-დან იღებს. **სერვერის Nginx** — `app.giorgi.ge`-ის server block-ში `root /var/www/app` და `try_files` იცვლება `proxy_pass`-ით: ```nginx sites-available/app server { server_name app.giorgi.ge; location / { proxy_pass http://127.0.0.1:4000; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; } # listen 443 ssl და ssl_certificate ხაზები — certbot-ისგან, უცვლელი } ``` `sudo nginx -t && sudo systemctl reload nginx`. ```note ეს კონფიგი რეპოშიც ჩადე — `deploy/nginx/lms.conf` (`app` და `api` ბლოკები, certbot-ის ხაზების გარეშე). მეორე ნაწილში, ახალ სერვერზე, ის ხელახლა წერის ნაცვლად უბრალოდ დაკოპირდება. ```

### ნაბიჯი 3 · deploy.yml — ორი image `deploy.yml`-ში სამი ცვლილებაა: ```yaml .github/workflows/deploy.yml (ცვლილებები) on: push: branches: [main] workflow_dispatch: # ... checkout და login — უცვლელი - uses: docker/build-push-action@v6 # api — უცვლელი with: push: true tags: | ghcr.io/${{ github.repository }}:latest ghcr.io/${{ github.repository }}:${{ github.sha }} - uses: docker/build-push-action@v6 # web — ახალი with: context: ./web push: true tags: | ghcr.io/${{ github.repository }}-web:latest ghcr.io/${{ github.repository }}-web:${{ github.sha }} - uses: appleboy/ssh-action@v1 with: host: ${{ secrets.SSH_HOST }} username: ${{ secrets.SSH_USER }} key: ${{ secrets.SSH_KEY }} script: | cd ~/lms git pull docker compose pull api web docker compose up -d ``` 1. `workflow_dispatch` — Actions-ში ჩნდება **Run workflow** ღილაკი. ახალ სერვერზე პირველი deploy-ისთვის დაგვჭირდება: ახალი commit არ გვექნება, deploy კი უნდა გაეშვას. 2. მეორე `build-push-action` — `context: ./web` (Dockerfile და ფაილები `web/`-დან), image-ის სახელი `…-web`. 3. `docker compose pull api web` — სერვერი ორივე ახალ image-ს იღებს. root-ის `.dockerignore`-ში ემატება `web/` და `.github/` — API-ის build-ს ისინი არ სჭირდება, და build ასე უფრო სწრაფია. merge → Actions: Deploy ✅ → `https://app.giorgi.ge` — ფრონტი, რომელიც API-დან მონაცემებს იღებს. ამიერიდან **მთელი სისტემა** ერთი გზით გადის. ```warn სერვერზე ერთხელ შეამოწმე, რომ GHCR-ის `read:packages` ტოკენი ახალ `lms-web` package-საც კითხულობს (`docker compose pull web`). ტოკენი მომხმარებლის ყველა package-ზე მოქმედებს, ამიტომ ჩვეულებრივ დამატებით არაფერი სჭირდება. ```

### გეგმა: კოდი თვითონ მიდის — მდგომარეობა კი არა სერვერის გამოცვლისას ყველაფერი ორ ჯგუფად იყოფა: | ✅ Git-შია და GHCR-ში — CD წაიღებს | ✋ Git-ში არ არის — ჩვენ გადაგვაქვს | |---|---| | კოდი, Dockerfile-ები, `compose.yaml` | სერვერის მომზადება (user, firewall, Docker, Nginx) | | workflow-ები, Nginx-ის კონფიგი (`deploy/nginx/`) | `.env` — საიდუმლოებები (Git-ში არასოდეს!) | | image-ები GHCR-ში | ბაზის **მონაცემები** | | | DNS ჩანაწერები და HTTPS სერტიფიკატი | რაც Git-შია, ის ახალ სერვერზე CD-ით თვითონ მიდის. დანარჩენი — **მდგომარეობაა** (state): ის სერვერზე ცხოვრობს და მასთან ერთად ქრება. ამიტომ მას ცალკე, ფრთხილად ვიტანთ. **გეგმა:** 1. ახალი Droplet — **cloud-init**-ით, რომ შექმნისთანავე მზად იყოს; 2. მომზადება: `git clone`, `.env`, GHCR login, Nginx-ის კონფიგი; 3. **მონაცემები**: ძველი ბაზა → ახალი; 4. **deploy**: GitHub-ში `SSH_HOST` → ახალი IP → Deploy; 5. **DNS** → ახალი IP, მერე **HTTPS**; 6. შემოწმება → ძველი სერვერის წაშლა. ```tip DNS-ის ჩანაწერის TTL **წინა დღეს** ჩამოწიე 300 წამამდე. თორემ ბრაუზერები და პროვაიდერები ძველ IP-ს საათობით დაიმახსოვრებენ, და გადასვლა ლექციაზე ვერ დასრულდება. ```

### ნაბიჯი 1 · Droplet + cloud-init მე-4 ლექციაზე სერვერს ხელით ვამზადებდით: user, გასაღები, `sshd`, `ufw`, swap. მე-8-ზე — Docker. ახლა ყველაფერს ერთ ფაილში ვწერთ, და Droplet შექმნისთანავე თვითონ ასრულებს. **cloud-init** — სტანდარტი, რომლითაც ღრუბლოვანი სერვერი პირველ ჩართვაზე თავისით მზადდება. DigitalOcean-ზე: **Create Droplet** → Ubuntu 24.04 → SSH key → **Advanced Options → Add Initialization scripts** → ჩასვი ფაილი: ```yaml cloud-init.yaml #cloud-config users: - name: giorgi groups: sudo shell: /bin/bash sudo: "ALL=(ALL) NOPASSWD:ALL" ssh_authorized_keys: - ssh-ed25519 AAAA... giorgi@laptop - ssh-ed25519 AAAA... github-actions-deploy package_update: true packages: [nginx, certbot, python3-certbot-nginx] runcmd: - curl -fsSL https://get.docker.com | sh - usermod -aG docker giorgi - fallocate -l 2G /swapfile && chmod 600 /swapfile - mkswap /swapfile && swapon /swapfile - echo '/swapfile none swap sw 0 0' >> /etc/fstab - sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config - systemctl restart ssh - ufw allow OpenSSH && ufw allow 'Nginx Full' && ufw --force enable ``` | ნაწილი | რას აკეთებს | ხელით — სად | |---|---|---| | `users` | user, sudo, ორი საჯარო გასაღები | მე-4 ლექცია | | `packages` | Nginx და certbot | მე-5 და მე-9 | | `runcmd` | Docker, swap, root-ის აკრძალვა, firewall | მე-4 და მე-8 | - `ssh_authorized_keys` — შენი გასაღების `.pub` (`cat ~/.ssh/id_ed25519.pub`) და **deploy** გასაღების `.pub` (`cat ~/.ssh/github-deploy.pub`). ასე GitHub Actions ახალ სერვერზეც შევა, და `SSH_KEY` secret-ის შეცვლა არ მოგვიწევს; - `NOPASSWD` — user-ს პაროლი არ აქვს (შესვლა მხოლოდ გასაღებით), ამიტომ `sudo` პაროლს არ ითხოვს. რამდენიმე წუთში: Termius-ში ახალი host **lms-new** (ახალი IP, user `giorgi`) და WSL-ის `~/.ssh/config`-ში `Host lms-new`: ```console Termius · lms-new $ cloud-init status --wait status: done $ docker --version && nginx -v ``` ```warn `runcmd` ერთხელ, პირველ ჩართვაზე სრულდება. თუ რამე ჩავარდა, ლოგი აქაა: `sudo tail -50 /var/log/cloud-init-output.log`. ```

### ნაბიჯი 2 · მომზადება: რეპო · .env · GHCR · Nginx ყველაფერი ნაცნობია — ოღონდ ახლა ხუთ წუთში: ```console Termius · lms-new $ git clone https://github.com/giorgi/lms.git ~/lms $ echo "ghp_xxxx" | docker login ghcr.io -u giorgi --password-stdin Login Succeeded $ sudo cp ~/lms/deploy/nginx/lms.conf /etc/nginx/sites-available/lms $ sudo ln -s /etc/nginx/sites-available/lms /etc/nginx/sites-enabled/ $ sudo rm /etc/nginx/sites-enabled/default $ sudo nginx -t && sudo systemctl reload nginx ``` - `git clone` — `compose.yaml` და Nginx-ის კონფიგი. თუ რეპო private-ია, clone-ს ტოკენი სჭირდება — იგივე PAT-ით, `repo` უფლებით; - `docker login ghcr.io` — PAT `read:packages`-ით (მე-11 ლექცია); შეგიძლია ძველი გამოიყენო; - Nginx-ის კონფიგი **რეპოდან** მოდის (`deploy/nginx/lms.conf`) — ხელით აღარ ვწერთ. HTTPS-ის ხაზებს certbot მოგვიანებით თვითონ დაამატებს. **`.env` — Git-ში არ არის**, ამიტომ ძველი სერვერიდან პირდაპირ გადმოგვაქვს: ```console WSL $ scp -3 lms:~/lms/.env lms-new:~/lms/.env $ ssh lms-new "chmod 600 ~/lms/.env" ``` `scp -3` ფაილს ორ სერვერს შორის **შენი კომპიუტერის გავლით** აკოპირებს — სერვერებს ერთმანეთის გასაღებები არ სჭირდებათ. ```warn `.env` **იგივე** უნდა იყოს. ბაზა ძველი `DB_PASSWORD`-ით გადმოვა, ხოლო ახალი JWT გასაღებით ყველა ძველი ტოკენი გაუქმდებოდა — ყველა მომხმარებელი სისტემიდან გამოვიდოდა. ```

### ნაბიჯი 5 · DNS + HTTPS **DNS** (მე-9 ლექცია): დომენის პანელში `app` და `api` A-ჩანაწერებს ახალ IP-ს ვუწერთ (თუ portfolio-ც ამ სერვერზე იყო — `@` და `www`-საც). ```console WSL $ dig +short app.giorgi.ge 167.71.40.8 ``` TTL-ის წყალობით (წინა დღეს 300 წამზე ჩამოვწიეთ), რამდენიმე წუთში ყველა ახალ IP-ს ხედავს. **HTTPS** — სერტიფიკატი ძველ სერვერზე დარჩა, ახალზე თავიდან ვიღებთ: ```console Termius · lms-new $ sudo certbot --nginx -d app.giorgi.ge -d api.giorgi.ge ``` certbot რეპოდან მოსულ Nginx-ის კონფიგს `listen 443 ssl` ხაზებს და HTTP → HTTPS redirect-ს თვითონ დაუმატებს — ზუსტად ისე, როგორც მე-9 ლექციაზე. ```warn certbot გაუშვი **მხოლოდ მას შემდეგ**, რაც `dig` ახალ IP-ს აჩვენებს. Let's Encrypt ამოწმებს, რომ დომენი ნამდვილად ამ სერვერზე მიდის — თუ DNS ჯერ ძველზეა, შემოწმება ჩავარდება. ``` ```note Let's Encrypt-ს ლიმიტები აქვს: ერთი და იგივე დომენების ნაკრებზე კვირაში მხოლოდ რამდენიმე სერტიფიკატი. თუ გადასვლას წინასწარ ცდი, გამოიყენე `--test-cert` — სატესტო სერტიფიკატი, რომელიც ლიმიტს არ ხარჯავს (ბრაუზერი მას არ ენდობა). ნამდვილზე — ბრძანება `--test-cert`-ის გარეშე. ```
