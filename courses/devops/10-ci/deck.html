## ნაწილი 1 · CI/CD — რა არის და რატომ მე-2 ლექციაზე Actions ჩანართში პირველი pipeline ვნახეთ — `pages build and deployment`, რომელიც GitHub-მა თვითონ შექმნა. დღეს ვხედავთ მთლიან სურათს: რა არის CI/CD, რა ნაბიჯებისგან შედგება და რატომ მუშაობს ასე ყველა თანამედროვე გუნდი. მერე პრაქტიკაში ვწერთ CI-ს; CD — შემდეგ ლექციაზე.
პრობლემა

ყოველი განახლება — ხელით

$ git push # შენთან # Termius → lms-server $ cd ~/lms $ git pull $ docker compose up -d --build # build 1 GB RAM-ზე 😬 $ docker compose logs -f api # მუშაობს?
😴 დაგავიწყდა → სერვერზე ძველი ვერსიაა
💥 main-ში მოხვდა კოდი, რომელიც არ იკომპილირდება → deploy ჩავარდა
👥 გუნდში 5 ადამიანი — ყველას სერვერის SSH უნდა ჰქონდეს?
CI — ყოველი ცვლილების შემოწმება · CD — ყოველი ცვლილების deploy. ავტომატურად
### პრობლემა: ყოველი განახლება — ხელით მე-8 ლექციის შემდეგ LMS-ის განახლება ასე გამოიყურება: ```console ყოველ ჯერზე $ git push # Termius → lms-server $ cd ~/lms $ git pull $ docker compose up -d --build $ docker compose logs -f api ``` - 😴 დაგავიწყდა — სერვერზე ძველი ვერსიაა; - 💥 `main`-ში მოხვდა კოდი, რომელიც არც კი იკომპილირდება — deploy ჩავარდება; - 👥 გუნდში ხუთი ადამიანია — ყველას სერვერზე SSH წვდომა ჰქონდეს? - 🐢 build 1 GB RAM-იან სერვერზე — ნელი და სახიფათო. **CI (Continuous Integration)** — ყოველი ცვლილება **ავტომატურად მოწმდება** (build, ტესტები), სანამ `main`-ში მოხვდება. **CD (Continuous Deployment)** — `main`-ის ყოველი ცვლილება **ავტომატურად** გადის სერვერზე. ორივეს GitHub Actions აკეთებს — ზუსტად იმ ნაბიჯებით, რასაც აქამდე ხელით ვაკეთებდით. დღეს ვხედავთ მთლიან სურათს და პრაქტიკაში ვწერთ **CI**-ს: `main`-ში მხოლოდ შემოწმებული კოდი უნდა მოხვდეს. შემდეგ ლექციაზე — **CD** პრაქტიკაში: შემოწმებულ კოდს სერვერზე ავტომატურად გავიტანთ.
სრული სურათი

pipeline — commit-იდან production-მდე

❌ ნებისმიერ ნაბიჯზე → pipeline ჩერდება, და გატეხილი კოდი შემდეგ ნაბიჯამდე ვერ მიდის
### pipeline — commit-იდან production-მდე **pipeline** — ავტომატური ნაბიჯების ჯაჭვი, რომელსაც ყოველი ცვლილება გადის, სანამ მომხმარებლამდე მივა: | ნაბიჯი | რას აკეთებს | ჩვენთან | |---|---|---| | **commit · PR** | ცვლილება Git-ში | `feature/...` → Pull Request | | **build** | კოდი იკომპილირდება? | `dotnet build` | | **test** | კოდი სწორად მუშაობს? | `dotnet test` | | **artifact** | გასაშვებად მზა „პაკეტი“ | Docker image | | **deploy** | artifact სერვერზე | `docker compose pull && up -d` | | **production** | მომხმარებელი ახალ ვერსიას ხედავს | `https://api.giorgi.ge` | ჯაჭვი ორ ნაწილად იყოფა: - **CI (Continuous Integration)** — build და test **ყოველ** ცვლილებაზე, `main`-ში შერწყმამდე. პასუხობს კითხვას: „კოდი სწორია?“ - **CD (Continuous Delivery / Deployment)** — შემოწმებული კოდიდან artifact-ის შექმნა და მისი გატანა სერვერზე. პასუხობს კითხვას: „კოდი მომხმარებელთანაა?“ მთავარი წესი: **ნებისმიერ ნაბიჯზე შეცდომა pipeline-ს აჩერებს.** ტესტი ჩავარდა — image არ აეწყობა და deploy არ მოხდება. ამიტომ გატეხილი კოდი production-მდე ვერ აღწევს. ```terms pipeline — ავტომატური ნაბიჯების ჯაჭვი: build → test → artifact → deploy artifact — pipeline-ის შედეგი, გასაშვებად მზა: ჩვენთან Docker image production — „ცოცხალი“ გარემო, რომელსაც ნამდვილი მომხმარებლები იყენებენ ```
ტერმინები და პრინციპები

CI · Delivery · Deployment

🔁 Continuous Integration

ყოველი ცვლილება — build + test. ბევრი პატარა merge დღეში, და არა ერთი დიდი — თვეში

📦 Continuous Delivery

main ყოველთვის მზადაა გასაშვებად. production-ში გატანა — ღილაკით, ადამიანის გადაწყვეტილებით

🚀 Continuous Deployment

merge → production ავტომატურად, ადამიანის გარეშე. ჩვენ ამას ვაკეთებთ

🐜პატარა ცვლილებები — პრობლემა მალე ჩანს და ადვილად ბრუნდება
⚡სწრაფი პასუხი — შეცდომა წუთებში, და არა მომხმარებლისგან
🏗️ერთხელ აეწყობა — ერთი და იგივე artifact ყველგან
🤖ყველაფერი კოდით — pipeline Git-შია, როგორც აპი
### CI · Continuous Delivery · Continuous Deployment „CD“ ორ რამეს ნიშნავს, და ინტერვიუზე ამ განსხვავებას ხშირად კითხულობენ: | | რა ხდება ავტომატურად | ვინ წყვეტს production-ს | |---|---|---| | **Continuous Integration** | build + test ყოველ ცვლილებაზე | — | | **Continuous Delivery** | build, test და artifact; `main` ყოველთვის გასაშვებად მზადაა | **ადამიანი** — ღილაკით (მაგ. ბანკები, სადაც გამოშვებას ამოწმებენ) | | **Continuous Deployment** | ყველაფერი, production-ის ჩათვლით | **pipeline** — merge-ის შემდეგ თვითონ | ჩვენ LMS-ისთვის **Continuous Deployment**-ს ვაკეთებთ: merge `main`-ში = ახალი ვერსია სერვერზე. **პრინციპები, რომლებზეც CI/CD დგას:** - 🐜 **პატარა, ხშირი ცვლილებები.** ერთდღიანი branch და პატარა PR. თვის განმავლობაში დაგროვილი დიდი merge — conflict-ები და „რომელმა ცვლილებამ გატეხა?“. - ⚡ **სწრაფი პასუხი.** შეცდომა უნდა გამოჩნდეს წუთებში, PR-ზე — და არა მაშინ, როცა მომხმარებელი მოგწერს. - 🏗️ **ერთხელ აეწყობა — ყველგან ერთი.** image ერთხელ იწყობა, და ზუსტად ის მიდის სერვერზე. სერვერზე ხელახლა აწყობა = რისკი, რომ სხვა რამ აეწყოს. - 🤖 **ყველაფერი კოდით.** pipeline YAML ფაილია რეპოში — მისი ცვლილებაც PR-ით და review-თი გადის. ```check ? რა განსხვავებაა Continuous Delivery-სა და Continuous Deployment-ს შორის? = Delivery: კოდი ყოველთვის მზადაა გასაშვებად, production-ში გატანას ადამიანი წყვეტს ღილაკით. Deployment: merge-ის შემდეგ production-ში ავტომატურად მიდის ```

## ნაწილი 2 · GitHub Actions და CI თეორია ვიცით. ახლა ვნახავთ, როგორ მუშაობს GitHub Actions ყველაზე მარტივ მაგალითზე, და მერე ვწერთ ნამდვილ CI-ს: ყოველ Pull Request-ზე LMS უნდა აეწყოს და ტესტები გაიაროს.
ცნებები

workflow · trigger · job · runner · step

workflowYAML ფაილი .github/workflows/-ში
ontrigger — როდის: push, pull_request, ხელით…
jobნაბიჯების ჯგუფი, რომელიც ერთ მანქანაზე სრულდება
runs-onrunner — GitHub-ის სუფთა ვირტუალური Ubuntu, ყოველ ჯერზე ახალი
stepsuses: მზა action · run: ბრძანება

🖥️ runner = ცარიელი Droplet

შენი კოდი იქ არ არის → პირველი ნაბიჯი ყოველთვის checkout. .NET არ არის → setup-dotnet

🧩 actions

მზა „ბლოკები“ Marketplace-იდან: owner/name@ვერსია — როგორც NuGet პაკეტი

### ცნებები: workflow · trigger · job · runner · step | ცნება | რა არის | |---|---| | **workflow** | YAML ფაილი რეპოს `.github/workflows/` საქაღალდეში | | **trigger** (`on:`) | **როდის** გაეშვას: `push`, `pull_request`, ხელით (`workflow_dispatch`), განრიგით | | **job** | ნაბიჯების ჯგუფი, რომელიც ერთ მანქანაზე სრულდება | | **runner** (`runs-on:`) | ეს მანქანა: GitHub-ის **ვირტუალური Ubuntu**, ყოველ გაშვებაზე ახალი და სუფთა | | **step** | ერთი ნაბიჯი: `uses:` — მზა action, `run:` — ბრძანება ტერმინალში | | **action** | მზა „ბლოკი“ (`actions/checkout@v4`) — `მფლობელი/სახელი@ვერსია`, როგორც NuGet პაკეტი | **runner = ცარიელი სერვერი.** მასზე შენი კოდი არ არის — ამიტომ პირველი ნაბიჯი ყოველთვის `actions/checkout` (რეპოს ჩამოტვირთვა). .NET SDK არ არის — `actions/setup-dotnet`. ეს ზუსტად ის, რასაც მე-6 ლექციაზე სერვერზე ხელით ვაკეთებდით, ოღონდ ყოველ ჯერზე ავტომატურად. ```note public რეპოებისთვის GitHub-ის runner-ები უფასოა; private-ისთვის — თვეში შეზღუდული წუთები. ```

YAML: მხოლოდ space (არა Tab) · - = სიის ელემენტი · შეწევა = ვის ეკუთვნის
### პირველი workflow — რა ხდება runner-ზე? სანამ LMS-ისთვის CI-ს დავწერთ, ვნახოთ, როგორ მუშაობს workflow ყველაზე მარტივ მაგალითზე. რეპოში ვქმნით ფაილს `.github/workflows/hello.yml`: ```yaml .github/workflows/hello.yml name: Hello on: push: workflow_dispatch: jobs: hello: runs-on: ubuntu-latest steps: - run: echo "გამარჯობა, $GITHUB_ACTOR" - run: uname -a && whoami - run: ls -la - uses: actions/checkout@v4 - run: ls -la ``` - `on: push` — ყოველ push-ზე ნებისმიერ branch-ში; `workflow_dispatch` — Actions ჩანართში ჩნდება ღილაკი **Run workflow**, ხელით გასაშვებად; - `run:` — ჩვეულებრივი Linux ბრძანება, ზუსტად ისე, როგორც Termius-ში; - პირველი `ls -la` **ცარიელს** აჩვენებს: runner ახალი, სუფთა მანქანაა, შენი კოდი მასზე ჯერ არ არის; - `actions/checkout@v4` რეპოს ჩამოტვირთავს — მეორე `ls -la` უკვე ფაილებს აჩვენებს. push → **Actions** ჩანართი → **Hello** → job **hello** → ყოველი step-ის ლოგი ცალკე იხსნება. ```warn YAML-ში შეწევა (indentation) მნიშვნელობას ცვლის — ის აჩვენებს, რა რას ეკუთვნის. მხოლოდ **space**-ები, Tab — არასოდეს. `-` სიის ელემენტია: ყოველი step `-`-ით იწყება. თუ workflow Actions-ში საერთოდ არ გამოჩნდა — ჯერ შეამოწმე, ფაილი ზუსტად `.github/workflows/`-შია და YAML სწორადაა შეწეული. ``` ```check ? რატომ აჩვენებს პირველი `ls -la` ცარიელ საქაღალდეს? = runner ყოველ გაშვებაზე ახალი, სუფთა ვირტუალური მანქანაა — შენი კოდი იქ `actions/checkout`-მდე არ არის ```

## შეჯამება · დღეს ვისწავლეთ - 🔁 **CI/CD** — pipeline: commit → build → test → artifact → deploy → production; ნებისმიერ ნაბიჯზე შეცდომა მას აჩერებს. CI — „კოდი სწორია?“, CD — „კოდი მომხმარებელთანაა?“. Continuous **Delivery** — production-ს ადამიანი წყვეტს ღილაკით; Continuous **Deployment** — merge-ის შემდეგ ავტომატურად. პრინციპები: პატარა ცვლილებები, სწრაფი პასუხი, ერთხელ აეწყობა, ყველაფერი კოდით. - ⚙️ **GitHub Actions** — `.github/workflows/*.yml`: trigger (`on`), job, runner (`runs-on: ubuntu-latest`), steps (`uses` / `run`). - 🖥️ **runner** — GitHub-ის სუფთა ვირტუალური Ubuntu, ყოველ გაშვებაზე ახალი: კოდი მხოლოდ `actions/checkout`-ის შემდეგ ჩნდება, .NET — `actions/setup-dotnet`-ის შემდეგ. - 🧪 **CI** — `ci.yml` ყოველ PR-ზე: checkout → setup-dotnet → restore → build → test. ჩავარდნისას: რომელი step → ლოგის ბოლო ხაზები → იგივე ბრძანება შენთან. - 🛡️ **branch protection** — `main`-ში პირდაპირ push აღარ შეიძლება, merge — მხოლოდ მწვანე CI-ით. **შემდეგ ლექციაზე:** CI ამოწმებს — მაგრამ სერვერზე განახლება ისევ ხელით ხდება.
