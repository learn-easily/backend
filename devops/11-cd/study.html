გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 10 — CI/CD — თეორია და CI პრაქტიკაში. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
CI და CD — რა განსხვავებაა?
CI (Continuous Integration) — ყოველი ცვლილების ავტომატური შემოწმება (build, ტესტები) main-ში შერწყმამდე. CD (Continuous Deployment) — main-ის ყოველი ცვლილების ავტომატური გაშვება სერვერზე
Continuous Delivery და Continuous Deployment — რა განსხვავებაა?
Delivery: main ყოველთვის მზადაა გასაშვებად, production-ში გატანას ადამიანი წყვეტს ღილაკით. Deployment: merge-ის შემდეგ ახალი ვერსია production-ში ავტომატურად მიდის — ჩვენ LMS-ისთვის ამას ვაკეთებთ
pipeline-ში ტესტი ჩავარდა. რა მოხდება შემდეგ ნაბიჯებზე?
pipeline ჩერდება: artifact (image) არ აეწყობა და deploy არ მოხდება — გატეხილი კოდი production-მდე ვერ მივა
uses: და run: — რა განსხვავებაა step-ში?
uses — მზა action-ის გამოყენება (მაგ. actions/checkout@v4), run — ბრძანება runner-ის ტერმინალში (მაგ. dotnet build)
workflow-ში პირველი ls -la ცარიელს აჩვენებს. რატომ?
runner ყოველ გაშვებაზე ახალი, სუფთა ვირტუალური Ubuntu-ა — შენი კოდი მასზე მხოლოდ actions/checkout-ის შემდეგ ჩნდება
რატომ არ ეყოფა CI-ს მხოლოდ dotnet build?
build ამოწმებს, რომ კოდი იკომპილირდება, მაგრამ არა — რომ სწორად მუშაობს. ამას dotnet test ამოწმებს: ჩავარდნილი ტესტი CI-ს წითლად აქცევს
PR-ზე CI წითელია, შენთან კი ყველაფერი მუშაობს. რას შეამოწმებ?
რომელ step-ზე ჩავარდა და მისი ლოგის ბოლო ხაზები; მერე — გარემოს განსხვავება: .NET-ის ვერსია, ფაილის სახელის დიდი/პატარა ასოები (runner Linux-ია), ფაილი, რომელიც .gitignore-შია
რას იძლევა branch protection main-ზე?
main-ში პირდაპირ push აღარ შეიძლება — მხოლოდ Pull Request-ით, და merge მხოლოდ მაშინ, როცა CI მწვანეა

დღის თემა

დღის თემა: CD — merge → LMS სერვერზე

სლაიდი 4

CI ყოველ PR-ს ამოწმებს — მაგრამ merge-ის შემდეგ სერვერზე განახლება ისევ ხელით ხდება: ssh → git pull → docker compose up --build, და image სერვერზე, 1 GB RAM-ზე იწყობა. დღეს ჯაჭვს ბოლომდე ვაგრძელებთ: merge-ის შემდეგ GitHub Actions image-ს ააწყობს, GHCR-ში შეინახავს და SSH-ით სერვერზე გაუშვებს. ხელით — არაფერი, და თუ ახალმა ვერსიამ რამე გატეხა, წამებში დავბრუნდებით წინაზე.

ლექციის ბოლოს შეძლებ:

  • CD-ის გეგმა: build GitHub-ზე, სერვერი მხოლოდ მზა image-ს იღებს
  • image-ის აწყობა და ატვირთვა GHCR-ში latest და commit-ის sha tag-ებით
  • GitHub Secrets და ცალკე deploy SSH გასაღები
  • deploy.yml: push main-ში → build → GHCR → SSH → compose pull + up -d
  • rollback წინა ვერსიაზე commit-ის sha-ით მონიშნული image-ით

1 · CD

ნაწილი 1 · CD — გეგმა და გასაღებები

სლაიდი 5

CI ყოველ PR-ს ამოწმებს. დღეს ჯაჭვს ვაგრძელებთ: merge-ის შემდეგ GitHub Actions image-ს ააწყობს, შეინახავს და სერვერზე თვითონ გაუშვებს.

პრობლემა: CI მწვანეა — deploy კი ისევ ხელით

სლაიდი 6

წინა ლექციის შემდეგ main-ში მხოლოდ შემოწმებული კოდი ხვდება. მაგრამ სერვერამდე ის ისევ ხელით მიდის:

merge-ის შემდეგ — ყოველ ჯერზე
# Termius → lms-server$ cd ~/lms$ git pull$ docker compose up -d --build
  • 😴 merge გააკეთე და სერვერზე შესვლა დაგავიწყდა — მომხმარებელი ძველ ვერსიას ხედავს;
  • 🐢 image სერვერზე იწყობა — 1 GB RAM-ზე ნელა, და ამ დროს საიტი მეხსიერებისთვის „ეჯიბრება“ build-ს;
  • 👥 გუნდში ხუთი ადამიანია — ყველას სერვერზე SSH წვდომა ჰქონდეს?

წინა ლექციის pipeline-ში CI-ის ნაწილი (build → test) უკვე მუშაობს. დღეს — მეორე ნაწილი, Continuous Deployment პრაქტიკაში: artifact (Docker image) → GHCR → deploy სერვერზე, ავტომატურად, merge-ის შემდეგ.

გეგმა: build — GitHub-ზე, სერვერი მხოლოდ იღებს

სლაიდი 7

მე-8 ლექციაში image-ს სერვერზე ვაწყობდით (up --build) — 1 GB RAM-ზე ნელა და რისკით. ახლა:

GitHub Actions runner-ზე:

  1. checkout — კოდი;
  2. docker build — იგივე Dockerfile, მე-7 ლექციიდან;
  3. push → GHCR (GitHub Container Registry) — image-ს ორი tag-ით ვინახავთ: latest და commit-ის sha (rollback-ისთვის);
  4. SSH-ით სერვერზე შესვლა.

სერვერზე (SSH-ით, ავტომატურად):

Termius · lms-server
$ cd ~/lms$ git pull                     # compose.yaml-ის ცვლილებებისთვის$ docker compose pull api      # ახალი image GHCR-იდან

სერვერი აღარაფერს აწყობს — მხოლოდ მზა image-ს იღებს. ეს უფრო სწრაფია, და რაც მთავარია: ზუსტად ის image, რომელიც აეწყო, მიდის სერვერზე.

📘 ტერმინები
GHCR
ghcr.io, GitHub-ის image-ების საცავი (registry) — როგორც Docker Hub, ოღონდ GitHub-ში
sha
commit-ის უნიკალური იდენტიფიკატორი (git log-ში ჩანს), image-ის tag-ად ვიყენებთ

ნაბიჯი 1 · deploy გასაღები და GitHub Secrets

სლაიდი 8

GitHub Actions-ს სერვერზე შესასვლელად SSH გასაღები სჭირდება. შენს გასაღებს არ ვაძლევთ — ვქმნით ცალკე, მხოლოდ ამ საქმისთვის:

WSL
$ ssh-keygen -t ed25519 -f ~/.ssh/github-deploy -N "" -C "github-actions-deploy"$ ssh-copy-id -i ~/.ssh/github-deploy.pub lms
  • -f — ფაილის სახელი, -N "" — passphrase-ის გარეშე (robot-ს მის აკრეფა არ შეუძლია);
  • ssh-copy-id — .pub-ს სერვერის ~/.ssh/authorized_keys-ში ამატებს.

რატომ ცალკე? თუ GitHub-ის secret ოდესმე გაჟონავს, საკმარისია ამ ერთი ხაზის წაშლა authorized_keys-იდან. შენი პირადი გასაღები და სხვა სერვერები ხელშეუხებელია.

GitHub Secrets — რეპოს Settings → Secrets and variables → Actions → New repository secret:

Secret მნიშვნელობა
SSH_HOST სერვერის IP
SSH_USER giorgi
SSH_KEY cat ~/.ssh/github-deploy-ის მთელი შიგთავსი, -----BEGIN-იდან -----END-ის ჩათვლით

workflow მათ ${{ secrets.SSH_KEY }}-ით კითხულობს. ლოგებში ისინი ***-ით იმალება, შენახვის შემდეგ კი GitHub მათ აღარავის აჩვენებს — მხოლოდ შეცვლა შეიძლება.

GITHUB_TOKEN — დროებითი ტოკენი, რომელსაც GitHub ყოველ workflow-ს თვითონ აძლევს. GHCR-ში image-ის ატვირთვას ის ეყოფა (თუ workflow-ში packages: write უფლებაა).

2 · deploy

ნაწილი 2 · deploy.yml — merge → live

სლაიდი 10

ნაბიჯი 2 · deploy.yml

სლაიდი 11
.github/workflows/deploy.yml
name: Deploy on:  push:    branches: [main] permissions:  contents: read  packages: write jobs:  deploy:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v4       - uses: docker/login-action@v3        with:          registry: ghcr.io          username: ${{ github.actor }}          password: ${{ secrets.GITHUB_TOKEN }}       - uses: docker/build-push-action@v6        with:          push: true          tags: |            ghcr.io/${{ github.repository }}:latest            ghcr.io/${{ github.repository }}:${{ github.sha }}       - uses: appleboy/ssh-action@v1        with:          host: ${{ secrets.SSH_HOST }}          username: ${{ secrets.SSH_USER }}          key: ${{ secrets.SSH_KEY }}          script: |            cd ~/lms            git pull            docker compose pull api            docker compose up -d
ნაწილი რას აკეთებს
on: push: branches: [main] ყოველ push-ზე main-ში — branch protection-ით ეს მხოლოდ merge-ია
permissions: packages: write GITHUB_TOKEN-ს GHCR-ში ჩაწერის უფლება
docker/login-action docker login ghcr.io
docker/build-push-action docker build + docker push — ორი tag-ით
appleboy/ssh-action SSH სერვერზე და script-ის ბრძანებები

${{ … }} — workflow-ის ცვლადები: github.repository = giorgi/lms, github.sha = commit-ის id, github.actor = ვინც გაუშვა.

⚠️

GHCR-ში image-ის სახელი მხოლოდ პატარა ასოებით შეიძლება. თუ რეპოს ჰქვია Giorgi/LMS, build-push ჩავარდება — გადაარქვი რეპოს სახელი პატარა ასოებით.

ნაბიჯი 3 · სერვერზე — ორი პატარა ცვლილება

სლაიდი 12

1. compose.yaml — api-ს ვუმატებთ image-ის სახელს:

compose.yaml — api
api:  build: .  image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest}  ...

როცა build და image ერთადაა: docker compose up --build (შენთან) ააწყობს და ამ სახელს დაარქმევს; docker compose pull (სერვერზე) კი GHCR-იდან ჩამოტვირთავს. ${IMAGE_TAG:-latest} — ნაგულისხმევად latest, rollback-ისთვის კი .env-იდან შეგვიძლია შევცვალოთ.

ეს ცვლილება commit → PR → merge — და deploy-ის git pull მას სერვერზე თვითონ მიიტანს.

2. GHCR-ში შესვლა სერვერზე — ერთხელ. GHCR-ის package ნაგულისხმევად private-ია, ამიტომ სერვერს წაკითხვის უფლება სჭირდება. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate, scope მხოლოდ read:packages:

Termius · lms-server
$ echo "ghp_xxxx" | docker login ghcr.io -u giorgi --password-stdin

--password-stdin — ტოკენი ბრძანებების ისტორიაში არ ჩაიწერება ისე, როგორც -p ghp_… ჩაიწერებოდა. Docker მას სერვერზე იმახსოვრებს.

💡

ტოკენი მინიმალური უფლებით (read:packages) — იგივე პრინციპი, რაც ცალკე deploy გასაღებისთვის და User=www-data-სთვის: ყველას — მხოლოდ ის, რაც სჭირდება.

ნაბიჯი 4 · პირველი ავტომატური deploy

სლაიდი 13

deploy.yml → commit → PR → CI ✅ → merge. Actions ჩანართში ჩაირთვება Deploy:

Actions → Deploy
✅ Set up job                          2s✅ Run actions/checkout@v4             1s✅ Run docker/login-action@v3          1s✅ Run docker/build-push-action@v6     1m 12s✅ Run appleboy/ssh-action@v1          14s

რამდენიმე წუთში https://api.giorgi.ge ახალ ვერსიას აჩვენებს — სერვერზე ხელით არაფერი გაგიშვია.

რა შეიცვალა გუნდისთვის:

  • deploy ყველასთვის ერთნაირია — merge main-ში. არავის სჭირდება სერვერზე SSH წვდომა;
  • ყოველი deploy ჩაწერილია Actions-ში: ვინ, როდის, რომელი commit, რა ლოგით;
  • ჩავარდა? — Actions-ში წითელი step, მისი ლოგი, და GitHub ელ-ფოსტითაც შეგატყობინებს.
👉

ნაბიჯი 5 · rollback

სლაიდი 14

ყოველი image GHCR-ში commit-ის sha-ითაცაა მონიშნული. ამიტომ წინა ვერსიაზე დაბრუნება = სხვა tag-ის გაშვება:

Termius · lms-server · ~/lms
$ git log --oneline -3a91c3f2 Add course capacity        ← გატეხა7be04d1 Fix grades pagination      ← მუშაობდა

GitHub-ზე commit-ის სრული sha (40 სიმბოლო) ჩანს commit-ის გვერდზე ან Actions-ის გაშვებაში:

Termius · lms-server · ~/lms
$ echo "IMAGE_TAG=7be04d1e5c..." >> .env$ docker compose up -d

compose.yaml-ში image: ghcr.io/giorgi/lms:${IMAGE_TAG:-latest} — ახლა ის ძველ ვერსიას იღებს. წამებში LMS ისევ მუშაობს, და მშვიდად ასწორებ შეცდომას — ჩვეულებრივ: branch → PR → CI → merge. მერე .env-იდან IMAGE_TAG შლი და up -d — ისევ latest.

⚠️

rollback კოდს აბრუნებს, ბაზას — არა. თუ ახალმა ვერსიამ მიგრაციით სქემა შეცვალა, ძველი კოდი შეიძლება ახალ სქემასთან ვერ იმუშაოს. ამიტომ რისკიანი მიგრაციების წინ — pg_dump backup (მე-8 ლექცია).
