ფინალი — მთელი სისტემა ახალ სერვერზე

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 11 — CD — merge → LMS სერვერზე. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
CI და CD — რა განსხვავებაა?
CI (Continuous Integration) — ყოველი ცვლილების ავტომატური შემოწმება (build, ტესტები) main-ში შერწყმამდე. CD (Continuous Deployment) — main-ის ყოველი ცვლილების ავტომატური გაშვება სერვერზე
SSH-ის პირადი გასაღები workflow-ს როგორ მივაწოდოთ?
GitHub Secrets-ში (Settings → Secrets and variables → Actions) — workflow მას ${{ secrets.SSH_KEY }}-ით კითხულობს, ლოგებში კი ის ***-ით იმალება. YAML-ში პირდაპირ — არასოდეს
რატომ ვიყენებთ deploy-ისთვის ცალკე SSH გასაღებს და არა საკუთარს?
თუ GitHub-ის secret გაჟონავს, საკმარისია ამ ერთი გასაღების წაშლა სერვერის authorized_keys-იდან — შენი პირადი გასაღები და სხვა სერვერები დაცული რჩება
რატომ ვაწყობთ image-ს GitHub Actions-ზე და არა სერვერზე?
სერვერს მცირე RAM აქვს და build საიტს ანელებს; Actions-ზე აწყობილი image GHCR-ში ინახება და სერვერი მხოლოდ მზას იღებს — სწრაფად, და ზუსტად იმას, რაც აეწყო
ახალმა ვერსიამ LMS გატეხა. როგორ დავბრუნდეთ წინაზე?
ყოველი image commit-ის sha-ითაცაა მონიშნული. სერვერის .env-ში IMAGE_TAG=<წინა sha> → docker compose up -d — წამებში ძველი ვერსია მუშაობს

საშინაოს განხილვა

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: შენი პროექტი — merge → live. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • კლასის დავალება — ბოლომდე, თქვენს პროექტზე: deploy გასაღები (ssh-keygen -f ~/.ssh/github-deploy) → .pub სერვერზე; Secrets: SSH_HOST, SSH_USER, SSH_KEY
  • deploy.yml: push main-ზე → GHCR (latest + sha) → SSH → compose pull api && up -d
  • სერვერზე: compose-ში image: ghcr.io/<user>/<repo>:${IMAGE_TAG:-latest}; ერთხელ docker login ghcr.io (PAT read:packages)
  • README: ცოცხალი ლინკები, CI badge, deploy-ის აღწერა

GHCR-ის image-ის სახელი პატარა ასოებით უნდა იყოს — თუ რეპოს სახელში დიდი ასოებია (Giorgi/LMS), გადაარქვით რეპოს სახელი პატარა ასოებით.

დღის თემა

დღის თემა: ფინალი — მთელი სისტემა ახალ სერვერზე

სლაიდი 4

API-ის კურსზე LMS-ს ფრონტიც დაეწერა — და ახლა მთელი სისტემა ერთად უნდა გავიდეს: ფრონტი, API და ბაზა. თან სერვერი შეიძლება გაფუჭდეს, ან უფრო ძლიერი დაგვჭირდეს. მე-6 ლექციაზე მხოლოდ API-ს ხელით გაშვებას მთელი ლექცია დასჭირდა. დღეს ფრონტს სისტემაში ვამატებთ და მთელ სისტემას, მონაცემებიანად, ახალ სერვერზე ვიტანთ — და ვნახავთ, რამდენად მარტივია ეს, როცა ყველაფერი ავტომატიზებულია.

ლექციის ბოლოს შეძლებ:

  • Angular ფრონტის multi-stage Dockerfile და Nginx კონტეინერში: try_files + /api proxy, CORS-ის გარეშე
  • ფრონტის დამატება Compose-სა და CD-ში — ორი image ერთი commit-იდან
  • ახალი სერვერის მომზადება cloud-init-ით
  • რა გადადის CD-ით და რა — ხელით: .env, ბაზის მონაცემები, DNS, სერტიფიკატი
  • სერვერის გამოცვლა: მონაცემები pg_dump | psql-ით → deploy → DNS → HTTPS → შემოწმება

1 · ფრონტი

ნაწილი 1 · ფრონტი სისტემაში

სლაიდი 5

API-ის კურსზე LMS-ს ფრონტიც დაეწერა. ახლა ის სისტემის ნაწილი უნდა გახდეს: იგივე Docker, იგივე Compose, იგივე CD — რომ მთელი სისტემა ერთად აეწყოს, ერთად გაეშვას და ერთად გადავიდეს ახალ სერვერზე.

პრობლემა: API — ავტომატურად, ფრონტი — ხელით?

სლაიდი 6

API უკვე სრულ გზას გადის: merge → CI → GHCR → სერვერი. ფრონტი კი, თუ მე-5 ლექციის გზით წავიდოდით, ხელით გავიდოდა: ng build → rsync → /var/www/app.

ორი პრობლემა:

  • API-ს მისამართი. თუ Angular-ის კოდში წერია https://api.giorgi.ge, ბრაუზერისთვის ეს სხვა დომენია (app. ≠ api.) — API-ს CORS სჭირდება, და ყოველ გარემოს (შენი ლეპტოპი, სერვერი) თავისი build.
  • ორი სხვადასხვა გზა. სერვერის გამოცვლისას ორივე ცალ-ცალკე უნდა გადავიტანოთ.

გამოსავალი: ფრონტსაც ვაქცევთ კონტეინერად. მის შიგნით — Nginx, რომელიც Angular-ის ფაილებს აძლევს, ხოლო /api/... მოთხოვნებს API-ის კონტეინერს გადასცემს. ბრაუზერისთვის ყველაფერი ერთ დომენზეა — CORS აღარ სჭირდება, და Angular-ში API-ის მისამართი უბრალოდ /api-ა, ნებისმიერ გარემოში.

ნაბიჯი 1 · web/Dockerfile — node აწყობს, nginx აძლევს

სლაიდი 7

ფრონტი რეპოს web/ საქაღალდეშია (API-ის გვერდით). მისი Dockerfile ორეტაპიანია — ზუსტად ისე, როგორც API-ის (მე-7 ლექცია): აწყობას ერთი გარემო სჭირდება, გაშვებას — სხვა, ბევრად პატარა.

web/Dockerfile
# 1 — აწყობა: Node + npmFROM node:24-alpine AS buildWORKDIR /appCOPY package*.json ./RUN npm ciCOPY . .RUN npm run build # 2 — გაშვება: მხოლოდ Nginx და მზა ფაილებიFROM nginx:alpineCOPY nginx.conf /etc/nginx/conf.d/default.confCOPY --from=build /app/dist/lms-web/browser /usr/share/nginx/html
  • npm ci — ზუსტად package-lock.json-ის ვერსიებს აყენებს (CI-სა და Docker-ისთვის ეს ჯობია npm install-ს);
  • dist/lms-web/browser — Angular-ის build-ის შედეგი; lms-web — პროექტის სახელი angular.json-დან;
  • საბოლოო image-ში Node არ არის — მხოლოდ Nginx და HTML/CSS/JS ფაილები.
web/nginx.conf
server {    listen 80;    root /usr/share/nginx/html;    index index.html;     location /api/ {        proxy_pass http://api:8080;        proxy_set_header Host $host;        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;        proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto;    }     location / {        try_files $uri $uri/ /index.html;    }}
  • location /api/ — /api/... მოთხოვნები API-ის კონტეინერს გადაეცემა. api — სერვისის სახელი Compose-ში (როგორც Host=db ბაზისთვის, მე-8 ლექცია), 8080 — port კონტეინერის შიგნით;
  • X-Forwarded-Proto — სერვერის Nginx-მა უკვე იცის, რომ მოთხოვნა HTTPS-ით მოვიდა; ამ ინფორმაციას API-მდე ვატარებთ (მე-9 ლექცია);
  • try_files … /index.html — SPA-ს refresh → 404 პრობლემა, მე-5 ლექციიდან.
⚠️

Angular-ში API-ის მისამართი ახლა ფარდობითია: /api/courses, არა https://api.giorgi.ge/api/courses. ასე ერთი და იგივე build ყველგან მუშაობს, და CORS არ გვჭირდება — ბრაუზერისთვის ფრონტიც და API-ც ერთ დომენზეა.

ნაბიჯი 2 · Compose + სერვერის Nginx

სლაიდი 8

compose.yaml-ში მესამე სერვისი ემატება:

compose.yaml — web
web:  build: ./web  image: ghcr.io/giorgi/lms-web:${IMAGE_TAG:-latest}  ports:    - "127.0.0.1:4000:80"  depends_on:    - api  restart: unless-stopped
  • build: ./web — Dockerfile web/ საქაღალდიდან (შენთან, up --build-ისთვის);
  • image — იგივე IMAGE_TAG, რაც API-ს: ორივე ერთი commit-იდან აეწყობა, და rollback-იც ორივეს ერთად აბრუნებს;
  • 127.0.0.1:4000 — როგორც API-ს 5000: ინტერნეტიდან პირდაპირ არ ჩანს, მხოლოდ სერვერის Nginx-ისთვის.

შენთან: docker compose up -d --build → http://localhost:4000 — ფრონტი იხსნება და /api/courses-ს API-დან იღებს.

სერვერის Nginx — app.giorgi.ge-ის server block-ში root /var/www/app და try_files იცვლება proxy_pass-ით:

sites-available/app
server {    server_name app.giorgi.ge;    location / {        proxy_pass http://127.0.0.1:4000;        proxy_set_header Host $host;        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;        proxy_set_header X-Forwarded-Proto $scheme;    }    # listen 443 ssl და ssl_certificate ხაზები — certbot-ისგან, უცვლელი}

sudo nginx -t && sudo systemctl reload nginx.

💡

ეს კონფიგი რეპოშიც ჩადე — deploy/nginx/lms.conf (app და api ბლოკები, certbot-ის ხაზების გარეშე). მეორე ნაწილში, ახალ სერვერზე, ის ხელახლა წერის ნაცვლად უბრალოდ დაკოპირდება.

ნაბიჯი 3 · deploy.yml — ორი image

სლაიდი 9

deploy.yml-ში სამი ცვლილებაა:

.github/workflows/deploy.yml (ცვლილებები)
on:  push:    branches: [main]  workflow_dispatch: # ... checkout და login — უცვლელი       - uses: docker/build-push-action@v6     # api — უცვლელი        with:          push: true          tags: |            ghcr.io/${{ github.repository }}:latest            ghcr.io/${{ github.repository }}:${{ github.sha }}       - uses: docker/build-push-action@v6     # web — ახალი        with:          context: ./web          push: true          tags: |            ghcr.io/${{ github.repository }}-web:latest            ghcr.io/${{ github.repository }}-web:${{ github.sha }}       - uses: appleboy/ssh-action@v1        with:          host: ${{ secrets.SSH_HOST }}          username: ${{ secrets.SSH_USER }}          key: ${{ secrets.SSH_KEY }}          script: |            cd ~/lms            git pull            docker compose pull api web            docker compose up -d
  1. workflow_dispatch — Actions-ში ჩნდება Run workflow ღილაკი. ახალ სერვერზე პირველი deploy-ისთვის დაგვჭირდება: ახალი commit არ გვექნება, deploy კი უნდა გაეშვას.
  2. მეორე build-push-action — context: ./web (Dockerfile და ფაილები web/-დან), image-ის სახელი …-web.
  3. docker compose pull api web — სერვერი ორივე ახალ image-ს იღებს.

root-ის .dockerignore-ში ემატება web/ და .github/ — API-ის build-ს ისინი არ სჭირდება, და build ასე უფრო სწრაფია.

merge → Actions: Deploy ✅ → https://app.giorgi.ge — ფრონტი, რომელიც API-დან მონაცემებს იღებს. ამიერიდან მთელი სისტემა ერთი გზით გადის.

⚠️

სერვერზე ერთხელ შეამოწმე, რომ GHCR-ის read:packages ტოკენი ახალ lms-web package-საც კითხულობს (docker compose pull web). ტოკენი მომხმარებლის ყველა package-ზე მოქმედებს, ამიტომ ჩვეულებრივ დამატებით არაფერი სჭირდება.

2 · ახალი სერვერი

ნაწილი 2 · ახალი სერვერი

სლაიდი 11

სერვერი შეიძლება გაფუჭდეს, ან LMS-ს მეტი მომხმარებელი ჰყავდეს და 1 GB RAM აღარ ეყოს. მე-6 ლექციაზე მხოლოდ API-ს ხელით გაშვებას მთელი ლექცია დასჭირდა. დღეს მთელ სისტემას — ფრონტს, API-ს და ბაზას მონაცემებით — ახალ სერვერზე ვიტანთ და ვნახავთ, რას გვაძლევს ყველაფერი, რაც კურსზე ავაწყეთ.

გეგმა: კოდი თვითონ მიდის — მდგომარეობა კი არა

სლაიდი 12

სერვერის გამოცვლისას ყველაფერი ორ ჯგუფად იყოფა:

✅ Git-შია და GHCR-ში — CD წაიღებს ✋ Git-ში არ არის — ჩვენ გადაგვაქვს
კოდი, Dockerfile-ები, compose.yaml სერვერის მომზადება (user, firewall, Docker, Nginx)
workflow-ები, Nginx-ის კონფიგი (deploy/nginx/) .env — საიდუმლოებები (Git-ში არასოდეს!)
image-ები GHCR-ში ბაზის მონაცემები
DNS ჩანაწერები და HTTPS სერტიფიკატი

რაც Git-შია, ის ახალ სერვერზე CD-ით თვითონ მიდის. დანარჩენი — მდგომარეობაა (state): ის სერვერზე ცხოვრობს და მასთან ერთად ქრება. ამიტომ მას ცალკე, ფრთხილად ვიტანთ.

გეგმა:

  1. ახალი Droplet — cloud-init-ით, რომ შექმნისთანავე მზად იყოს;
  2. მომზადება: git clone, .env, GHCR login, Nginx-ის კონფიგი;
  3. მონაცემები: ძველი ბაზა → ახალი;
  4. deploy: GitHub-ში SSH_HOST → ახალი IP → Deploy;
  5. DNS → ახალი IP, მერე HTTPS;
  6. შემოწმება → ძველი სერვერის წაშლა.
👉

DNS-ის ჩანაწერის TTL წინა დღეს ჩამოწიე 300 წამამდე. თორემ ბრაუზერები და პროვაიდერები ძველ IP-ს საათობით დაიმახსოვრებენ, და გადასვლა ლექციაზე ვერ დასრულდება.

ნაბიჯი 1 · Droplet + cloud-init

სლაიდი 13

მე-4 ლექციაზე სერვერს ხელით ვამზადებდით: user, გასაღები, sshd, ufw, swap. მე-8-ზე — Docker. ახლა ყველაფერს ერთ ფაილში ვწერთ, და Droplet შექმნისთანავე თვითონ ასრულებს.

cloud-init — სტანდარტი, რომლითაც ღრუბლოვანი სერვერი პირველ ჩართვაზე თავისით მზადდება. DigitalOcean-ზე: Create Droplet → Ubuntu 24.04 → SSH key → Advanced Options → Add Initialization scripts → ჩასვი ფაილი:

cloud-init.yaml
#cloud-configusers:  - name: giorgi    groups: sudo    shell: /bin/bash    sudo: "ALL=(ALL) NOPASSWD:ALL"    ssh_authorized_keys:      - ssh-ed25519 AAAA... giorgi@laptop      - ssh-ed25519 AAAA... github-actions-deploypackage_update: truepackages: [nginx, certbot, python3-certbot-nginx]runcmd:  - curl -fsSL https://get.docker.com | sh  - usermod -aG docker giorgi  - fallocate -l 2G /swapfile && chmod 600 /swapfile  - mkswap /swapfile && swapon /swapfile  - echo '/swapfile none swap sw 0 0' >> /etc/fstab  - sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config  - systemctl restart ssh  - ufw allow OpenSSH && ufw allow 'Nginx Full' && ufw --force enable
ნაწილი რას აკეთებს ხელით — სად
users user, sudo, ორი საჯარო გასაღები მე-4 ლექცია
packages Nginx და certbot მე-5 და მე-9
runcmd Docker, swap, root-ის აკრძალვა, firewall მე-4 და მე-8
  • ssh_authorized_keys — შენი გასაღების .pub (cat ~/.ssh/id_ed25519.pub) და deploy გასაღების .pub (cat ~/.ssh/github-deploy.pub). ასე GitHub Actions ახალ სერვერზეც შევა, და SSH_KEY secret-ის შეცვლა არ მოგვიწევს;
  • NOPASSWD — user-ს პაროლი არ აქვს (შესვლა მხოლოდ გასაღებით), ამიტომ sudo პაროლს არ ითხოვს.

რამდენიმე წუთში: Termius-ში ახალი host lms-new (ახალი IP, user giorgi) და WSL-ის ~/.ssh/config-ში Host lms-new:

Termius · lms-new
$ cloud-init status --waitstatus: done
⚠️

runcmd ერთხელ, პირველ ჩართვაზე სრულდება. თუ რამე ჩავარდა, ლოგი აქაა: sudo tail -50 /var/log/cloud-init-output.log.

ნაბიჯი 2 · მომზადება: რეპო · .env · GHCR · Nginx

სლაიდი 14

ყველაფერი ნაცნობია — ოღონდ ახლა ხუთ წუთში:

Termius · lms-new
$ git clone https://github.com/giorgi/lms.git ~/lms $ echo "ghp_xxxx" | docker login ghcr.io -u giorgi --password-stdinLogin Succeeded $ sudo cp ~/lms/deploy/nginx/lms.conf /etc/nginx/sites-available/lms$ sudo ln -s /etc/nginx/sites-available/lms /etc/nginx/sites-enabled/$ sudo rm /etc/nginx/sites-enabled/default
  • git clone — compose.yaml და Nginx-ის კონფიგი. თუ რეპო private-ია, clone-ს ტოკენი სჭირდება — იგივე PAT-ით, repo უფლებით;
  • docker login ghcr.io — PAT read:packages-ით (მე-11 ლექცია); შეგიძლია ძველი გამოიყენო;
  • Nginx-ის კონფიგი რეპოდან მოდის (deploy/nginx/lms.conf) — ხელით აღარ ვწერთ. HTTPS-ის ხაზებს certbot მოგვიანებით თვითონ დაამატებს.

.env — Git-ში არ არის, ამიტომ ძველი სერვერიდან პირდაპირ გადმოგვაქვს:

WSL
$ scp -3 lms:~/lms/.env lms-new:~/lms/.env

scp -3 ფაილს ორ სერვერს შორის შენი კომპიუტერის გავლით აკოპირებს — სერვერებს ერთმანეთის გასაღებები არ სჭირდებათ.

⚠️

.env იგივე უნდა იყოს. ბაზა ძველი DB_PASSWORD-ით გადმოვა, ხოლო ახალი JWT გასაღებით ყველა ძველი ტოკენი გაუქმდებოდა — ყველა მომხმარებელი სისტემიდან გამოვიდოდა.

ნაბიჯი 3 · მონაცემები: ბაზა ძველიდან ახალში

სლაიდი 15

pg_dump და აღდგენა მე-8 ლექციიდან ვიცით. ახლა ორ სერვერს შორის ვაკეთებთ — pipe-ით, ფაილის გარეშე:

WSL
# 1 — ძველზე: API-ს და ფრონტს ვაჩერებთ, ბაზა მუშაობს$ ssh lms "cd ~/lms && docker compose stop web api" # 2 — ახალზე: ჯერ მხოლოდ ბაზა$ ssh lms-new "cd ~/lms && docker compose up -d db" # 3 — pg_dump ძველზე → psql ახალზე$ ssh lms "cd ~/lms && docker compose exec -T db pg_dump -U lms lms" \
  • | (pipe) — პირველი ბრძანების გამოსავალი მეორის შესავალი ხდება. pg_dump-ის SQL ძველი სერვერიდან პირდაპირ ახალი სერვერის psql-ში მიედინება;
  • -T — exec ტერმინალის გარეშე: pipe-ისთვის აუცილებელია;
  • შემოწმება — ცხრილში ჩანაწერების რაოდენობა ორივე სერვერზე ერთნაირი უნდა იყოს.

რატომ ჩერდება API ძველზე? თუ გადატანის დროს ვინმე ახალ კურსს შექმნის, ის ძველ ბაზაში ჩაიწერება და ახალში ვეღარ მოხვდება. რამდენიმე წუთი LMS მიუწვდომელია — ეს დაგეგმილი გაჩერებაა (maintenance). რეალურ პროექტებში მას წინასწარ აცხადებენ და ღამით აკეთებენ.

⚠️

თანმიმდევრობა მნიშვნელოვანია: ჯერ მონაცემები, მერე API. API ჩართვისას მიგრაციებს თვითონ უშვებს (მე-8 ლექცია) — ცარიელ ბაზაზე ის ცარიელ ცხრილებს შექმნიდა, და აღდგენა კონფლიქტით ჩავარდებოდა. თუ ასე მოხდა: docker compose down -v ახალზე (მხოლოდ ახალზე! -v volume-ს შლის) და ნაბიჯი 2-დან თავიდან.

ნაბიჯი 4 · deploy: ერთი secret — და CD აკეთებს დანარჩენს

სლაიდი 16
  1. GitHub → რეპო → Settings → Secrets and variables → Actions → SSH_HOST → ახალი IP. SSH_USER და SSH_KEY არ იცვლება — user იგივეა, deploy გასაღები კი cloud-init-მა უკვე დაამატა.
  2. Actions → Deploy → Run workflow (workflow_dispatch, ნაწილი 1).

Deploy იგივე ნაბიჯებს გადის, ოღონდ ახლა ახალ სერვერზე: image-ები → GHCR → SSH → git pull, compose pull api web, up -d.

Termius · lms-new
$ docker compose pslms-db-1   Up (healthy)lms-api-1  Up

API ჩაირთო, ბაზაში უკვე ყველა ცხრილი და მონაცემია — მიგრაციებს გასაშვები არაფერი აქვს.

👉

DNS ჯერ ძველ IP-ზეა. ახალი სერვერის შემოწმება DNS-ის შეცვლამდეც შეიძლება: curl --resolve api.giorgi.ge:80:167.71.40.8 http://api.giorgi.ge/api/courses — curl სახელს მითითებულ IP-ზე გაგზავნის, DNS-ის კითხვის გარეშე.

ნაბიჯი 5 · DNS + HTTPS

სლაიდი 17

DNS (მე-9 ლექცია): დომენის პანელში app და api A-ჩანაწერებს ახალ IP-ს ვუწერთ (თუ portfolio-ც ამ სერვერზე იყო — @ და www-საც).

WSL
$ dig +short app.giorgi.ge

TTL-ის წყალობით (წინა დღეს 300 წამზე ჩამოვწიეთ), რამდენიმე წუთში ყველა ახალ IP-ს ხედავს.

HTTPS — სერტიფიკატი ძველ სერვერზე დარჩა, ახალზე თავიდან ვიღებთ:

Termius · lms-new

certbot რეპოდან მოსულ Nginx-ის კონფიგს listen 443 ssl ხაზებს და HTTP → HTTPS redirect-ს თვითონ დაუმატებს — ზუსტად ისე, როგორც მე-9 ლექციაზე.

⚠️

certbot გაუშვი მხოლოდ მას შემდეგ, რაც dig ახალ IP-ს აჩვენებს. Let's Encrypt ამოწმებს, რომ დომენი ნამდვილად ამ სერვერზე მიდის — თუ DNS ჯერ ძველზეა, შემოწმება ჩავარდება.

💡

Let's Encrypt-ს ლიმიტები აქვს: ერთი და იგივე დომენების ნაკრებზე კვირაში მხოლოდ რამდენიმე სერტიფიკატი. თუ გადასვლას წინასწარ ცდი, გამოიყენე --test-cert — სატესტო სერტიფიკატი, რომელიც ლიმიტს არ ხარჯავს (ბრაუზერი მას არ ენდობა). ნამდვილზე — ბრძანება --test-cert-ის გარეშე.

ნაბიჯი 6 · შემოწმება → მერე ძველის წაშლა

სლაიდი 18

ძველ სერვერს მანამდე არ ვშლით, სანამ ახალზე ყველაფერი არ შევამოწმეთ:

  • ☐ https://app.giorgi.ge 🔒 იხსნება; შიდა გვერდზე refresh — არა 404;
  • ☐ ძველი მონაცემები ჩანს — კურსები, სტუდენტები, ყველაფერი, რაც გადატანამდე იყო;
  • ☐ შესვლა მუშაობს, და ვინც უკვე შესული იყო, სისტემიდან არ გამოაგდო (იგივე JWT გასაღები .env-ში);
  • ☐ CD: პატარა PR → merge → Deploy → ცვლილება ახალ სერვერზე ჩანს;
  • ☐ sudo certbot renew --dry-run — სერტიფიკატი 90 დღეში თვითონ განახლდება.

ყველაფერი ✓? ძველი Droplet რამდენიმე დღე გამორთული დატოვე (Power Off) — თუ რამე გამოგრჩა, მონაცემები ჯერ კიდევ იქაა. მერე — Destroy: გამორთული Droplet-იც ფასიანია (მე-4 ლექცია).

Termius-ში ძველი host წაშალე, ხოლო lms-new გადაარქვი lms-ად — და WSL-ის ~/.ssh/config-შიც.

შედარება: მე-6 ლექცია vs დღეს

სლაიდი 19
მე-6 ლექცია — ხელით დღეს
სერვერის მომზადება user, sshd, ufw, swap, runtime — ბრძანება-ბრძანება cloud-init — Droplet-თან ერთად
აპის გაშვება publish, rsync, systemd, მიგრაციები SSH_HOST + Run workflow
რა გავიდა მხოლოდ API ფრონტი + API + ბაზა მონაცემებით
დრო მთელი ლექცია ~20 წუთი, უმეტესად ლოდინი

ეს არის ავტომატიზაციის მთავარი სარგებელი: სერვერი ადვილად შესაცვლელი ხდება. ის აღარ არის „ძვირფასი“ კომპიუტერი, რომელსაც ხელით ააწყობ და ეშინია, რომ გაფუჭდება — ნებისმიერ დროს შეგიძლია ახალი აიღო.

ხელით რაც დარჩა — Droplet-ის შექმნა, DNS, .env და მონაცემები — ისიც ავტომატიზდება: Terraform (სერვერი და DNS კოდით), Ansible (სერვერის მომზადება), managed ბაზები (მონაცემები სერვერისგან ცალკე). ეს უკვე შემდეგი დონეა — DevOps-ის რუკაზე.

ნაწილი 3 · კურსის ფინალი

სლაიდი 20

გავლილი გზა: ლეპტოპიდან — ადვილად შესაცვლელ სერვერამდე

სლაიდი 21
ლექცია თემა რა შეგიძლია ახლა

დავალება · web/Dockerfile + nginx.conf + Compose

ნაბიჯები

  • ფრონტი რეპოს web/ საქაღალდეში; Angular-ში API-ის მისამართი — ფარდობითი: /api
  • web/Dockerfile: node:24-alpine → npm ci → npm run build → nginx:alpine + dist/<project>/browser
  • web/nginx.conf: location /api/ → proxy_pass http://api:8080; და location / → try_files $uri $uri/ /index.html;
  • compose.yaml-ში web სერვისი (build: ./web, 127.0.0.1:4000:80); root-ის .dockerignore-ში web/
  • შენთან: docker compose up -d --build → http://localhost:4000

✓ მზადაა, როცა

localhost:4000-ზე ფრონტი იხსნება, მონაცემებს API-დან იღებს, შიდა გვერდზე refresh → არა 404, ხოლო DevTools → Network-ში მოთხოვნები მიდის localhost:4000/api/...-ზე (CORS-ის შეცდომის გარეშე)

⭐ ბონუსი

  • deploy.yml-ში მეორე build-push-action (context: ./web) და docker compose pull api web → PR → merge → https://app.<domain>

💡 მინიშნება

build-ის საქაღალდის სახელი ნახეთ angular.json-ში: projects.<სახელი>.architect.build.options.outputPath. თუ COPY --from=build ჩავარდა not found-ით — გზა არასწორია.
