ჰოსტინგის საფუძვლები და Git/GitHub

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

დღის თემა: ჰოსტინგის საფუძვლები და Git/GitHub

სლაიდი 1

შენი საიტი ახლა მხოლოდ შენს ლეპტოპზე ცხოვრობს — localhost-ის ლინკს მეგობარი ვერ გახსნის. ამ კურსში ვისწავლით, როგორ მივიყვანოთ კოდი ლეპტოპიდან ყველა მომხმარებლამდე: GitHub → სერვერი → ინტერნეტი. დღეს ორ საფუძველს ვყრით: რა არის ჰოსტინგი და ვებ-სერვერი, და Git/GitHub — საიდანაც ყოველი თანამედროვე დეპლოიმენტი იწყება.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რა ხდება მისამართის აკრეფიდან გვერდის გამოჩენამდე
  • ჰოსტინგის ტიპების გარჩევა: Shared, VPS, PaaS, სტატიკური
  • Git-ის ციკლი: add → commit → branch → merge
  • პროექტის ატვირთვა GitHub-ზე, .gitignore-ით

ნაწილი 1 · სად „ცხოვრობს“ საიტი?

სლაიდი 5

ჰოსტინგი, სერვერი და ვებ-სერვერი. სანამ წაიკითხავ — სცადე, საკუთარი სიტყვებით თქვა: სად არის ფიზიკურად ის საიტი, რომელსაც ახლა ხსნი?

პრობლემა: „გახსენი, ჩემი საიტია!“

სლაიდი 6

Angular-ის პროექტი გაუშვი (ng serve), ბრაუზერში localhost:4200 ლამაზად იხსნება. ლინკი მეგობარს მესენჯერით გაუგზავნე — მასთან კი: This site can't be reached.

რატომ? localhost ნიშნავს „ეს კომპიუტერი“. შენთან ეს შენი ლეპტოპია, მეგობართან — მისი ტელეფონი. მისი ტელეფონი შენს საიტს საკუთარ თავში ეძებს, და, ბუნებრივია, ვერ პოულობს.

📘 ტერმინები
localhost
მისამართი, რომელიც ყოველთვის იმავე მოწყობილობას ნიშნავს, რომელზეც ბრაუზერი მუშაობს (IP: 127.0.0.1)

რა სჭირდება კომპიუტერს, რომ საიტი ყველამ გახსნას?

სლაიდი 7

თეორიულად შენი ლეპტოპიც გამოდგება, პრაქტიკულად — არა:

  • 🔌 24/7 ჩართული — ლეპტოპს ღამით თიშავ, საიტიც ითიშება.
  • 🌍 საჯარო IP მისამართი — სახლის როუტერს ინტერნეტში ერთი IP აქვს, ის ხშირად იცვლება და შიგნით მყოფი მოწყობილობები გარედან პირდაპირ არ ჩანს.
  • 🚀 სწრაფი, სტაბილური ქსელი — ათასი სტუმარი ერთად სახლის ინტერნეტს გადატვირთავს.
  • 🛡️ დაცვა — ინტერნეტიდან ნებისმიერს შეუძლია შენს კომპიუტერზე „დააკაკუნოს“.

ასეთ კომპიუტერს სერვერი ჰქვია. საკუთარს, როგორც წესი, არ ვყიდულობთ — ვქირაობთ. სწორედ ეს არის ჰოსტინგი.

სერვერი · დატა-ცენტრი · ჰოსტინგი

სლაიდი 8
  • 🖥️ სერვერი — ჩვეულებრივი კომპიუტერი: პროცესორი, მეხსიერება, დისკი. ოღონდ ეკრანი და კლავიატურა არ აქვს, უფრო მძლავრია და არასოდეს ითიშება. სერვერების აბსოლუტური უმრავლესობა Linux-ზე მუშაობს — ამიტომ მე-4 ლექციაზე Linux-ს ვსწავლობთ.
  • 🏢 დატა-ცენტრი — შენობა ათასობით სერვერით: სარეზერვო ელექტროენერგია, გაგრილება, ძალიან სწრაფი ინტერნეტი, ფიზიკური დაცვა.
  • 🏠 ჰოსტინგი — სერვისი: კომპანია გაქირავებს სერვერს ან მის ნაწილს, სადაც შენი საიტი „იცხოვრებს“.

ჰოსტინგის პროვაიდერები: DigitalOcean (ამ კურსის მთავარი), AWS, Azure, Google Cloud, Hetzner; სტატიკური საიტებისთვის — GitHub Pages (მე-2 ლექცია), Cloudflare.

რა ხდება, როცა აკრეფ myportfolio.ge?

სლაიდი 9
  1. DNS — ბრაუზერმა სახელი იცის, მაგრამ ინტერნეტში კომპიუტრები IP მისამართით პოულობენ ერთმანეთს. DNS „სატელეფონო წიგნია“: myportfolio.ge → 164.90.12.34.
  2. მოთხოვნა — ბრაუზერი ამ IP-ზე აგზავნის HTTP მოთხოვნას: GET /.
  3. ვებ-სერვერი — სერვერზე მომუშავე პროგრამა (მაგ. Nginx) იღებს მოთხოვნას და პოულობს შესაბამის ფაილს.
  4. პასუხი — 200 OK და HTML-ის შიგთავსი.
  5. დამატებითი მოთხოვნები — ბრაუზერი HTML-ში ხედავს style.css-ს, app.js-ს, სურათებს და თითოეულს ცალკე ითხოვს. ერთი გვერდი = ათობით მოთხოვნა.
💡

DNS-ს და დომენებს მე-2 და მე-5 ლექციებზე დეტალურად გავივლით (Cloudflare), ვებ-სერვერ Nginx-ს — მე-5-ზე. დღეს მთავარია სურათი: სახელი → IP → სერვერი → ვებ-სერვერი → ფაილი → პასუხი.

ვებ-სერვერი — პროგრამა, რომელიც კარზე დგას

სლაიდი 10

ერთ სერვერზე ბევრი პროგრამა მუშაობს: ვებ-სერვერი, ბაზა, SSH... როგორ ხვდება მოთხოვნა სწორ პროგრამამდე?

  • IP = შენობის მისამართი, პორტი = ბინის ნომერი. ყოველი პროგრამა თავის პორტს „უსმენს“.
  • სტანდარტული პორტები: 80 — HTTP, 443 — HTTPS, 22 — SSH (სერვერის მართვა, მე-4 ლექცია), 5432 — PostgreSQL.

ვებ-სერვერი არის პროგრამა, რომელიც 80/443 პორტს უსმენს, იღებს HTTP მოთხოვნას და პასუხს აბრუნებს. ორი მთავარი საქმე აქვს:

  1. ფაილების გაცემა — GET /about.html → დისკზე პოულობს /var/www/site/about.html-ს და აბრუნებს.
  2. მოთხოვნის გადაცემა აპლიკაციისთვის (reverse proxy) — GET /api/products → გადასცემს სერვერზე გაშვებულ ASP.NET აპს და მის პასუხს უკან აბრუნებს. ამას მე-9 ლექციაზე ავაწყობთ.

პოპულარული ვებ-სერვერები: Nginx (ამ კურსში ვიყენებთ), Apache, IIS (Windows), Caddy.

რეპოზიტორია (repository, „რეპო“) — ჩვეულებრივი საქაღალდე, რომელშიც Git-მა ისტორიის შენახვა დაიწყო.

plain

⚠️

.git საქაღალდეს ხელით არ ვეხებით. თუ წაშლი — საქაღალდე ჩვეულებრივ საქაღალდედ იქცევა და მთელი ისტორია ქრება.

ცნება 3 · Commit — ისტორიის ერთი ფოტო

სლაიდი 24

Commit — პროექტის შენახული მდგომარეობა. ყოველ commit-ს აქვს:

  • hash — უნიკალური იდენტიფიკატორი, მაგ. a3f9c21 (სრულად 40 სიმბოლოა, ჩვეულებრივ პირველ 7-ს ვიყენებთ);
  • ავტორი და თარიღი;
  • მესიჯი — რა გაკეთდა;
  • მშობელი — წინა commit-ის hash. ასე იქმნება ისტორიის ჯაჭვი.

კარგი მესიჯი მომავალი შენთვის იწერება — ექვსი თვის შემდეგ უნდა მიხვდე, რა გააკეთე:

✓ კარგი ✗ ცუდი
Add contact section fix
Fix broken link on projects page asdfgh
Update profile photo ცვლილებები

წესი: რა გააკეთე, ბრძანებითი ფორმით, მოკლედ: „Add…“, „Fix…“, „Update…“, „Remove…“.

👉

ერთი commit = ერთი აზრი. „დავამატე კონტაქტები და შევცვალე ფერები და გავასწორე ბმული“ — ეს სამი commit-ია.

ისტორია = commit-ების ჯაჭვი

სლაიდი 25

ყოველი commit წინას „იცნობს“ (მშობლის hash-ით) — ასე იქმნება ჯაჭვი:

Git Bash
$ git log --onelinea3f9c21 (HEAD -> main) Add contact sectionc41a8e0 Add styles

ზემოდან ქვემოთ — ახლიდან ძველისკენ.

  • main — მთავარი branch (შტო). ის უბრალოდ მიმთითებელია ბოლო commit-ზე და ახალ commit-თან ერთად წინ მიიწევს.
  • HEAD — „სად ვარ ახლა“: რომელ branch-ზე ან commit-ზე ვდგავართ.
💡

ძველ პროექტებში მთავარ branch-ს master ჰქვია. დღეს სტანდარტია main — GitHub-იც ასე ქმნის.

ცნება 4 · Branch (შტო)

სლაიდი 26

პრობლემა: საიტი მუშაობს და სერვერზე დევს. გინდა ახალი სექცია დაამატო, მაგრამ ამას 2 დღე სჭირდება — ამ ხნის განმავლობაში main ნახევრად დაწერილი კოდით უნდა იყოს? და თუ ამასობაში main-ზე სასწრაფო შესწორება დაგჭირდა?

Branch — ისტორიის პარალელური ხაზი. ის მიმდინარე commit-იდან იწყება და main-ს არ ეხება.

  • 🌿 იზოლაცია — main სტაბილური რჩება, ახალ ფიჩაზე branch-ში მუშაობ.
  • 🧪 ექსპერიმენტი — არ გამოვიდა? branch-ს წაშლი, main-ს არაფერი მოსვლია.
  • 👥 გუნდი — ყველა თავის branch-ზე მუშაობს და ერთმანეთს ხელს არ უშლის.
bash
git branch                       # რა branch-ები მაქვსgit switch -c feature/contacts   # ახალი branch + გადასვლაgit switch main                  # main-ზე დაბრუნება
👉

სახელი — feature/... ახალი ფუნქციონალისთვის, fix/... შესწორებისთვის. ასე ერთი შეხედვით ჩანს, რას ეხება branch-ი.
