რა არის DevOps

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

დღის თემა

დღის თემა: რა არის DevOps

სლაიდი 1

შენი საიტი ახლა მხოლოდ შენს ლეპტოპზე ცხოვრობს — localhost-ის ლინკს მეგობარი ვერ გახსნის. სანამ ინსტრუმენტებს ვისწავლით, უნდა გესმოდეს მთლიანი სურათი: რა არის DevOps, რატომ გაჩნდა, რას აკეთებს DevOps ინჟინერი დღის განმავლობაში, რას ისწავლი ამ კურსში — და სად ცხოვრობს კოდი, როცა ინტერნეტში გადის.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რა არის DevOps და რატომ გაჩნდა
  • DevOps ციკლის და DevOps ინჟინრის ყოველდღიური საქმეების აღწერა
  • DevOps-ის ხელსაწყოების ჯგუფების გარჩევა — რა არის ამ კურსში და რა შემდეგი ნაბიჯი
  • ახსნა, სად ცხოვრობს საიტი: სერვერი, DNS, ჰოსტინგის სახეები

რა არის DevOps?

სლაიდი 3

რატომ არსებობს DevOps

წარმოიდგინე ორი გუნდი:

  • 👩‍💻 Dev (Development) — დეველოპერები. წერენ კოდს და მათ ლეპტოპზე ყველაფერი მუშაობს.
  • 🛠️ Ops (Operations) — ადმინისტრატორები. მართავენ სერვერებს, სადაც საიტი რეალურად ცხოვრობს.

ძველად მათ შორის კედელი იდგა: დეველოპერი კოდს „კედელს იქით გადააგდებდა“, ადმინისტრატორი კი ცდილობდა, ის სერვერზე როგორმე გაეშვა. შედეგი:

  • 🐢 ახალი ვერსია თვეში ერთხელ გამოდიოდა — ხელით და შიშით.
  • 🔥 რამე თუ გაფუჭდა, იწყებოდა: „ჩემთან მუშაობს!“ — „სერვერზე არ მუშაობს!“
  • 🌙 სერვერი ღამით ჩავარდებოდა და დილამდე ამას ვერავინ ამჩნევდა.

DevOps = Dev + Ops. კედელი ქრება: კოდი დეველოპერის ლეპტოპიდან მომხმარებლამდე ერთი, ავტომატური გზით მიდის, და ამ გზას ერთი გუნდი აკონტროლებს.

როგორ გაჩნდა DevOps?

სლაიდი 4
  • 2000-იანები — ორი ცალკე გუნდი. დეველოპერები (Dev) კოდს წერდნენ, ადმინისტრატორები (Ops) კი მას სერვერზე უშვებდნენ. ახალი ვერსია თვეში ან კვარტალშიც კი ერთხელ გამოდიოდა, და ყოველი გაშვება დიდი, საშიში მოვლენა იყო.
  • 2009 · Flickr. Velocity კონფერენციაზე Flickr-ის ორმა ხელმძღვანელმა — John Allspaw (Ops) და Paul Hammond (Dev) — აჩვენეს მოხსენება „10+ Deploys Per Day: Dev and Ops Cooperation at Flickr“: Dev და Ops ერთად მუშაობენ, ყველაფერი ავტომატიზებულია, და საიტი დღეში 10-ჯერ და მეტჯერ ახლდება.
  • 2009 · ბელგია. Patrick Debois-მ ამ მოხსენებით შთაგონებულმა საკუთარი კონფერენცია მოაწყო — DevOpsDays. სიტყვა „DevOps“ აქედან გავრცელდა.
  • დღეს. DevOps კულტურა თითქმის ყველა სერიოზულ IT კომპანიაშია, ხოლო DevOps / Cloud ინჟინერი მოთხოვნადი პროფესიაა.

მთავარი: DevOps ტექნოლოგია ან პროგრამა არ არის — ეს შეთანხმებაა: ერთი გუნდი, ერთი მიზანი და ავტომატური გზა კოდიდან მომხმარებლამდე.

DevOps ციკლი — კოდის უწყვეტი გზა ♾️

სლაიდი 5

DevOps ხშირად უსასრულობის ნიშნით (♾️) იხატება: მარცხენა ნახევარი Dev-ია, მარჯვენა — Ops. ციკლი არასოდეს მთავრდება — მონიტორინგში დანახული პრობლემა შემდეგი გეგმის ნაწილი ხდება.

ეტაპი რა ხდება ამ კურსში
📝 Plan ვწყვეტთ, რას ვაკეთებთ —
💻 Code ვწერთ კოდს და ვინახავთ Git-ში Git/GitHub — დღეს
⚙️ Build კოდიდან გასაშვებ ვერსიას ვაწყობთ GitHub Actions
🧪 Test ავტომატურად ვამოწმებთ, ხომ არაფერი გატყდა GitHub Actions
📦 Release ვამზადებთ ვერსიას გასაშვებად სრული CI/CD
🚀 Deploy ვერსია სერვერზე მიდის GitHub Pages, Droplet
🖥️ Operate სერვერი მუშაობს და ვუვლით Linux + SSH
📈 Monitor ვაკვირდებით: სწრაფია? ჩავარდა? მონიტორინგი

DevOps ერთი პროგრამა არ არის — ეს მიდგომაა: ყველაფერი, რაც კოდს მომხმარებლამდე მიიყვანს, ავტომატური, სწრაფი და კონტროლირებადი უნდა იყოს. Git, GitHub Actions, Linux, Nginx, Docker — ეს ის ინსტრუმენტებია, რომლითაც ამას ვაკეთებთ.

📘 ტერმინები
DevOps
Development + Operations: მიდგომა, რომლითაც კოდი დეველოპერიდან მომხმარებლამდე სწრაფად, ავტომატურად და კონტროლირებადად მიდის
Deploy (დეპლოი)
ახალი ვერსიის სერვერზე გაშვება, რომ მომხმარებელმა დაინახოს
CI/CD
ავტომატური აწყობა, ტესტი და დეპლოი ყოველ ცვლილებაზე

თანამედროვე მიდგომა: git push = deploy

სლაიდი 6

დღეს კარგ გუნდში საიტს ხელით არავინ ტვირთავს. DevOps ინჟინერი ერთხელ აწყობს გზას, და მერე ის ასე მუშაობს:

  1. 💻 დეველოპერი კოდს წერს და git push-ით GitHub-ზე აგზავნის.
  2. 🐙 GitHub ამას ამჩნევს და ავტომატურად უშვებს GitHub Actions-ს.
  3. ⚙️ Actions აწყობს (build) და ამოწმებს (ტესტები) პროექტს.
  4. ☁️ წარმატების შემთხვევაში ახალი ვერსია სერვერზე ავტომატურად იდება.
  5. 👥 მომხმარებელი ახალ ვერსიას ხედავს.

ძველად: ფაილებს ხელით ტვირთავდი FTP-ით. რომელი ვერსია დევს სერვერზე? ვინ ატვირთა? რა შეიცვალა? — არავინ იცოდა.

დღეს: კოდი Git-შია, გზა კი ერთხელ არის აწყობილი. ყოველი ცვლილება ჩანს, ავტომატურად ქვეყნდება და, თუ რამე გაფუჭდა, წინა ვერსიაზე დაბრუნება წამებია. git push თავისით არაფერს აქვეყნებს — ამას ჩვენ ვაწყობთ, და ამის აწყობას ვისწავლით.

ამ პროცესს CI/CD ჰქვია. მის აწყობას და მოვლას DevOps ინჟინერი აკეთებს — და ის Git-ით იწყება, ამიტომ კურსს Git-ით დავიწყებთ.

DevOps ინჟინრის ერთი დღე

სლაიდი 7

DevOps ინჟინრის დღე ასე შეიძლება გამოიყურებოდეს:

დრო საქმე რას აკეთებს
09:00 📈 მონიტორინგი ამოწმებს, ღამით ყველაფერი რიგზე იყო თუ არა: დატვირთვა, შეცდომები, alert-ები (ავტომატური გაფრთხილებები)
10:00 🔁 pipeline ავტომატური build ან ტესტი ჩავარდა („გაწითლდა“) — დეველოპერთან ერთად პოულობს მიზეზს
12:00 🖥️ ინფრასტრუქტურა ახალი ფიჩისთვის ამზადებს სერვერს ან ბაზას: დომენი, firewall, HTTPS
14:00 🤖 ავტომატიზაცია რასაც გუნდი ხელით და ხშირად აკეთებს, სკრიპტად ან pipeline-ად აქცევს
16:00 🚀 deploy ახალი ვერსია მომხმარებლამდე მიდის. თუ რამე გაფუჭდა — სწრაფად აბრუნებს წინა ვერსიას (rollback)
⏰ ნებისმიერ დროს 🔥 ინციდენტი საიტი ჩავარდა: ჯერ აღადგენს, მერე არკვევს, რატომ მოხდა, რომ აღარ განმეორდეს

და მუდმივად: უსაფრთხოება (პაროლები, გასაღებები, განახლებები), ბექაპები (მონაცემი არ უნდა დაიკარგოს) და ხარჯი (სერვერები ფულს ითხოვს).

💡

ბევრ კომპანიაში DevOps ინჟინრები რიგრიგობით „მორიგეობენ“ (on-call): ღამითაც, თუ საიტი ჩავარდა, ტელეფონზე alert მოდის. სწორედ ამიტომ ცდილობენ, ყველაფერი ისე ააწყონ, რომ ჩავარდნა იშვიათი იყოს.

ხელსაწყოები ბევრია და მუდმივად იცვლება. მთავარია, ჯგუფები გესმოდეს — ყოველ ჯგუფში ერთის ცოდნა დანარჩენის სწავლას ამარტივებს.

ეს კურსი ≠ მთელი DevOps

სლაიდი 9

გულწრფელად: DevOps ძალიან დიდი სფეროა, და ერთ კურსში მთლიანად არ ისწავლება. ჩვენ საძირკველს ვყრით — აისბერგის იმ ნაწილს, რომელიც წყლის ზემოთ ჩანს.

✓ ამ კურსში ვისწავლით (საფუძველი):

  • Git, GitHub და GitHub Actions — კოდის ისტორია და ავტომატიზაცია;
  • Linux და SSH — საკუთარი სერვერის მართვა;
  • Docker-ის საფუძვლები — აპის კონტეინერში ჩასმა და მისით deploy;
  • დომენი, HTTPS და ავტომატური deploy — ერთი აპის სრული გზა ლეპტოპიდან ინტერნეტამდე.

🌊 წყლის ქვეშ — შემდეგი ნაბიჯები, თუ DevOps-ში გააგრძელებ:

  • ☸️ Kubernetes — ბევრი კონტეინერის მართვა დიდი მასშტაბით (Docker-ის საფუძვლებს კურსში ვისწავლით);
  • 🏗️ Terraform, Ansible — ინფრასტრუქტურა კოდით;
  • ☁️ AWS / Azure — დიდი ღრუბლოვანი პლატფორმები (ხშირად სერტიფიკატებით);
  • 📈 Prometheus, Grafana — სერიოზული მონიტორინგი;
  • 🔐 DevSecOps — უსაფრთხოება მთელ გზაზე;
  • ⚖️ მასშტაბირება და 🧯 SRE (Site Reliability Engineering) — მილიონობით მომხმარებლის მომსახურება.

რატომ ღირს საძირკველი: წყლის ქვეშ ყველაფერი სწორედ ამ ცოდნაზე დგას. ვინც Git-ს, Linux-ს, სერვერს და deploy-ს არ იცნობს, Kubernetes-ს ვერ გაიგებს.

თეორიულად შენი ლეპტოპიც გამოდგება, პრაქტიკულად — არა:

DNS — სახელების და მისამართების საცავი

სლაიდი 16

ინტერნეტში კომპიუტერები ერთმანეთს IP მისამართით პოულობენ — მაგალითად 164.90.12.34. ადამიანისთვის ციფრების დამახსოვრება რთულია, ამიტომ გვაქვს დომენის სახელები: google.com, myportfolio.ge.

DNS (Domain Name System) — ინტერნეტის „კონტაქტების წიგნი“: საცავი, სადაც ყოველ სახელს მისი სერვერის მისამართი (IP) უწერია.

სახელი (დომენი) მისამართი (IP)
google.com 142.250.185.78
facebook.com 157.240.1.35
myportfolio.ge 164.90.12.34

როგორ მუშაობს:

  1. ① ბრაუზერი DNS-ს ეკითხება: „myportfolio.ge სად არის?“
  2. ② DNS წიგნში პოულობს და პასუხობს: „164.90.12.34“.
  3. ③ ბრაუზერი ამ მისამართზე მიდის — სერვერთან.

📱 ანალოგია — ტელეფონის კონტაქტები: შენ ეძებ „დედა“-ს, ტელეფონი კი ნომერზე რეკავს. სახელს იმახსოვრებ შენ, ნომერს — ტელეფონი.

💡

ეს „წიგნი“ თვითონ არ ივსება: როცა დომენს იყიდი, DNS-ში შენ ჩაწერ, რომ myportfolio.ge → შენი სერვერის IP. ამას კურსში თვითონ გავაკეთებთ. (ცხრილის IP-ები მაგალითისთვისაა.)

  2. მოთხოვნა — ბრაუზერი ამ IP-ზე აგზავნის HTTP მოთხოვნას: GET /.

შეჯამება · DevOps — ერთი წინადადებით

სლაიდი 20

DevOps = Dev + Ops: ერთი გუნდი და ავტომატური გზა, რომლითაც კოდი ლეპტოპიდან მომხმარებლამდე სწრაფად და უსაფრთხოდ მიდის.

  • 🧱 რატომ გაჩნდა — Dev და Ops ცალ-ცალკე მუშაობდნენ: ვერსიები იშვიათად და შიშით გამოდიოდა, პრობლემებზე ერთმანეთს ადანაშაულებდნენ. 2009 წელს Flickr-მა აჩვენა „10+ deploys per day“, Patrick Debois-მ კი DevOpsDays მოაწყო.
  • ♾️ ციკლი — Plan → Code → Build → Test → Release → Deploy → Operate → Monitor, და თავიდან.
  • ☀️ DevOps ინჟინრის დღე — მონიტორინგი, pipeline-ის გამართვა, სერვერები და ბაზები, ავტომატიზაცია, deploy და rollback, ინციდენტები; მუდმივად — უსაფრთხოება, ბექაპები, ხარჯი.
  • 🧊 ეს კურსი ≠ მთელი DevOps — ვყრით საძირკველს: Git/GitHub, GitHub Actions, Linux + SSH, საკუთარი სერვერი, Docker-ის საფუძვლები, დომენი, HTTPS, ავტომატური deploy. Kubernetes, Terraform და სხვა — შემდეგი ნაბიჯებია.
  • 🌐 სად ცხოვრობს კოდი — სერვერზე (მუდამ ჩართული კომპიუტერი საჯარო IP-ით). გზა: სახელი → DNS → IP → სერვერი → პასუხი. ჰოსტინგის სახეები: საკუთარი სახლი, საერთო ბინა, ნაქირავები ბინა, სასტუმრო.

შემდეგ ლექციაზე: მოკლედ ვიმეორებთ Git-ს — რაც DevOps-ს სჭირდება — და ვაკეთებთ პირველ deploy-ს: საიტი GitHub Pages-ზე. მოიტანე GitHub-ის ანგარიში და, თუ გაქვს, Frontend-ის რომელიმე HTML/CSS პროექტი.

🤖 გამოცდა პირველ ლექციაზე
ვსწავლობ DevOps-ს. პირველ ლექციაზე გავიარეთ: რა არის DevOps და რატომ გაჩნდა (Dev vs Ops, Flickr 2009, DevOpsDays); DevOps ციკლი; რას აკეთებს DevOps ინჟინერი დღის განმავლობაში; DevOps-ის ხელსაწყოების ჯგუფები (Git, CI/CD, Cloud, Linux, კონტეინერები, IaC, მონიტორინგი, უსაფრთხოება); რა არის ჰოსტინგი, სერვერი, DNS და ჰოსტინგის სახეები (On-premise, Shared, VPS, PaaS). დამისვი 8 კითხვა სათითაოდ, მარტივიდან რთულისკენ — ნაწილი სიტუაციური იყოს („შენ DevOps ინჟინერი ხარ და…“). ყოველ პასუხზე შემიფასე და ამიხსენი. ბოლოს მითხარი, რა გავიმეორო. ქართულად.
🤖 DevOps-ის ვაკანსია ამიხსენი
ვსწავლობ DevOps-ის საფუძვლებს. ქვემოთ ჩავსვამ DevOps / Cloud ინჟინრის ვაკანსიის ტექსტს. ამიხსენი მარტივად, ქართულად: რა უნდა აკეთოს ამ ადამიანმა დღის განმავლობაში, და თითოეული ხსენებული ხელსაწყო რისთვისაა. ბოლოს მითხარი, რომელია „საფუძველი“ და რომელი „შემდეგი ნაბიჯი“. ვაკანსია: [აქ ჩასვი ტექსტი]
