LMS API სერვერზე — ხელით

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 5 — Nginx — საიტი შენს სერვერზე. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
რა არის ვებ-სერვერი და რატომ დაგვჭირდა?
პროგრამა, რომელიც port 80/443-ს უსმენს, ბრაუზერის მოთხოვნას იღებს და პასუხს (მაგ. ფაილს) აბრუნებს. მის გარეშე სერვერის IP-ზე არავინ პასუხობს
sites-available და sites-enabled — რა განსხვავებაა?
sites-available — ყველა საიტის კონფიგი; sites-enabled — მხოლოდ ჩართულები, symlink-ებით sites-available-ზე. Nginx მხოლოდ sites-enabled-ს კითხულობს
კონფიგი შევცვალე. რა ორი ბრძანება გავუშვა?
sudo nginx -t — სინტაქსის შემოწმება; თუ OK — sudo systemctl reload nginx, რომ ცვლილება ამოქმედდეს
Angular აპში /courses გვერდზე refresh → 404. რატომ და როგორ ვასწორებთ?
სერვერზე ფაილი courses არ არსებობს — როუტინგს Angular ბრაუზერში აკეთებს. try_files $uri $uri/ /index.html; — თუ ფაილი არ არის, Nginx აბრუნებს index.html-ს და Angular თვითონ ხსნის გვერდს
ბრაუზერი წერს „This site can't be reached“. პირველი რას შეამოწმებ?
Nginx მუშაობს? (systemctl status nginx), port-ს უსმენს? (ss -tlnp), და firewall-ში port ღიაა? (ufw status)
403 Forbidden — რა არის ყველაზე ხშირი მიზეზი?
Nginx-ს (user www-data) ფაილის ან საქაღალდის წაკითხვის უფლება არ აქვს, ან საქაღალდეში index.html არ არის. ლოგი: sudo tail /var/log/nginx/error.log

საშინაოს განხილვა

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: Angular აპი სერვერზე + deploy სკრიპტი. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • Angular: ng build → rsync → /var/www/app; server block listen 8080 + try_files … /index.html; ufw allow 8080/tcp
  • შიდა როუტზე refresh → გვერდი იხსნება, არა 404
  • my-portfolio-ში deploy.sh — ერთი ბრძანებით ატვირთავს საიტს

ამოხსნა

/etc/nginx/sites-available/app
server {    listen 8080;    server_name _;     root /var/www/app;    index index.html;     location / {        try_files $uri $uri/ /index.html;    }}

$ sudo mkdir -p /var/www/app && sudo chown -R $USER:$USER /var/www/app$ sudo ln -s /etc/nginx/sites-available/app /etc/nginx/sites-enabled/$ sudo nginx -t && sudo systemctl reload nginx
WSL (Angular-ის პროექტში)
$ ng build
deploy.sh
#!/bin/bashset -ersync -avz --delete --exclude .git --exclude deploy.sh ./ lms:/var/www/portfolio/echo "✅ portfolio განახლდა"

set -e — თუ რომელიმე ბრძანება ჩავარდა, სკრიპტი ჩერდება. ეს სკრიპტი უკვე პატარა ავტომატიზაციაა — კურსის ბოლოს მას GitHub Actions შეცვლის.

დღის თემა

დღის თემა: LMS API სერვერზე — ხელით

სლაიდი 4

სტატიკური საიტისთვის Nginx-ს ფაილები ეყოფა. API კი გაშვებული პროგრამაა: სჭირდება .NET runtime, ბაზა, სერვისი, რომელიც 24/7 მუშაობს, და Nginx, რომელიც მას ინტერნეტს დაუკავშირებს. დღეს LMS-ს (და შენს პროექტს) ყველაფერს ხელით ვუწყობთ — ნაბიჯ-ნაბიჯ. ბოლოს დავთვლით, რამდენი ნაბიჯი დაგვჭირდა და რა შეიძლება გაფუჭდეს — ეს შემდეგი ლექციის, Docker-ის მიზეზია.

ლექციის ბოლოს შეძლებ:

  • სერვერზე ASP.NET Core runtime-ის და PostgreSQL-ის დაყენება, ბაზის და user-ის შექმნა
  • API-ს dotnet publish და ატვირთვა; მიგრაციების გაშვება SQL სკრიპტით
  • systemd სერვისის დაწერა: API მუშაობს ფონზე და crash-ის შემდეგ თავისით ირთვება
  • Nginx, როგორც reverse proxy: proxy_pass → Kestrel
  • 502 Bad Gateway-ის მიზეზის პოვნა systemctl status და journalctl-ით

1 · მომზადება

ნაწილი 1 · სერვერის მომზადება

სლაიდი 5

API-ს გასაშვებად სერვერს ორი რამ აკლია: .NET runtime და ბაზა.

გეგმა: API-ს რა სჭირდება, რაც საიტს არ სჭირდებოდა

სლაიდი 6

portfolio-სთვის Nginx-ს მხოლოდ ფაილები სჭირდებოდა. API კი გაშვებული პროგრამაა (მე-2 ლექცია), და ოთხი რამ სჭირდება:

  1. ⚙️ .NET runtime — რომ .dll გაეშვას;
  2. 🗄️ ბაზა — PostgreSQL, user, პაროლი, ცხრილები;
  3. ♾️ მუდმივად მუშაობა — terminal-ის დახურვის შემდეგაც, crash-ის შემდეგაც, reboot-ის შემდეგაც;
  4. 🚪 კარი ინტერნეტში — Nginx, რომელიც მოთხოვნებს API-ს გადასცემს.
⚠️

დღეს ყველაფერს განზრახ ხელით ვაკეთებთ და ნაბიჯებს ვითვლით. ასე ნახავ, რა არის deploy „შიგნიდან“ — და რატომ გვჭირდება შემდეგ ლექციებზე Docker და CI/CD.

ნაბიჯი 1 · .NET runtime

სლაიდი 7

სერვერზე კოდს არ ვწერთ და არ ვაკომპილირებთ — მხოლოდ მზა აპს ვუშვებთ. ამიტომ SDK კი არა, runtime გვჭირდება. ASP.NET Core აპისთვის — aspnetcore-runtime, რომელიც ჩვეულებრივ .NET runtime-საც შეიცავს:

Termius · lms-server
$ sudo apt update$ sudo apt install -y aspnetcore-runtime-10.0 $ dotnet --list-runtimesMicrosoft.AspNetCore.App 10.0.x [/usr/lib/dotnet/shared/Microsoft.AspNetCore.App]

dotnet --version შეცდომას დაწერს — „No .NET SDKs were found“. ეს ნორმალურია: SDK სერვერზე არ გვჭირდება.

SDK runtime
რისთვის კოდის წერა, build, dotnet ef მხოლოდ გაშვება
სად დეველოპერის კომპიუტერზე სერვერზე
ზომა დიდი პატარა
⚠️

runtime-ის ვერსია აპის ვერსიას უნდა ემთხვეოდეს: .NET 10-ის აპი .NET 8-ის runtime-ზე არ გაეშვება. ეს ერთ-ერთი კლასიკური „ჩემთან მუშაობს, სერვერზე — არა“.

Termius-ის მეორე tab-იდან:

Termius · lms-server · tab 2

API მუშაობს და ბაზას უკავშირდება. მაგრამ ზუსტად იგივე პრობლემები, რაც მე-2 ლექციაზე dotnet run-ს ჰქონდა:

  • tab დახურე → API გაჩერდა;
  • crash → არავინ ჩართავს თავიდან;
  • სერვერის reboot → API აღარ ირთვება.
💡

Production-ში Swagger ჩვეულებრივ გამორთულია (if (app.Environment.IsDevelopment())), ამიტომ ვამოწმებთ curl-ით. curl — HTTP მოთხოვნა ტერმინალიდან.

API-ს ვაქცევთ სერვისად — ისევე, როგორც Nginx-ია — და Nginx-ს ვაყენებთ მის წინ.

ნაბიჯი 6 · systemd სერვისი

სლაიდი 15

systemd-ს ვუხსნით, როგორ გაუშვას ჩვენი API — unit ფაილით:

Termius · lms-server
/etc/systemd/system/lms-api.service
[Unit]Description=LMS APIAfter=network.target postgresql.service [Service]WorkingDirectory=/var/www/lms-apiExecStart=/usr/bin/dotnet /var/www/lms-api/Lms.Api.dllRestart=alwaysRestartSec=5User=www-dataEnvironment=ASPNETCORE_ENVIRONMENT=ProductionEnvironment=ASPNETCORE_URLS=http://127.0.0.1:5000Environment="ConnectionStrings__Default=Host=localhost;Database=lms;Username=lms;Password=Str0ng!Pass" [Install]WantedBy=multi-user.target
ხაზი რას ნიშნავს
After= ჯერ ქსელი და PostgreSQL ჩაირთოს, მერე API
WorkingDirectory / ExecStart სად და რა გაუშვას
Restart=always, RestartSec=5 თუ პროცესი გაჩერდა — 5 წამში თავიდან

ნაბიჯი 8 · Nginx — reverse proxy

სლაიდი 17

API 127.0.0.1:5000-ზე უსმენს — ინტერნეტიდან არ ჩანს. Nginx-ს ვაყენებთ მის წინ, როგორც reverse proxy: ის იღებს მოთხოვნას და API-ს გადასცემს.

sites-available/lms-api
server {    listen 8081;    server_name _;     location / {        proxy_pass http://127.0.0.1:5000;        proxy_http_version 1.1;        proxy_set_header Host $host;        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;        proxy_set_header X-Forwarded-Proto $scheme;    }}
  • proxy_pass — სად გადასცეს მოთხოვნა;
  • proxy_set_header — API-ს გადაეცემა ორიგინალი დომენი (Host), მომხმარებლის ნამდვილი IP (X-Forwarded-For) და პროტოკოლი (X-Forwarded-Proto: http თუ https). მის გარეშე API-ს ეგონება, რომ ყველა მოთხოვნა Nginx-იდან (127.0.0.1) მოდის.
Termius · lms-server
$ sudo ln -s /etc/nginx/sites-available/lms-api /etc/nginx/sites-enabled/$ sudo nginx -t && sudo systemctl reload nginx

ბრაუზერში http://<IP>:8081/api/courses → JSON. 🎉

რატომ არ ვხსნით Kestrel-ს პირდაპირ? Nginx — სასტუმროს მიმღებია: სტუმარს იღებს და სწორ ოთახში აგზავნის.

  • ერთ სერვერზე ბევრი აპი — portfolio, Angular, API — ყველა Nginx-ის უკან;
  • HTTPS ერთ ადგილას — Nginx-ში (მე-9 ლექცია), API-ს ამაზე ფიქრი არ სჭირდება;
  • ლოგები, შეზღუდვები, სტატიკური ფაილები — Nginx ამაში ძლიერია.
💡

8081 — დროებითია, სანამ დომენი არ გვაქვს. მე-9 ლექციაზე API იქნება api.<შენი-დომენი>-ზე, port 443-ზე.
