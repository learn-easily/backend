Docker Compose — LMS + ბაზა სერვერზე

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 7 — Docker — აპი გარემოსთან ერთად. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
image და container — რა განსხვავებაა?
image — შაბლონი (როგორც კლასი C#-ში): აპი + runtime + ყველა ფაილი, მხოლოდ წასაკითხად. container — image-იდან გაშვებული ეგზემპლარი (როგორც ობიექტი). ერთი image-იდან ბევრი container შეიძლება
-p 8080:8080-ში რომელი რიცხვი რას ნიშნავს?
ჰოსტის-port:კონტეინერის-port — შენი კომპიუტერის 8080-ზე მოსული მოთხოვნა კონტეინერის შიგნით 8080-ზე მიდის
PostgreSQL-ის კონტეინერი წავშალე. მონაცემები დაიკარგა?
თუ volume (-v lms-data:/var/lib/postgresql/data) იყო მიბმული — არა, მონაცემები volume-ში რჩება და ახალი კონტეინერი მათ დაინახავს. volume-ის გარეშე — კი, ყველაფერი წაიშალა
რატომ აქვს Dockerfile-ს ორი FROM (multi-stage)?
პირველი ეტაპი (sdk) აპს აწყობს — მას SDK სჭირდება. მეორე (aspnet) მხოლოდ მზა ფაილებს იღებს და runtime-ზე უშვებს — საბოლოო image ბევრად პატარა და უსაფრთხოა, მასში SDK და კოდი არ არის
რატომ ვაკოპირებთ ჯერ მხოლოდ .csproj-ს და ვუშვებთ restore-ს, მერე დანარჩენს?
Docker ყოველ ნაბიჯს (layer) ქეშავს. თუ .csproj არ შეცვლილა, restore ქეშიდან აიღება — კოდის ცვლილებისას build ბევრად სწრაფია
რისთვის არის .dockerignore?
build-ში არ გადაიგზავნოს ზედმეტი: bin/, obj/, .git, .vs — build სწრაფია, image სუფთა, და ლოკალური საიდუმლოებები image-ში არ ხვდება

საშინაოს განხილვა

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: შენი API კონტეინერში. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • პროექტის root-ში: multi-stage Dockerfile (sdk:10.0 → aspnet:10.0) და .dockerignore
  • docker build -t lms-api . → გაშვება -p 8080:8080, host.docker.internal-ით lms-db-ზე, Development-ით
  • Dockerfile და .dockerignore → GitHub

ამოხსნა

Dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS buildWORKDIR /srcCOPY Lms.Api/Lms.Api.csproj Lms.Api/RUN dotnet restore Lms.Api/Lms.Api.csprojCOPY . .RUN dotnet publish Lms.Api/Lms.Api.csproj -c Release -o /app/publish FROM mcr.microsoft.com/dotnet/aspnet:10.0WORKDIR /appCOPY --from=build /app/publish .USER $APP_UIDEXPOSE 8080ENTRYPOINT ["dotnet", "Lms.Api.dll"]
.dockerignore
**/bin/**/obj/.git/.vs/.vscode/*.user
WSL
$ docker build -t lms-api .$ docker run -d --name lms-api -p 8080:8080 \    -e ASPNETCORE_ENVIRONMENT=Development \    -e ConnectionStrings__Default="Host=host.docker.internal;Database=lms;Username=lms;Password=dev" \    lms-api

Lms.Api — პროექტის საქაღალდე და სახელი; თქვენი თუ სხვაა, შეცვალეთ.

დღის თემა

დღის თემა: Docker Compose — LMS + ბაზა სერვერზე

სლაიდი 4

წინა ლექციაზე ორი კონტეინერისთვის ორი გრძელი docker run დაგვჭირდა, API ბაზას „შემოვლით“ პოულობდა, და თუ ბაზაზე ადრე ჩაირთვებოდა — ვარდებოდა. Docker Compose მთელ სისტემას ერთ ფაილში აღწერს და ერთი ბრძანებით უშვებს. დღეს LMS-ს და PostgreSQL-ს ჯერ შენთან ვუშვებთ, მერე — სერვერზე, და მე-6 ლექციის 10 ხელით ნაბიჯი სამ ბრძანებად იქცევა.

ლექციის ბოლოს შეძლებ:

  • compose.yaml-ის დაწერა: services, image/build, ports, environment, volumes
  • სერვისებს შორის კავშირი სახელით (Host=db), depends_on + healthcheck, restart
  • საიდუმლოებები .env-ში და მიგრაციები აპის ჩართვისას
  • სერვერზე Docker-ის დაყენება და LMS-ის გაშვება docker compose up -d --build-ით
  • Nginx → კონტეინერი, port-ის დაცვა 127.0.0.1-ით, განახლება და ბაზის backup

ნაწილი 1 · compose.yaml

სლაიდი 5

ჯერ ყველაფერს შენს კომპიუტერზე ვაწყობთ — და მხოლოდ მერე სერვერზე, უცვლელად.

პრობლემა: ორი კონტეინერი — ორი გრძელი ბრძანება

სლაიდი 6

წინა ლექციის ბოლოს LMS ორი კონტეინერით მუშაობდა — მაგრამ:

  • 📝 ორი გრძელი docker run — ზეპირად ან README-დან კოპირებით; ერთი შეცდომა და არ მუშაობს;
  • 🔗 API ბაზას host.docker.internal-ით პოულობს — „შემოვლით“, შენი კომპიუტერის გავლით;
  • ⏱️ თუ API ბაზაზე ადრე ჩაირთო — ვარდება.

Docker Compose მთელ სისტემას — ყველა კონტეინერს, მათ პარამეტრებს და კავშირებს — ერთ ფაილში აღწერს: compose.yaml. ფაილი Git-ში ინახება, და ნებისმიერ კომპიუტერზე ერთი ბრძანებით ეშვება.

ნაბიჯი 1 · compose.yaml

სლაიდი 7

LMS-ის რეპოს root-ში, Dockerfile-ის გვერდით:

compose.yaml
services:  db:    image: postgres:17    environment:      POSTGRES_USER: lms      POSTGRES_PASSWORD: ${DB_PASSWORD}      POSTGRES_DB: lms    volumes:      - lms-data:/var/lib/postgresql/data    healthcheck:      test: ["CMD-SHELL", "pg_isready -U lms -d lms"]      interval: 5s      retries: 10    restart: unless-stopped   api:    build: .    ports:      - "127.0.0.1:5000:8080"    environment:      ASPNETCORE_ENVIRONMENT: ${ASPNETCORE_ENVIRONMENT:-Production}      ConnectionStrings__Default: "Host=db;Database=lms;Username=lms;Password=${DB_PASSWORD}"    depends_on:      db:        condition: service_healthy    restart: unless-stopped volumes:  lms-data:
ნაწილი რას ნიშნავს docker run-ში იყო
services: კონტეინერების სია; სახელი (db, api) — შენი არჩეული --name
image: / build: . მზა image / ააწყე მიმდინარე საქაღალდის Dockerfile-ით docker build
environment: გარემოს ცვლადები -e
volumes: volume-ის მიბმა; ქვედა volumes: — მისი გამოცხადება -v
ports: IP:ჰოსტი:კონტეინერი -p
healthcheck: ბრძანება, რომელიც ამოწმებს, ბაზა მართლა მზადაა თუ არა (pg_isready) —
depends_on + service_healthy API მხოლოდ healthy ბაზის შემდეგ ირთვება —
restart: unless-stopped crash-ზე და სერვერის reboot-ზე თავისით ირთვება — როგორც systemd-ის Restart=always —

Host=db — Compose ყველა სერვისს ერთ ქსელში სვამს, სადაც სერვისის სახელი მისამართად მუშაობს. host.docker.internal აღარ გვჭირდება.

YAML — ფორმატი, სადაც სტრუქტურას შეწევა (space-ები) განსაზღვრავს, არა { }. მხოლოდ space-ები, არა Tab; ერთ დონეზე — ერთნაირი შეწევა.

ნაბიჯი 2 · საიდუმლოებები და მიგრაციები

სლაიდი 8

.env — Compose compose.yaml-ის გვერდით მდებარე .env ფაილს ავტომატურად კითხულობს და ${სახელი}-ს მის მნიშვნელობას უსვამს:

.env (შენთან)
DB_PASSWORD=devASPNETCORE_ENVIRONMENT=Development

${ASPNETCORE_ENVIRONMENT:-Production} — თუ ცვლადი არ არის მითითებული, ნაგულისხმევად Production. შენთან .env-ში Development წერია (Swagger ჩანს), სერვერზე — Production.

⚠️

.env არასოდეს Git-ში — დაამატე .gitignore-ში (მე-2 ლექცია). სერვერზე ცალკე .env შეიქმნება, სხვა, ძლიერი პაროლით.

მიგრაციები ჩართვისას. წინა ლექციებზე მიგრაციებს ცალკე SQL სკრიპტით ვუშვებდით. ახლა აპი ჩართვისას თვითონ უშვებს მათ:

Program.cs
var app = builder.Build(); using (var scope = app.Services.CreateScope()){    var db = scope.ServiceProvider.GetRequiredService<LmsDbContext>();    db.Database.Migrate();}

Migrate() ამოწმებს, რომელი მიგრაცია აკლია ბაზას, და მხოლოდ მათ უშვებს — იგივე, რაც --idempotent სკრიპტი. depends_on: service_healthy-ის წყალობით ამ დროს ბაზა უკვე მზადაა.

💡

ერთი სერვერისთვის და სასწავლო პროექტისთვის ეს მარტივი და საიმედოა. დიდ სისტემებში, სადაც API რამდენიმე ეგზემპლარად ეშვება, მიგრაციებს ცალკე ნაბიჯად უშვებენ (efbundle ან SQL სკრიპტი pipeline-ში).

ნაბიჯი 3 · გაშვება

სლაიდი 9

წინა ლექციის კონტეინერები აღარ გვჭირდება: docker rm -f lms-api lms-db. მერე:

WSL · LMS-ის რეპო
$ docker compose up -d --build ✔ Network lms_default   Created ✔ Volume "lms_lms-data" Created ✔ Container lms-db-1    Healthy

Compose-მა შექმნა ქსელი, volume, ჩართო ბაზა, დაელოდა healthy-ს და მხოლოდ მერე ჩართო API. ბრაუზერში — http://localhost:5000/swagger.

WSL
$ docker compose logs -f apiinfo: Microsoft.EntityFrameworkCore.Migrations[20402]      Applying migration '20261128_InitialCreate'.
ბრძანება რას აკეთებს
docker compose up -d --build (ხელახლა) ააწყე image და გაუშვი ყველაფერი ფონზე
docker compose ps სერვისების სტატუსები
docker compose logs -f api ერთი სერვისის ლოგი ცოცხლად
docker compose restart api ერთი სერვისის გადატვირთვა
docker compose exec db psql -U lms ბრძანება სერვისის შიგნით
docker compose down კონტეინერების და ქსელის წაშლა — volume (ბაზა) რჩება
docker compose down -v ⚠ volume-ებიც — ბაზა სამუდამოდ იკარგება
⚠️

down -v სერვერზე = მთელი ბაზის წაშლა. ეს ბრძანება მხოლოდ მაშინ, როცა ზუსტად გინდა ბაზის ნულიდან შექმნა — და backup გაქვს.

ნაბიჯი 4 · Docker სერვერზე

სლაიდი 12

სერვერზე Docker Desktop არ გვჭირდება — მხოლოდ Docker Engine (ტერმინალის ვერსია):

Termius · lms-server
$ curl -fsSL https://get.docker.com | sudo sh$ sudo usermod -aG docker $USER# Termius: გაითიშე და თავიდან დაუკავშირდი
  • get.docker.com — Docker-ის ოფიციალური სკრიპტი: ამატებს Docker-ის apt repo-ს და აყენებს Engine-ს და Compose-ს. (curl … | sh — ინტერნეტიდან ჩამოტვირთული სკრიპტის გაშვება; ამას მხოლოდ სანდო, ოფიციალურ წყაროზე ვაკეთებთ.)
  • usermod -aG docker $USER — docker ჯგუფში ყოფნა საშუალებას გაძლევს sudo-ს გარეშე იმუშაო. ჯგუფი ამოქმედდება ხელახლა შესვლის შემდეგ.

ძველის გაჩერება. მე-6 ლექციის systemd სერვისი და apt-ით დაყენებული PostgreSQL აღარ გვჭირდება — ისინი RAM-ს ჭამენ:

Termius · lms-server

disable --now = გაჩერება ახლა + აღარ ჩაირთოს reboot-ზე.

👉

ნაბიჯი 6 · Nginx → კონტეინერი

სლაიდი 14

Nginx-ის კონფიგი არ იცვლება: მე-6 ლექციაში API 127.0.0.1:5000-ზე იყო, და კონტეინერი ზუსტად იმავე port-ზე გამოვიყვანეთ ("127.0.0.1:5000:8080"). Nginx-ისთვის განსხვავება არ არსებობს — http://<IP>:8081/api/courses ახლა კონტეინერიდან პასუხობს.

⚠ ხაფანგი: Docker ufw-ს გვერდს უვლის. Docker port-ების გასახსნელად firewall-ის წესებს პირდაპირ ცვლის — ufw-ის გავლის გარეშე. ამიტომ:

ჩანაწერი შედეგი
"5000:8080" port 5000 ინტერნეტში ღიაა, ufw-ის მიუხედავად
"127.0.0.1:5000:8080" მხოლოდ სერვერის შიგნიდან — Nginx-ისთვის ✓

ბაზის სერვისს ports საერთოდ არ აქვს: API მას Docker-ის შიდა ქსელში, db სახელით პოულობს. ინტერნეტიდან ბაზამდე გზა არ არსებობს.

⚠️

სერვერზე ports-ში ყოველთვის 127.0.0.1: — თუ port-ს მხოლოდ Nginx იყენებს. ბაზის port-ს კი არასოდეს ვხსნით.
