წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 1 — რა არის DevOps. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი

დღის თემა: Git → GitHub Pages — საიტი ინტერნეტში

სლაიდი 3

Git უკვე იცით — Frontend-ზეც და Backend-ზეც. DevOps-ში კი git push ახალ მნიშვნელობას იძენს: ის deploy-ს იწყებს. დღეს მოკლედ ვიმეორებთ, რაც კურსს სჭირდება, და პირველ deploy-ს ვაკეთებთ: my-portfolio ნამდვილ მისამართზე, რომელიც ყოველ git push-ზე თავისით ახლდება. და ვნახავთ, სად მთავრდება GitHub Pages-ის შესაძლებლობა — რატომ ვერ გაუშვებს ის შენს API-ს.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რა როლი აქვს Git-ს DevOps-ში: git push → GitHub → pipeline → საიტი
  • public რეპოს დაცვა .gitignore-ით და რა ვქნა, თუ საიდუმლო უკვე ავტვირთე
  • my-portfolio-ს გამოქვეყნება GitHub Pages-ით: username.github.io/my-portfolio
  • საიტის განახლება git push-ით, Actions-ში სტატუსის ნახვა და ტიპური შეცდომების გასწორება (404, CSS არ იტვირთება)
  • ახსნა, რატომ ვერ გაეშვება API GitHub Pages-ზე და რა გვჭირდება ამისთვის

1 · Git

ნაწილი 1 · Git — რაც DevOps-ს სჭირდება

სლაიდი 4

Git Frontend-სა და Backend-ზე უკვე ისწავლეთ და ყოველდღე იყენებთ. ამიტომ თავიდან არ ვსწავლობთ — ვიმეორებთ მხოლოდ იმას, რაზეც ეს კურსი დგას, და ვნახავთ, რატომ იწყება DevOps-ის ყოველი გზა Git-ით.

Git DevOps-ში — ყველაფრის დასაწყისი

სლაიდი 5

DevOps-ში კოდი ლეპტოპიდან მომხმარებლამდე ერთი გზით მიდის, და ეს გზა Git-ით იწყება:

git push → GitHub → pipeline (ავტომატური ნაბიჯები) → საიტი ან სერვერი.

ბრძანება DevOps-ში სად დაგვჭირდება
git clone კოდის ჩამოტანა სერვერზე და CI-ის runner-ზე
git status · add · commit ყოველი ცვლილება ისტორიაშია — ცუდი ვერსია შეიძლება დავაბრუნოთ
git push deploy-ის „ღილაკი“: დღეს GitHub Pages-ზე, კურსის ბოლოს — CI/CD-ით საკუთარ სერვერზე
git pull სხვის (ან სხვა კომპიუტერზე გაკეთებულ) ცვლილებებს ჩამოიტანს
git switch -c · git merge main = რაც ინტერნეტშია; ახალი ფიჩა branch-ზე იწერება
👉

დღეიდან main-ს სხვა მნიშვნელობა აქვს: რაც main-შია, ის ინტერნეტშია. სწორედ ამიტომ ახალ ფიჩაზე branch-ზე ვმუშაობთ.

.gitignore — DevOps-ში ეს უკვე უსაფრთხოებაა

სლაიდი 6

.gitignore უკვე იცით. DevOps-ში კი მისი მნიშვნელობა იზრდება:

  • რეპო public ხდება. GitHub Pages უფასო ანგარიშზე მხოლოდ public რეპოზე მუშაობს — კოდს ყველა ხედავს.
  • ბოტები GitHub-ს უწყვეტად კითხულობენ. ატვირთულ პაროლს, API გასაღებს ან ბაზის connection string-ს ისინი წუთებში პოულობენ.
  • კურსის მეორე ნახევარში სერვერის პაროლები, SSH გასაღებები და JWT გასაღებები გვექნება — არცერთი არ უნდა მოხვდეს Git-ში.
.gitignore
# საიდუმლოებები — არასოდეს Git-ში.env*.pem # ავტომატურად იქმნებაnode_modules/dist/bin/obj/ # რედაქტორი.vscode/.idea/
⚠️

საიდუმლო უკვე GitHub-ზე მოხვდა? ფაილის წაშლა და ახალი commit არ შველის — ის ისტორიაში რჩება და იქიდან იკითხება. ერთადერთი სწორი გზა: საიდუმლო შეცვალე (ახალი პაროლი, ახალი გასაღები), ფაილი კი .gitignore-ში ჩაწერე.

საიდუმლოებებს როგორ ვინახავთ სწორად — სერვერზე .env-ში და GitHub Secrets-ში — მე-9 და მე-11 ლექციებზე ვნახავთ.

ნაწილი 2 · GitHub Pages

სლაიდი 8

საიტი ნამდვილ მისამართზე — ერთი ღილაკით. ეს არის ჩვენი პირველი deploy: კოდი ლეპტოპიდან მომხმარებლამდე მიდის.

პრობლემა: კოდი GitHub-ზეა — საიტი კი არა

სლაიდი 9

პირველ ნაწილში my-portfolio GitHub-ზე ავიტანეთ. მაგრამ თუ მეგობარს გაუგზავნი github.com/giorgi/my-portfolio-ს, ის დაინახავს ფაილების სიას და კოდს — არა საიტს.

ლოკალურად (Live Server, 127.0.0.1:5500) საიტი მუშაობს, მაგრამ მხოლოდ შენს ლეპტოპზე: სხვა კომპიუტერიდან ეს მისამართი არ იხსნება, ლეპტოპის დახურვისას კი საიტი ქრება.

GitHub კოდს ინახავს. საიტის ჩვენება ინტერნეტში — ჰოსტინგის საქმეა. პირველ ლექციაზე ჰოსტინგის სახეები ვნახეთ; დღეს ყველაზე მარტივით ვიწყებთ.

GitHub Pages — რეპო → საიტი

სლაიდი 10

GitHub Pages — GitHub-ის უფასო ჰოსტინგი. ის რეპოს ერთი branch-იდან ფაილებს იღებს და აქვეყნებს მისამართზე:

plain
https://<username>.github.io/<რეპოს-სახელი>/
რას იძლევა რა პირობით
საჯარო მისამართი და HTTPS უფასოდ, public რეპოსთვის
ავტომატური განახლება ყოველ git push-ზე ფაილები ერთი branch-იდან (ჩვენთან main)
HTML, CSS, JS, სურათები მხოლოდ ფაილები

პირველი ლექციის ტერმინებით: ეს სტატიკური ჰოსტინგია — სერვერს შენ არ მართავ, GitHub ყველაფერს თვითონ აკეთებს. შენ მხოლოდ ფაილებს აწვდი.

ნაბიჯი 1 · Pages-ის ჩართვა

სლაიდი 11
  1. my-portfolio-ს გვერდზე GitHub-ზე → ⚙ Settings.
  2. მარცხენა მენიუში, განყოფილებაში Code and automation → Pages.
  3. Build and deployment → Source: Deploy from a branch. Branch: main, Folder: / (root) → Save.

დაახლოებით ერთ წუთში გვერდის ზემოთ გამოჩნდება: Your site is live at https://<username>.github.io/my-portfolio/.

⚠️

index.html უნდა იყოს რეპოს root-ში (არა რომელიმე საქაღალდეში) და დაწერილი პატარა ასოებით — Index.html არ ჩაითვლება. ეს ფაილი საიტის მთავარი გვერდია: მისამართის ბოლოს ფაილის სახელი თუ არ წერია, სერვერი index.html-ს აბრუნებს.

💡

უფასო ანგარიშზე Pages მხოლოდ public რეპოსთვის მუშაობს. ამიტომ რეპოში არაფერი საიდუმლო არ უნდა იყოს — სწორედ ამიტომ ვისწავლეთ .gitignore.

ნაბიჯი 2 · Actions ჩანართი — პირველი pipeline

სლაიდი 12

Save-ზე დაჭერის შემდეგ GitHub-მა workflow გაუშვა — სახელით pages build and deployment. მას ნახავ რეპოს Actions ჩანართში.

ის ორი ნაბიჯისგან შედგება:

  • build — ფაილების მომზადება გამოსაქვეყნებლად;
  • deploy — მათი გამოქვეყნება github.io-ზე.

სტატუსი: 🟡 მიმდინარეობს · ✅ წარმატებით დასრულდა · ❌ შეცდომა (დააჭირე — ნახავ, რომელ ნაბიჯზე და რატომ).

📘 ტერმინები
workflow
ავტომატური ნაბიჯების თანმიმდევრობა, რომელსაც GitHub რაღაც მოვლენაზე (მაგ. push) უშვებს
pipeline
გზა კოდიდან გამოქვეყნებამდე, ნაბიჯებად დაყოფილი: build → deploy
👉

ეს workflow GitHub-მა თვითონ შექმნა. მე-10 და მე-11 ლექციებზე ასეთს ჩვენ თვითონ დავწერთ — ოღონდ არა სტატიკური საიტისთვის, არამედ შენი API-სთვის, რომელიც საკუთარ სერვერზე გაეშვება.

ნაბიჯი 3 · განახლება: შეცვალე → push → საიტი განახლდა

სლაიდი 13

Pages-ის ჩართვა ერთხელ ხდება. მერე ყოველი git push main-ში ახალ deploy-ს უშვებს:

Git Bash
$ git switch -c feature/about# index.html-ში „ჩემ შესახებ“ ბლოკი დავამატეთ$ git add index.html$ git commit -m "Add about section" $ git switch main$ git merge feature/about

Actions-ში გამოჩნდება ახალი pages build and deployment — მწვანე ✓-ის შემდეგ ახალი ვერსია ყველასთვის ჩანს.
