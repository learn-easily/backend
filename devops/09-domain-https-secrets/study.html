დომენი, HTTPS და საიდუმლოებები

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 8 — Docker Compose — LMS + ბაზა სერვერზე. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
API ბაზას რა მისამართით უკავშირდება Compose-ში და რატომ?
Host=db — სერვისის სახელით. Compose ყველა სერვისს ერთ ქსელში სვამს, სადაც სახელი = მისამართი
რას აკეთებს depends_on + condition: service_healthy?
API მხოლოდ მაშინ ირთვება, როცა ბაზის healthcheck (pg_isready) წარმატებულია — ანუ ბაზა მართლა მზადაა მოთხოვნებისთვის
რატომ ვწერთ ports: "127.0.0.1:5000:8080" და არა "5000:8080"?
Docker port-ს ufw-ის გვერდის ავლით ხსნის. 127.0.0.1-ით port მხოლოდ სერვერის შიგნიდან ჩანს — ინტერნეტიდან API-მდე მხოლოდ Nginx-ის გავლით მიდიან
docker compose down და docker compose down -v — რა განსხვავებაა?
down კონტეინერებს და ქსელს შლის, volume-ები (ბაზა) რჩება. down -v volume-ებსაც შლის — ბაზა სამუდამოდ იკარგება
სერვერზე LMS-ის ახალი ვერსია როგორ გავუშვა?
git pull → docker compose up -d --build. Compose ახალ image-ს ააწყობს და მხოლოდ შეცვლილ კონტეინერს შეცვლის; ბაზა volume-ში რჩება
როგორ გავაკეთო ბაზის backup?
docker compose exec db pg_dump -U lms lms > backup.sql — SQL ფაილი, რომლითაც ბაზა ნებისმიერ დროს აღდგება

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: შენი API სერვერზე — კონტეინერებით. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • სერვერზე Docker (get.docker.com, docker ჯგუფი); ძველი lms-api და postgresql → disable --now
  • git clone → სერვერის .env (ძლიერი პაროლი, Production, chmod 600) → docker compose up -d --build
  • backup: pg_dump → ~/backups/lms-<თარიღი>.sql

$(date +%F) — დღევანდელი თარიღი (2026-12-05) ფაილის სახელში. restart: unless-stopped-ის წყალობით reboot-ის შემდეგ კონტეინერები თავისით ირთვება.

დღის თემა

დღის თემა: დომენი, HTTPS და საიდუმლოებები

სლაიდი 4

http://164.90.12.34:8081 — არავინ დაიმახსოვრებს, ბრაუზერი „Not secure“-ს წერს, და ვინც შენთან ერთ Wi-Fi-შია, ხედავს პაროლებს, რომლებიც LMS-ში შედის. დღეს სერვერს ვაძლევთ სახელს — დომენს, ვრთავთ უფასო HTTPS-ს Let's Encrypt-ით და საიდუმლოებებს (ბაზის პაროლი, JWT გასაღები) ისე ვალაგებთ, რომ Git-ში არასოდეს მოხვდეს.

ლექციის ბოლოს შეძლებ:

  • DNS ჩანაწერების დამატება: A (@, api, app) და CNAME (www), შემოწმება dig-ით
  • Nginx-ში საიტების დაყოფა server_name-ით port-ების ნაცვლად
  • HTTPS Let's Encrypt-ით: certbot --nginx, HTTP → HTTPS redirect, ავტომატური განახლება
  • ASP.NET Core-ის კონფიგურაციის რიგი: appsettings → environment → user-secrets → გარემოს ცვლადები
  • საიდუმლოებები: user-secrets შენთან, .env სერვერზე; JWT გასაღების გენერაცია და proxy-ს უკან HTTPS-ის სწორად აღქმა

1 · დომენი

ნაწილი 1 · დომენი და DNS

სლაიდი 5

პირველ ლექციაზე ვთქვით: DNS — ინტერნეტის „მისამართების წიგნია“, სახელი → IP. დღეს ამ წიგნში ჩანაწერს თვითონ ვაკეთებთ.

პრობლემა: http://164.90.12.34:8081

სლაიდი 6

ახლა ჩვენი სამი საიტი ასე იხსნება:

საიტი მისამართი
portfolio http://164.90.12.34
Angular http://164.90.12.34:8080
LMS API http://164.90.12.34:8081

სამი პრობლემა:

  • 🧠 არავინ დაიმახსოვრებს — CV-ში, კლიენტთან ან მეგობართან ასეთ ლინკს ვერ გაუგზავნი.
  • ⚠ Not secure — ბრაუზერი მისამართის გვერდით აფრთხილებს, ზოგი ფუნქცია (მაგ. Secure cookie) HTTP-ზე საერთოდ არ მუშაობს.
  • 👀 ღია ტექსტი — HTTP-ზე ყველაფერი, მათ შორის ლოგინი და პაროლი, დაუშიფრავად მიდის. კაფეს Wi-Fi-ში ვინც იმავე ქსელშია, შეუძლია ეს მოთხოვნა დაინახოს.

გამოსავალი: დომენი (სახელი) + HTTPS (დაშიფვრა).

ნაბიჯი 1 · დომენის ყიდვა და DNS ჩანაწერები

სლაიდი 7

დომენი ყიდვით კი არა, ქირით იღება — წლიურად, registrar-თან (დომენების რეგისტრატორი). .com-ის ფასი დაახლოებით $10 წელიწადში; .ge — ქართულ registrar-თან.

👉

სწავლისთვის არის უფასო ვარიანტიც — სერვისები, რომლებიც უფასო ქვედომენს გაძლევენ (მაგ. DuckDNS: giorgi.duckdns.org). ყველაფერი, რასაც დღეს ვაკეთებთ, HTTPS-ის ჩათვლით, მასზეც მუშაობს.

registrar-ის (ან DNS პროვაიდერის) panel-ში ვამატებთ DNS ჩანაწერებს:

Type Name Value შედეგი
A @ 164.90.12.34 giorgi.ge → სერვერი (portfolio)
CNAME www giorgi.ge www.giorgi.ge → იგივე, რაც giorgi.ge
A app 164.90.12.34 app.giorgi.ge → Angular
A api 164.90.12.34 api.giorgi.ge → LMS API
  • A — სახელი → IP მისამართი.
  • CNAME — სახელი → სხვა სახელი; IP-ს DNS მერე თვითონ პოულობს.
  • @ — თვითონ დომენი, ქვედომენის გარეშე.
  • TTL — რამდენ ხანს ინახავენ სხვა სერვერები ამ პასუხს ქეშში (ნაგულისხმევი მნიშვნელობა საკმარისია).

ოთხივე სახელი ერთ სერვერზე მიდის. როგორ გაარჩევს Nginx, რომელი საიტი აჩვენოს — შემდეგ სლაიდზე.

WSL
$ dig +short api.giorgi.ge

ახალი ჩანაწერი რამდენიმე წუთში (ზოგჯერ — საათებში) ვრცელდება. სანამ dig IP-ს არ დააბრუნებს, HTTPS-ზე არ გადავდივართ.

ნაბიჯი 2 · server_name: ერთი IP, ერთი port — სამი საიტი

სლაიდი 8

აქამდე საიტებს port-ებით ვყოფდით (80, 8080, 8081). დომენებით ყველა 80-ზე (და მერე 443-ზე) იქნება — ბრაუზერი ყოველ მოთხოვნაში აგზავნის header-ს Host: api.giorgi.ge, და Nginx მას server block-ების server_name-ს ადარებს:

sites-available/portfolio
server {    listen 80 default_server;    server_name giorgi.ge www.giorgi.ge;    root /var/www/portfolio;    ...}
sites-available/app
server {    listen 80;                  # იყო 8080    server_name app.giorgi.ge;    root /var/www/app;    ...}
sites-available/lms-api
server {    listen 80;                  # იყო 8081    server_name api.giorgi.ge;    location / {        proxy_pass http://127.0.0.1:5000;        ...    }}

default_server — თუ Host არცერთ server_name-ს არ ემთხვევა (მაგ. ვინმემ პირდაპირ IP გახსნა), ეს block პასუხობს.

Termius · lms-server

http://app.giorgi.ge, http://api.giorgi.ge/api/courses — მუშაობს. port-ები 8080/8081 აღარ გვჭირდება — HTTPS-ის შემდეგ მათ ufw-დან წავშლით.

2 · HTTPS

ნაწილი 2 · HTTPS — უფასოდ

სლაიდი 9

HTTPS: სერტიფიკატი — „პასპორტი“ დომენისთვის

სლაიდი 10

HTTPS = HTTP + დაშიფვრა (TLS). ორ რამეს აკეთებს:

  • 🔐 დაშიფვრა — ბრაუზერსა და სერვერს შორის ყველაფერი დაშიფრულია; კაფეს Wi-Fi-ში ვერავინ წაიკითხავს.
  • 🪪 ავთენტიკაცია — სერტიფიკატი ადასტურებს, რომ ეს ნამდვილად giorgi.ge-ის სერვერია და არა ყალბი. სერტიფიკატს გასცემს ორგანიზაცია, რომელსაც ბრაუზერები ენდობიან (Certificate Authority).

Let's Encrypt — უფასო Certificate Authority. მისი სერტიფიკატები 90 დღე მოქმედებს და certbot მათ ავტომატურად აახლებს.

სად მთავრდება HTTPS? ჩვენთან — Nginx-ზე: ბრაუზერი ⇄ HTTPS ⇄ Nginx ⇄ HTTP ⇄ API. Nginx-სა და API-ს შორის კავშირი სერვერის შიგნითაა (127.0.0.1), ამიტომ დაშიფვრა იქ არ სჭირდება. ამას TLS termination ჰქვია — და ეს reverse proxy-ს ერთ-ერთი მთავარი სარგებელია (მე-6 ლექცია).

ნაბიჯი 3 · certbot --nginx

სლაიდი 11
Termius · lms-server
$ sudo apt install -y certbot python3-certbot-nginx$ sudo ufw allow 'Nginx Full'          # 80 + 443$ sudo ufw delete allow 'Nginx HTTP'   # ძველი წესი — Nginx Full მას მოიცავს $ sudo certbot --nginx -d giorgi.ge -d www.giorgi.ge -d app.giorgi.ge -d api.giorgi.geEnter email address: giorgi@mail.ge...Successfully received certificate.Deploying certificate to VirtualHost /etc/nginx/sites-enabled/portfolio...

certbot ოთხ რამეს აკეთებს:

  1. ამოწმებს, რომ დომენი შენს სერვერზე მიდის: Let's Encrypt http://<domain>/.well-known/...-ზე მოითხოვს სპეციალურ ფაილს (ამიტომ port 80 ღია უნდა იყოს და DNS — მზად);
  2. იღებს სერტიფიკატს და ინახავს /etc/letsencrypt/live/<domain>/-ში;
  3. ცვლის Nginx-ის კონფიგს: ამატებს listen 443 ssl-ს, სერტიფიკატის გზებს და redirect-ს HTTP → HTTPS;
  4. ავტომატურ განახლებას აწყობს: systemd timer დღეში ორჯერ ამოწმებს და ვადის ამოწურვამდე 30 დღით ადრე აახლებს.
Termius · lms-server
$ sudo certbot renew --dry-run      # განახლების „რეპეტიცია“Congratulations, all simulated renewals succeeded

https://giorgi.ge 🔒, https://app.giorgi.ge 🔒, https://api.giorgi.ge/api/courses 🔒. http://-ით გახსნა ავტომატურად https://-ზე გადაგიყვანს.

რა შეცვალა certbot-მა

სლაიდი 12

certbot-მა server block-ი ორად გაყო:

sites-available/lms-api (certbot-ის შემდეგ)
server {    server_name api.giorgi.ge;    location / { proxy_pass http://127.0.0.1:5000; ... }     listen 443 ssl; # managed by Certbot    ssl_certificate /etc/letsencrypt/live/giorgi.ge/fullchain.pem; # managed by Certbot    ssl_certificate_key /etc/letsencrypt/live/giorgi.ge/privkey.pem; # managed by Certbot    include /etc/letsencrypt/options-ssl-nginx.conf; # managed by Certbot} server {    if ($host = api.giorgi.ge) {        return 301 https://$host$request_uri;    } # managed by Certbot    listen 80;    server_name api.giorgi.ge;    return 404; # managed by Certbot}
  • პირველი block — HTTPS (port 443): სერტიფიკატი (fullchain.pem) და პირადი გასაღები (privkey.pem).
  • მეორე block — HTTP (port 80): ყველაფერს 301-ით (მუდმივი redirect) HTTPS-ზე აგზავნის.
⚠️

privkey.pem — სერტიფიკატის პირადი გასაღები: იგივე პრინციპი, რაც SSH-ის პირადი გასაღებისთვის. certbot მას დახურული უფლებებით ინახავს — არ დააკოპირო და არ შეცვალო. კონფიგში # managed by Certbot ხაზებს არ ვშლით.

3 · საიდუმლოებები

ნაწილი 3 · კონფიგი და საიდუმლოებები

სლაიდი 14

LMS-ს ორი საიდუმლო აქვს: ბაზის პაროლი და — ავთენტიკაციის შემდეგ — JWT-ის ხელმოწერის გასაღები. ვინც JWT გასაღებს გაიგებს, ნებისმიერი user-ის სახელით „ტოკენს დაბეჭდავს“.

კონფიგურაციის რიგი: ვინ ვის ფარავს

ნაბიჯი 5 · proxy-ს უკან: API-ს ჰგონია, რომ http-ია

სლაიდი 17

HTTPS Nginx-ზე მთავრდება (TLS termination). API-მდე მოთხოვნა უკვე http-ით მიდის, Docker-ის შიდა მისამართიდან. ამიტომ API-ისთვის:

  • Request.Scheme = http — აპის მიერ შექმნილი ლინკები და redirect-ები http://-ით იქნება;
  • RemoteIpAddress = Docker-ის შიდა IP — ლოგებში ყველა მომხმარებელი ერთი IP-დან ჩანს.

Nginx ნამდვილ მონაცემებს header-ებით გადასცემს (მე-6 ლექციიდან გვაქვს): X-Forwarded-Proto: https და X-Forwarded-For: <მომხმარებლის IP>. API-მ ისინი უნდა წაიკითხოს — ამას ASP.NET Core-ის Forwarded Headers აკეთებს. ერთი გარემოს ცვლადით:

compose.yaml — api.environment
ASPNETCORE_FORWARDEDHEADERS_ENABLED: "true"

ეს ცვლადი რთავს Forwarded Headers-ს X-Forwarded-For-ისთვის და X-Forwarded-Proto-სთვის, და ენდობა proxy-ს Docker-ის ქსელიდანაც. ახლა Request.Scheme = https, IP — მომხმარებლის ნამდვილი.

💡

ეს ცვლადი სწორია, როცა API-ზე მხოლოდ Nginx-ის გავლით მიდიან — ჩვენთან ასეა: port 127.0.0.1-ზეა გამოტანილი (მე-8 ლექცია). თუ API ინტერნეტში პირდაპირ იქნებოდა ღია, ვინმე ამ header-ებს გააყალბებდა.

დავალება · DNS + server_name + certbot

ნაბიჯები

  • DNS-ში: A @ → <IP>, CNAME www → @, A api → <IP>, A app → <IP> → dig +short <domain> აბრუნებს IP-ს

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
A და CNAME ჩანაწერი — რა განსხვავებაა?
A — სახელი → IP მისამართი (api.giorgi.ge → 164.90.12.34). CNAME — სახელი → სხვა სახელი (www → giorgi.ge), რომლის IP-საც მერე DNS თვითონ პოულობს
ერთ სერვერზე, ერთ port 443-ზე სამი საიტია. როგორ იცის Nginx-მა, რომელი აჩვენოს?
ბრაუზერი მოთხოვნაში აგზავნის დომენს (Host header). Nginx მას server_name-ს ადარებს და შესაბამის server block-ს ირჩევს
რას აკეთებს certbot --nginx?
Let's Encrypt-ისგან იღებს უფასო სერტიფიკატს (ამოწმებს, რომ დომენი შენს სერვერზეა), Nginx-ის კონფიგს უმატებს listen 443 ssl-ს და HTTP → HTTPS redirect-ს, და აწყობს ავტომატურ განახლებას
Let's Encrypt-ის სერტიფიკატი 90 დღეა. ყოველ 3 თვეში ხელით უნდა განვაახლო?
არა — certbot-ის timer დღეში ორჯერ ამოწმებს და ვადის ამოწურვამდე 30 დღით ადრე თვითონ აახლებს. შემოწმება: sudo certbot renew --dry-run
JWT გასაღები სად ინახება შენთან და სად სერვერზე?
შენთან — dotnet user-secrets-ში (პროექტის საქაღალდის გარეთ). სერვერზე — .env-ში (chmod 600), საიდანაც Compose მას Jwt__Key ცვლადად გადასცემს. Git-ში — არასოდეს
API Nginx-ის უკანაა და HTTPS-ით იხსნება, მაგრამ აპს ჰგონია, რომ მოთხოვნა http-ით მოვიდა. რატომ და როგორ ვასწორებთ?
HTTPS Nginx-ზე მთავრდება, API-ს უკვე http სწვდება. Nginx ორიგინალს X-Forwarded-Proto-ში წერს; აპი მას წაიკითხავს, თუ ჩართულია ASPNETCORE_FORWARDEDHEADERS_ENABLED=true
