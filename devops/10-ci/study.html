CI/CD — თეორია და CI პრაქტიკაში

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 9 — დომენი, HTTPS და საიდუმლოებები. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
A და CNAME ჩანაწერი — რა განსხვავებაა?
A — სახელი → IP მისამართი (api.giorgi.ge → 164.90.12.34). CNAME — სახელი → სხვა სახელი (www → giorgi.ge), რომლის IP-საც მერე DNS თვითონ პოულობს
ერთ სერვერზე, ერთ port 443-ზე სამი საიტია. როგორ იცის Nginx-მა, რომელი აჩვენოს?
ბრაუზერი მოთხოვნაში აგზავნის დომენს (Host header). Nginx მას server_name-ს ადარებს და შესაბამის server block-ს ირჩევს
რას აკეთებს certbot --nginx?
Let's Encrypt-ისგან იღებს უფასო სერტიფიკატს (ამოწმებს, რომ დომენი შენს სერვერზეა), Nginx-ის კონფიგს უმატებს listen 443 ssl-ს და HTTP → HTTPS redirect-ს, და აწყობს ავტომატურ განახლებას
Let's Encrypt-ის სერტიფიკატი 90 დღეა. ყოველ 3 თვეში ხელით უნდა განვაახლო?
არა — certbot-ის timer დღეში ორჯერ ამოწმებს და ვადის ამოწურვამდე 30 დღით ადრე თვითონ აახლებს. შემოწმება: sudo certbot renew --dry-run
JWT გასაღები სად ინახება შენთან და სად სერვერზე?
შენთან — dotnet user-secrets-ში (პროექტის საქაღალდის გარეთ). სერვერზე — .env-ში (chmod 600), საიდანაც Compose მას Jwt__Key ცვლადად გადასცემს. Git-ში — არასოდეს
API Nginx-ის უკანაა და HTTPS-ით იხსნება, მაგრამ აპს ჰგონია, რომ მოთხოვნა http-ით მოვიდა. რატომ და როგორ ვასწორებთ?
HTTPS Nginx-ზე მთავრდება, API-ს უკვე http სწვდება. Nginx ორიგინალს X-Forwarded-Proto-ში წერს; აპი მას წაიკითხავს, თუ ჩართულია ASPNETCORE_FORWARDEDHEADERS_ENABLED=true

საშინაოს განხილვა

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: API და Angular — ქვედომენებზე, HTTPS-ით. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • lms-api → api.<domain>, app → app.<domain> (listen 80 + server_name) → certbot --nginx
  • ufw: წაშალეთ 8080/tcp, 8081/tcp, Nginx HTTP
  • .env-ში JWT_KEY (openssl rand) → compose: Jwt__Key და ASPNETCORE_FORWARDEDHEADERS_ENABLED
  • Angular: apiUrl: 'https://api.<domain>' → ng build → rsync

ამოხსნა

/etc/nginx/sites-available/lms-api
server {    listen 80;    server_name api.giorgi.ge;     location / {        proxy_pass http://127.0.0.1:5000;        proxy_http_version 1.1;        proxy_set_header Host $host;        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;        proxy_set_header X-Forwarded-Proto $scheme;    }}
Termius · lms-server
$ sudo nginx -t && sudo systemctl reload nginx$ sudo certbot --nginx -d api.giorgi.ge -d app.giorgi.ge$ sudo ufw delete allow 8080/tcp$ sudo ufw delete allow 8081/tcp$ sudo ufw delete allow 'Nginx HTTP'$ echo "JWT_KEY=$(openssl rand -base64 64 | tr -d '\n')" >> ~/lms/.env
compose.yaml — api
environment:  ASPNETCORE_ENVIRONMENT: ${ASPNETCORE_ENVIRONMENT:-Production}  ASPNETCORE_FORWARDEDHEADERS_ENABLED: "true"  ConnectionStrings__Default: "Host=db;Database=lms;Username=lms;Password=${DB_PASSWORD}"  Jwt__Key: ${JWT_KEY}

tr -d '\n' — openssl-ის შედეგიდან ხაზის გადატანებს შლის, რომ გასაღები .env-ში ერთ ხაზზე ჩაიწეროს.

დღის თემა

დღის თემა: CI/CD — თეორია და CI პრაქტიკაში

სლაიდი 4

LMS დომენზეა, HTTPS-ით, კონტეინერებში. მაგრამ ყოველი განახლება ჯერ კიდევ ხელით ხდება, და main-ში შეიძლება ისეთი კოდი მოხვდეს, რომელიც არც კი იკომპილირდება — ამას სერვერზე, deploy-ის დროს გაიგებ. დღეს ვნახავთ მთლიან სურათს: რა არის CI/CD, რა ნაბიჯებისგან შედგება pipeline და რატომ მუშაობს ასე ყველა თანამედროვე გუნდი. პრაქტიკაში კი ვწერთ CI-ს GitHub Actions-ით: ყოველ Pull Request-ზე LMS აეწყობა და ტესტებს გაივლის. CD — შემდეგ ლექციაზე.

ლექციის ბოლოს შეძლებ:

  • CI/CD-ის ახსნა: pipeline-ის ნაბიჯები build → test → artifact → deploy
  • Continuous Integration, Continuous Delivery და Continuous Deployment-ის გარჩევა და CI/CD-ის პრინციპები
  • GitHub Actions-ის ცნებები და პირველი workflow: trigger, job, runner, step, uses და run
  • CI ყოველ Pull Request-ზე: restore → build → test, და ჩავარდნილი CI-ის მიზეზის პოვნა ლოგით
  • branch protection — main-ში მხოლოდ მწვანე PR

1 · CI/CD

ნაწილი 1 · CI/CD — რა არის და რატომ

სლაიდი 5

მე-2 ლექციაზე Actions ჩანართში პირველი pipeline ვნახეთ — pages build and deployment, რომელიც GitHub-მა თვითონ შექმნა. დღეს ვხედავთ მთლიან სურათს: რა არის CI/CD, რა ნაბიჯებისგან შედგება და რატომ მუშაობს ასე ყველა თანამედროვე გუნდი. მერე პრაქტიკაში ვწერთ CI-ს; CD — შემდეგ ლექციაზე.

პრობლემა: ყოველი განახლება — ხელით

სლაიდი 6

მე-8 ლექციის შემდეგ LMS-ის განახლება ასე გამოიყურება:

ყოველ ჯერზე
$ git push# Termius → lms-server$ cd ~/lms$ git pull$ docker compose up -d --build
  • 😴 დაგავიწყდა — სერვერზე ძველი ვერსიაა;
  • 💥 main-ში მოხვდა კოდი, რომელიც არც კი იკომპილირდება — deploy ჩავარდება;
  • 👥 გუნდში ხუთი ადამიანია — ყველას სერვერზე SSH წვდომა ჰქონდეს?
  • 🐢 build 1 GB RAM-იან სერვერზე — ნელი და სახიფათო.

CI (Continuous Integration) — ყოველი ცვლილება ავტომატურად მოწმდება (build, ტესტები), სანამ main-ში მოხვდება. CD (Continuous Deployment) — main-ის ყოველი ცვლილება ავტომატურად გადის სერვერზე.

ორივეს GitHub Actions აკეთებს — ზუსტად იმ ნაბიჯებით, რასაც აქამდე ხელით ვაკეთებდით. დღეს ვხედავთ მთლიან სურათს და პრაქტიკაში ვწერთ CI-ს: main-ში მხოლოდ შემოწმებული კოდი უნდა მოხვდეს. შემდეგ ლექციაზე — CD პრაქტიკაში: შემოწმებულ კოდს სერვერზე ავტომატურად გავიტანთ.

pipeline — commit-იდან production-მდე

სლაიდი 7

pipeline — ავტომატური ნაბიჯების ჯაჭვი, რომელსაც ყოველი ცვლილება გადის, სანამ მომხმარებლამდე მივა:

ნაბიჯი რას აკეთებს ჩვენთან
commit · PR ცვლილება Git-ში feature/... → Pull Request
build კოდი იკომპილირდება? dotnet build
test კოდი სწორად მუშაობს? dotnet test
artifact გასაშვებად მზა „პაკეტი“ Docker image
deploy artifact სერვერზე docker compose pull && up -d
production მომხმარებელი ახალ ვერსიას ხედავს https://api.giorgi.ge

ჯაჭვი ორ ნაწილად იყოფა:

  • CI (Continuous Integration) — build და test ყოველ ცვლილებაზე, main-ში შერწყმამდე. პასუხობს კითხვას: „კოდი სწორია?“
  • CD (Continuous Delivery / Deployment) — შემოწმებული კოდიდან artifact-ის შექმნა და მისი გატანა სერვერზე. პასუხობს კითხვას: „კოდი მომხმარებელთანაა?“

მთავარი წესი: ნებისმიერ ნაბიჯზე შეცდომა pipeline-ს აჩერებს. ტესტი ჩავარდა — image არ აეწყობა და deploy არ მოხდება. ამიტომ გატეხილი კოდი production-მდე ვერ აღწევს.

📘 ტერმინები
pipeline
ავტომატური ნაბიჯების ჯაჭვი: build → test → artifact → deploy
artifact
pipeline-ის შედეგი, გასაშვებად მზა: ჩვენთან Docker image
production
„ცოცხალი“ გარემო, რომელსაც ნამდვილი მომხმარებლები იყენებენ

CI · Continuous Delivery · Continuous Deployment

სლაიდი 8

„CD“ ორ რამეს ნიშნავს, და ინტერვიუზე ამ განსხვავებას ხშირად კითხულობენ:

რა ხდება ავტომატურად ვინ წყვეტს production-ს
Continuous Integration build + test ყოველ ცვლილებაზე —
Continuous Delivery build, test და artifact; main ყოველთვის გასაშვებად მზადაა ადამიანი — ღილაკით (მაგ. ბანკები, სადაც გამოშვებას ამოწმებენ)
Continuous Deployment ყველაფერი, production-ის ჩათვლით pipeline — merge-ის შემდეგ თვითონ

ჩვენ LMS-ისთვის Continuous Deployment-ს ვაკეთებთ: merge main-ში = ახალი ვერსია სერვერზე.

პრინციპები, რომლებზეც CI/CD დგას:

  • 🐜 პატარა, ხშირი ცვლილებები. ერთდღიანი branch და პატარა PR. თვის განმავლობაში დაგროვილი დიდი merge — conflict-ები და „რომელმა ცვლილებამ გატეხა?“.
  • ⚡ სწრაფი პასუხი. შეცდომა უნდა გამოჩნდეს წუთებში, PR-ზე — და არა მაშინ, როცა მომხმარებელი მოგწერს.
  • 🏗️ ერთხელ აეწყობა — ყველგან ერთი. image ერთხელ იწყობა, და ზუსტად ის მიდის სერვერზე. სერვერზე ხელახლა აწყობა = რისკი, რომ სხვა რამ აეწყოს.
  • 🤖 ყველაფერი კოდით. pipeline YAML ფაილია რეპოში — მისი ცვლილებაც PR-ით და review-თი გადის.
✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
რა განსხვავებაა Continuous Delivery-სა და Continuous Deployment-ს შორის?
Delivery: კოდი ყოველთვის მზადაა გასაშვებად, production-ში გატანას ადამიანი წყვეტს ღილაკით. Deployment: merge-ის შემდეგ production-ში ავტომატურად მიდის

2 · CI

ნაწილი 2 · GitHub Actions და CI

სლაიდი 10

თეორია ვიცით. ახლა ვნახავთ, როგორ მუშაობს GitHub Actions ყველაზე მარტივ მაგალითზე, და მერე ვწერთ ნამდვილ CI-ს: ყოველ Pull Request-ზე LMS უნდა აეწყოს და ტესტები გაიაროს.

ცნებები: workflow · trigger · job · runner · step

სლაიდი 11
ცნება რა არის
workflow YAML ფაილი რეპოს .github/workflows/ საქაღალდეში
trigger (on:) როდის გაეშვას: push, pull_request, ხელით (workflow_dispatch), განრიგით
job ნაბიჯების ჯგუფი, რომელიც ერთ მანქანაზე სრულდება
runner (runs-on:) ეს მანქანა: GitHub-ის ვირტუალური Ubuntu, ყოველ გაშვებაზე ახალი და სუფთა
step ერთი ნაბიჯი: uses: — მზა action, run: — ბრძანება ტერმინალში
action მზა „ბლოკი“ (actions/checkout@v4) — მფლობელი/სახელი@ვერსია, როგორც NuGet პაკეტი

runner = ცარიელი სერვერი. მასზე შენი კოდი არ არის — ამიტომ პირველი ნაბიჯი ყოველთვის actions/checkout (რეპოს ჩამოტვირთვა). .NET SDK არ არის — actions/setup-dotnet. ეს ზუსტად ის, რასაც მე-6 ლექციაზე სერვერზე ხელით ვაკეთებდით, ოღონდ ყოველ ჯერზე ავტომატურად.

💡

public რეპოებისთვის GitHub-ის runner-ები უფასოა; private-ისთვის — თვეში შეზღუდული წუთები.

პირველი workflow — რა ხდება runner-ზე?

სლაიდი 12

სანამ LMS-ისთვის CI-ს დავწერთ, ვნახოთ, როგორ მუშაობს workflow ყველაზე მარტივ მაგალითზე. რეპოში ვქმნით ფაილს .github/workflows/hello.yml:

.github/workflows/hello.yml
name: Hello on:  push:  workflow_dispatch: jobs:  hello:    runs-on: ubuntu-latest    steps:      - run: echo "გამარჯობა, $GITHUB_ACTOR"      - run: uname -a && whoami      - run: ls -la      - uses: actions/checkout@v4      - run: ls -la
  • on: push — ყოველ push-ზე ნებისმიერ branch-ში; workflow_dispatch — Actions ჩანართში ჩნდება ღილაკი Run workflow, ხელით გასაშვებად;
  • run: — ჩვეულებრივი Linux ბრძანება, ზუსტად ისე, როგორც Termius-ში;
  • პირველი ls -la ცარიელს აჩვენებს: runner ახალი, სუფთა მანქანაა, შენი კოდი მასზე ჯერ არ არის;
  • actions/checkout@v4 რეპოს ჩამოტვირთავს — მეორე ls -la უკვე ფაილებს აჩვენებს.

push → Actions ჩანართი → Hello → job hello → ყოველი step-ის ლოგი ცალკე იხსნება.

⚠️

YAML-ში შეწევა (indentation) მნიშვნელობას ცვლის — ის აჩვენებს, რა რას ეკუთვნის. მხოლოდ space-ები, Tab — არასოდეს. - სიის ელემენტია: ყოველი step --ით იწყება. თუ workflow Actions-ში საერთოდ არ გამოჩნდა — ჯერ შეამოწმე, ფაილი ზუსტად .github/workflows/-შია და YAML სწორადაა შეწეული.

სლაიდი 13

dotnet build ამოწმებს, რომ კოდი იკომპილირდება. მაგრამ კოდი, რომელიც იკომპილირდება, შეიძლება არასწორად მუშაობდეს: კურსზე ტევადობაზე მეტი სტუდენტი ჩაეწეროს, ფასი არასწორად დაითვალოს. ამას ტესტი ამოწმებს — პატარა მეთოდი, რომელიც შენს კოდს იძახებს და შედეგს ამოწმებს.

ტესტების სრული თემა ცალკე საკითხია. CI-სთვის ერთი ტესტიც საკმარისია, რომ ნახო, როგორ აჩერებს ის გატეხილ კოდს:

ნაბიჯი 1 · ci.yml — ყოველ Pull Request-ზე

სლაიდი 14
.github/workflows/ci.yml
name: CI on:  pull_request:    branches: [main] jobs:  build:    runs-on: ubuntu-latest    steps:      - uses: actions/checkout@v4      - uses: actions/setup-dotnet@v4        with:          dotnet-version: '10.0.x'      - run: dotnet restore      - run: dotnet build --no-restore -c Release      - run: dotnet test --no-build -c Release
  • on: pull_request → branches: [main] — ყოველ PR-ზე, რომელიც main-ში უნდა შეირწყას (და მის ყოველ ახალ push-ზე);
  • jobs: build: — ერთი job, სახელით build (ეს სახელი branch protection-ში დაგვჭირდება);
  • with: — action-ის პარამეტრები; 10.0.x — .NET 10-ის უახლესი patch;
  • --no-restore / --no-build — წინა ნაბიჯი უკვე გაკეთდა, თავიდან აღარ ვაკეთებთ.

push → Actions ჩანართში ჩანს გაშვება: ყოველი step-ის ლოგი, ხანგრძლივობა, შეცდომა. PR-ის გვერდზე კი — ❌ ან ✅.

👉

შეადარე ხელით deploy-ს (მე-6 ლექცია): იქაც restore → build → publish ვაკეთებდით, ოღონდ სერვერზე და ხელით. CI იგივე ბრძანებებია, ოღონდ ყოველ PR-ზე, ავტომატურად და სუფთა მანქანაზე.

განზრახ ვამტვრევთ: ❌ → ✅

  1. branch feature/break-enroll → Enroll-ში ტევადობის შემოწმებას ვშლით → commit → push → Pull Request;

CI ჩავარდა? თანმიმდევრობა ყოველთვის ერთია: რომელ step-ზე → მისი ლოგის ბოლო ხაზები → იგივე ბრძანება შენთან (dotnet build, dotnet test). თუ შენთან მუშაობს და CI-ზე არა — ეძებე განსხვავება გარემოში: .NET-ის ვერსია, ფაილის სახელის ასოები (Linux!), ფაილი, რომელიც .gitignore-შია.

ნაბიჯი 2 · branch protection: main — მხოლოდ მწვანე PR-ით

სლაიდი 16

CI სასარგებლოა მხოლოდ მაშინ, თუ წითელ PR-ს ვერ შეურწყავ. ამას branch protection აკეთებს.

რეპოს Settings → Rules → Rulesets → New branch ruleset (ძველ ინტერფეისში: Settings → Branches → Add branch protection rule):

  • Target branches: main (Include default branch);
  • ✓ Require a pull request before merging — პირდაპირ push main-ში აკრძალულია;
  • ✓ Require status checks to pass → დაამატე build (ჩვენი CI job-ის სახელი).
⚠️

build სიაში მხოლოდ მას შემდეგ ჩნდება, რაც CI ერთხელ მაინც გაეშვა. ამიტომ ჯერ PR და CI, მერე — ruleset.

ამიერიდან გზა ერთია — ის, რაც მე-2 ლექციაზე branch-ებით დავიწყეთ:

  1. feature/... branch → git push;
  2. Pull Request GitHub-ზე — ცვლილების აღწერა;
  3. CI ავტომატურად აწყობს კოდს → ❌ ან ✅;
  4. review — გუნდელი კითხულობს კოდს, წერს კომენტარებს;
  5. merge main-ში → შემდეგ ლექციაზე აქედან ავტომატური deploy დაიწყება (CD).

$ git push origin main
👉

Pull Request-ში review გუნდურ მუშაობაში ერთ-ერთი ყველაზე მნიშვნელოვანი ჩვევაა — junior-ისთვის მის კოდზე დაწერილი კომენტარი ყველაზე სწრაფი სწავლაა.

შპარგალკა: CI

სლაიდი 17

workflow-ის ჩონჩხი: .github/workflows/*.yml → on (როდის) → jobs → runs-on: ubuntu-latest → steps (uses — მზა action, run — ბრძანება).

CI-ის ნაბიჯები .NET-ისთვის: actions/checkout@v4 → actions/setup-dotnet@v4 (10.0.x) → dotnet restore → dotnet build --no-restore -c Release → dotnet test --no-build -c Release.

გზა main-მდე: branch → push → Pull Request → CI ❌ → ლოგი → გასწორება → push → CI ✅ → review → merge.

თუ არ მუშაობს: workflow არ ჩანს → ფაილი .github/workflows/-შია? YAML-ში Tab ხომ არ არის? → step წითელია → მისი ლოგის ბოლო ხაზები → იგივე ბრძანება შენთან.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
CI და CD — რა განსხვავებაა?
CI (Continuous Integration) — ყოველი ცვლილების ავტომატური შემოწმება (build, ტესტები) main-ში შერწყმამდე. CD (Continuous Deployment) — main-ის ყოველი ცვლილების ავტომატური გაშვება სერვერზე
Continuous Delivery და Continuous Deployment — რა განსხვავებაა?
Delivery: main ყოველთვის მზადაა გასაშვებად, production-ში გატანას ადამიანი წყვეტს ღილაკით. Deployment: merge-ის შემდეგ ახალი ვერსია production-ში ავტომატურად მიდის — ჩვენ LMS-ისთვის ამას ვაკეთებთ
pipeline-ში ტესტი ჩავარდა. რა მოხდება შემდეგ ნაბიჯებზე?
pipeline ჩერდება: artifact (image) არ აეწყობა და deploy არ მოხდება — გატეხილი კოდი production-მდე ვერ მივა
uses: და run: — რა განსხვავებაა step-ში?
uses — მზა action-ის გამოყენება (მაგ. actions/checkout@v4), run — ბრძანება runner-ის ტერმინალში (მაგ. dotnet build)
workflow-ში პირველი ls -la ცარიელს აჩვენებს. რატომ?
runner ყოველ გაშვებაზე ახალი, სუფთა ვირტუალური Ubuntu-ა — შენი კოდი მასზე მხოლოდ actions/checkout-ის შემდეგ ჩნდება
რატომ არ ეყოფა CI-ს მხოლოდ dotnet build?
build ამოწმებს, რომ კოდი იკომპილირდება, მაგრამ არა — რომ სწორად მუშაობს. ამას dotnet test ამოწმებს: ჩავარდნილი ტესტი CI-ს წითლად აქცევს
PR-ზე CI წითელია, შენთან კი ყველაფერი მუშაობს. რას შეამოწმებ?
რომელ step-ზე ჩავარდა და მისი ლოგის ბოლო ხაზები; მერე — გარემოს განსხვავება: .NET-ის ვერსია, ფაილის სახელის დიდი/პატარა ასოები (runner Linux-ია), ფაილი, რომელიც .gitignore-შია
რას იძლევა branch protection main-ზე?
main-ში პირდაპირ push აღარ შეიძლება — მხოლოდ Pull Request-ით, და merge მხოლოდ მაშინ, როცა CI მწვანეა

შეჯამება · დღეს ვისწავლეთ

სლაიდი 20
  • 🔁 CI/CD — pipeline: commit → build → test → artifact → deploy → production; ნებისმიერ ნაბიჯზე შეცდომა მას აჩერებს. CI — „კოდი სწორია?“, CD — „კოდი მომხმარებელთანაა?“. Continuous Delivery — production-ს ადამიანი წყვეტს ღილაკით; Continuous Deployment — merge-ის შემდეგ ავტომატურად. პრინციპები: პატარა ცვლილებები, სწრაფი პასუხი, ერთხელ აეწყობა, ყველაფერი კოდით.
  • ⚙️ GitHub Actions — .github/workflows/*.yml: trigger (on), job, runner (runs-on: ubuntu-latest), steps (uses / run).
  • 🖥️ runner — GitHub-ის სუფთა ვირტუალური Ubuntu, ყოველ გაშვებაზე ახალი: კოდი მხოლოდ actions/checkout-ის შემდეგ ჩნდება, .NET — actions/setup-dotnet-ის შემდეგ.
  • 🧪 CI — ci.yml ყოველ PR-ზე: checkout → setup-dotnet → restore → build → test. ჩავარდნისას: რომელი step → ლოგის ბოლო ხაზები → იგივე ბრძანება შენთან.
