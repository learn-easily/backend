Docker — აპი გარემოსთან ერთად

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

გამეორება

გავიხსენოთ წინა ლექცია

სლაიდი 1

ლექცია 6 — LMS API სერვერზე — ხელით. ახალ თემამდე ვამოწმებთ, რა დაგვამახსოვრდა. ჯერ თვითონ უპასუხე, მერე გახსენი პასუხი. თუ რომელიმე გაგიჭირდა, წინა ლექციის კონსპექტს გადახედე.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
რატომ ვაყენებთ სერვერზე aspnetcore-runtime და არა SDK-ს?
სერვერზე კოდს არ ვწერთ და არ ვაკომპილირებთ — მხოლოდ მზა (publish-ებულ) აპს ვუშვებთ. runtime ამისთვის საკმარისია და SDK-ზე ბევრად პატარაა
რას აკეთებს dotnet publish -c Release -o ./publish?
აპს Release რეჟიმში აკომპილირებს და გასაშვებად საჭირო ყველა ფაილს (.dll, appsettings.json…) ერთ საქაღალდეში — publish-ში — აგროვებს
systemd სერვისში რას აკეთებს Restart=always?
თუ API crash-დება, systemd მას რამდენიმე წამში თავიდან რთავს. enable-თან ერთად API სერვერის reboot-ის შემდეგაც ავტომატურად ირთვება
რა არის reverse proxy და რატომ არ ვხსნით Kestrel-ს პირდაპირ ინტერნეტში?
Nginx იღებს მოთხოვნას და proxy_pass-ით გადასცემს API-ს, რომელიც მხოლოდ 127.0.0.1-ზე უსმენს. Nginx ერთ IP-ზე ბევრ აპს ემსახურება, მოგვიანებით HTTPS-ს ამუშავებს და ლოგებს წერს
ბრაუზერი აბრუნებს 502 Bad Gateway. რას ნიშნავს და სად ეძებ მიზეზს?
Nginx მუშაობს, მაგრამ API-მ არ უპასუხა — ის გაჩერებულია ან crash-დება. systemctl status lms-api და journalctl -u lms-api -n 50
როგორ აწვდის systemd API-ს connection string-ს და რატომ ვწერთ __-ს?
Environment= ხაზით გარემოს ცვლადად. ASP.NET Core ConnectionStrings__Default-ს კითხულობს, როგორც ConnectionStrings:Default-ს — __ JSON-ის ჩადგმულ დონეს ნიშნავს

საშინაოს განხილვა

სლაიდი 3

წინა ლექციის საშინაო: API — სერვისად და Nginx-ის უკან. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • lms-api.service (Restart=always, URL, connection string) → daemon-reload → enable --now
  • Nginx: listen 8081 + proxy_pass http://127.0.0.1:5000 → ufw allow 8081/tcp
  • crash-ის ტესტი: kill -9 <PID> → 5 წამში ისევ running
  • README-ში — ყველა ნაბიჯი, რაც პროექტის გასაშვებად გადადგით

ამოხსნა

/etc/systemd/system/lms-api.service
[Unit]Description=LMS APIAfter=network.target postgresql.service [Service]WorkingDirectory=/var/www/lms-apiExecStart=/usr/bin/dotnet /var/www/lms-api/Lms.Api.dllRestart=alwaysRestartSec=5User=www-dataEnvironment=ASPNETCORE_ENVIRONMENT=ProductionEnvironment=ASPNETCORE_URLS=http://127.0.0.1:5000Environment="ConnectionStrings__Default=Host=localhost;Database=lms;Username=lms;Password=Str0ng!Pass" [Install]WantedBy=multi-user.target

დღის თემა

დღის თემა: Docker — აპი გარემოსთან ერთად

სლაიდი 4

წინა ლექციაზე LMS-ის გასაშვებად 10-ზე მეტი ნაბიჯი დაგვჭირდა: სწორი runtime, ბაზის დაყენება, ცვლადები… ახალ სერვერზე ან გუნდელის კომპიუტერზე — ყველაფერი თავიდან, და „ჩემთან მუშაობს“. Docker აპს მთელ გარემოსთან ერთად ერთ „ყუთში“ — კონტეინერში — ალაგებს, რომელიც ყველგან ერთნაირად ეშვება. დღეს PostgreSQL-ს ერთი ბრძანებით გავუშვებთ და LMS-ს Dockerfile-ს დავუწერთ.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რა არის image და container (კლასი და ობიექტი) და რით განსხვავდება კონტეინერი ვირტუალური მანქანისგან
  • მზა image-ის გაშვება: docker run — port-ები, გარემოს ცვლადები, volume
  • კონტეინერების მართვა: ps, logs, exec, stop, rm
  • LMS-ის multi-stage Dockerfile-ის დაწერა და .dockerignore
  • საკუთარი image-ის აწყობა docker build-ით და გაშვება

1 · კონტეინერი

ნაწილი 1 · რა არის კონტეინერი

სლაიდი 5

იდეა, ტერმინები და პირველი სასარგებლო კონტეინერი — PostgreSQL ინსტალაციის გარეშე.

პრობლემა: „ჩემთან მუშაობს“ — სერვერზე არა

სლაიდი 6

ერთი და იგივე LMS სამ ადგილას:

შენი ლეპტოპი გუნდელის ლეპტოპი სერვერი
OS Windows 11 macOS Ubuntu 24.04
.NET 10.0.3 SDK 9 SDK 10.0.1 runtime
ბაზა SQL Server LocalDB PostgreSQL 15 PostgreSQL 16, ხელით დაყენებული

ყოველ ადგილას გარემო ცოტა სხვანაირია — და ყოველი განსხვავება შეიძლება „უცნაური“ შეცდომის მიზეზი გახდეს. წინა ლექციაზე სერვერის მოსამზადებლად 10-ზე მეტი ხელით ნაბიჯი დაგვჭირდა.

ანალოგია. 1950-იანებამდე გემზე ტვირთს ცალ-ცალკე ტვირთავდნენ — ტომრები, კასრები, ყუთები — და ყოველ პორტში სხვანაირად. მერე გამოიგონეს სტანდარტული საზღვაო კონტეინერი: შიგნით რაც არ უნდა იყოს, გარედან ყველა ერთნაირია — ერთნაირად იტვირთება ნებისმიერ გემზე, მატარებელზე, სატვირთოზე.

Docker იგივეს აკეთებს პროგრამებისთვის.

image = კლასი · container = ობიექტი

სლაიდი 7

C#-ში უკვე იცი ეს იდეა:

C#
class Course { ... }            // შაბლონიvar c1 = new Course();          // ეგზემპლარიvar c2 = new Course();          // კიდევ ერთი, დამოუკიდებელი

Docker-ში:

ტერმინი რა არის C# ანალოგია
image აპი + runtime + საჭირო ფაილები, „გაყინული“ — მხოლოდ წასაკითხი შაბლონი კლასი
container image-იდან გაშვებული ეგზემპლარი: საკუთარი იზოლირებული ფაილებით, ქსელით, პროცესებით ობიექტი
registry image-ების საცავი, საიდანაც docker მათ ჩამოტვირთავს NuGet

ცნობილი registry-ები: Docker Hub (postgres, nginx, redis...), mcr.microsoft.com (Microsoft-ის .NET image-ები), GHCR (GitHub-ის — მე-11 ლექციაზე გამოვიყენებთ).

image-ის სახელი: postgres:17 — სახელი:tag, სადაც tag ჩვეულებრივ ვერსიაა. latest — ნაგულისხმევი tag.

კონტეინერი vs ვირტუალური მანქანა

სლაიდი 8

ვირტუალური მანქანა (VM — მაგ. ჩვენი Droplet) — მთელი კომპიუტერის იმიტაცია: თავისი სრული OS-ით. ყოველი VM რამდენიმე GB-ია და ჩართვას წუთები სჭირდება.

კონტეინერი მთელ OS-ს არ შეიცავს: ყველა კონტეინერი ერთ საერთო Linux-ის ბირთვს იყენებს, თითოეულს კი მხოლოდ საკუთარი ფაილები, ბიბლიოთეკები და აპი აქვს. ამიტომ კონტეინერი MB-ებია და წამებში ირთვება.

VM კონტეინერი
შეიცავს მთელ OS-ს აპს და მის ფაილებს
ზომა GB-ები MB-ები
ჩართვა წუთები წამები
იზოლაცია ძალიან ძლიერი ძლიერი, საკმარისი აპებისთვის

ისინი ერთმანეთს არ ცვლის: ჩვენ Droplet-ზე (VM) კონტეინერებს გავუშვებთ.

💡

Windows-ზე Docker Desktop კონტეინერებს WSL 2-ის Linux-ში უშვებს — სწორედ ამიტომ გჭირდებოდათ virtualization BIOS-ში.

ნაბიჯი 1 · PostgreSQL — ერთი ბრძანებით

სლაიდი 9

ჯერ შემოწმება — Docker Desktop ჩართულია და მუშაობს:

WSL
$ docker run hello-world

ახლა — წინა ლექციის „PostgreSQL-ის დაყენება + user + ბაზა“, ერთი ბრძანებით:

WSL
$ docker run -d --name lms-db \    -e POSTGRES_USER=lms \    -e POSTGRES_PASSWORD=dev \    -e POSTGRES_DB=lms \    -p 5432:5432 \    -v lms-data:/var/lib/postgresql/data \
ნაწილი რას ნიშნავს
-d detached — ფონზე, terminal-ი თავისუფალი რჩება
--name lms-db სახელი, რომლითაც კონტეინერს მივმართავთ
-e POSTGRES_USER=lms … გარემოს ცვლადები: image პირველ გაშვებაზე თვითონ ქმნის user-ს, პაროლს და ბაზას
-p 5432:5432 ჰოსტის-port:კონტეინერის-port — შენი კომპიუტერის 5432 → კონტეინერის 5432
-v lms-data:/var/lib/postgresql/data volume — სადაც PostgreSQL მონაცემებს ინახავს (იხ. შემდეგი სლაიდები)
postgres:17 image Docker Hub-იდან, ვერსია 17

პირველად Docker image-ს ჩამოტვირთავს (pull), შემდეგ ჯერზე — უკვე ლოკალურად აქვს.

WSL
$ docker psCONTAINER ID  IMAGE        STATUS        PORTS                   NAMES

LMS-ის connection string ლოკალურად: Host=localhost;Database=lms;Username=lms;Password=dev → dotnet ef database update → dotnet run. ბაზა მზადაა — ინსტალაციის გარეშე.

ნაბიჯი 2 · კონტეინერების მართვა

სლაიდი 10
WSL
$ docker ps                     # მუშა კონტეინერები$ docker ps -a                  # ყველა, გაჩერებულებიც$ docker logs -f lms-db         # ლოგი ცოცხლად (Ctrl+C — გამოსვლა)$ docker exec -it lms-db psql -U lms     # ბრძანება კონტეინერის შიგნით$ docker stop lms-db            # გაჩერება$ docker start lms-db           # ჩართვა$ docker rm -f lms-db           # წაშლა (-f: გაჩერებულიც და მუშაც)
ბრძანება ანალოგია უკვე ნასწავლიდან
docker ps ps aux / systemctl status
docker logs -f journalctl -u … -f
docker exec -it <name> bash ssh — „შესვლა“ კონტეინერში
docker stop / start systemctl stop / start

exec -it: -i — შეყვანა ღიაა, -t — ტერმინალი. docker exec -it lms-db bash — Linux-ის ტერმინალი კონტეინერის შიგნით (exit — გამოსვლა).

volume — კონტეინერი ქრება, მონაცემები რჩება

სლაიდი 11

კონტეინერის ფაილები დროებითია: docker rm — და ყველაფერი, რაც კონტეინერის შიგნით შეიქმნა, ქრება. აპისთვის ეს კარგია (ახალი ვერსია = ახალი კონტეინერი, სუფთა). ბაზისთვის — კატასტროფა.

volume — Docker-ის მიერ მართული საცავი დისკზე, რომელიც კონტეინერის შიგნით საქაღალდედ ჩანს:

plain
-v lms-data:/var/lib/postgresql/data   ↑ volume     ↑ საქაღალდე კონტეინერში, სადაც PostgreSQL მონაცემებს წერს

ექსპერიმენტი:

WSL
$ docker rm -f lms-db$ docker run -d --name lms-db ... -v lms-data:/var/lib/postgresql/data postgres:17$ docker exec -it lms-db psql -U lms -c 'SELECT * FROM "Courses";'
WSL
$ docker volume ls              # ყველა volume
⚠️

ბაზის კონტეინერს ყოველთვის volume სჭირდება. volume-ის გარეშე docker rm (ან სერვერზე კონტეინერის განახლება) = ბაზა წაიშალა.

ნაწილი 2 · Dockerfile LMS-სთვის

სლაიდი 13

postgres:17 ვიღაცამ ააწყო. LMS-ის image ჩვენ თვითონ უნდა ავაწყოთ — Dockerfile-ით: ტექსტური „რეცეპტით“, რომელშიც ნაბიჯ-ნაბიჯ წერია, როგორ.

ნაბიჯი 3 · Dockerfile: ორი ეტაპი

სლაიდი 14

LMS-ის რეპოს root-ში (იქ, სადაც .sln-ია) — ფაილი Dockerfile (გაფართოების გარეშე):

Dockerfile
# ── ეტაპი 1: build (SDK) ──FROM mcr.microsoft.com/dotnet/sdk:10.0 AS buildWORKDIR /srcCOPY Lms.Api/Lms.Api.csproj Lms.Api/RUN dotnet restore Lms.Api/Lms.Api.csprojCOPY . .RUN dotnet publish Lms.Api/Lms.Api.csproj -c Release -o /app/publish # ── ეტაპი 2: runtime (მხოლოდ გაშვება) ──FROM mcr.microsoft.com/dotnet/aspnet:10.0WORKDIR /appCOPY --from=build /app/publish .USER $APP_UIDEXPOSE 8080ENTRYPOINT ["dotnet", "Lms.Api.dll"]
ინსტრუქცია რას აკეთებს
FROM <image> AS build საწყისი image; AS — ეტაპის სახელი
WORKDIR /src მიმდინარე საქაღალდე image-ის შიგნით (არ არსებობს — შეიქმნება)
COPY <შენთან> <image-ში> ფაილების კოპირება
RUN <ბრძანება> ბრძანება აწყობისას (restore, publish)
COPY --from=build ფაილები წინა ეტაპიდან
USER $APP_UID .NET-ის image-ში მზა არა-root user app
EXPOSE 8080 დოკუმენტაცია: აპი 8080-ს უსმენს (.NET image-ის ნაგულისხმევი port)
ENTRYPOINT ბრძანება, რომელიც კონტეინერის ჩართვისას სრულდება

რატომ ორი ეტაპი (multi-stage)? აწყობას SDK სჭირდება (დიდია), გაშვებას — მხოლოდ runtime (წინა ლექციის იგივე იდეა). საბოლოო image მხოლოდ მეორე ეტაპია: მასში არ არის SDK და შენი საწყისი კოდი — ის პატარაა და უსაფრთხო.

💡

Lms.Api — პროექტის საქაღალდე და სახელი. შენი თუ სხვაა, შეცვალე. თუ რამდენიმე პროექტია (მაგ. ცალკე class library), COPY ყველა .csproj-ისთვის დაამატე, ან უბრალოდ COPY . . → restore.

ნაბიჯი 4 · ფენები და .dockerignore

სლაიდი 15

ფენები (layers). Dockerfile-ის ყოველი ინსტრუქცია ქმნის ფენას და Docker მას ქეშავს. თუ ფენის შემავალი არ შეცვლილა, Docker მას ხელახლა აღარ ასრულებს:

docker build — მეორედ, კოდის ცვლილების შემდეგ
① COPY Lms.Api/Lms.Api.csproj      ✓ CACHED② RUN dotnet restore               ✓ CACHED   ← NuGet პაკეტები აღარ იტვირთება③ COPY . .                         ↻ კოდი შეიცვალა④ RUN dotnet publish               ↻

ამიტომ ჯერ მხოლოდ .csproj-ს ვაკოპირებთ და restore-ს ვუშვებთ: პაკეტები იშვიათად იცვლება, კოდი — ხშირად. COPY . . რომ პირველი ყოფილიყო, კოდის ყოველი ცვლილება restore-ს თავიდან გაუშვებდა.

.dockerignore — როგორც .gitignore, ოღონდ docker build-ისთვის: ეს ფაილები build-ში არ გადაიგზავნება.

.dockerignore
**/bin/**/obj/.git/.vs/.vscode/*.user

ლოკალური bin/ და obj/ image-ში არ გვინდა — publish თავისას შექმნის. ნაკლები ფაილი = სწრაფი build და სუფთა image.

✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
image და container — რა განსხვავებაა?
image — შაბლონი (როგორც კლასი C#-ში): აპი + runtime + ყველა ფაილი, მხოლოდ წასაკითხად. container — image-იდან გაშვებული ეგზემპლარი (როგორც ობიექტი). ერთი image-იდან ბევრი container შეიძლება
-p 8080:8080-ში რომელი რიცხვი რას ნიშნავს?
ჰოსტის-port:კონტეინერის-port — შენი კომპიუტერის 8080-ზე მოსული მოთხოვნა კონტეინერის შიგნით 8080-ზე მიდის
PostgreSQL-ის კონტეინერი წავშალე. მონაცემები დაიკარგა?
თუ volume (-v lms-data:/var/lib/postgresql/data) იყო მიბმული — არა, მონაცემები volume-ში რჩება და ახალი კონტეინერი მათ დაინახავს. volume-ის გარეშე — კი, ყველაფერი წაიშალა
რატომ აქვს Dockerfile-ს ორი FROM (multi-stage)?
პირველი ეტაპი (sdk) აპს აწყობს — მას SDK სჭირდება. მეორე (aspnet) მხოლოდ მზა ფაილებს იღებს და runtime-ზე უშვებს — საბოლოო image ბევრად პატარა და უსაფრთხოა, მასში SDK და კოდი არ არის
რატომ ვაკოპირებთ ჯერ მხოლოდ .csproj-ს და ვუშვებთ restore-ს, მერე დანარჩენს?
Docker ყოველ ნაბიჯს (layer) ქეშავს. თუ .csproj არ შეცვლილა, restore ქეშიდან აიღება — კოდის ცვლილებისას build ბევრად სწრაფია
რისთვის არის .dockerignore?
build-ში არ გადაიგზავნოს ზედმეტი: bin/, obj/, .git, .vs — build სწრაფია, image სუფთა, და ლოკალური საიდუმლოებები image-ში არ ხვდება
