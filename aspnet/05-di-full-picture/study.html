დღის თემა

დღის თემა: Dependency Injection: სრული სურათი

სლაიდი 4

წინა ლექციაზე ერთმა Controller-მა ერთი Store ითხოვა. რეალურ პროექტში კლასს კლასი სჭირდება, იმას — კიდევ რამდენიმე, და ლოგიკა Controller-ში აღარ ეტევა. დღეს ვნახავთ DI-ს სრულ სურათს: ვინ აწყობს დამოკიდებულებების ჯაჭვს, რა სერვისები აქვს framework-ს უკვე მზად და რა არ უნდა გავაკეთოთ.

ლექციის ბოლოს შეძლებ:

  • Controller → Service → Store ჯაჭვის აწყობა: ვის რა საქმე აქვს
  • dependency-ს მოთხოვნის გზები: constructor, [FromServices] action-ში, primary constructor
  • ILogger და IConfiguration გამოყენება რეგისტრაციის გარეშე
  • Service Locator-ის ამოცნობა და lifetime-ის მნიშვნელობა

ლექციის გეგმა

სლაიდი 5
  1. შეკვეთები — პირველი დამოკიდებულებების ჯაჭვი: კლასი, რომელსაც კლასი სჭირდება, რომელსაც კიდევ კლასი სჭირდება.
  2. Framework-ის სერვისები — ILogger და IConfiguration, რომლებიც უკვე Container-შია.
  3. ჩანაწერის გზები — constructor, action-ის პარამეტრი, primary constructor.
  4. როგორ არ უნდა — Service Locator და ერთი ექსპერიმენტი lifetime-ზე.

Container მთელ ჯაჭვს თვითონ აწყობს

სლაიდი 13

Container constructor-ებს კითხულობს:

  1. OrdersController უნდა შექმნას → მის constructor-ს კითხულობს: OrderService სჭირდება.
  2. OrderService-ის შესაქმნელად — მის constructor-საც კითხულობს: ProductStore და OrderStore.
  3. ProductStore ♻️ უკვე არსებობს (Singleton — ProductsController-მა უკვე გამოიყენა) → იმავეს იღებს. OrderStore 🆕 ჯერ არ არსებობს → ქმნის.
  4. ⬆ ქვემოდან ზემოთ: ჯერ Store-ები, მერე OrderService, ბოლოს OrdersController.

ჯაჭვი რამდენი რგოლიც არ უნდა იყოს, Container ერთნაირად აწყობს.

Anti-pattern: Service Locator

სლაიდი 25
OrdersController.cs · ❌ ასე არა
public class OrdersController : ControllerBase{    // constructor ცარიელია — თითქოს არაფერი სჭირდება     [HttpGet]    public IActionResult GetAll()    {        var orderService = HttpContext.RequestServices            .GetRequiredService<OrderService>();         return Ok(orderService.GetAll());    }}

ეს მუშაობს — მეთოდის შიგნით Container-ს პირდაპირ ვთხოვთ ობიექტს. მაგრამ:

  • მალავს: constructor-ზე არ ჩანს, რას იყენებს კლასი. შეხედავ და იფიქრებ — არაფერი სჭირდება.
  • შეცდომა გვიან ჩანს: რეგისტრაცია თუ დაგავიწყდა, constructor-ით შეცდომა Controller-ის შექმნისთანავე ჩანს; აქ — მხოლოდ მაშინ, როცა ვინმე სწორედ ამ endpoint-ს გამოიძახებს. შეიძლება კვირების შემდეგ.

წესი: ითხოვე constructor-ით (ან პარამეტრით) — Container-ს ნუ ეძებ.

📘 ტერმინები
Service Locator
როცა კლასი Container-ს თვითონ ეკითხება ობიექტს, ნაცვლად იმისა, რომ constructor-ით მოითხოვოს. ცუდ პრაქტიკად ითვლება

POST „მონიტორი“ → 201. GET → ისევ 3 პროდუქტი 😱

Transient = „ყოველ ჯერზე, როცა ვინმე ითხოვს — ახალი“. ეს ზუსტად ის ბაგია, რაც წინა ლექციაზე new-ით გვქონდა! ანუ როგორ დავარეგისტრირებთ, მნიშვნელოვანია. ამას lifetime ჰქვია — ობიექტის სიცოცხლის ხანგრძლივობა:

Lifetime რამდენი ობიექტი
Singleton ერთი — მთელ აპლიკაციაზე
Scoped ერთი — ერთ HTTP მოთხოვნაზე
Transient ახალი — ყოველ მოთხოვნისას (ყოველ ჯერზე, როცა ვინმე ითხოვს)

რომელი როდის — მონაცემთა ბაზასთან ერთად ვნახავთ, იქ ყველაზე კარგად ჩანს.
