წინა ლექციის საშინაო: შენი სფერო: მთლიანად Vertical Slices-ზე. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

დღის თემა

დღის თემა: Rich Entity, Value Object და Result

სლაიდი 4

09-ის საშინაოში ერთი კითხვა დარჩა: Create-ისა და Update-ის შემოწმებები ისევ მეორდება, Email ოთხ ადგილას სუფთავდება, ნებისმიერ კოდს კი შეუძლია დაწეროს course.DurationWeeks = -5. Entity ჯერ მხოლოდ მონაცემების ყუთია და თავის წესებს ვერ იცავს. დღეს წესებს მათ ნამდვილ ადგილას გადავიტანთ: entity-ში და Value Object-ში. შეცდომას exception-ით კი არ ვისვრით, Result-ით დავაბრუნებთ. ბოლოს ამ ყველაფრით ახალ feature-ს ვწერთ: ჯგუფებს.

ლექციის ბოლოს შეძლებ:

  • ანემიური და rich entity-ის განსხვავება: ვინ იცავს წესს და რატომ
  • Result pattern: მოსალოდნელი შეცდომა დაბრუნებით, exception-ის გარეშე
  • Value Object Email: ერთხელ შემოწმებული, ყველგან სანდო · EF Core-ის HasConversion
  • ახალი feature: ჯგუფი (Group), rich entity-დ, ≤ 20 ადგილით

სადაც შევჩერდით

სლაიდი 5

09-ის საშინაოს ბოლოს ერთი კითხვა დარჩა: Create-ისა და Update-ის შემოწმებები ისევ მეორდება. VSA-მ ეს რატომ ვერ მოაგვარა?

VSA ფაილებს feature-ის მიხედვით ალაგებს, წესების ადგილს კი არ ცვლის. დღეს LMS-ში სამი პრობლემა გვაქვს:

  1. ერთი წესი ორჯერ. „ხანგრძლივობა 1–52 კვირა“ CreateCourse-შიც წერია და UpdateCourse-შიც. თუ ბიზნესი იტყვის „ახლა 1–40“, ორივე უნდა შეცვალო და ერთი შეიძლება დაგავიწყდეს.
  2. Email ოთხ ადგილას სუფთავდება. Trim().ToLowerInvariant() Student-ის და Lecturer-ის Create-შიც და Update-შიც.
  3. entity-ს არავინ იცავს. ნებისმიერ კოდს შეუძლია დაწეროს course.DurationWeeks = -5;: კომპილირდება, ბაზაშიც ჩაიწერება.

დღეს წესებს მათ ნამდვილ ადგილას გადავიტანთ: entity-ში და Value Object-ში.

1 · Rich Entity

ნაწილი 1 · Rich Entity

სლაიდი 6

ჯერ ვნახავთ, რატომ არის ჩვენი Course „ცარიელი ყუთი“ და როგორ ვაქციოთ ის კლასად, რომელიც საკუთარ წესებს თვითონ იცავს.

ანემიური entity

სლაიდი 7

ჩვენი Course ასეთია:

Entities/Course.cs
public class Course{    public Guid Id { get; set; }    public string Title { get; set; } = string.Empty;    public string? Description { get; set; }    public int DurationWeeks { get; set; }    public DateTime CreatedAt { get; set; }}

ყველა თვისებას public set აქვს. ეს ნიშნავს, რომ ნებისმიერ კოდს, ნებისმიერ handler-ში, შეუძლია ჩაწეროს რაც უნდა:

csharp
var course = await _db.Courses.FindAsync(id);course.Title = "";course.DurationWeeks = -5;await _db.SaveChangesAsync();   // ინახება

კომპილერი არაფერს ამბობს, ბაზა იღებს. „1–52 კვირა“ მხოლოდ იმ handler-ში მოქმედებს, სადაც დავწერეთ. ახალი handler-ის ავტორს შეიძლება არც კი სცოდნოდა, რომ ასეთი წესი არსებობს.

ასეთ entity-ს ანემიური ჰქვია: მასში მხოლოდ მონაცემებია, ქცევა და წესები კი სხვაგანაა.

📘 ტერმინები
ანემიური entity (anemic)
მხოლოდ get; set; თვისებები; წესები და ქცევა entity-ს გარეთაა

Rich entity: ცვლილება მხოლოდ „კარიდან“

სლაიდი 8

Rich entity (მდიდარი entity) თავის მონაცემებს თვითონ იცავს. ამისთვის ოთხი რამ ვცვალეთ:

  1. private set. თვისებას გარედან წაიკითხავ (course.Title), მაგრამ ვერ შეცვლი. course.DurationWeeks = -5; აღარ კომპილირდება.
  2. private constructor. new Course { ... } გარედან აღარ შეიძლება. EF Core-ს მაინც შეუძლია მისი გამოძახება, როცა ბაზიდან კითხულობს: მას private constructor-იც „ხედავს“.
  3. შექმნა მხოლოდ Create-ით. ეს static მეთოდია, რომელიც ჯერ წესს ამოწმებს და მხოლოდ მერე ქმნის ობიექტს. ასეთ მეთოდს factory method ჰქვია.
  4. ცვლილება მხოლოდ მეთოდით. Update ჯერ წესს ამოწმებს, მერე ცვლის.

ასე წესი ერთ ადგილას იწერება და ყველა handler, ახალიც, ავტომატურად ემორჩილება მას.

ერთი კითხვა დარჩა: თუ წესი დაირღვა, რა დააბრუნოს Create-მა? ამაზე შემდეგ ნაწილში.

📘 ტერმინები
Rich entity
entity, რომელიც თავის წესებს თვითონ იცავს: private set, ცვლილება მხოლოდ მეთოდებით
Factory method
static მეთოდი (Create), რომელიც ობიექტს ქმნის მხოლოდ მაშინ, თუ წესი დაცულია

2 · Result

ნაწილი 2 · Result pattern

სლაიდი 9

Create-მა ან კურსი უნდა დააბრუნოს, ან ახსნა, რატომ ვერ შექმნა. ამის ორი გზა არსებობს: exception და Result. ვნახოთ ორივე და ავირჩიოთ.

exception თუ Result?

სლაიდი 10

exception-ით:

csharp
if (durationWeeks is < 1 or > 52)    throw new ArgumentException("ხანგრძლივობა 1-დან 52 კვირამდეა");

სამი პრობლემა აქვს:

  • მეთოდის ხელმოწერა Course Create(...) არ ამბობს, რომ შეიძლება ჩავარდეს. ამას მხოლოდ კოდის წაკითხვით გაიგებ.
  • თუ handler-მა try/catch დაავიწყდა, კლიენტი 500-ს მიიღებს („სერვერის შეცდომა“), თუმცა ბრალი მისია და სწორი პასუხი 400-ია.
  • exception შეიქმნა მოულოდნელი სიტუაციებისთვის და შედარებით ძვირია. ცარიელი სახელი მოულოდნელი არ არის: მომხმარებლები ამას ყოველდღე აკეთებენ.

Result-ით:

csharp
if (durationWeeks is < 1 or > 52)    return Result<Course>.Failure(CourseErrors.InvalidDuration);
  • ხელმოწერა Result<Course> Create(...) თვითონ ამბობს: „შეიძლება კურსი მოგცე, შეიძლება შეცდომა“.
  • handler-ი შედეგს ამოწმებს და თვითონ წყვეტს, რა უპასუხოს: 400, 404 თუ 409.
  • ჩვეულებრივი return-ია, არაფერი „ფრინავს“.

წესი: მოსალოდნელი, ბიზნესის შეცდომა → Result. მოულოდნელი (ბაზა გაითიშა, კოდში ბაგი) → exception.

📘 ტერმინები
Result pattern
მეთოდი აბრუნებს ან მნიშვნელობას (წარმატება), ან შეცდომას (Error), exception-ის სროლის ნაცვლად

ორი ლიანდაგი

Result-ს ხშირად „რკინიგზას“ ადარებენ (Railway-Oriented Programming). გვაქვს ორი ლიანდაგი:
