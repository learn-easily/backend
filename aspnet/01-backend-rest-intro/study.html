Backend, API, REST და პირველი Web API

წაიკითხე ლექციის შემდეგ, ან პრეზენტაციასთან ერთად: პრეზენტაციაში დააჭირე P და ეს გვერდი სლაიდებს გაჰყვება. კოდი და AI-ს პრომპტები კოპირდება ერთი დაჭერით.

დღის თემა

დღის თემა: Backend, API, REST და პირველი Web API

სლაიდი 1

საიტზე ყოველი ღილაკის უკან სერვერია, რომელიც მონაცემებს ინახავს და წესებს იცავს — Backend. ამ კურსში ასეთ სერვერს C#-ზე დავწერთ. დღეს სრულ სურათს ვხედავთ: რატომ არსებობს Backend, რა არის API და REST, როგორ ელაპარაკება საიტი სერვერს — და ვწერთ პირველ endpoint-ს.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რატომ ვერ იარსებებს მაღაზია Backend-ის გარეშე
  • Request/Response-ის, JSON-ის და სტატუს კოდების წაკითხვა
  • REST: რესურსი + 5 მეთოდი (GET, POST, PUT, PATCH, DELETE)
  • ASP.NET Core Web API პროექტის შექმნა და პირველი MapGet

ლექციის გეგმა — 6 გაჩერება

სლაიდი 3

თითოეული წინაზე დგას — ერთიც რომ გამოტოვო, შემდეგი გაგიჭირდება.

  1. ⚙️ Backend — რა არის და რატომ ვერ გავძლებთ მის გარეშე.
  2. API — როგორ ელაპარაკება საიტი Backend-ს.
  3. როგორ მუშაობს საიტი — რა ხდება, როცა ღილაკს აჭერ.
  4. REST — წესები, რომლითაც API-ს ვაპროექტებთ, და 5 მეთოდი.
  5. .NET — რა პროექტის ტიპები გვაქვს და რომელს ვირჩევთ.
  6. ⌨️ პრაქტიკა — Visual Studio-ში პირველი API.

1 · Backend

ნაწილი 1 · რა არის Backend?

სლაიდი 4

და რატომ ვერ ავაწყობთ საიტს მის გარეშე. სანამ წაიკითხავ — სცადე, საკუთარი სიტყვებით თქვა, რა გგონია.

აისბერგი: რასაც ხედავ — და რასაც ვერ ხედავ

სლაიდი 5

საიტი აისბერგს ჰგავს:

  • ზემოთ, პატარა ნაწილი — Frontend: ღილაკები, ფერები, ტექსტი, ფორმები. ის, რასაც მომხმარებელი ხედავს.
  • წყლის ქვეშ, დიდი ნაწილი — Backend: მონაცემების შენახვა, წესები და ლოგიკა, ვინ ხარ და რა შეგიძლია, გადახდა, ფოსტა, SMS.

რასაც ეკრანზე ხედავ, საიტის მხოლოდ პატარა ნაწილია.

ექსპერიმენტი: ონლაინ მაღაზია Backend-ის გარეშე

სლაიდი 6

❌ მხოლოდ ბრაუზერი. ანა და გიორგი, თითოეული საკუთარ კომპიუტერთან, ხედავენ: მარაგში 1 ლეპტოპია. ორივე ერთდროულად აჭერს „ვიყიდე“ — და ორივეს ეუბნება „წარმატებით!“. გაიყიდა 2 ლეპტოპი, მარაგში კი 1 იყო. რატომ? ბრაუზერის კოდი თითოეულის კომპიუტერზე მუშაობს: ანას ბრაუზერმა არ იცის, რა ხდება გიორგისთან.

✅ Backend-ით. მარაგი ერთ საერთო ადგილას — სერვერზე — ინახება. ანა აგზავნის „ვყიდულობ“ → სერვერი ამოწმებს: მარაგი 1-ია, ყიდის, მარაგი ხდება 0. გიორგი იგივეს აგზავნის → მარაგი 0-ია → „ამოიწურა“.

Backend = ერთი საერთო ადგილი, სადაც მონაცემი და წესები ცხოვრობს.

⚠️

ბრაუზერში კოდს ნებისმიერი შეცვლის DevTools-ით — ფასსაც კი. ამიტომ წესებს ბრაუზერს ვერ ვანდობთ.

Backend-ის 4 მთავარი მოვალეობა

სლაიდი 7
  • 🗄️ ინახავს მონაცემებს — მომხმარებლები, პროდუქტები, შეკვეთები.
  • 📏 ამოწმებს წესებს — „მარაგი 0-ზე ნაკლები ვერ იქნება“.
  • 🔐 იცავს — ვინ ხარ? რის უფლება გაქვს? (მაგ. სხვისი შეკვეთა ვერ ნახო.)
  • 🔌 აკავშირებს — ბანკს, ფოსტას, SMS-ს, სხვა სერვისებს.

Backend = პროგრამა, რომელიც სერვერზე მუშაობს და ყველა მომხმარებელს ემსახურება.

ანალოგია: საიტი = რესტორანი 🍽️

სლაიდი 8

ამ ანალოგიას მთელ ლექციაზე გამოვიყენებთ:

რესტორანში საიტში
დარბაზი — ლამაზი, სტუმარი აქ ზის Frontend
მიმტანი ? — მალე გავიგებთ
სამზარეულო — სტუმარი აქ ვერ შედის Backend
საწყობი — პროდუქტები ინახება Database

სტუმარი სამზარეულოში არ შედის. მაშ, როგორ აღწევს მისი შეკვეთა მზარეულამდე?

2 · API

ნაწილი 2 · რა არის API?

სლაიდი 9

მიმტანი, რომელიც Frontend-სა და Backend-ს აკავშირებს — ეს არის API.

API = მიმტანი

სლაიდი 10

სტუმარს ხაჭაპური უნდა:

  1. სტუმარი მიმტანს ეუბნება, მიმტანი შეკვეთას სამზარეულოში მიაქვს — ეს მოთხოვნაა (Request).
  2. სამზარეულო ამზადებს, მიმტანი კერძს უკან მოიტანს — ეს პასუხია (Response).

სტუმარმა არ იცის, როგორ მზადდება კერძი — და არც სჭირდება. სამზარეულო სტუმარს არ იცნობს — მხოლოდ შეკვეთას ხედავს.

მიმტანმა იცის, ვის მიუტანოს

სლაიდი 11

სამზარეულოში ყველაფერს ერთი მზარეული არ აკეთებს:

  • „ხაჭაპური“ → თონე
  • „სალათი“ → ცივი კერძები
  • „ანგარიში“ → სალარო

მიმტანი თვითონ არაფერს ამზადებს — მან იცის, რომელი თხოვნა სად წაიღოს. API-შიც ასეა: ყოველ მოთხოვნას თავისი ადგილი აქვს.

API შედგება Endpoint-ებისგან

სლაიდი 12

API ერთი დიდი კარი არ არის — ეს ბევრი პატარა კარია. თითოეულს Endpoint ჰქვია:

Endpoint რას აკეთებს
GET /api/products პროდუქტების სია
GET /api/products/5 ერთი პროდუქტი
POST /api/products ახალი პროდუქტი

Endpoint = მეთოდი + მისამართი, ერთი კონკრეტული მიზნით. მოთხოვნა მოდის Endpoint-ზე → Endpoint Backend-ში შესაბამის ფუნქციას ააქტიურებს.

📘 ტერმინები
Endpoint
მეთოდი (GET, POST…) + მისამართი (/api/products), რომელიც Backend-ში ერთ კონკრეტულ ფუნქციას იძახებს

API — სიტყვა-სიტყვით

სლაიდი 13
  • Application — პროგრამა
  • Programming — პროგრამირების
  • Interface — ინტერფეისი, „შეხების წერტილი“

API = წესები, რომლითაც ერთი პროგრამა ელაპარაკება მეორეს. ადამიანი პროგრამას ღილაკებით ელაპარაკება — ეს UI-ა. პროგრამა სხვა პროგრამას API-ით ელაპარაკება.

📘 ტერმინები
API
Application Programming Interface: წესები, რომლითაც პროგრამები ერთმანეთს ელაპარაკებიან
UI
User Interface: ის, რითაც ადამიანი ელაპარაკება პროგრამას (ღილაკები, ფორმები)

რატომ არსებობს API? ერთი Backend — ბევრი კლიენტი

სლაიდი 14

ერთსა და იმავე API-ს იყენებს ვებ საიტიც, მობილური აპიც, სმარტ საათიც და სხვა კომპანიის სისტემაც. ლოგიკა იწერება ერთხელ — და ყველა კლიენტი ერთსა და იმავე API-ს იყენებს.

ამიტომაა შენი ბალანსი ბანკის საიტზეც და აპლიკაციაშიც ერთნაირი: ორივე ერთ API-ს ეკითხება.

3 · როგორ მუშაობს საიტი

ნაწილი 3 · როგორ მუშაობს საიტი?

სლაიდი 15

სრული სურათი: Frontend ↔ Backend ↔ Database — ზუსტად რა ხდება, როცა საიტზე ღილაკს აჭერ.

სამი ნაწილი

სლაიდი 16
სად ინახება / მუშაობს რას აკეთებს ტექნოლოგიები
💻 Frontend ინახება სერვერზე, მუშაობს ბრაუზერში აჩვენებს და იღებს კლიკებს HTML, CSS, JavaScript, Angular, React
⚙️ Backend (API) ინახება და მუშაობს სერვერზე წესები, ლოგიკა, უსაფრთხოება C#, ASP.NET Core
🗄️ Database ინახება და მუშაობს სერვერზე მონაცემს ინახავს მუდმივად SQL Server, PostgreSQL

ერთი კლიკის მოგზაურობა

სლაიდი 17

ანამ საიტზე დააჭირა „პროდუქტები“:

  1. კლიკი — ჯერ არაფერი ჩანს.
  2. Request — Frontend API-ს აგზავნის მოთხოვნას: GET /api/products.
  3. SQL — Endpoint Backend-ში ფუნქციას იძახებს, ფუნქცია ბაზას ეკითხება: SELECT * FROM Products.
  4. მონაცემი — ბაზა Backend-ს პროდუქტებს უბრუნებს.
  5. Response — Backend Frontend-ს JSON-ს უგზავნის: 200 OK.
  6. ეკრანი — Frontend ამ მონაცემს ლამაზ ბარათებად ხატავს.

ეს ყველაფერი წამის მეასედებში ხდება.

HTTP — საერთო ენა

სლაიდი 18

Frontend და Backend ერთმანეთს HTTP-ით ელაპარაკებიან — წარმოიდგინე წერილი და პასუხი.

✉️ Request (რას ვითხოვთ): - მეთოდი — რა გვინდა? GET - მისამართი — რისი? /api/products - მონაცემი (თუ საჭიროა) — მაგ. ახალი პროდუქტი

📬 Response (რა მივიღეთ): - სტატუსი — გამოვიდა? 200 OK - მონაცემი — პროდუქტების სია (JSON)

http
GET /api/products HTTP/1.1→ HTTP/1.1 200 OK  [ { "id": 1, "name": "ლეპტოპი" } ]

JSON — მონაცემი, რომელიც ყველას ესმის

სლაიდი 19

მომხმარებელი პროდუქტს ლამაზ ბარათად ხედავს. API-დან კი ის ასე მოდის:

json
{  "id": 1,  "name": "ლეპტოპი",  "price": 2400,  "inStock": true}

"გასაღები": მნიშვნელობა — უბრალო ტექსტი. API ხატვაზე არ ზრუნავს, მხოლოდ მონაცემს აბრუნებს; როგორ გამოჩნდება — Frontend-ის საქმეა. ეს ფორმატი ყველა ენას ესმის: JavaScript-საც, C#-საც.

📘 ტერმინები
JSON
JavaScript Object Notation: მონაცემის ტექსტური ფორმატი "გასაღები": მნიშვნელობა წყვილებით

სტატუს კოდები — პასუხის „შუქნიშანი“ 🚦

სლაიდი 20
მნიშვნელობა მაგალითები
2xx ✓ ყველაფერი კარგად 200 OK · 201 Created · 204 No Content
4xx 🙋 შენ შეცდი (კლიენტი) 400 Bad Request · 401 ვინ ხარ? · 404 Not Found
5xx ⚙️ სერვერი შეცდა 500 Internal Server Error
✅ შეამოწმე თავი დაფიქრდი, მერე გახსენი პასუხი
ბრაუზერში გახსენი საიტის არარსებული გვერდი. რომელი კოდი მოვა და რომელ ჯგუფს ეკუთვნის?
404 Not Found — 4xx: კლიენტმა ისეთი რამ მოითხოვა, რაც არ არსებობს
ახალი პროდუქტი წარმატებით დაემატა. რომელი კოდი ჯობია: 200 თუ 201?
201 Created — „შეიქმნა“; 200 უფრო ზოგადი „OK“-ა

4 · REST

GET — წაკითხვა 👀

GET არაფერს ცვლის — მხოლოდ კითხულობს. 100-ჯერ გამოიძახო, ცხრილი იგივე დარჩება. GET /products (id-ის გარეშე) — ყველა პროდუქტი, სიად. SQL-ში ეს SELECT-ია.

POST — შექმნა ✨

სლაიდი 26

POST /products — „დაამატე ახალი პროდუქტი“. მისამართში id არ არის — ჯერ არ არსებობს!

Request body
{ "name": "ყურსასმენი", "price": 180 }

ცხრილში ახალი ხაზი ჩნდება, #4. Id-ს სერვერი ანიჭებს, არა კლიენტი. პასუხი: 201 Created + ახალი ჩანაწერი. SQL-ში — INSERT.

PUT — მთლიანი ჩანაცვლება 🔄

სლაიდი 27

PUT /products/2 — „პროდუქტი #2 შეცვალე ამით“:

Request body — სრული ობიექტი
{ "name": "მაუსი Pro", "price": 60 }

მეორე ხაზი მთლიანად ახლით იცვლება. PUT-ში ყველა ველს აგზავნი, თუნდაც ერთი იცვლებოდეს — როგორც ფორმის თავიდან შევსება. პასუხი: 204 No Content („შევასრულე, დასაბრუნებელი არაფერი მაქვს“) ან 200. SQL-ში — UPDATE.

PATCH — ნაწილობრივი შეცვლა ✏️

სლაიდი 28

PATCH /products/2 — „პროდუქტ #2-ს მხოლოდ ფასი შეუცვალე“:

Request body — მხოლოდ ის, რაც იცვლება
{ "price": 39 }

იცვლება მხოლოდ ერთი უჯრა, სახელი ხელუხლებელი რჩება. მოსახერხებელია, როცა ობიექტი დიდია და ერთი ველი იცვლება.

PUT — მთელი ფორმა თავიდან; PATCH — მხოლოდ ერთი ველის გასწორება. პროფილში მხოლოდ ფოტოს თუ ცვლი — PATCH.

DELETE — წაშლა 🗑️

სლაიდი 29

DELETE /products/3 — „წაშალე პროდუქტი #3“. Body არ სჭირდება — მისამართშივე ჩანს, რომელი. პასუხი: 204 No Content. SQL-ში — DELETE.
