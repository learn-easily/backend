სლაიდი 3

წინა ლექციის საშინაო: შენი სფერო: rich entity-ები, Email და „ჯგუფი“. ქვემოთ არის ერთ-ერთი სწორი ამოხსნა. შენი კოდი შეიძლება სხვანაირად იყოს დაწერილი — მთავარია, მოთხოვნები სრულდებოდეს.

მოთხოვნები

  • Common/Result.cs: Error, Result, Result<T> — როგორც ლექციაზე
  • კატალოგი (შენი „კურსი“) — rich entity: private set, private constructor, Create და Update აბრუნებს Result-ს · ყველა შეცდომა …Errors კლასში
  • Email Value Object (sealed record) · ორივე როლის ადამიანი მას იყენებს · HasConversion DataContext-ში
  • ორივე როლის ადამიანები — rich entity (Create იღებს Email-ს, არა string-ს)
  • შენი „ჯგუფი“ სფეროს ცხრილიდან: rich entity, ადგილების ლიმიტი შენი სფეროს წესით, წარსულში ვერ დაიწყება · slice-ები: Create და GetById · მიგრაცია
  • handler-ებში შეცდომა: entity → 400, „არ არსებობს“ → 404, უნიკალურობა → 409

დღის თემა: Aggregate და Concurrency: ჩარიცხვა ჯგუფში

სლაიდი 4

ჯგუფები გვაქვს, ახლა მათში სტუდენტები უნდა ჩავრიცხოთ. R3 სამ რამეს ითხოვს: ჯგუფში ადგილი უნდა იყოს, სტუდენტი ერთხელ ირიცხება, დაწყებულ ჯგუფში მხოლოდ პირველ კვირაში. ეს წესები ერთ სტუდენტს კი არა, მთელ ჯგუფს ეხება, ამიტომ ჯგუფმა უნდა დაიცვას. დღეს ვნახავთ, რა არის Aggregate და რატომ იცვლება ჩარიცხვა მხოლოდ ჯგუფის გავლით. მერე ცოცხლად ვნახავთ, როგორ იღებს 20-ადგილიანი ჯგუფი 21-ე სტუდენტს, როცა ორი მენეჯერი ბოლო ადგილს ერთდროულად ავსებს, და როგორ ვიცავთ ამისგან optimistic concurrency-ით.

ლექციის ბოლოს შეძლებ:

  • Aggregate და Aggregate Root: რა იცვლება ერთად და ვინ იცავს წესს
  • ჩარიცხვა group.Enroll(...)-ით · 400 vs 409
  • aggregate-ის საზღვარი ბაზაში: Cascade შიგნით, Restrict გარეთ · Repository pattern: რას ხსნის და როდის ღირს
  • race condition: რატომ არ კმარა if შემოწმება, როცა მოთხოვნები ერთდროულია
  • optimistic concurrency: rowversion, DbUpdateConcurrencyException → 409 · unique index

Aggregate და Aggregate Root

სლაიდი 8

Aggregate არის ობიექტების ჯგუფი, რომელიც ერთად იცვლება და ერთად იცავს წესს. ჩვენთან: Group და მისი Enrollment-ები.

Aggregate Root ამ ჯგუფის „კარია“: ჩვენთან Group. ოთხი წესი:

  1. გარედან მივმართავთ მხოლოდ root-ს. handler-ი ჯგუფს ტვირთავს, არა ცალკე ჩარიცხვებს.
  2. შვილები მხოლოდ root-ის მეთოდით იცვლება: group.Enroll(...). ასე R3 ერთ ადგილას ცხოვრობს და ყველა slice, „გადაყვანაც“, მას ემორჩილება.
  3. aggregate იტვირთება და ინახება მთლიანად, ერთ ტრანზაქციაში: ჯგუფი თავისი ჩარიცხვებით.
  4. aggregate პატარაა: მხოლოდ ის, რაც წესს სჭირდება. Student და Course ცალკე aggregate-ებია და ჯგუფი მათ Id-ით იცნობს. სტუდენტის სახელის შესაცვლელად ჯგუფის ჩატვირთვა არ გვჭირდება.

  • Repository იწერება aggregate root-ზე (Group), არა ყველა entity-ზე. Course-ს, Student-ს, Lecturer-ს ის არ სჭირდება: მარტივი entity-ებია და DataContext (DbSet) თვითონ არის repository.
  • Generic repository (IRepository<T> ყველაფრისთვის) ცუდი პრაქტიკაა: EF Core-ის შესაძლებლობებს მალავს და არაფერს იცავს.

pessimistic vs optimistic

სლაიდი 16

Pessimistic concurrency (პესიმისტური): ვვარაუდობთ, რომ კონფლიქტი ხშირია. წაკითხვისას ჯგუფს ვკეტავთ და B ელოდება, სანამ A არ დაასრულებს. სანდოა, მაგრამ ნელია, ბაზაში ჩაკეტვები გროვდება და შეიძლება deadlock-იც მოხდეს (ორი მოთხოვნა ერთმანეთს ელოდება). ვებ API-ში იშვიათად იყენებენ.

Optimistic concurrency (ოპტიმისტური): ვვარაუდობთ, რომ კონფლიქტი იშვიათია. არაფერს ვკეტავთ. შენახვისას ბაზას ვეკითხებით: „ჩემი წაკითხვის შემდეგ ეს ჩანაწერი ვინმემ შეცვალა?“. თუ შეცვალა, შენახვა არ ხდება და კლიენტს ვეუბნებით, თავიდან სცადოს.

ამისთვის ჩანაწერს ვერსია სჭირდება: წაკითხვისას ვიმახსოვრებთ, შენახვისას ვადარებთ.

SQL Server-ს აქვს სპეციალური ტიპი rowversion: ბაზა მას ყოველ UPDATE-ზე თვითონ ცვლის. ჩვენ მასში არაფერს ვწერთ.

IsRowVersion()-ის შემდეგ EF ჯგუფის UPDATE-ს ასე წერს:

sql
UPDATE Groups SET EnrolledCount = 20WHERE Id = @id AND RowVersion = 0x07D1;

0x07D1 ის ვერსიაა, რომელიც ჩვენ წავიკითხეთ. ახლა ჩვენი ცდა:

  1. A და B ორივე კითხულობს ჯგუფს ვერსიით 0x07D1.
  2. A ინახავს: ვერსია ემთხვევა, 1 რიგი შეიცვალა. ბაზამ ვერსია 0x07D2-ად შეცვალა.
  3. B ინახავს: WHERE RowVersion = 0x07D1 ვეღარ პოულობს, 0 რიგი შეიცვალა. EF ამას ხედავს და ისვრის DbUpdateConcurrencyException-ს.
  4. SaveChanges ერთი ტრანზაქციაა, ამიტომ ლუკას INSERT-იც უკან ბრუნდება. ბაზაში 20 ჩარიცხვა რჩება.

აი, რატომ გვჭირდება EnrolledCount. rowversion მხოლოდ მაშინ იცვლება, როცა Groups-ის რიგი იცვლება. Enrollment-ის დამატება სხვა ცხრილში INSERT-ია: ჯგუფის რიგი ხელუხლებელი რჩება და დაცვა არ იმუშავებდა. EnrolledCount++ ჯგუფის რიგს ცვლის და aggregate-ის ყოველი ცვლილება root-ის ვერსიას ზრდის. რეალურ სისტემებშიც ასე აკეთებენ: aggregate-ის ცვლილება ყოველთვის root-ს „ეხება“.

  1. Aggregate ობიექტების ჯგუფია, რომელიც ერთად იცვლება და ერთად იცავს წესს: Group + Enrollment-ები. Root (Group) ერთადერთი კარია.

  3. aggregate მთლიანად იტვირთება (Include) და ერთ ტრანზაქციაში ინახება. ის პატარაა: სხვა aggregate-ებს Id-ით იცნობს.
  4. 400 — მოთხოვნა თავისთავად არასწორია. 409 — მოთხოვნა სწორია, მაგრამ მიმდინარე მდგომარეობას ეწინააღმდეგება (ჯგუფი სავსეა).

  6. Optimistic concurrency: rowversion + IsRowVersion(). EF შენახვისას ვერსიას ადარებს; თუ სხვამ შეცვალა → DbUpdateConcurrencyException → 409. aggregate-ის ყოველმა ცვლილებამ root-ის რიგი უნდა შეცვალოს (EnrolledCount++).
  7. ბაზა ბოლო ზღუდეა: unique index (GroupId, StudentId).
