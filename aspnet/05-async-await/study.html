დღის თემა: Async / Await API-ში

სლაიდი 4

ShopApi ბაზასთან მუშაობს, მაგრამ ყოველ ToList()-ზე და SaveChanges()-ზე სერვერის ნაკადი ჩერდება და ბაზის პასუხს ელოდება. ერთ მომხმარებელზე ამას ვერ შეამჩნევ — ფასდაკლების დღეს კი საიტი „იჭედება“, თუმცა პროცესორი თითქმის ისვენებს. დღეს ვნახავთ, რატომ ხდება ეს, როგორ ხსნის მას async/await, და — რაც არანაკლებ მნიშვნელოვანია — როდის გვჭირდება async და როდის არაფერს გვაძლევს.

ლექციის ბოლოს შეძლებ:

  • ახსნა, რა არის Thread და Thread Pool და რატომ „იჭედება“ სინქრონული სერვერი დატვირთვისას
  • Task, Task<T>, async და await — რას აკეთებს თითოეული და რა ხდება await-ზე
  • ShopApi-ის Controller-ების გადაყვანა async-ზე: ToListAsync, FindAsync, SaveChangesAsync, CountAsync
  • გადაწყვეტილება: სად გვჭირდება async (I/O) და სად არა (გამოთვლა) · ხშირი შეცდომების ამოცნობა

1 · ლოდინის პრობლემა

ნაწილი 1 · ლოდინის პრობლემა

სლაიდი 6

ჯერ ვნახავთ პრობლემას — ისეთს, რომელსაც ერთ მომხმარებელზე ტესტირებისას ვერასდროს შეამჩნევ, მაგრამ ნამდვილ საიტზე დატვირთვისას აუცილებლად გამოჩნდება.

მენეჯერი წერს: „ფასდაკლების დღეს საიტი გაიჭედა“

სლაიდი 7

„Black Friday-ზე ერთდროულად ბევრი ხალხი შემოვიდა. გვერდი 30 წამს იტვირთებოდა, ზოგს შეცდომა ამოუვიდა. ადმინი ამბობს, რომ სერვერის პროცესორი 10%-ზე მეტად არ დატვირთულა. მაშინ რა მოხდა?“

ერთი შეხედვით ეს ორი ფაქტი ერთმანეთს ეწინააღმდეგება:

  1. მომხმარებლები ელოდებიან — გვერდი ნელა იტვირთება, ზოგს timeout-ის შეცდომა ამოუდის.
  2. პროცესორი ისვენებს — სერვერი თითქოს არაფერს აკეთებს.

თუ სერვერი დაკავებული არ არის, რატომ არ ემსახურება მომხმარებლებს? პასუხი ლოდინშია — და ამას ახლა ნაბიჯ-ნაბიჯ ვნახავთ.

Thread და Thread Pool

სლაიდი 8

Thread (ნაკადი) — „მუშა“, რომელიც კოდს ხაზ-ხაზ ასრულებს. აქამდე ჩვენს კონსოლის პროგრამებს ერთი ნაკადი ასრულებდა: Main-იდან დაიწყებდა და ბოლომდე მივიდოდა.

სერვერზე სხვა სურათია: ერთდროულად ბევრი მოთხოვნა მოდის. ASP.NET Core-ს აქვს Thread Pool — მზა ნაკადების „აუზი“. მოთხოვნა მოვიდა → აუზიდან თავისუფალი ნაკადი იღებს და ჩვენს Controller-ის მეთოდს ასრულებს → მოთხოვნა დასრულდა → ნაკადი აუზში ბრუნდება და შემდეგ მოთხოვნას ელოდება.

თუ ყველა ნაკადი დაკავებულია, ახალი მოთხოვნა რიგში დგება.

რატომ არ ვქმნით ათასობით ნაკადს? იმიტომ, რომ ნაკადი ძვირია:

  • თითოეულს საკუთარი მეხსიერება სჭირდება (სტეკისთვის — დაახლოებით 1 MB);
  • ოპერაციულ სისტემას მათ შორის გადართვა უწევს;
  • Thread Pool ახალ ნაკადებს ნელ-ნელა ამატებს — უეცარ დატვირთვაზე ვერ ასწრებს.

Black Friday-ს საიდუმლო: ყველა ნაკადი დგას და ელოდება

სლაიდი 9

ახლა მენეჯერის ამოცანა იხსნება. სინქრონულ კოდში ToList()-ის ხაზზე ნაკადი ჩერდება და ბაზის პასუხამდე იქ რჩება. დატვირთვისას ასე ხდება:

  1. ბევრი მოთხოვნა მოდის, აუზის ყველა ნაკადს თითო მოთხოვნა უჭირავს.
  2. ყველა ნაკადი ბაზას ელოდება — დაკავებულია, მაგრამ არაფერს აკეთებს.
  3. ახალ მოთხოვნებს თავისუფალი ნაკადი აღარ ხვდებათ — რიგში დგებიან. რიგი იზრდება, ზოგი timeout-ით მთავრდება.
  4. პროცესორი კი ისვენებს: ლოდინს პროცესორი არ სჭირდება. აქედანაა „CPU 10%“.

ამ მდგომარეობას ჰქვია Thread Pool Starvation — ნაკადების „შიმშილი“: ნაკადები გვაქვს, მაგრამ ყველა ლოდინშია გაჭედილი.

გამოსავალი ნაკადების გამრავლება კი არა — ლოდინის დროს ნაკადის გათავისუფლებაა: მან შეკვეთა ჩააბაროს და სხვა მაგიდასთან წავიდეს. ზუსტად ამას აკეთებს async/await.

ნაწილი 2 · Task და await

სლაიდი 10

C#-ში ასინქრონული ლოდინისთვის სამი რამ გვჭირდება: Task — „ქვითარი“ მომავალ შედეგზე, async — მეთოდის ნიშანი და await — „დაელოდე, ოღონდ ნაკადი გაათავისუფლე“.

Task — პეიჯერი, რომელიც დარეკავს

სლაიდი 11

ფუდ-კორტში ბურგერს შეუკვეთავ. კერძი ჯერ არ არის — მას მომზადება სჭირდება. გაძლევენ პეიჯერს — პატარა მოწყობილობას, რომელიც კერძის მზადყოფნისას დარეკავს. რიგში აღარ დგახარ: სხედხარ, მეგობრებს ესაუბრები. დარეკა → მიდიხარ და კერძს იღებ.

C#-ში ეს პეიჯერი არის Task:

ცნება რას ნიშნავს ფუდ-კორტში
Task დაპირება: ოპერაცია დაიწყო და ოდესმე დასრულდება. შედეგს არ აბრუნებს — როგორც void „შენი შეკვეთა მიღებულია“
Task<T> დაპირება T ტიპის შედეგზე. Task<List<Product>> — „სია იქნება“ პეიჯერი, რომელსაც ბოლოს კერძი მოჰყვება
await „დაელოდე ამ დაპირებას“. ლოდინის დროს ნაკადი თავისუფლდება; შედეგი რომ მოვა, მეთოდი იქიდან გრძელდება, სადაც გაჩერდა სხედხარ და ელოდები ზარს — რიგში არ დგახარ

ადრე — სინქრონული
[HttpGet]public IActionResult GetAll(){    var products = _db.Products.ToList();    return Ok(products);}
ახლა — ასინქრონული
[HttpGet]public async Task<IActionResult> GetAll(){    var products = await _db.Products.ToListAsync();    return Ok(products);}
  1. async — მეთოდის ნიშანი: „ამ მეთოდში await იქნება“. მის გარეშე await-ის დაწერა არ შეიძლება.
  2. Task<IActionResult> — async მეთოდი თვითონაც დაპირებას აბრუნებს. Controller-ის მეთოდიც ლოდინს შეიცავს, ესე იგი ისიც მაშინვე შედეგს ვერ აბრუნებს. ASP.NET Core ამ Task-ს თვითონ ელოდება და პასუხს მერე აგზავნის.
  3. await _db.Products.ToListAsync() — ToListAsync მოთხოვნას ბაზაში აგზავნის და მაშინვე Task<List<Product>>-ს აბრუნებს. await ამბობს: „დაველოდოთ შედეგს“ — და ამ დროს ნაკადი თავისუფლდება.

await-ის შემდეგ products უკვე List<Product>-ია, არა Task: await დაპირებას „ხსნის“ და შიგნით არსებულ შედეგს გვაძლევს. ამიტომ დანარჩენი კოდი (Ok(products)) არ იცვლება.

👉

async მეთოდი თავიდან ბოლომდე ჩვეულებრივ კოდს ჰგავს — ზემოდან ქვემოთ იკითხება. ეს არის async/await-ის მთავარი ღირსება: ასინქრონულ კოდს ვწერთ ისე, თითქოს სინქრონული იყოს.

სიმულაცია: 4 ნაკადი, სინქრონული vs ასინქრონული

  • ყოველ მოთხოვნას სჭირდება: 0.2 წმ კოდი → 1.4 წმ ბაზის ლოდინი → 0.2 წმ კოდი;

სცადე სამი ექსპერიმენტი:

  1. სინქრონული, 2 მოთხოვნა/წმ — თითქმის მუშაობს, თუმცა ნაკადები უმეტესად ლოდინში დგანან (დაშტრიხული ზოლი).
  2. სინქრონული, 4 მოთხოვნა/წმ — რიგი იზრდება, timeout-ები ჩნდება, CPU კი დაბალია — ეს არის Black Friday.
  3. ასინქრონული, 4 და 8 მოთხოვნა/წმ — იგივე 4 ნაკადი ყველაფერს ასწრებს: ლოდინის დროს მოთხოვნა „ბაზასთანაა“ ნაკადის გარეშე, ნაკადი კი შემდეგ მოთხოვნას იღებს.

რატომ? სინქრონულად ნაკადს ერთი მოთხოვნა 1.8 წამით უჭირავს — 4 ნაკადი წამში ~2 მოთხოვნას ასწრებს. ასინქრონულად ნაკადს მოთხოვნა მხოლოდ 0.4 წამით (კოდის ნაწილი) უჭირავს — იგივე 4 ნაკადი წამში ~10-ს ასწრებს.

ბაზაში მიდის? → …Async + await

სლაიდი 16

წესი მარტივია: ის მეთოდი, რომელიც ბაზაში მიდის, Async ვერსიით იცვლება და მას await ეწერება.

ადრე ახლა
_db.Products.ToList() await _db.Products.ToListAsync()
_db.Products.Find(id) await _db.Products.FindAsync(id)
_db.SaveChanges() await _db.SaveChangesAsync()
.Count() · .Sum(…) · .Any(…) await .CountAsync() · await .SumAsync(…) · await .AnyAsync(…)
.FirstOrDefault(…) await .FirstOrDefaultAsync(…)

რჩება როგორც იყო:

  • Add და Remove — ბაზაში არ მიდიან, მხოლოდ Change Tracker-ში ნიშნავენ „დასამატებელია“ / „წასაშლელია“. ბაზაში ყველაფერი SaveChangesAsync-ზე მიდის.
  • Where, OrderBy, Select — SQL-ის „რეცეპტს“ აწყობენ, ბაზაში ჯერ არაფერი იგზავნება. მოთხოვნა ბოლო მეთოდზე სრულდება — მაგ. await _db.Products.Where(p => p.Price > 100).ToListAsync().
⚠️

ToListAsync, CountAsync და სხვები Microsoft.EntityFrameworkCore namespace-ის extension მეთოდებია. თუ Controller-ში using Microsoft.EntityFrameworkCore; არ წერია, კომპილატორი იტყვის: „'DbSet' does not contain a definition for 'ToListAsync'“.

💡

EF Core-ს AddAsync-იც აქვს, მაგრამ ჩვეულებრივ შემთხვევაში ის არ გვჭირდება — Add ბაზაში არ მიდის. AddAsync მხოლოდ სპეციალური Id-გენერატორებისთვისაა.

სლაიდი 20

ეს ყველაზე ხშირი მცდარი წარმოდგენაა — და გასაუბრებაზეც ხშირად ამოწმებენ.

ერთ მომხმარებელზე სინქრონულიც და ასინქრონულიც ერთნაირ დროს ხარჯავს: ბაზა ისევ 40 ms-ს ფიქრობს, ქსელიც იგივეა. async-ს ცოტა დამატებითი სამუშაოც აქვს (კომპილატორის მიერ აგებული „მდგომარეობის მანქანა“), მაგრამ ის მიკროწამებია — შეუმჩნეველი.

ბევრ მომხმარებელზე კი სურათი იცვლება:

  • სინქრონულად ნაკადები ლოდინში დგანან → ახალი მოთხოვნები რიგში → ყველასთვის ნელდება, ზოგს timeout.
  • ასინქრონულად ნაკადები ლოდინის დროს თავისუფლდებიან → იგივე სერვერი ბევრად მეტ ერთდროულ მომხმარებელს ემსახურება, და თითოეული ისევ ~40 ms-ში იღებს პასუხს.

async-ის მოგება მასშტაბია (scalability) — რამდენ მომხმარებელს გაუძლებს სერვერი, და არა ერთი მოთხოვნის სიჩქარე.

📘 ტერმინები
Scalability (მასშტაბირება)
რამდენ დატვირთვას უძლებს სისტემა ისე, რომ არ ნელდება

ერთი კითხვა ყოველ მეთოდზე

სლაიდი 21

მეთოდი რამეს ელოდება პროგრამის გარეთ — ბაზას, ქსელს, ფაილს?

  • კი → async. async Task<…>, Async მეთოდები, await ყველგან — და ზემოთ, ვინც მას იძახებს, ბოლომდე. მაგალითები: GetAll, Create, StatsController.Get, ბანკში გადახდა, AI-სთვის კითხვის გაგზავნა.
  • არა → ჩვეულებრივი მეთოდი. აბრუნებს decimal-ს, bool-ს, ProductResponse-ს — Task-ის გარეშე. მაგალითები: ფასდაკლების დათვლა, mapper, ვალიდაცია.
⚠️

ზოგი ნელ გამოთვლას Task.Run(() => …)-ში ახვევს და await-ს უწერს, რომ „async გახდეს“. API-ში ეს არაფერს იძლევა: Task.Run სამუშაოს იმავე Thread Pool-ის სხვა ნაკადზე გადაიტანს — ერთი ნაკადი თავისუფლდება, მეორე იკავებს. თავისუფალი ნაკადი არ ემატება, ზედმეტი გადართვა კი ემატება. async ლოდინისთვისაა, გამოთვლისთვის — არა.

🤖 async თუ არა — შემამოწმე
ვსწავლობ C#-ში async/await-ს ASP.NET Core Web API-ში. მომეცი 8 მოკლე მეთოდის აღწერა რეალური პროექტებიდან (ონლაინ მაღაზია, რესტორნის დაჯავშნა, ბანკი) — მაგალითად „ფასდაკლების დათვლა“, „შეკვეთის შენახვა ბაზაში“, „SMS-ის გაგზავნა“. თითოეულზე მკითხე: უნდა იყოს async თუ არა და რატომ (I/O-bound თუ CPU-bound)? ჩემს პასუხს დაელოდე და შემიფასე. ქართულად.

ხუთი ხშირი შეცდომა

სლაიდი 22

1. დავიწყებული await

❌
var products = _db.Products.ToListAsync();   // Task<List<Product>>, არა სია!return Ok(products);

products სია კი არა — Task-ია (პეიჯერი, არა ბურგერი). კოდი კომპილირდება, მაგრამ კლიენტს სიის ნაცვლად Task-ის ობიექტი მიდის. სწორი: var products = await _db.Products.ToListAsync();

2. .Result ან .Wait()

❌
var products = _db.Products.ToListAsync().Result;

.Result Task-ს ბლოკავს: ნაკადი დგება და ელოდება — ზუსტად სინქრონულივით, ოღონდ უფრო რთული კოდით. ზოგ გარემოში პროგრამა სამუდამოდ „იჭედება“ (deadlock). სწორი: await.

3. ორი Task ერთ DataContext-ზე ერთდროულად

❌
var countTask = _db.Products.CountAsync();var sumTask = _db.Products.SumAsync(p => p.Price);   // 💥

await-ის გარეშე მეორე მოთხოვნა მაშინ იწყება, როცა პირველი ჯერ არ დასრულებულა. წინა ლექციიდან ვიცით: DataContext ერთ ჯერზე მხოლოდ ერთ ოპერაციას აკეთებს → A second operation was started on this context instance before a previous operation completed. სწორი: თითოს თავისი await, რიგრიგობით.

4. async void

❌
public async void Delete(Guid id) { ... }

void Task-ს არ აბრუნებს — ASP.NET Core-ს დასალოდებელი არაფერი აქვს. ის პასუხს მაშინვე აგზავნის და მოთხოვნას ხურავს, DataContext-იც (Scoped!) იხურება — მეთოდი კი ჯერ კიდევ მუშაობს → ObjectDisposedException. async მეთოდი ყოველთვის Task ან Task<T>-ს აბრუნებს.

5. async მეთოდი, მაგრამ შიგნით სინქრონული გამოძახება

❌
public async Task<IActionResult> GetAll() => Ok(_db.Products.ToList());

async წერია, მაგრამ await არსად — კომპილატორი გაფრთხილებს: CS1998 „This async method lacks 'await' operators and will run synchronously“. ToList() ნაკადს ისევ ბლოკავს.

👉

წესი სამ ხაზად: Task-ს → await · ბაზაში მიდის → …Async · void → Task. და კომპილატორის warning-ებს (ყვითელი ტალღოვანი ხაზი) ნუ უგულებელყოფ — async-ის შეცდომების ნახევარს ისინი გეუბნებიან.

დაიმახსოვრე:

  1. ASP.NET Core ყოველ მოთხოვნას Thread Pool-იდან ნაკადს აძლევს. ნაკადები შეზღუდულია.
  2. სინქრონულ კოდში ნაკადი ბაზის პასუხს ელოდება და ამ დროს დგას — დატვირთვისას ნაკადები მთავრდება (Thread Pool Starvation), პროცესორი კი ისვენებს.
  3. Task<T> — დაპირება შედეგზე. await — დაელოდე, ოღონდ ნაკადი გაათავისუფლე; შედეგის შემდეგ მეთოდი გრძელდება (შეიძლება სხვა ნაკადზე). async — მეთოდის ნიშანი; async მეთოდი Task-ს აბრუნებს.
  4. EF Core: ბაზაში მიდის → …Async + await (ToListAsync, FindAsync, SaveChangesAsync, CountAsync…). Add/Remove უცვლელია.
  5. async ერთ მოთხოვნას არ აჩქარებს — სერვერს მეტი მომხმარებლის ატანას აძლევს.
  6. I/O-bound (ბაზა, ქსელი, ფაილი) → async. CPU-bound (გამოთვლა) → ჩვეულებრივი მეთოდი.
  7. არა: დავიწყებული await, .Result/.Wait(), async void, ორი Task ერთ DataContext-ზე.

ვემზადები .NET Junior გასაუბრებისთვის. დამისვი კითხვები async/await-ზე ASP.NET Core Web API-ში: Thread, Thread Pool, Thread Pool Starvation, Task და Task<T>, რას აკეთებს await, I/O-bound vs CPU-bound, რატომ არ აჩქარებს async ერთ მოთხოვნას, .Result და async void-ის პრობლემები, EF Core-ის Async მეთოდები, CancellationToken. სათითაოდ დასვი, დაელოდე ჩემს პასუხს, შემიფასე და აუხსენი, რა გამომრჩა. 8 კითხვა. ქართულად.
