დღის თემა: Dependency Injection და DbContext

სლაიდი 4

ShopApi-ის პროდუქტები ჯერ კიდევ Controller-ის static სიაშია: სერვერის გადატვირთვაზე ყველაფერი ქრება, მეორე Controller კი მათ ვერ წვდება. დღეს API-ს ნამდვილ ბაზას ვუერთებთ — EF Core-ს, რომელიც კონსოლში ვისწავლეთ — და ამ გზაზე ვპასუხობთ კითხვას, რომელსაც ყველა .NET გასაუბრებაზე გკითხავენ: ვინ ქმნის ობიექტებს? პასუხი — Inversion of Control და Dependency Injection — და სამი გზა, რამდენ ხანს იცოცხლოს ობიექტმა: Singleton, Scoped, Transient.

ლექციის ბოლოს შეძლებ:

  • EF Core-ის მიერთება Web API-ზე: DataContext, მიგრაცია, CRUD Controller-ში
  • ახსნა, რატომ არ ვწერთ Controller-ში new DataContext()-ს და რა არის IoC და DI
  • DataContext-ის constructor-ით მოთხოვნა, AddDbContext რეგისტრაცია, connection string — appsettings.json-ში
  • Singleton, Scoped და Transient-ის განსხვავება და რატომ არის DataContext Scoped

ორივე Controller-ში new DataContext()

სლაიდი 9

კონსოლში TodoService DataContext-ს ველში ქმნიდა. იგივეს ვაკეთებთ Controller-ში — static სია ქრება, მის ადგილას DataContext დგება:

Controllers/ProductsController.cs
[ApiController][Route("api/[controller]")]public class ProductsController : ControllerBase{    private readonly DataContext _db = new DataContext();     [HttpGet]    public IActionResult GetAll() => Ok(_db.Products.ToList());     [HttpGet("{id:guid}")]    public IActionResult GetById(Guid id)    {        var product = _db.Products.Find(id);        if (product is null) return NotFound();        return Ok(product);    }     [HttpPost]    public IActionResult Create(Product product)    {        _db.Products.Add(product);        _db.SaveChanges();        return CreatedAtAction(nameof(GetById), new { id = product.Id }, product);    }     [HttpPut("{id:guid}")]    public IActionResult Update(Guid id, Product updated)    {        var product = _db.Products.Find(id);        if (product is null) return NotFound();        product.Name = updated.Name;        product.Price = updated.Price;        _db.SaveChanges();        return NoContent();    }     [HttpDelete("{id:guid}")]    public IActionResult Delete(Guid id)    {        var product = _db.Products.Find(id);        if (product is null) return NotFound();        _db.Products.Remove(product);        _db.SaveChanges();        return NoContent();    }}
  • ნაცნობი EF Core: ToList, Find, Add, Remove, SaveChanges. Update-ში Find-ით ნაპოვნ პროდუქტს ვცვლით — Change Tracker-მა იცის, რა შეიცვალა.
  • Id-ს EF Core Add-ის დროს თვითონ ავსებს — CreatedAtAction-ში უკვე მზა product.Id გადის.
Controllers/StatsController.cs
[ApiController][Route("api/[controller]")]public class StatsController : ControllerBase{    private readonly DataContext _db = new DataContext();     [HttpGet]    public IActionResult Get()    {        return Ok(new        {            Count = _db.Products.Count(),            TotalValue = _db.Products.Sum(p => p.Price)        });    }}

ვამოწმებთ Swagger-ში: POST-ით ვამატებთ მონიტორს → პროგრამას ვაჩერებთ და თავიდან ვუშვებთ → GET — მონიტორი ადგილზეა. /api/stats-იც მას ითვლის. ორივე მოთხოვნა შესრულდა.

სლაიდი 10
  1. 🔑 Connection String კოდშია. ყველა დეველოპერს სხვა კომპიუტერი აქვს, სერვერზე კი სულ სხვა ბაზაა. ბაზის შეცვლა = კოდის შეცვლა და თავიდან აწყობა. ნამდვილ პროექტში სტრიქონში პაროლიც წერია — და ის Git-ში, ყველას თვალწინ მოხვდება.
  2. 🔌 DataContext-ს არავინ ხურავს. კონსოლში using var db = new DataContext(); ვწერდით — using ბოლოს კავშირს ხურავდა. აქ Controller ყოველ მოთხოვნაზე ახალია, მასთან ერთად — DataContext-იც, და არცერთი არ იხურება. ბაზასთან კავშირები გროვდება.
  3. ⛓️ new DataContext() ყველა Controller-შია. ProductsController თავისას ქმნის, StatsController — თავისას, და ყოველი ახალი Controller კიდევ ერთს დაამატებს. ყოველმა Controller-მა იცის, როგორ შექმნას DataContext. მის შექმნას რამე დასჭირდა? ყველა Controller-ს გადაუვლი.

სამივე პრობლემის ფესვი ერთია: Controller თვითონ ქმნის იმას, რაც სჭირდება.

სლაიდი 11
  • 🙅 თვითონ Controller-ი — ყველა თავის ასლს ქმნის, და ვერავინ აკონტროლებს, რამდენი ასლია, როგორ იქმნება და როდის იხურება.
  • 🤝 ვიღაც გარედან — ერთ ადგილას იცის, როგორ შექმნას, მიაწვდის ყველას, ვისაც სჭირდება, და საქმის ბოლოს თვითონ დახურავს. Controller მხოლოდ იტყვის: „მე DataContext მჭირდება“.

Inversion of Control (IoC)

სლაიდი 15

IoC — პრინციპი: პროგრამის მართვას შენი კოდიდან გადასცემ framework-ს. შენ წერ ნაწილებს, framework წყვეტს, როდის და როგორ გამოიყენოს. ეს იდეაა, არა კონკრეტული კოდი.

ჰოლივუდში მსახიობს კასტინგის შემდეგ ეუბნებიან: „ნუ დაგვირეკავთ — ჩვენ დაგირეკავთ“. ჩვენი Controller ზუსტად ასე იქცევა: [Route] და [HttpGet]-ით „ნომერს ტოვებს“, ASP.NET Core კი თვითონ წყვეტს, როდის „დაურეკოს“ — როცა შესაბამისი მოთხოვნა მოვა.

კონტროლს ორი მხარე აქვს:

ვინ აკეთებს
📞 ვინ იძახებს მეთოდებს ASP.NET Core იძახებს GetAll()-ს ✓ უკვე გადაბრუნებულია
🏭 ვინ ქმნის ობიექტებს Controller-ები თვითონ წერენ new DataContext() ✗ კონტროლი ჯერ ჩვენთანაა

შესვენების შემდეგ მეორე მხარესაც გადავაბრუნებთ — და სამივე პრობლემა გადაიჭრება.

Dependency — დამოკიდებულება

სლაიდი 18

ორივე Controller იყენებს DataContext-ს. შეუძლია ProductsController-ს იმუშაოს DataContext-ის გარეშე? არა — ბაზასთან სწორედ მისით ლაპარაკობს. ესე იგი ის DataContext-ზეა დამოკიდებული.

DataContext არის ProductsController-ის dependency — ის, რაც მას სამუშაოდ სჭირდება. ერთ კლასს შეიძლება ბევრი dependency ჰქონდეს.

📘 ტერმინები
Dependency
ობიექტი, რომელიც კლასს სამუშაოდ სჭირდება (ProductsController-ისთვის — DataContext)

Injection — მზარეული ბაზარში არ დადის

სლაიდი 19

რესტორნის მაგალითი:

  • 🧑‍🍳 თვითონ ყიდულობს — ყოველ დილით ყველა მზარეული ბაზარში მიდის, ყველას სხვადასხვა პომიდორი აქვს. ეს არის new DataContext() Controller-ში.
  • 🚚 მომწოდებელი მოაქვს — მზარეული მხოლოდ ამბობს „პომიდორი მჭირდება“, და მომწოდებელი სამზარეულოს კარამდე მიუტანს. ეს არის: Controller ითხოვს, ვიღაც აწვდის.
  • 📋 მენეჯერი წყვეტს — ვინ არის მომწოდებელი, რესტორნის მენეჯერი ერთხელ, ერთ ადგილას წყვეტს. ჩვენთან ეს ადგილი Program.cs იქნება.

Injection = შეყვანა, მიწოდება: კლასს dependency გარედან მიეწოდება.

DI Container — ობიექტების ქარხანა

სლაიდი 22

ASP.NET Core-ს აქვს ჩაშენებული DI Container: ის ქმნის ობიექტებს და აწვდის მათ, ვისაც სჭირდება. Controller-ებსაც ის ქმნის.

ეს ხაზები Program.cs-ში პირველი ლექციიდან გვიწერია:

Program.cs
var builder = WebApplication.CreateBuilder(args); builder.Services.AddControllers();builder.Services.AddOpenApi();builder.Services.AddSwaggerGen();

builder.Services — სწორედ Container-ის სიაა. AddControllers, AddOpenApi, AddSwaggerGen — რეგისტრაციებია: Container-ს ვეუბნებით „ესენი იცოდე“. მასში ასობით სერვისია, მაგრამ DataContext სიაში არ არის — ამიტომ Container ვერ ქმნის მას.

📘 ტერმინები
DI Container
ASP.NET Core-ის ნაწილი, რომელიც ობიექტებს ქმნის და მათ, ვისაც სჭირდება, constructor-ით აწვდის
builder.Services
Container-ის სია: რა ტიპები იცის და როგორ შექმნას

AddDbContext — DataContext-ს Container ქმნის

სლაიდი 23

Container-ს DataContext უნდა ვასწავლოთ. EF Core-ს ამისთვის მზა მეთოდი აქვს — AddDbContext. რომელ ბაზასთან და როგორ დაუკავშირდეს, აქ ვეუბნებით:

Program.cs
builder.Services.AddControllers();builder.Services.AddOpenApi();builder.Services.AddSwaggerGen(); builder.Services.AddDbContext<DataContext>(options =>    options.UseSqlServer("Server=(localdb)\\MSSQLLocalDB;Database=ShopApiDb;Trusted_Connection=True;TrustServerCertificate=True"));
  • Add… — „Container, DataContext იცოდე · ვინც მოითხოვს, შექმენი და მიაწოდე“.
  • UseSqlServer OnConfiguring-იდან აქ გადმოვიდა.
  • Program.cs-ის თავში — using Microsoft.EntityFrameworkCore; და using ShopApi.Data;.

DataContext-ში OnConfiguring ვშლით და მის ნაცვლად constructor-ს ვწერთ:

Data/DataContext.cs
public class DataContext : DbContext{    public DataContext(DbContextOptions<DataContext> options)        : base(options)    {    }     public DbSet<Product> Products { get; set; }}
  • DataContext-იც ითხოვს — პარამეტრებს (options: რომელი ბაზა, რა სტრიქონით). მათ Container აწყობს იმ ლამბდიდან, რომელიც AddDbContext-ს მივეცით.
  • : base(options) — მიღებულ პარამეტრებს მშობელ კლასს, DbContext-ს გადასცემს. ესაა მემკვიდრეობის constructor-ების ჯაჭვი, რომელიც C#-ში ვნახეთ.

ვუშვებთ — 200.

AddDbContext DataContext-ს Scoped-ად არეგისტრირებს — ერთი ობიექტი ერთი მოთხოვნისთვის. რას ნიშნავს ეს და რა ვარიანტები არსებობს, ნაწილ 4-ში ვნახავთ.

ბაზა ხელახლა შექმნა არ სჭირდება: ცხრილი იგივეა. ახალი მიგრაცია მხოლოდ მაშინ გვჭირდება, როცა Entity-ები იცვლება. Add-Migration-იც ასე იმუშავებს — EF Core-ის ბრძანებები DataContext-ს Program.cs-ის რეგისტრაციიდან იღებს.

რა ხდება ახლა: Container აწყობს — და ხურავს

სლაიდი 25

ერთი მოთხოვნა, ნაბიჯ-ნაბიჯ:

  1. მოდის GET /api/products. ASP.NET Core-ს ProductsController სჭირდება.
  2. Container კითხულობს constructor-ს: ProductsController-ს DataContext სჭირდება.
  3. ჯერ dependency-ს ქმნის: ① DataContext → მერე ② ProductsController, და constructor-ში DataContext-ს აწვდის. (თუ DataContext-საც რამე სჭირდებოდა, ჯერ იმას შექმნიდა — Container ჯაჭვს ქვემოდან ზემოთ აწყობს.)
  4. ASP.NET Core იძახებს GetAll()-ს — ეს ჩვენი კოდია.
  5. პასუხი წავიდა — Container მოთხოვნის ობიექტებს ასუფთავებს და DataContext-ს ხურავს, ისე, როგორც კონსოლში using ხურავდა. პრობლემა 2 გადაწყდა.

ჩვენს კოდში new DataContext() აღარ არის: Controller მხოლოდ ამბობს, რა სჭირდება.

თუ DataContext-ის შექმნა ოდესმე შეიცვლება, ერთ ადგილას შევცვლით, და არა ყველა Controller-ში.

სამი ტერმინი — ერთმანეთის შიგნით

სლაიდი 27
  • Inversion of Control — პრინციპი: კონტროლს framework-ს ვაძლევთ. ის ქმნის ობიექტებს და იძახებს ჩვენს კოდს.
  • Dependency Injection — ტექნიკა: IoC ობიექტების შექმნაზე. კლასი dependency-ს constructor-ში ითხოვს და თვითონ არ ქმნის.
    • DI Container — ინსტრუმენტი: ის, ვინც ქმნის, აწვდის და ხურავს. ASP.NET Core-ში — builder.Services.
💡

გასაუბრებაზე თუ გკითხეს „რა განსხვავებაა IoC-სა და DI-ს შორის?“ — IoC პრინციპია, DI მისი ერთ-ერთი რეალიზაცია.

4 · სამი Lifetime

ნაწილი 4 · რამდენ ხანს ცოცხლობს ობიექტი?

რეგისტრაციისას Container-ს ორ რამეს ვეუბნებით: რა შექმნას და რამდენ ხანს იცოცხლოს შექმნილმა ობიექტმა. მეორეს lifetime ჰქვია. სამი ვარიანტია — და ბაზაზე კარგად ჩანს, რატომ არის არჩევანი მნიშვნელოვანი.

სამი რეგისტრაცია — სამი lifetime

სლაიდი 29
რეგისტრაცია რამდენი ობიექტი როდის იქმნება ახალი
AddSingleton<T>() ერთი მთელი აპლიკაციისთვის მხოლოდ პირველად. მერე ყველას, ყველა მოთხოვნაზე იმავეს აწვდის
AddScoped<T>() ერთი თითო მოთხოვნაზე ყოველ ახალ მოთხოვნაზე. მოთხოვნის შიგნით ყველა იმავეს იღებს; ბოლოს იხურება
AddTransient<T>() ახალი ყოველ ჯერზე ყოველთვის, როცა ვინმე ითხოვს — ერთ მოთხოვნაშიც კი

„Scope“ — არე, ჩარჩო. ASP.NET Core-ში ეს ჩარჩო ერთი HTTP მოთხოვნაა.

ექსპერიმენტი: რამდენი DataContext იქმნება?

სლაიდი 30

lifetime-ს თვალით რომ დავინახოთ, DataContext-ის constructor-ში დროებით მთვლელს ვამატებთ. static ველი ყველა ობიექტისთვის საერთოა — ამიტომ ითვლის, სულ რამდენი შეიქმნა:

Data/DataContext.cs · დროებით
private static int _created; public DataContext(DbContextOptions<DataContext> options)    : base(options){    _created++;    Console.WriteLine($"new DataContext #{_created}");}

AddDbContext-ს მესამე პარამეტრად lifetime შეიძლება გადავცეთ. ნაგულისხმევად ის Scoped-ია — ექსპერიმენტისთვის ცხადად ვწერთ, რომ მერე შევცვალოთ:

Program.cs
builder.Services.AddDbContext<DataContext>(options =>    options.UseSqlServer(        builder.Configuration.GetConnectionString("Default")),    ServiceLifetime.Scoped);

Swagger-ში სამ მოთხოვნას ვაგზავნით და აპლიკაციის console ფანჯარას ვუყურებთ:

ShopApi · Console · Scoped
GET /api/products   → new DataContext #1POST /api/products  → new DataContext #2GET /api/stats      → new DataContext #3

ყოველ მოთხოვნაზე ახალი DataContext — Scoped. მოთხოვნა დასრულდა — Container მას ხურავს.

💡

ჩვენს კლასებს lifetime-ს მეთოდის სახელით ვაძლევთ: AddSingleton<T>(), AddScoped<T>(), AddTransient<T>(). DataContext-ს EF Core-ის AddDbContext არეგისტრირებს, ამიტომ მას lifetime პარამეტრად გადაეცემა — ServiceLifetime.Singleton, .Scoped ან .Transient. აზრი ერთი და იგივეა.

ექსპერიმენტი: Transient — არაფერი შეიცვალა?

სლაიდი 31

ServiceLifetime.Scoped-ს ვცვლით ServiceLifetime.Transient-ით და ისევ ვაგზავნით მოთხოვნებს. console-ში — იგივე სურათი: ყოველ მოთხოვნაზე ერთი DataContext.

რატომ? Transient ახალს მაშინ ქმნის, როცა ვინმე ითხოვს. ჩვენთან ერთ მოთხოვნაზე DataContext-ს მხოლოდ ერთი კლასი ითხოვს — Controller. ერთხელ ითხოვს — ერთხელ იქმნება. Scoped-თან განსხვავება მაშინ ჩანს, როცა ერთ მოთხოვნაში ერთსა და იმავეს ორი კლასი ითხოვს.

ეს მალე მოხდება: როცა პროექტს სტრუქტურას მივცემთ, ლოგიკა Controller-იდან ცალკე კლასებში გადავა. მაგალითად, შეკვეთისას ერთი კლასი მარაგს აკლებს, მეორე შეკვეთას ამატებს — ორივეს DataContext სჭირდება:

კლასი A (მარაგი) კლასი B (შეკვეთა) შედეგი
Scoped ✓ DataContext #1 DataContext #1 ერთი SaveChanges ორივე ცვლილებას ერთად ინახავს
Transient ✗ DataContext #1 DataContext #2 ერთის SaveChanges მეორის ცვლილებებს ვერ ხედავს — ნახევარი შეინახება, ნახევარი არა

ამიტომაა DataContext Scoped: ერთ მოთხოვნაში ყველა ერთ DataContext-ზე მუშაობს. Change Tracker ერთია და SaveChanges ყველაფერს ერთად ინახავს.

ექსპერიმენტი: Singleton — ერთი DataContext ყველასთვის

სლაიდი 32

ახლა ServiceLifetime.Singleton:

Program.cs · ❌ ასე არა
builder.Services.AddDbContext<DataContext>(options =>    options.UseSqlServer(        builder.Configuration.GetConnectionString("Default")),    ServiceLifetime.Singleton);

console-ში — new DataContext #1 და მეტი არაფერი, რამდენი მოთხოვნაც არ უნდა გავაგზავნოთ. ერთი DataContext ყველა მოთხოვნას, ყველა მომხმარებელს ემსახურება. მუშაობს, მაგრამ:

  1. Change Tracker იზრდება. ყველა პროდუქტი, რაც DataContext-მა ოდესმე წაიკითხა, მასთან რჩება — მეხსიერება სულ იზრდება. Find ჯერ Change Tracker-ში ეძებს, ამიტომ შეიძლება ბაზაში უკვე შეცვლილი პროდუქტის ძველი ასლი დააბრუნოს.
  2. ორი მომხმარებელი ერთდროულად. სერვერი მოთხოვნებს პარალელურად ამუშავებს. DataContext ერთ ჯერზე მხოლოდ ერთ ოპერაციას აკეთებს, და მეორე მომხმარებელი მიიღებს:
System.InvalidOperationException
A second operation was started on this context instance before a previous operationcompleted. This is usually caused by different threads concurrently using the sameinstance of DbContext.

ლოკალურად, მარტო რომ ვტესტავთ, ამას ვერ შევამჩნევთ — პრობლემა სერვერზე, ნამდვილ მომხმარებლებთან ჩნდება. DataContext ერთი მოთხოვნისთვისაა — სწორედ ამიტომ არის AddDbContext ნაგულისხმევად Scoped.

Lifetime-ის არჩევა

სლაიდი 33
Lifetime ჩვენი კლასისთვის როდის მაგალითი
Singleton AddSingleton<T>() ერთი, საერთო ყველასთვის; არ ინახავს მოთხოვნაზე დამოკიდებულ მონაცემს IConfiguration — framework-მა თვითონ დაარეგისტრირა Singleton-ად
Scoped AddScoped<T>() ერთი მოთხოვნის საქმე — ყველაფერი, რაც DataContext-ს იყენებს DataContext (AddDbContext)
Transient AddTransient<T>() მსუბუქი კლასი, საკუთარი მდგომარეობის და DataContext-ის გარეშე მაგ. ფასდაკლების გამომთვლელი
  • DataContext: AddDbContext თვითონ ირჩევს Scoped-ს. lifetime-ს არ ვცვლით — ექსპერიმენტი მხოლოდ იმისთვის იყო, რომ განსხვავება დაგვენახა.
  • ჩვენი კლასები — AddScoped<T>() და სხვები — მაშინ დაგვჭირდება, როცა პროექტს სტრუქტურას მივცემთ და ლოგიკა Controller-იდან ცალკე კლასებში გადავა. წესი იქაც მარტივია: კლასი DataContext-ს იყენებს → Scoped.
⚠️

ექსპერიმენტის მთვლელი (_created და Console.WriteLine) DataContext-იდან წაშალე და AddDbContext-ში lifetime-ის პარამეტრიც მოაშორე — ნაგულისხმევი Scoped საკმარისია.

🤖 Singleton, Scoped, Transient — შემამოწმე
ვსწავლობ ASP.NET Core-ში DI-ს lifetime-ებს: AddSingleton, AddScoped, AddTransient და AddDbContext (ნაგულისხმევად Scoped). მომეცი 5 პატარა სცენარი (კლასი და რას აკეთებს), და თითოეულზე მკითხე, რომელი lifetime მივცე. ჩემს პასუხს დაელოდე, შემიფასე და ამიხსენი. ერთ-ერთი სცენარი იყოს DataContext Singleton-ად. ქართულად.

სამი Lifetime — კონკრეტულ სიტუაციებში

სლაიდი 34

ცხრილი „როდის რომელი“ წესია. ახლა — როგორ გამოიყურება ეს ნამდვილ პროექტებში. ამათ ახლა არ ვწერთ: მაგალითებია, რომ წესი ცოცხალ სიტუაციებს დაუკავშირო.

🟧 Singleton — ერთი ობიექტი ყველასთვის

  • 💱 ვალუტის კურსი. ონლაინ მაღაზია ფასებს ლარში, დოლარში და ევროში აჩვენებს. კურსი ეროვნული ბანკიდან მოდის და დღეში რამდენჯერმე იცვლება. ერთი ობიექტი საათში ერთხელ მოიტანს მას და ინახავს — ათასივე მომხმარებელი ერთსა და იმავე ციფრს ხედავს, და ბანკის API-ს ყოველ მოთხოვნაზე არ ვაწუხებთ.
  • 🚚 მიწოდების ზონები. საკვების მიწოდების სერვისს აქვს სია: საბურთალო — 3 ₾, ვაკე — 4 ₾, გლდანი — 5 ₾. ის ყველასთვის ერთია და იშვიათად იცვლება — აპლიკაციის გაშვებისას ერთხელ იტვირთება.
  • ⚙️ framework-ის ხელსაწყოები — IConfiguration, ლოგერი, მეხსიერების ქეში. ASP.NET Core-მა ისინი თვითონ დაარეგისტრირა Singleton-ად.

საერთო ნიშანი: მონაცემი ყველასთვის ერთია და არ ეკუთვნის კონკრეტულ მომხმარებელს ან მოთხოვნას.

🟪 Scoped — ერთი ობიექტი ერთი მოთხოვნისთვის

  • 🗄️ DataContext — მთელი მოთხოვნა ერთ Change Tracker-ზე მუშაობს და ერთი SaveChanges-ით ინახება.
  • 🧾 შეკვეთის გაფორმება. მომხმარებელი „ყიდვას“ აჭერს: მარაგი უნდა დაიკლოს, შეკვეთა და გადახდის ჩანაწერი დაემატოს. ამას რამდენიმე კლასი აკეთებს, მაგრამ ყველა ერთ DataContext-ზე — და ბოლოს ერთი SaveChanges ყველაფერს ერთად ინახავს, ან არაფერს.
  • 👤 ვინ შემოვიდა. როცა ავტორიზაციას ვისწავლით: ობიექტი „მიმდინარე მომხმარებელი“ (ან რესტორნის დაჯავშნის სისტემაში — „რომელი რესტორანი“). ერთ მოთხოვნაში ბევრ კლასს სჭირდება, მაგრამ ორ სხვადასხვა მოთხოვნას ორი სხვადასხვა მომხმარებელი ჰყავს.

საერთო ნიშანი: მონაცემი ამ მოთხოვნას ეკუთვნის — მის შიგნით საერთოა, მოთხოვნებს შორის — არა.

🟦 Transient — ახალი ყოველ ჯერზე

  • 🏷️ ფასდაკლების გამომთვლელი. პრომო კოდი −10%, დღგ 18%: ფასს იღებს, შედეგს აბრუნებს და არაფერს ინახავს. იაფია შესაქმნელად, და ორ ადგილას ორი ასლი არაფერს აფუჭებს.
  • ✅ ვალიდატორი. „სახელი ცარიელი ხომ არ არის?“, „ფასი უარყოფითი ხომ არ არის?“ — მსუბუქი შემოწმება, მდგომარეობის გარეშე.
  • 🧾 ჩეკის ან email-ის ამწყობი. ხაზ-ხაზ აგროვებს ტექსტს: „ლეპტოპი — 2400 ₾“, „მაუსი — 45 ₾“… თუ ორი შეკვეთა ერთ ობიექტს გაიზიარებს, ხაზები აირევა. ამიტომ ყოველ ჩეკს თავისი, სუფთა ობიექტი სჭირდება.

საერთო ნიშანი: მსუბუქია და ან არაფერს ინახავს, ან ინახავს მხოლოდ ერთი გამოყენებისთვის.

რეალური შეცდომები — და რას ხედავს მომხმარებელი

სლაიდი 35

არასწორი lifetime კომპილაციის შეცდომას არ იძლევა. პროგრამა ირთვება და ლოკალურად ხშირად მუშაობს კიდეც. პრობლემა ნამდვილ მომხმარებლებთან ჩნდება — ამიტომ ასეთი შეცდომები ძვირი ჯდება.

# რა დარეგისტრირდა რას ხედავს მომხმარებელი სწორი
1 კალათა — Singleton ნინოს კალათაში გიორგის ლეპტოპი ჩნდება: ერთი ობიექტი ყველა მომხმარებელს ემსახურება და ყველას ნივთი ერთ სიაში იყრება კალათა მომხმარებელს ეკუთვნის — ბაზაში ინახება, მასთან მომუშავე კლასი Scoped-ია
2 DataContext — Singleton ლოკალურად ყველაფერი კარგადაა. საღამოს, დატვირთვისას — „A second operation was started…“; ადმინმა ფასი შეცვალა, საიტზე კი ძველი ჩანს (Change Tracker-ის ძველი ასლი) Scoped
3 DataContext — Transient შეკვეთის გაფორმებისას ორი კლასი ორ DataContext-ს იღებს: შეკვეთა შეინახა, მარაგის კლება — არა. საწყობში ლეპტოპი „ჯერ კიდევ არის“ და მეორე მომხმარებელს იგივე ლეპტოპი მიეყიდება Scoped
4 ვალუტის კურსი — Transient ყოველ გვერდის გახსნაზე ახალი ობიექტი, და თითოეული ბანკის API-ს თავიდან ეკითხება. საიტი ნელდება, ხოლო API ზედმეტი მოთხოვნებისთვის გვბლოკავს Singleton

კითხვა, რომელიც ყოველ რეგისტრაციაზე უნდა დაუსვა თავს: ეს მონაცემი ვის ეკუთვნის?

  • ყველას ერთნაირად → Singleton
  • ამ მოთხოვნას / ამ მომხმარებელს → Scoped
  • არავის — მხოლოდ ერთ გამოთვლას → Transient
🤖 რეალური სიტუაციები — შემამოწმე
ვსწავლობ ASP.NET Core DI-ის lifetime-ებს (Singleton, Scoped, Transient). მომიყევი 6 მოკლე სიტუაცია რეალური ვებ-პროექტებიდან (ონლაინ მაღაზია, მიწოდება, დაჯავშნა, ბანკი) — თითოეულში კლასი და რას აკეთებს. თითოეულზე მკითხე: რომელ lifetime-ს მივცემ და რა მოხდება, თუ შევცდები? ჩემს პასუხს დაელოდე და შემიფასე. ქართულად.
