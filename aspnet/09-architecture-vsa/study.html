დღის თემა: არქიტექტურა: Layers vs Vertical Slices

სლაიდი 4

წინა ლექციაზე story №1 ნაცნობი გზით დავწერეთ და სამი ტკივილი დავინახეთ: ერთი feature 3–4 საქაღალდეშია გაბნეული, Controller ყოველ endpoint-ზე იზრდება, ბიზნესის წესები კი HTTP-ის კოდშია. LMS-ს ათობით feature ექნება, ამიტომ კოდი ისე უნდა დავალაგოთ, რომ ზრდასთან ერთად არ აირიოს. დღეს ორ არქიტექტურას შევადარებთ, Layers-ს და Vertical Slices-ს, გავიგებთ ორ პრინციპს (SRP, DIP), Controller-ებს Minimal API-ით შევცვლით და Swagger-ს Scalar-ით.

ლექციის ბოლოს შეძლებ:

  • Layers და Vertical Slice Architecture-ის შედარება: რას აჯგუფებს თითოეული და რა ფასი აქვს
  • SRP და DIP: ახსნა მარტივად და ჩვენს კოდში დანახვა
  • ერთი slice-ის აწყობა: Request · Handler · Endpoint (Minimal API, MapGroup)
  • Swagger-ის ნაცვლად Scalar: .NET 10-ის OpenAPI დოკუმენტი

სამი ტკივილი 08 ლექციიდან

სლაიდი 5

story №1 (კურსის შექმნა) და საშინაოში Students და Lecturers ნაცნობი გზით დავწერეთ. ყველაფერი მუშაობს, მაგრამ სამი რამ გვაწუხებს:

  1. გაბნეული feature. „კურსის შექმნა“ ოთხ საქაღალდეშია: Controllers, Dtos, Mappers, Entities. ერთი ცვლილებისთვის ოთხ ადგილას უნდა იარო.
  2. Controller იზრდება. სამ Controller-ში უკვე 15 endpoint-ია. LMS-ს ათობით ექნება.
  3. ბიზნესის წესი HTTP-ის კოდშია. R1 და „1–52 კვირა“ Controller-ის მეთოდშია ჩაწერილი, თანაც ორჯერ, Create-ში და Update-ში.

ერთი კითხვა რჩება: სად რა უნდა იდოს, რომ კოდი ზრდასთან ერთად არ აირიოს? ამ კითხვაზე პასუხს არქიტექტურა ჰქვია: კოდის დალაგების წესები, რომლებზეც გუნდი თანხმდება.

Controller → Service → Data

სლაიდი 7

Layered Architecture (ფენოვანი არქიტექტურა) კოდს ტექნიკური როლის მიხედვით ყოფს:

ფენა რას აკეთებს
🌐 Controllers HTTP: მისამართი, მეთოდი, სტატუს კოდი
⚙️ Services ბიზნესის ლოგიკა და წესები
🗄️ Data DataContext და ბაზა

ერთი feature ყველა ფენაშია

სლაიდი 8

Layers კოდს ჰორიზონტალურად ჭრის: ყველა Controller ერთ „სართულზეა“, ყველა Service მეორეზე, ყველა DTO მესამეზე.

„კურსის შექმნის“ შესაცვლელად ისევ ყველა სართულზე უნდა იარო: CoursesController, CourseService, CourseDtos, CourseMapper.
✓ მოწესრიგებული HTTP ცალკეა, წესები ცალკე. ყველამ იცის, სად ეძებოს Service.
✗ ტკივილი №1 დარჩა ერთი ცვლილება ისევ ყველა ფენას ეხება.
✗ ტკივილი №2 გადავიდა Controller-ი დაპატარავდა, სამაგიეროდ CourseService იზრდება: ყოველ ახალ story-ზე („კურსის დაარქივება“, „კურსის კოპირება“, „კურსის სტატისტიკა“) მას ახალი მეთოდი და ახალი დამოკიდებულებები ემატება.

Layers ცუდი არ არის: დიდ ნაწილ პროექტებში შეხვდებით და კარგად მუშაობს. მაგრამ პრობლემის მხოლოდ ნაწილს ხსნის. ვიდრე სხვა გზას ვნახავთ, ორი პრინციპი გვჭირდება, რომლებიც ამ ტკივილს ზუსტად ასახელებს.

2 · SRP და DIP

ნაწილი 2 · SRP და DIP

სლაიდი 9

SOLID ხუთი პრინციპია, რომლებიც კოდის დიზაინის შეფასებაში გვეხმარება. დღეს ორი გვჭირდება: S (SRP) და D (DIP). ორივეს ჩვენს კოდზე ვნახავთ.

SRP: კლასს შეცვლის ერთი მიზეზი უნდა ჰქონდეს

სლაიდი 10

SRP (Single Responsibility Principle, ერთი პასუხისმგებლობის პრინციპი): კლასს შეცვლის მხოლოდ ერთი მიზეზი უნდა ჰქონდეს.

ჩამოვწეროთ, როდის იცვლება CoursesController (ან Layers-ში CourseService):

  1. კურსის შექმნას ახალი წესი დაემატა;
  2. სიას დალაგება შეეცვალა;
  3. ერთი კურსის პასუხს ველი დაემატა;
  4. ცვლილებას ახალი შემოწმება დაემატა;
  5. წაშლა აიკრძალა, თუ კურსს ჯგუფები აქვს.

ხუთი მიზეზი ხუთი პასუხისმგებლობაა ერთ კლასში. როცა ერთს ცვლი, დანარჩენ ოთხსაც ეხები და შეიძლება გააფუჭო.

SRP-ს მიხედვით: ერთი კლასი, ერთი საქმე. თუ გვექნება CreateCourseHandler, ის მხოლოდ მაშინ შეიცვლება, როცა კურსის შექმნა იცვლება.

⚠️

„ერთი საქმე“ „ერთ მეთოდს“ არ ნიშნავს. საზომი ისაა, ვინ და რატომ მოითხოვს ცვლილებას. თუ ორ სხვადასხვა მოთხოვნას ერთი კლასის შეცვლა სჭირდება, კლასს ორი პასუხისმგებლობა აქვს.

სლაიდი 11

DIP (Dependency Inversion Principle, დამოკიდებულების ინვერსიის პრინციპი) ორ რამეს ამბობს:

  1. კლასი თავის დამოკიდებულებებს თვითონ არ ქმნის, ითხოვს. ეს 04 ლექციიდან ვიცით: DataContext-ს constructor-ით ვითხოვთ, Container კი ქმნის და გვაწვდის.
  2. კლასი აბსტრაქციაზე მუშაობს და არა დეტალზე. ბიზნესის კოდს არ უნდა აინტერესებდეს, რომელი ბაზაა, როგორი connection string აქვს ან როგორ იგზავნება email.
❌ თვითონ ქმნის
public class CreateCourseHandler{    private readonly DataContext _db = new DataContext(        "Server=(localdb)\\MSSQLLocalDB;Database=LmsDb;…");}
✅ ითხოვს
public class CreateCourseHandler{    private readonly DataContext _db;     public CreateCourseHandler(DataContext db)    {        _db = db;    }}

მეორე ვერსიაში handler-მა არ იცის, როგორ იქმნება DataContext. მან ისიც არ იცის, რომ ბაზა SQL Server-ია: _db.Courses.AnyAsync(…) ნებისმიერ ბაზაზე იმუშავებს, რომელსაც EF Core იცნობს. თუ აკადემია PostgreSQL-ზე გადავა, შეიცვლება მხოლოდ Program.cs (UseSqlServer → UseNpgsql). ერთი handler-იც არ შეიცვლება.

DataContext აქ აბსტრაქციაა: ის SQL Server-ის დეტალებს მალავს. სხვა შემთხვევაში აბსტრაქციად interface გამოიყენება, მაგალითად email-ის გაგზავნისთვის, სადაც ნამდვილი სერვისი და სატესტო ვერსია უნდა შევცვალოთ. interface-ს მაშინ შემოვიტანთ, როცა ასეთი საჭიროება მართლა გაჩნდება.

Layers კოდს ჰორიზონტალურად ჭრის. ახლა ვნახავთ, რა მოხდება, თუ ვერტიკალურად მოვჭრით.

ერთი feature, ერთი საქაღალდე

სლაიდი 13

Vertical Slice Architecture (VSA) კოდს feature-ის მიხედვით ჭრის. თითო feature („slice“, ნაჭერი) ერთ backlog story-ს ან მის ერთ მოქმედებას შეესაბამება: CreateCourse, GetCourses, EnrollStudent. ყველაფერი, რაც ამ feature-ს სჭირდება, ერთ საქაღალდეში დევს:

Lms.Api
Features/  Courses/    CreateCourse/      CreateCourseRequest.cs     ← რა შემოდის      CreateCourseHandler.cs     ← საქმე: წესები, ბაზა, პასუხი      CreateCourseEndpoint.cs    ← მისამართი და მეთოდი    GetCourses/ …    GetCourseById/ …    CourseResponse.cs            ← საერთო Courses-ის slice-ებისთვის    CourseMapper.cs              ← საერთო (ToResponse)    CourseEndpoints.cs           ← Courses-ის რეგისტრაცია  Students/ …Entities/                        ← საერთო ყველასთვისData/                            ← საერთო ყველასთვის

ერთი მთავარი წესი: რაც ერთად იცვლება, ერთად დევს.

  • „კურსის შექმნას“ ახალი ველი დაემატა? → მხოლოდ CreateCourse/ საქაღალდე (და, თუ ბაზაშიც უნდა შეინახო, Course entity).
  • ორი დეველოპერი ორ სხვადასხვა feature-ზე მუშაობს? → ორ სხვადასხვა საქაღალდეში. ერთ ფაილზე აღარ ეჯახებიან.

რა რჩება საერთო? ის, რასაც ბევრი slice იყენებს: Entities (ბიზნესის ცნებები), Data (DataContext) და ერთი ჯგუფის საერთო პასუხი (CourseResponse). ToEntity-ს მხოლოდ CreateCourse იყენებს, ამიტომ ის handler-ში გადადის. Mapper-ში მხოლოდ ToResponse რჩება.

ნაწილი რას აკეთებს რა არის C#-ში
📨 Request რა შემოდის მოთხოვნაში record (DTO, 03 ლექციიდან)
🌐 Endpoint მისამართი და მეთოდი; მოთხოვნას handler-ს გადასცემს Minimal API: MapPost(...) (02 ლექციიდან)
⚙️ Handler საქმე: წესები, ბაზა, პასუხი ჩვეულებრივი class, DataContext-ს constructor-ით ითხოვს

რატომ ცალკე Endpoint და Handler? SRP: Endpoint მხოლოდ HTTP-ის „მისამართს“ იცნობს, Handler კი feature-ის საქმეს. Controller აღარ გვჭირდება: მის როლს ერთი slice-ის ერთი Endpoint ასრულებს.

💡

VSA-ს ბევრი პროექტი MediatR-ის ბიბლიოთეკით აწყობს: handler-ს ავტომატურად პოულობს და იძახებს. ჩვენ ამას არ ვაკეთებთ. Handler ჩვეულებრივი class-ია, რეგისტრაციას ხელით ვწერთ, ხოლო Endpoint მას პირდაპირ იძახებს. ასე ყოველი ნაბიჯი ჩანს და არაფერი „ჯადოსნურად“ არ ხდება.

using Lms.Api.Data;using Lms.Api.Entities;using Microsoft.EntityFrameworkCore; namespace Lms.Api.Features.Courses.CreateCourse; public class CreateCourseHandler{    private readonly DataContext _db;     public CreateCourseHandler(DataContext db)    {        _db = db;    }     public async Task<IResult> HandleAsync(CreateCourseRequest request)    {        if (string.IsNullOrWhiteSpace(request.Title))            return Results.BadRequest("კურსის სახელი სავალდებულოა");        if (request.DurationWeeks is < 1 or > 52)            return Results.BadRequest("ხანგრძლივობა 1-დან 52 კვირამდეა");         var title = request.Title.Trim();        if (await _db.Courses.AnyAsync(c => c.Title == title))            return Results.Conflict($"კურსი „{title}“ უკვე არსებობს");         var course = new Course        {            Title = title,            Description = request.Description,            DurationWeeks = request.DurationWeeks,            CreatedAt = DateTime.UtcNow        };        _db.Courses.Add(course);        await _db.SaveChangesAsync();        return Results.Created($"/api/courses/{course.Id}", course.ToResponse());    }}

რა შეიცვალა Controller-ის მეთოდთან შედარებით:

  • ჩვეულებრივი class, ControllerBase-ის გარეშე. DataContext-ს constructor-ით ითხოვს (DIP).
  • IResult Minimal API-ის „პასუხის ტიპია“, როგორც Controller-ში IActionResult. BadRequest() → Results.BadRequest(), Conflict() → Results.Conflict().
  • Results.Created(url, body) 201-ს აბრუნებს. CreatedAtAction Controller-ის action-ს ეძებდა; აქ მისამართს თვითონ ვწერთ.
  • ToEntity აღარ არის Mapper-ში. new Course { ... } handler-შია, რადგან მხოლოდ ამ slice-ს სჭირდება.

შემოწმებები ზუსტად იგივეა. ბიზნესის ლოგიკა არ შეცვლილა: შეიცვალა მხოლოდ ის, სად დევს.

დაიმახსოვრე:

  1. Layers (Controller → Service → Data) კოდს ტექნიკური როლით ყოფს. ის მოწესრიგებულია, მაგრამ ერთი feature ყველა ფენაში ხვდება, Service-ები კი იზრდება.
  2. SRP: კლასს შეცვლის ერთი მიზეზი უნდა ჰქონდეს. CoursesController-ს ხუთი ჰქონდა.
  3. DIP: კლასი დამოკიდებულებებს ითხოვს და აბსტრაქციაზე მუშაობს. handler-მა არ იცის, რომ ბაზა SQL Server-ია.
  4. Vertical Slice Architecture კოდს feature-ით ყოფს: რაც ერთად იცვლება, ერთად დევს. Entities და DataContext საერთოა.
  5. Slice = Request + Handler + Endpoint. Handler ჩვეულებრივი class-ია, Scoped-ად რეგისტრირებული. Endpoint Minimal API-ა MapGroup-ის შიგნით. ყველაფერი ხელით ჩანს: MediatR არ არის.
  6. Minimal API პარამეტრებს თვითონ ავსებს: body-დან (Request), DI-დან (Handler) და მისამართიდან (Guid id).
  7. .NET 10 OpenAPI დოკუმენტს თვითონ ქმნის, Scalar კი მას /scalar-ზე ხატავს.
